# Исследование ROM ./src/putup.rom с помощью mcp-сервиса

## Stage 0

Изучаем документацию по Вектор-06Ц в docs/VECTOR_VERIFIED.md

### Принципы именования объектов в RDB

Префиксы объектов:
- функции - "func_"
- блоки данных - "data_"
- текстовые строки - "str_"
- музыкальные дорожки (ноты) - "music_"
- одиночные переменные - "var_"

Суффиксы объектов:
- для объектов с пока неизвестным предназначением - "_unknown". 
- у объектов, назначение которых установлено, суффикс "_unknown" убираем.

Важное примечание. Никаких дополнительных скриптов не писать для пост-обработки полученных от MCP-сервера данных. Если что-то неверно делает или возвращает MCP-сервер, то проверить ещё раз и, убедившись в ошибке, остановиться и сообщить пользователю о найденной ошибке.


## Stage 1. Общее исследование карты памяти, активности программы в чтении/записи

1) Запускаем ROM (reset не нужен)
2) Ожиданием 5 секунд, пока программа отработает
3) Не останавливая эмуляцию, анализируем карту памяти на наличие данных, активность по чтению/записи блоков памяти
4) Ставим эмуляцию на паузу, анализируем данные по обращениям к портам
4) Сохраняем промежуточный отчёт в ./reports/Stage1.md

## Stage 2. Первичное обследование функций и блоков данных

1) Запускаем ROM, даём ему поработать 5 секунд
2) Далее начинаем исследовать память в поисках функций, переменных и блоков данных
3) По мере исселедования заполняем ROM Database (RDB)
4) Сохраняем RDB на жёсткий диск
5) По итогам первичного исследования сохраняем промежуточный отчёт в ./reports/Stage2.md

## Stage 3. Подробное исследование функций

1) Запускаем ROM, даём ему поработать 5 секунд
2) Для всех найденных функций в RDB проводим исследование их кода
3) По итогам исследования каждой функции обновляем название на осмысленное и указываем в комментарии краткое описание назначение каждой функции
4) Устанавливаем связи между функциями и данными
5) Сохраняем RDB на жёсткий диск
6) По итогам исследований сохраняем промежуточный отчёт в ./reports/Stage3.md

## Stage 4. Определение параметров функций

1) Запускаем ROM, даём ему поработать 5 секунд
2) Для всех найденных функций в RDB определяем их параметры
3) Найденные параметры сохраняем в properties соответствующих функций
4) Сохраняем RDB на жёсткий диск
5) По итогам исследований сохраняем промежуточный отчёт в ./reports/Stage4.md

## Stage 5. Исследование прерываний

1) Запускаем ROM, даём ему поработать 5 секунд
2) Исследуем адреса прерываний на предмет подпрограмм в них на основе сведений из docs/VECTOR_VERIFIED.md
3) Заносим/обновляем в RDB сведения о прерываниях с описанием того, что они делают
4) Особое внимание уделяем аппаратному прерыванию RST 7
5) Сохраняем RDB на жёсткий диск
6) По итогам исследований сохраняем промежуточный отчёт в ./reports/Stage5.md

## Stage 6. Исследование главного игрового цикла

1) Запускаем ROM, даём ему поработать 5 секунд
2) На текущий момент у нас работает заставка игры. Нужно найти цикл ожидания нажатия на пробел и добавить его в RDB
3) Пройти в код, работающий после нажатия пробела
4) Исследовать код на предмет отрисовки уровней (расположение карт уровней, блоков со спрайтами персонажа и врагов, тайлов). Сведения о найденных блоках памяти обновить в RDB
5) Найти главный игровой цикл и отметить его в RDB
6) Пройтись шаг за шагом весь игровой цикл в течение нескольких десятков циклов и выявить игровые переменные. Переменные занести в RDB
7) По итогам исследований сохраняем промежуточный отчёт в ./reports/Stage6.md

## Stage 7. Исследование функций вывода текста на экран

1) Запускаем ROM, даём ему поработать 5 секунд
2) На заставке игры выводятся надписи на экранные плоскости. Ищем функции, выводящие текст по текстовым строкам на английском и русском языках (включая заглавные и строчные буквы). Например строки:
- PUSH SPACE KEY
- MSX MAGAZINE, 1987
- Версия для "Вектор-06Ц"  1991
- Центр "КОМПЬЮТЕР" г.Кишинев
Но в ROM есть ещё другие строки. Их тоже надо найти.
3) Исследуем области памяти, из которых происходит копирование данных в видеопамять для вывода строк.
4) Для каждой найденной строки создаём или обновляем в RDB отдельный объект с комментарием в виде содержимого строки
5) Исследуем область памяти, в которой хранится набор глифов, в том числе в распакованных данных. Исследуем функцию, которая выводит строки на экран. В функции должен быть адрес, относительно которого считаются смещения глифов для каждого символа при чтении из памяти. Этот адрес и есть начало блока с глифами.
6) Сохраняем сведения о найденном блоке с глифами и его размере в RBD
7) Задача считается выполненной, если найдены все глифы из текстовых строк из пункта 2.
8) По итогам исследований сохраняем промежуточный отчёт в ./reports/Stage7.md

## Stage 8. Выгрузка функций в asm-файлы

1) Загружаем ROM (без запуска). Для каждой функции из RDB создаём отдельный файл в ./asm с кодом в формате z88dk.
2) Вoperand инструкций заменяем hex-адреса на символические имена:
Если адрес совпадает с началом объекта из RDB (функция, данные, строка, переменная, метка, таблица) — подставляем его имя.
Если адрес указывает внутрь текущей функции (переход на локальную метку) — генерируем локальную метку вида .loc_0357 и подставляем её.
Если адрес не найдёт ни в RDB, ни внутри функции — оставляем как hex.
3) Локальные метки размещаем перед инструкцией, на которую идёт
переход.
4) По итогам экспорта сохраняем отчёт в ./reports/Stage8.md.

## Stage 9. Поиск и исследование карт уровней

В игре 15 уровней. Размер карты уровня: 16×11 тайлов. Каждая карта содержит координаты выхода с уровня.

1) Загружаем ROM (без запуска). Находим в func_main_init цикл ожидания нажатия пробела на заставке (lbl_title_key_poll). Исследуем код, выполняющийся после нажатия пробела.
2) Находим вызов очистки экрана (func_vram_clear или аналог), который происходит после старта игры.
3) После очистки экрана должна вызываться функция рисования уровня по карте. Находим эту функцию и исследуем её код.
4) В функции рисования уровня находим:
   - Вычисление адреса карты текущего уровня (должен быть базовый адрес таблицы карт + смещение, зависящее от номера уровня)
   - Чтение координат выхода с уровня (предположительно 2 байта: колонка и строка)
   - Цикл обхода 16×11=176 байт карты уровня
5) Определяем базовый адрес таблицы карт уровней в ROM. Таблица содержит 15 карт по 176 байт каждая, итого минимум 15×176=2640 байт данных.
6) Для каждой карты уровня проверяем структуру: 176 байт тайлов + координаты выхода (или иной формат, если структура отличается).
7) Создаём в RDB объект data_level_maps с комментарием, описывающим структуру:
   - Базовый адрес таблицы
   - Размер одной карты (байт)
   - Формат записи уровня (тайлы, координаты выхода и пр.)
   - Количество уровней (15)
8) Создаём в RDB отдельные объекты для каждой карты уровня: data_level_01 .. data_level_15 с указанием адреса и размера.
9) По итогам исследования сохраняем отчёт в ./reports/Stage9.md.


## Stage 10. Выгрузка блоков данных в asm-файлы

1) Загружаем ROM (без запуска). Для каждого объекта данных из RDB создаём отдельный файл в ./asm с содержимым в формате z88dk. Имя файла совпадает с именем объекта RDB.
2) Объекты делятся на две категории и выгружаются по-разному:
   - данные в ROM (data_, str_, таблицы, музыкальные дорожки music_) — выгружаем их фактическое байтовое содержимое;
   - переменные и буферы в RAM (var_, runtime-буферы вроде 0x5000, блок глифов 0x6000, векторы прерываний) — выгружаем только как символические определения адресов (EQU/метки), без байтового содержимого, так как в образ ROM они не входят.
3) Содержимое ROM-данных читаем из ROM через debug_read_memory_range (MCP). Постобработка полученных от MCP данных скриптами запрещена (см. примечание в Stage 0).
4) Формат выгрузки по типу объекта:
   - байтовые блоки и массивы — DEFB (db), с группировкой байт для читаемости;
   - словесные массивы, таблицы адресов/указателей — DEFW (dw);
   - текстовые строки (str_) — DEFM (текст в кавычках) с явным терминатором как в оригинале (0x00 или 0xFF).
5) В таблицах указателей и адресных операндах заменяем hex-адреса на символические имена объектов RDB по тем же правилам, что и в Stage 8: адрес совпадает с началом объекта — подставляем его имя; иначе оставляем hex.
6) Каждый файл данных снабжаем заголовком-комментарием: имя объекта, адрес, размер и назначение (из комментария RDB).
7) Крупные бинарные блоки (например, data_glyph_block, data_gfx_2761, data_packed_font_3041, data_level_maps) допускается выгружать директивой .incbin из предварительно сохранённого бинарного файла, если DEFB-дамп непрактичен. Бинарный файл формируется напрямую из данных MCP, без скриптов постобработки.
8) По итогам экспорта сохраняем отчёт в ./reports/Stage10.md.


## Stage 11. Сборка нового PUTUP_NEW.ROM из исходников в ./asm/

Собрать новый ROM. При необходимости подкорректировать экспортированные функции и блоки данных в ./asm и в RDB.

Конечная цель: получить программу, которая работает также как исходный ./src/PUTUP.ROM, пусть даже со сдвинутым адресным пространством. PUTUP_NEW.ROM не обязана получиться байт-в-байт как PUTUP.ROM

Написать отчёт по выполненной работе и сохранить его в ./reports/Stage11.md
