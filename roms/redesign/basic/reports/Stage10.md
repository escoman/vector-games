# Stage 10. Сборка нового образа + приёмка (инкремент 10.1)

Дата: 2026-10-18. Ветвь A (побайтовый монолит, выбрана на Stage 9).
Объём этого коммита — **10.1**: воспроизводимая сборка/упаковка/сверка через
`Makefile`. Поведенческая **функциональная батарея** (TZ §10 п.3) — отдельный
инкремент **10.2** (ниже, «что дальше»).

## 0. Специфика таргета (почему сборка — не «как у игр»)

Объект реконструкции — **RAM-образ интерпретатора** `basic.r0m`
(org `0x0000`, 17152 байта), а не самораспаковывающийся `bas2997.rom`.
Два разных формата загрузки эмулятора (см. `dump_interp.py`, `finally.mk`):

| | адрес загрузки | старт | что это |
|---|---|---|---|
| `.rom` | `0x0100` | с `0x0100` | обычный образ игры |
| `.r0m` | `0x0000` | reset-вектор на нуле | RAM-образ / упакованный самолётчик |

`bas2997.rom` (оригинал, 13247 б) — самолётчик: стаб на `0x0100` грузит LZ-поток
в staging `0x8000`, разворачивает интерпретатор в `0x0000..0x42FF`, затем `JP 0000`.
Наш реконструированный `basic_new.r0m` — **уже развёрнутый RAM-образ**, поэтому
эмулятор грузит его в `0x0000` и **запускает напрямую**, распаковщик не нужен.

Следствие: **побайтовое `basic_new.* == bas2997.rom` невозможно в принципе** —
у оригинала собственный LZ-кодек и приём Медноногова (TZ п.92: нетипичное
выравнивание стека). Это зафиксировано ещё в TZ (§10 п.2: «при
не-детерминированности compress допустимо `INCBIN`»). Воспроизведение точного
байтового потока оригинала — работа со стабом, её относим к аппаратной фазе
(Stage 11), а не к сквозной приёмке.

## 1. Ярусы приёмки

- **Tier 1 — детерминированный, байт-в-байт (этот коммит):** собранный
  `src/basic_new.r0m` == эталон `src/basic.r0m` (17152 б, **0 расхождений**).
  Закреплён в `make verify`. Проходит и после регенерации из RDB (`make layout`).
- **Tier 2 — поведенческий (10.2):** `basic_new.r0m` против `bas2997.rom` на
  живом эмуляторе через MCP, сверка REPL/VRAM-снапшота и trace портов на
  эталонных `.bas`. Критерий — совпадение **поведения**, не байтов.

## 2. `Makefile` (`roms/redesign/basic/Makefile`)

По образцу `putup/Makefile` (`include config.mk` + `finally.mk`), но org `0x0000`
— без среза выходного файла.

| цель | действие | статус |
|---|---|---|
| `layout` | `tools/stage9_asm_layout.py --apply` → `asm/{code,equates,basic_new}.asm` | ✅ воспроизводит |
| `build` (`all`) | `z80asm -b -m=8080_strict asm/basic_new.asm` → `src/basic_new.r0m` (17152) | ✅ |
| `verify` | Tier 1: `basic_new.r0m` == `basic.r0m`, байт-в-байт | ✅ **diffs=0** |
| `pack` | ZX0-поток `src/basic_new.zx0` + self-verify `zx0.decompress==образ` | ✅ round-trip OK |
| `snapshot` | `tools/dump_interp.py` — свежий снимок `basic.r0m` с `bas2997.rom` (нужен MCP; opt-in) | есть инструмент |
| `deploy` | кладёт `basic_new.r0m` в ROMS эмулятора (boot-напрямую) — `finally.mk` | ✅ цель |
| `full` | `clean + all + deploy` | ✅ |

Артефакты сборки в `.gitignore`: `basic_new.r0m` (покрыт глобальным `*.r0m`),
`basic_new.zx0`. Эталон `basic.r0m` и `basic.rdb` остаются отслеживаемыми.

## 3. Результаты прогонов

```
make build   →  built src/basic_new.r0m (17152 bytes)
make verify  →  RAM image: new=17152 ref=17152 ; byte diffs=0
make pack    →  ZX0 17152 -> 14179 байт (82.7%), decompress round-trip OK
```

Сравнение степени сжатия: оригинал `bas2997.rom` = **13247 б** (77.2% от 17152);
наш ZX0-поток payload = **14179 б** (82.7%, без учёта ~116 б стаба). То есть
собственный LZ оригинала сжимает заметно лучше стандартного ZX0 — ещё один
аргумент, что байтовая копия `bas2997.rom` недостижима нашим кодеком и цель
приёмки — поведение (Tier 2), а не поток.

Сквозная воспроизводимость: `run_pipeline.sh basic --from export_asm` → **6/6
SUCCESS** (round-trip побайтово), затем `make layout` → `make clean` →
`make build` → `make verify` → **diffs=0**. То есть цепочка
`RDB → export → asm → bin → сравнение` полностью воспроизводима из дерева.

### Boot-проверка нового образа через MCP (подтверждение Tier 2 на уровне запуска)

Сессия `v06c-mcp 0.6.6` (git `9731ffa`, clean). `basic_new.r0m` загружен в
`org 0x0000` (reset-вектор на нуле), `debug_reset` → `debug_run`:

- CPU живёт: `running=true`, PC идёт по low-RAM-инициализации, прерывания
  разрешены (`iff=true`) — boot-последовательность `0x0000 → JMP 0x19CC → init`.
- Кадр на ТВ-фреймбуфере стабилен между фреймами 731 → 2181: штатный экран
  Вектора-06Ц с заголовком **«ВЕКТОР-06Ц»**, логотипом и блоком версии/памяти
  справа + boot-развёртка. То есть интерпретатор дошёл до устоявшегося
  ready-состояния и отображает его.

Так как `basic_new.r0m` побайтово равен `basic.r0m`, а `basic.r0m` — это ровно
RAM-образ оригинала *после* исполнения его стаба, прямой запуск реконструкции
воспроизводит тот же экран, к которому приходит `bas2997.rom`. Гонять сам
`bas2997.rom` через стаб в отладчике намеренно не стали (boot-путь эмулятора и
«stale ROM» — ненадёжный контур; побайтная эквивалентность уже связывает их).
Полная поведенческая батарея (несколько `.bas`, сверка вывода) — инкремент 10.2.
