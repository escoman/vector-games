## 2. Активность чтения/записи во время выполнения

Замер: `debug_clear_memory_access_map` → прогон ~2с на рабочем (steady-state) режиме → `debug_get_memory_access_map` + `debug_get_memory_access_log`. `debug_create_memory_snapshot` (id=1) → ~2с → snapshot (id=2) → `debug_compare_memory_snapshots`.

### 2.1 Карта обращений (steady-state, активные блоки по 256 байт)

| Блок | read | write | read_count | write_count | Интерпретация |
|------|------|-------|-----------|------------|---------------|
| 0x0000 | + | + | 3562 | 1424 | Стек ИСН (push/pop возврата при RST 7) + чтение вектора |
| 0x0100 | + | – | 8 056 475 | 0 |_fetch_ кода (код + ISR 0x0100–0x0176) — доминирующая активность |
| 0x0200 | + | – | 182 528 | 0 | Чтение «заготовленной» таблицы в стековой области (0x0269–0x0270 и др.) |
| 0x0300 | + | – | 182 528 | 0 | тоже чтение |
| 0x0400 | + | – | 182 528 | 0 | тоже чтение |
| 0x0500 | + | – | 84 847 | 0 | хвост стековой области (SP стартовал с 0x0577) |

**VRAM-блоки (0x8000–0xFFFF) в списке активных ОТСУТСТВУЮТ** — во время замера к ним нет обращений CPU.

### 2.2 Сравнение снапшотов (write-активность)

`debug_compare_memory_snapshots(1, 2)` → **`changed_ranges: []`**. За ~2с steady-state **ни один байт памяти не изменился**.

- **Fact:** устойчивый режим программы НЕ создаёт перманентных записей в память (ни VRAM, ни переменных). Единственные записи — транзиентные push/pop стека, возвращающие прежнее содержимое.
- **Inference:** весь наблюдаемый эффект программы идёт через **I/O (запись в порт палитры)**, а не через изменение памяти.

### 2.3 Содержимое VRAM

`debug_read_memory_range(0x8000,16)` → все `0x00`; `debug_read_memory_range(0xE000,16)` → все `0x00`.

- **Fact:** пиксельные данные во всех проверенных точках плоскостей = 0.
- **Inference:** на старте (ДО нашего замера активности) был выполнен одноразовый цикл очистки VRAM. Виден в дизассемблировании инициализации: `0x0101 LXI H,8000` → `0x0104 MVI M,00` → `INR L` / `INR H` с `JNZ 0x0104` — обнуление диапазона 0x8000–0xFFFF. Эти записи произошли в первые мгновения после запуска и потому НЕ попали в окно access-map (оно было очищено позже, на steady-state).

## 3. Точка входа и исполнение

- **Start:** PC=0x0000 после загрузки; 0x0000–0x00FF = `00` (NOP), выполнение «скатывается» в 0x0100.
- **SP:** после boot = 0xC300 (Fact, `debug_get_state`). Инициализация затем переставляет SP: `LXI SP,0577` (заготовка таблицы), затем `LXI SP,0100`.
- **Текущий PC на steady-state (до паузы):** `0x013B` = `HLT`, `iff=true` (`debug_get_cpu_state`). Основной поток припаркован в цикле `HLT / JMP 0x013B` (0x013B–0x013E).
- **Активный код на steady-state:** по access-log PC ходит в диапазоне **0x013F–0x0176** — это обработчик прерывания (ИСН). Он и выполняет основную «работу» (запись в порт).
- **Видео-режим:** `debug_get_screen_info` → mode512=false (256-колоночный, 16 цветов), visible 256×256, frame 576×288, pixels_per_byte=8, scroll_value=255.

### Вектор прерывания (Fact)
- `debug_read_memory_range(0x0038,4)` → `C3 3F 01 00` = **`JP 0x013F`**.
- Подтверждено в инициализации (`disassemble_range`): `0x010E MVI A,C3` → `0x0110 STA 0038`; `0x0113 LXI H,013F` → `0x0116 SHLD 0039`.
- Т.е. установлен обработчик **RST 7 (аппаратное VBlank-прерывание, вектор 0x0038, ~50 Гц)** → переход на 0x013F.
- Статус механизма RST 7=VBlank: VERIFIED_BY_CODE по KB (VECTOR_VERIFIED §10). Прямое событие прерывания в trace не записано, но связка `iff=true` + `HLT` в основном потоке + непрерывное выполнение ИСН на 0x013F + установленный вектор = **Inference (High)**: ИСН вызывается кадровой синхронизацией.

## 4. Обращения к портам (после `debug_pause`)

`debug_get_io_trace` записывает только **OUT на порт 0x0C** с циклически меняющимися значениями. Типичная повторяющаяся последовательность значений:
`F8 F9 FA FB FC FD FE FF 00` → затем снова `F8 …` (8-значный счётчик + 00, зациклен). Ни одного **IN**, ни одного другого порта в окне трассировки нет.

| Порт | Напр. | Наблюдаемые значения | Назначение | Статус |
|------|-------|----------------------|-----------|--------|
| 0x0C | OUT | F8…FF,00 (цикл) | Запись физического цвета в палитру (индекс ячейки задаётся данными пикселя, не портом) | **Fact** (io_trace) — порт; назначение по KB io.md/video.md |
| 0x02 | OUT (однократно, при инициализации) | — (в steady-state не пишется) | PIA1 Port B: border (биты 0–3) + режим 512 (бит 4) | **Fact**: `0x0135 OUT 02`; `read_io(0x02)=0x00` → border=0, 256-колоночный режим |
| 0x02 | IN | 0x00 | чтение состояния | **Fact** (read_io) |
| 0x0C | IN | 0x0F→0xFF (read_io вернул 0xFF) | порт только на запись (W) | чтение неинформативно, **UNCONFIRMED** |
| 0x14/0x15 | — | не наблюдались | AY-3-8910 (звук) | **Fact (negative):** в трассировке обращений к AY нет → звука программа не генерирует (на этом ROM/прогоне) |
| 0x08–0x0B | — | не наблюдались | таймер ВИ53 | **UNCONFIRMED / нет активности** |
| 0x00/0x01/0x03 | — | не наблюдались | PIA1 CW / Port C / scroll | **UNCONFIRMED / нет активности** |

- **Inference (High):** единственный постоянный канал вывода — быстрая перезапись **палитры** через 0x0C изнутри VBlank-ИСН. Это «racing the beam»: смена цвета палитры по ходу развёртки кадра.
- **Note:** байты `AA/A9/A8/AF`, видимые в access-log в районе 0x015x–0x016x — это НЕ значения палитры, а старшие байты операндов инструкций `D3 0C` (код ИСН). Истинные значения палитры — из `io_trace` (F8…FF,00). Различаем decode-операнд vs semantics-значение.

## 5. Предварительные гипотезы о назначении ROM

Основа: все VRAM=0 (одноразово очищена на старте), перманентных записей в память в steady-state нет, единственный постоянный канал вывода — зацикленная запись меняющихся значений в палитру (порт 0x0C) из VBlank-обработчика на 0x013F.

- **Hypothesis (High):** `clrs` = «colors» — демонстрация **динамической смены палитры во время развёртки (racing the beam)**. При обнулённом кадре (все пиксели = индекс 0) перезапись ячейки палитры на разных строках растра даёт горизонтальные цветовые полосы / анимацию цветов на экране. Прямая поддержка KB: video.md §Mid-Frame Palette Changes (явно упоминает технику и «confirmed by clrs.asm»).
- **Hypothesis (Medium):** Механизм ИСН использует **стек как запрограммированную последовательность** («bytecode»): на инициализации в область ~0x0200–0x0576 заготовлены значения/адреса возврата (`PUSH H`/`PUSH PSW` в цикле 0x0128–0x0133), а ИСН их «исполняет» через `POP`/`RET`+`OUT 0x0C`, создавая программные задержки между сменами цвета. Обоснование: доминирующие чтения блоков 0x0200–0x0500 + циклы `F1 (POP PSW)` в access-log. Требуется разбор на Stage 2/3.
- **Hypothesis (Low):** точный визуальный паттерн (сколько полос, как движутся) — пока UNKNOWN; значения палитры F8…FF/00 цикличны, детали зависят от синхронизации с растром.

Не является гипотезой-фактом: конкретные имена функций (пока `isr@0x013F`, `init@0x0100` — временные метки, не установленные имена).

## 6. Замечания / конфликты

1. **Учёт fetch как read.** В `debug_get_memory_access_map` у кодового блока 0x0100 стоит `read=true, fetch=false`, `read_count≈8 млн`. Похоже, эмулятор засчитывает выборки инструкций (opcode fetch) как «read», не выставляя отдельный флаг `fetch`. Учитывать при интерпретации «чтений кода». (Emulator Behavior, не Hardware Fact.)
2. **`vram_base` в `debug_get_vram_info`/`debug_get_screen_info` = 0xC000**, тогда как список planes корректен (0x8000/0xA000/0xC000/0xE000). Значение `vram_base=0xC000` выглядит как артефакт/частичный отчёт эмулятора, а не реальная база дисплея. Отмечено как конфликт поля, не влияющий на выводы по плоскостям.
3. **Окно access-map ≠ вся история.** VRAM-очистка и первичная запись вектора/порта 0x02 произошли до `debug_clear_memory_access_map`, поэтому в steady-state-окне не видны; они подтверждены отдельными чтениями памяти/снапшотов и дизассемблированием инициализации, а не access-map.
4. **Порт 0x02 и палитра.** По KB (video.md/io.md) порт 0x02 НЕ задаёт индекс палитры (только border + режим 512); индекс палитры берётся из данных пикселя. Есть задокументированный CONFLICT с TIMSoft (порт 02h = «код цвета»). В нашем ROM пиксельные данные = 0, значит активна ячейка палитры с индексом 0, куда и пишутся значения через 0x0C. Выводы строим на модели эмулятора (VERIFIED_BY_CODE), hardware-статус точной трассировки индекса — UNVERIFIED.
5. Смежный артефакт `roms/tests/clrs/clrs.asm` (та же величина 119 байт) использовался ТОЛЬКО как источник гипотез; все фактические утверждения в отчёте опираются на MCP-данные по целевому ROM `roms/redesign/clrs/src/clrs.rom`.
