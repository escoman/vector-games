# fire3 — огонь методом «racing the beam» (Вектор-06Ц)

Этап калибровки. Идея: вместо поплоскостной записи в VRAM каждый кадр
(`fire2`: 1280 точек = 5120 байт/кадр) один раз очистить VRAM и **менять
цвет ячейки палитры №0 в тот момент, когда луч рисует очередную строку**
(`OUT 0Ch`). Движок гонки — в [fire3.asm](fire3.asm), внутренний буфер
64×20 и калибровочные рисунки — в [main.c](main.c).

## Как это проверить без «глазомера»

`beam_timing.py` собирает ISR ассемблером `utils/emulator/v06_emu.py`,
исполняет `_beam_isr` по одной инструкции и начисляет **video-такты
(v_cycles)** по таблице, извлечённой прямо из ядра
`vector-psp/src/i8080.cpp` (`utils/analyze/extract_vcycles.py`). Вывод:

```
$ python3 beam_timing.py            # или beam_timing.py 953 — переопределить COARSE
всего v_cycles за гонку: 227276   (= 295.932 строк)
OUT(0Ch) всего: 256
первый OUT: v_cycle 30572, индекс строки картинки = 0
дельта между строками (v_cycles): уникальные = [768]
строки картинки по OUT: head=[0, 1, 2, 3, 4] tail=[251, 252, 253, 254, 255]
```

Ключевое: **дельта между всеми 256 строками = ровно 768 v_cycles** — тело
строки фазо-закрыто к развёртке, дрейфа по высоте нет.

## Геометрия развёртки (из ядра vector-psp)

| Факт | Значение |
|------|----------|
| Строка развёртки | 768 v_cycles |
| Кадр | 312 строк = 239616 v_cycles |
| Картинка по вертикали | строки 40..295 (`render_full_frame_256`) |
| Пиксель | 2 v_cycles |
| Кадрирование | `filler.cpp commit_palette(index)`, index — пиксель ПОД лучом |
| Запись палитры | `OUT 0Ch` в байт цвета ячейки `index`; при чистой VRAM index=0 для картинки И бордюра |

Поэтому **один `OUT 0Ch` в начале строки перекрашивает всю строку**. Порт
0x0C пишет не в «выбранный» слот, а в слот индекса под лучом.

## Тело строки — ровно 768 v_cycles

```
mov  a,m     8   ; A = color[i], HL — единственный указатель по _row_table
inx  h       8   ; HL -> &table[i+1]
out  (0Ch)   12  ; луч в начале строки -> цвет всей строки
inr  c       8   ; счётчик строк (стартует с 0 после грубой задержки)
NOP x180     720 ; заполнитель, NOP флаги не трогает
jnz  body    12  ; пока C<>0 — следующая строка; оборот C=0 завершает гонку
               ---
               768
```

Самоизменяемого кода нет. Патчится только операнд `LXI B` грубой задержки
(`fire3_set_coarse`), длина от этого не меняется — фаза луча не съезжает.
`_row_table` — 256 байт (цвет на строку 40..295), заполняет `fire3_sync()`
из `main.c`. ISR сам ведёт `frame_count`, чтобы `gfx_next_frame()` работал
после подмены вектора RST 7.

## Ограничение текущей гранулярности

Горизонталь дорогая: смена цвета на строке стоит вывод (~12 v_cycles) плюс
позиционирование внутри строки, а строка — всего 768. Физически выходит не
больше нескольких цветов на строку, **не 64**. Поэтому на этом этапе одна
строка экрана = один цвет, а точка буфера по высоте = 4 строки (масштаб 4×4
по вертикали работает, по горизонтали — нет). От буфера 64×20 берётся левая
точка строки. Ограничивающий прямоугольник потому и виден как две яркие
горизонтальные полосы (верх/низ буфера) — это и есть проверка вертикального
позиционирования.

   буфер лежит на строках 40+128=168..247, нижняя половина).

   целиком станет виден прямоугольник.
