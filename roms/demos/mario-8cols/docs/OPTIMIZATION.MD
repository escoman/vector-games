# mario-8cols: оптимизация горизонтального скролла (перерисовка тайлового окна)

Горизонтального аппаратного скролла у Вектора-06Ц нет (порт 03h сдвигает только
вертикаль), поэтому **шаг скролла = стоимость перерисовки**
[`mario.asm`](../mario.asm) → `_render_window` / `_rw_block` / `_rw_put_cell` /
`_rw_copy8`. Логика запекания окна — [`main.c`](../main.c) → `bake_window` /
`bake_shift` / `bake_groups` / `bake_clear`.

Ограничения платформы, актуальные для всех пунктов:

- только Intel 8080: нет `jr`/`djnz`, нет префиксов `CB/DD/ED/FD`, `DCR/INR` не
  меняют CY;
- `DAD h` = `HL << 1` и **не трогает флаги** — на этом построен `_mulshift`;
- сборка `--no-crt`: **BSS не обнуляется**, порядок объявлений в модуле =
  порядок в BSS (на этом держится колонка-страж);
- хот-путь на `__z88dk_callee` (callee чистит стек, `inx sp / inx sp`),
  аргументы `sccz80` пушит **слева направо** ⇒ последний лежит по `sp+2`;
- бюджет кадра **59 904 T** (3 МГц / 50 Гц), wait states видеоконтроллера
  учитываются в офлайн-профиле по таблице `EMU80::getCpuWaitStates`.

## Как мерить

```bash
python3 tools/profile_scroll.py             # базовые замеры + модель ходьбы 240 кадров
python3 tools/profile_scroll.py sweep       # проход камеры 0..287, T на каждый шаг
python3 tools/profile_scroll.py sweep --rom /tmp/rom_ref/mario-8c.rom \
                                      --map /tmp/rom_ref/mario-8c.map   # та же мерка на другой сборке
python3 tools/check_bake.py                 # паритет Python-модели окна и ROM bake_* по всем базам
python3 tools/check_boundary.py             # кадр перехода окна против эталонной перепечки
python3 tools/check_boundary.py --noguard   # воспроизводит исходный дефект (75 байт VRAM)
python3 tools/check_render_regress.py       # SHA-1 VRAM по шагам скролла, для паритета до/после
```

Эталонную сборку для сравнения удобно делать так: текущая `main.c` + `mario.asm`
из предыдущего коммита (`git show HEAD~1:./mario.asm`), тогда расхождение VRAM
указывает именно на правку ассемблера.

### Прототип кандидата без пересборки ROM (быстрый A/B)

`make` ради одной микроправки `copy8` — самое узкое место цикла «идея → цифры».
`utils/emulator/v06_emu.py` несёт **мини-ассемблер** (`Assembler8080`), поэтому
черновик рутины можно собрать и замерить на реальном состоянии окна, не трогая
z88dk — те же `cycles()`/`wait_cycles()`, что у встроенных замеров:

```python
from v06_emu import Assembler8080
# внешние метки рендера задаём EQU'ами (у mini-ассемблера нет EXTERN):
head = "TILESET EQU %dh\nTILEWIN EQU %dh\n" % (rom.at('_tileset'), rom.at('_tile_win'))
asm = Assembler8080().assemble_text((head + open('cand.asm')).read().splitlines())
scr = 0x4C00            # свободная RAM ниже SP=0x7E00 и < 0x8000 — проверить по map!
for i, b in enumerate(asm.data):
    if b: cpu.mem[scr + i] = b
res = call_asm(cpu, scr + asm.labels['cand'], [cam, old, blk0, nblk])
print(f'{res.cyc:,} T  {res.instr:,} инстр  {res.vram:,} записей VRAM')
```

Правила, иначе A/B врёт:
- **`scr` — свободная RAM**: подобрать по map диапазон без символов **ниже** `SP`
  (`0x7E00`) и не там, куда кандидат развернёт свой стек/аргументы; адрес ниже
  `0x8000`, чтобы не засорить счётчик записей VRAM;
- внешние символы (`_tileset`, `_tile_win`, `_tile_nz`, `_pair_top`, `_cam_row`,
  `_tile_stride`) подставлять **числовыми адресами** через `EQU` из `rom.sym` —
  `Assembler8080` игнорирует `SECTION/PUBLIC/EXTERN`;
- аргументы `__z88dk_callee` — тем же `call_asm`/`push_args` (параметры слева
  направо, `sentinel`-возврат), иначе callee съест чужой стек;
- **паритет по VRAM обязателен**: прогнать кандидата на входах baseline и сверить
  `vram_of(cpu)` (`check_render_regress`) прежде чем верить T — «быстрее, но
  иначе» не считается.

### Две модели стоимости — не путать и сверять между собой

| инструмент | откуда такты | гранулярность | wait states | что НЕ моделирует |
|---|---|---|---|---|
| `tools/profile_scroll.py` | захардкоженная таблица `cycles()` + `WAITS[]` | по **участкам** (метки map) | ✅ `wait_cycles()` | IRQ 50 Гц, клавиатуру, физику, музыку, палитру, `IN/OUT` |
| `../mario-16cols/tools/frame_cost.py` | **из исходников эмулятора**: `utils/analyze/extract_vcycles.py` парсит `v_cycles` из `vector-psp/src/i8080.cpp` | по **строкам `mario.asm`** | ❌ только база | то же |

`profile_scroll` считает **изолированный вызов** рутины: «4,58 кадра на шаг» —
это путь render+bake+спрайт без кадровой обвязки (IRQ, опрос клавиатуры,
`solid_at` на каждый шаг физики, `pick_sprite`, `gfx_next_frame`). Реальный кадр
чуть дороже; финальное слово — за **cycle-accurate** эмулятором (`vector-debugger`
MCP / C++ EMU80), а не за офлайн-моделью.

Что стоит сделать с моделями:
- генерировать `cycles()` из `extract_vcycles.py` (таблица из исходников
  эмулятора) вместо ручной копии — при новой инструкции ручная таблица молча
  считает по умолчанию (см. «Ямы»);
- перенести **атрибуцию по строкам** (как в `frame_cost.py`) в `profile_scroll.py`,
  чтобы оценку #4/#7 сверять ровно по тем `stax/inx/dcx`, что правим.

## Внедрено

### ✅ #7. Инлайн `_rw_copy8` в `_rw_put_cell`

Копирование 8 байт плоскости встроено прямо в обе ветки `_rw_put_cell` вместо
`call _rw_copy8` — убраны `CALL`(18)+`RET`(10) на каждую записанную плоскость
(~2 записи на грязную клетку × ~143 клетки/шаг). `_rw_copy8` оставлен рутиной:
его по-прежнему зовёт `_render_rowband` (вертикальный скролл), где инлайн не
оправдан размером. Последовательность `mov a,m / stax d / inx h / dcx d` не
изменена ⇒ VRAM **побайтово идентичен** (проверено `check_render_regress` на 47
кадрах). ROM 17 994 → 18 052 байта. Эффект: средний шаг 210 660 → 204 951 T
(−5 700 T/шаг), медиана ходьбы 209 508 → 203 608 T, худший 275 304 → 268 644 T.

### ✅ #9. Инлайн `_rw_put_cell` в `_rw_scan` (убран `call/ret` на грязную клетку)

Поверх #7 тело `_rw_put_cell` перенесено прямо в цикл `rw_scan` — убраны
`CALL`(17)+`RET`(10) на каждую грязную клетку (отдельная рутина `_rw_put_cell`
удалена, `rw_p0w`/`rw_p1` теперь локальные метки внутри `_rw_block`). Раскладка
регистров не менялась: вызывающий по-прежнему пушит `b/d/h` вокруг тела, поэтому
риск нулевой. Последовательность `mov a,m / stax d / inx h / dcx d` та же ⇒ VRAM
**побайтово идентичен** (проверено `check_render_regress`: 86 хэшей, включая
покрытие `cam_row` и `render_rowband`). ROM 18 205 → 18 201 байта.

Эффект (`profile_scroll`, wait states учтены): средний шаг **204 535 → 201 571 T**
(−2 964 T/шаг, −1,45 %), худший шаг 308 088 → 302 668 T, медиана скролла
258 840 → 255 000 T, худший кадр ходьбы 275 392 → 271 592 T. Малый, но бесплатный
вин — снимает только `call/ret`, `push/pop` трёх регистров остаться вынуждены
(нет свободной пары под `nzmask`, переживающий цикл записи плоскости).

### ✅ #4. Заливка нулями вместо copy8 для стираемой плоскости

Поверх инлайна #9 ветка «новый тайл пуст, а старый содержал плоскость» льёт
нули напрямую (`xra a` + 8×`stax d / dcx d`), не читая tileset и не двигая `HL`
через 8 байт тайла — стерание ≈96 T вместо copy8 ≈192 T на плоскость. Отличие от
ранней изолированной попытки (см. заметку ниже): маска теперь в `B` и различает
`nz[new]`/`nz[ref]` (биты 0/1 = новый, 2/3 = старый, задаётся сдвигом `nzref<<2`
при разборе), поэтому решение copy/erase/skip — это пара `ani/jnz`, а copy-путь
(самый частый) не дорожает вовсе: добавка `add a / add a` на разбор маски и
второй `ani/jz` исполняются только на не-copy плоскостях.

Эффект (`profile_scroll sweep`, 288 шагов, wait states учтены; VRAM-паритет
`check_render_regress` 65/65 хэшей побайтово, включая покрытие `cam_row` и
`render_rowband`): средний шаг **201 571 → 199 332 T** (−2 239 T/шаг, −1,1 %),
худший шаг (cam 263, плотная часть) 302 668 → **297 616 T** (−5 052, −1,7 %); на
плотных шагах cam 255…270 экономия стабильно ~4…5k T/шаг (там ~18 % стираемых
плоскостей от 4 000+ записей). Худший кадр ходьбы (полный кадр сцены, 7 832
записи VRAM): 555 540 → **525 988 T** (−29 552 T, −5,3 %) — главный выигрыш как
раз там, где жалоба «скролл заметен, когда много объектов». ROM 18 201 → 18 269
байт (+68). Регрессий нет (один кадр перехода окна cam 288 +1,6k из-за доп.
разбора маски — один раз на 32 колонки).

### ⚠️ Исторямка: первая версия #4 (до инлайна) не окувалась

Патч «лить нули через отдельную `_rw_zero8` + `sta`/`lda` комбинированной маски
на каждой клетке» был собран и измерен ДО инлайна #7/#9: паритет VRAM идеальный,
но шаг стал чуть **дороже** (медиана 209 508 → ~209 944 T). Экономия ~96 T на
erased-плоскость съедалась ветвлением на **каждой** клетке. Вывод подтверждён
сейчас: `zero8`/erase оправдан **только поверх инлайна** (без `call`-обязательств
ветвление дёшево) — как ровно и сделано в #4 выше.

### ✅ Правка бага на границе блоков «выпекания» (колонка-страж)

На кадре перехода базы окна вперёд (`base: b → b+32`, `cam=b+32`, `old_cam=b+31`)
ref-указатель нулевого блока = `tile_win + (old_cam − base)·LEVEL_ROWS = tile_win−64`,
то есть читает мусор BSS **перед** окном. Мусор случайно совпадал с пустыми
клетками новой колонки → клетки левого края не стирались, на границе перепечки
залипались кусочки уехавшего фона (измерено: 75 байт VRAM, плоскости 8/4, блок 0).

Правка: `tile_win_prevcol[LEVEL_ROWS]`, объявлена **непосредственно перед**
`tile_win` (при `--no-crt` порядок объявлений = порядок в BSS, смежность
проверяется по map-файлу в `check_boundary.py`). `bake_shift` при сдвиге вперёд
сохраняет в неё уезжающую мировую колонку `base−1` **до** memmove.
Арифметика ассемблера не меняется: `newwalk − stride` теперь указывает ровно в
страж. Цена — 64 байта BSS и копирование колонки раз на перепечку. Обратные
переходы безопасны сами (данные уже лежат в `local 32..63`).

### ✅ #5. `_mulstride` → сдвиги + `refwalk = newwalk ∓ stride`

`_mulshift`: `HL = DE`, затем `_tile_stride_shl` раз `dad h` (11 T, флаги не
трогает) ≈ 90 T вместо ≈ 700 T на 8-итерационном сдвиг-сложении. Показатель
степени считает `main.c` на старте (`tile_stride_shl`), `0xFF` = «не степень
двойки» → откат в `_mulstride`.

В `rw_have_ref` при обычном скролле `|old − cam| == 1`, поэтому умножение не
нужно вовсе: `refwalk = newwalk ∓ один шаг окна` (со знаком, обратным ходу
камеры) ≈ 45 T. Дальний прыжок камеры идёт по общему пути через `_mulshift`.
Примечание: ветка «−1» из-за бага сравнения не работала с момента внедрения —
исправлено позднее (см. ниже «Фикс распознавания `delta = −1`»).

### ✅ #2. `_rw_put_cell` в регистрах, `dst_low` в `C`

Все промежуточные значения (`B` = новый тайл, затем `nzmask`; `DE` = база
`tile_nz`) живут в регистрах, `*16` — четырьмя `dad h`. Кольцевой `dst_low`
строки переехал из BSS в `C` (вызывающий пушит пару BC), обмен двух указателей
в `_rw_block` — через стек. Удалены `rw_refcell`, `rw_dstlow_cur`, `rw_dstlow`,
`rw_nzmask`, `rw_tnew`, `rw_tref`.

Эффект правок вместе: шаг 250 150 → 210 660 T (−15,8 %), худший 381 316 →
319 024 T, кадр перехода окна 272 896 → 229 260 T, `put_cell` 77 293 → 48 426
T/шаг (−37 %) при **неизменных** 2 283 байтах VRAM на шаг (паритет по VRAM
подтверждён против эталонной сборки).

### ✅ Фикс распознавания `delta = −1` (ветка #5 наконец заработала)

В проверке разницы `old − cam` младший байт сравнивался с `01h` вместо `0FFh`
(16-битное `−1` = `0FFFFh`), поэтому ветка «скролл вперёд ⇒ `refwalk =
newwalk − stride`» из #5 **не срабатывала никогда** — каждый кадр скролла шёл
через общий `_mulstride`/`_mulshift`. Правка одной константы; по VRAM ничего
не меняется (путь даёт тот же `refwalk`), меняется только цена. Эффект: средний
шаг 204 951 → **204 535 T** (−416 T/шаг), худший 308 504 → 308 088 T, ROM
без изменений (18 052 байта). Паритет — `check_render_regress` (66 хэшей,
включая покрытие `cam_row`).

## Не прошло

### ❌ #1. Офлайн-маска грязных строк — реализована, измерена, откачена

Сделано ровно как в плане: ассет `dirty_mask` в `gen_assets.py` (320 колонок ×
8 байт = 2,5 KB, бит r = `tile[q][r] != tile[q−1][r]`), быстрый путь
`_rw_block_mask` в ASM (4 байта маски на блок: чистый байт — пропуск 8 строк
сдвигом курсоров, грязный — прежний построчный скан), активация при `delta=−1`
и `cam_row % 8 == 0` (без ring-shift маски). Паритет VRAM достигнут (66/66
хэшей) — попутно нашлись два своих бага быстрых путей (см. «Ямы»).

Замер (`profile_scroll sweep`, 288 шагов): **221 249 T/шаг против 204 951 —
регрессия +16 298 T/шаг**. Причина — загрузка уровня, а не механика: на
основной высоте ходьбы (`cam_row = 32`, земля+декор) полностью чистых
(пропускаемых) байтов маски только **65,8 %**, а чтение каждого байта маски
(`LHLD/SHLD` + стек, ~100 T на группу) **на грязных группах не отменяет
скан, а добавляется к нему**. Точка безубыточности ≈75 % чистых байтов; на
плотной части уровня (cam 262…266) — ещё хуже. Пункты **#8 (ран-листы) и
1-lite (`pair_bottom`) закрываются как направление**: они делят ту же модель
экономии «пропустить заведомо одинаковые строки», а измеренная доля чистых
строк её не окупает. Быстрый путь, ассет и ссылки сняты (`gen_assets.py` /
`level.inc` / `mario.asm` — возврат к baseline+фиксы); фикс `delta=−1`
оставлен как отдельная правка выше.

### Уточнение к #4: дешёвый erase и где реально применять `PUSH`

Идея «лить тайлы/спрайты через `PUSH`» для **переменных** данных ускорения не
даёт: чтобы запушить пару байт, их всё равно надо прочитать из ROM (`LDS` = 16 T
+ wait) — столько же обращений к памяти, что `MOV A,M`+`STAX`; плюс `PUSH` меняет
порядок строк тайла внутри пары (нужен свап `B↔C`) и на шве `0xXX00` уводит
старший байт адреса в соседнюю колонку (портит кадр — потому `mario_draw` и идёт
побайтным `dcr e`, а не `dcx d`). `PUSH` — идиома **константной** заливки: она
доказана в `lib/gfx/clr.asm::gfx_fill_planes` (`di` → `ld sp, верх_плоскости` →
`push hl` ×N → восстановить SP → `ei`) и применима к обнулению целых плоскостей,
не к клеткам.

Для самого #4 «стереть пустую плоскость» `PUSH` не нужен: достаточно **не читать
tileset** — заранее занулить `A` и лить его (признак «плоскость пуста» уже лежит
в `nz[new]`, который `put_cell` держит в регистре):

```asm
; было   (copy8, читает tileset): mov a,m / stax d / inx h / dcx d  ×8 = 192 T
; станет (erase, без чтения):     xra a … stax d / dcx d            ×8 ≈  96 T
; не забыть сдвинуть HL на 8 (lxi d,8 / dad d), если после erase идёт след. плоскость
```

Т.е. стирание вдвое дешевле copy8 **без** работы со стеком и без `di/ei`.
`PUSH`-обнуление (8×`push b` с `BC=0` = 88 T за 16 байт) оправдано лишь для
прогонов ≥16 байт и **со страховкой от шва** (только если прогон не пересекает
`0xXX00`), иначе — откат на `stax`. Для per-cell #4 этого не требуется.

## Ямы, в которые уже наступили

- **Оптимизация может «не работать» молча и без бага в выводе.** Ветка
  `delta=−1` из #5 сравнивала младший байт разницы с `01h` вместо `0FFh` и не
  срабатывала никогда: VRAM-паритет её не ловит (результат верный, просто
  медленнее), ловится только сверкой T до/после с теорией. Быстрая ветка,
  которую добавили «ради ускорения», обязана дать измеримый эффект — иначе
  искать, что она не исполняется.
- **16-битная адресная арифметика на 8080: перенос из `add` младшего байта
  теряется молча.** `mov a,l / add c / mov l,a` без `mov a,h / aci 0 / mov h,a`
  уводит указатель ровно на страницу (в маске #1: `$1F03` превратился в
  `$1E03`) — паритет VRAM ломается не на всех кадрах, а только когда сумма
  переполняет L. Ловится трейсом обращений к памяти (`debug_get_memory_access_log`
  / read-trace), который показывает, что читаются не те адреса.
- **Доля «пропускаемого» надо измерять до реализации оптимизации, а не после.**
  Маска грязных строк (#1) была написана целиком (ассет + ~150 строк ASM +
  паритет), и только замер показал, что на рабочей высоте `cam_row=32` чистых
  байтов 66 % при точке безубыточности ~75 %: распределение маски считается
  двумя строчками на Python-модели окна в `gen_assets.py` за полчаса до
  всякого ASM.
- **Офлайн-харнес обязан инициализировать весь читаемый BSS.** Сборка
  `--no-crt` не обнуляет BSS, тесты вызывают `main()`-инициализацию руками:
  любая новая переменная, которую читает ASM (`tile_stride_shl`), должна
  выставляться **во всех** инструментах (`set_stride()`), иначе паритет ломается
  сразу на всех кадрах и выглядит как регрессия оптимизации.
- **Нельзя вызывать `bake_groups`/`bake_shift` с мировыми колонками при другой
  базе окна**: они пишут по `(c0 − tile_win_base)`, уводят указатель за буфер и
  дают «вечный цикл» в профиле. Перед замером C-хот-пути окно ставится к базе 0
  (`install_window(..., 0, ...)`).
- **`bake_shift(win, base, nb, lv)` изменяет `win` на месте** и возвращает `nb`
  (не новое окно), поэтому уезжающую колонку для стража надо читать **до** сдвига.
- **Кольцевое окно обязано иметь «призрачную» колонку слева** — иначе любой
  diff-рендер на границе базы читает чужую память.
- **Таблица `cycles()` обязана покрывать новый опкод, иначе профиль молча
  занижает.** Неизвестный опкод уходит в `.get(lo, 4)` = 4 T; например `SPHL`
  (`0xF9`) там стоит 4 T против 5 T в `docs/VECTOR_CPU_COMMANDS.md`, и любая
  новая команда (`sphl`/`lxi sp`/`xthl` из `PUSH`-варианта) посчитается по
  минимуму. После правки — пересобрать/поверить таблицу (лучше генерировать из
  `extract_vcycles.py`) и свериться с `frame_cost.py`.
- **Офлайн-профиль мерит изолированный вызов, а не весь кадр.** Бюджет ходьбы в
  `profile_scroll` = render+bake+спрайт без 50 Гц IRQ, клавиатуры, `solid_at` на
  каждом шаге физики, `pick_sprite` и `gfx_next_frame`. Итоговое время проверять
  на cycle-accurate эмуляторе (`vector-debugger` MCP), иначе «ускорили на 15 %,
  а на железе всё равно проседает».
