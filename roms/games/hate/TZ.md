> Zaxxon: техника игрока (танк → самолёт → ховеркрафт) движется над чужой планетой,
> уничтожает ядерные генераторы, собирает открывшиеся плазменные ячейки

## 1. Что разобрано в оригинале (факты, на которые опирается порт)

Разбор zx-disasm выполнен полностью (2 базы: титульная + постоянный движок
$CF32–$F2DF, покрытие 4880 адресов). Ключевые установленные факты:

1. **Рендер — тайловый конвейер на кольцевом буфере** (не векторный и не
   спрайтовый; ENGINE.MD — источник истины):
   - банк шаблонов `$C400`: 64 клетки 8×8 по 8 байт, MSB-first; код 00 = пустая;
   - **кольцевой буфер** `$8000–$BFFF`: 64 страницы × 256 Б; страница = один
     столбец ландшафта из 16 клеток (128 Б) + та же колонка, сдвинутая на 2 px
     (`+$80`, фазы подпиксельного скролла);
   - **лесенка** `$D5B2`: готовый список адресов экрана (перспектива: дальние
     столбцы короче и выше);
   - **блиттер** `$D2E3/$D35E`: `SP=$D5B2`, `POP HL` → 8 × (`LDAX D; STAX H;
     INX D; DCX H`) — клетки пишутся вверх по экрану; `$FFFF` = конец списка;
   - **атрибутный проход** `$D338`: цвет клетки по вертикальной полосе (4
     «дороги» `$58..$5B`), а не по коду шаблона;
   - геометрия кольца: `off(x+1) = off(x) + $200 − 4` (mod $4000) — «две страницы
     вперёд и 4 байта вверх» на каждый столбец экрана; отсюда наклон рельефа;
   - **сборка страницы** `$D51D`: специальная ближняя клетка (4 фазы дороги) +
     15 клеток из очереди `$CA43` (указатели из `$C8EA`) по записям столбцов
     `$C6xx` (15 кодов клеток подряд);
   - **объекты**: 16 записей по 16 Б в `$C000–$C0FF` (тип/дистанция/боковое/
     клиренс/индекс формы/фаза/X/полоса); проекция `$EFA5` прикрепляет объект к
     СТРАНИЦЕ КОЛЬЦА: `page = $80 | (($C32E) + 2*band + $78) & $3F`; вывод
     `$D9D6` → `$DD44` снимает фон в `$F800`, `$DD6C` кладёт ряды объекта
     обратно в кольцо; объект рисует ТОТ ЖЕ блиттер, что и ландшафт;
   - формы объектов — потоковые патчи в координатах кольца (ряды × ширина,
     шаг ряда `+$1FC`); три размерных класса: 4×21 / 3×17 / 2×13, по 4 фазы
     ракурса; таблица указателей `$C300`;
2. **Данные уровня**: таблица трассы/высоты `$6000–$62FF` (24×32, читает
   `LE3BF` — скан клиренса для ИИ и проверки «можно ли ехать»), дескриптор
   сцены по указателю `($CF2E)`, части уровня `$C8EA`;
3. **Статичный банк геометрии `$653A–$8008`** (6863 Б, инвариантен между
   далёкими кадрами) — дамп `data/gfx/bank_653A.bin`; формат рёбер/вершин
   распарсен не до конца, но для порта банк переносится как данные (см. §5.6);
4. **Шрифт `$6300`**: 96 глифов 8×8, MSB-first, индекс = код − $20 —
   `data/gfx/font_6300.bin` (768 Б);
5. **HUD**: панель SCORE/HIGH/MAX справа внизу + узкие вертикальные полосы
   приборов (blit `AND (HL)` $DECB–$DF05), текст «вырезается» из панели;
6. **Окна** `$EE17`: структуры `$F0EB/$F12C…`, бит 7 кода символа = разрыв
   строки, `$FF` = конец; строковый банк `$F0E4–$F1A4` (SELECT/DEMO/PAUSE!/
   ABORT!…);
7. **Состояния и секреты**: меню SELECT (1–4 = режимы ввода, 5 = DEMO,
   6 = START GAME, гейт SPACE); в миссии `p` = окно ABORT! (ENTER → GAME OVER),
   `u+g` = DEMO-автопилот (`$F0DB=$FF`, зелёный рельеф);
8. **Ввод** `$E6FF` по режиму `$C28F`: биты 2/3 = горизонталь (Q/A, W/S с
   флагом направления из записи игрока), биты 0/1 = вертикаль (ENTER/L),
   бит 4 = SPACE-ряд (огонь); + SINCLAIR/KEMPSTON/PROTEK-режимы;
9. **Звук — 1-битный бипер (порт `$FE`), два независимых движка** (полный
   разбор, извлечение и грабли — SOUND.MD; готовые эталоны — `sound/`):
   **на Векторе тот же бипер выводится через TapeOut** — ПИА #1, порт `01h`,
   бит 0 («магн. out»), установка/сброс — запись `01h`/`00h` в BSR-порт
   `00h`; это ровно та же 1-битная схема, что `OUT ($FE)` у ZX, поэтому оба
   движка переносятся тем же кодом (§3.8, решение обязательное):
   - **музыка заставки** `$8000–$85C5` (`asm/HATE_title.asm`): рабочее окно
     `$058C` байт с двойной буферизацией (`$803A` ↔ копия), ровно один шаг
     партитуры на кадр (`EI/HALT` в `$8109`); диспетчер событий `$8243`
     (потоки `$85A3`/`$85B1`; коды: 0 = пусто, 1 = закольцовка,
     2 = пауза `$836A/$8375`, 3 = шум `$8389` из ROM `$0064`,
     4/5/6 = тональные семейства `$839A/$83C6/$8398`); два голоса
     `L82A3/L82C1` (A) и `L8305/L8323` (B) на самомодифицируемых парах
     «период + шаг» (`$82CA/$82CC/$82D0/$82D4`, `$832C/$832E/$8332/$8336`);
   - **SFX миссии** `$F1AA–$F2DF` (`asm/HATE_engine.asm`): тон `$F284/$F288`
     (`L` — период, `H` — длительность), свип `$F2A3` (4 параметра),
     резолвер `$F2C0`: бит `k` байта `$F2BF` → запись `$F2E2 + 5·k`, таблица
     5×5 байт; бит живёт один кадр (`LD050_1` гасит `$F2BF`), поэтому при
     удержании условия звук превращается в «трещотку» коротких бипов;
   - **триггеры SFX**: выстрел (бит 0, `$ECF3`), попадание/гибель (бит 1,
     `$E3BF_18`/`$E9CE_30`), разрушение (бит 2, `$E3BF_14`), конец миссии
     (бит 3, `$E5C9_4`), трансляция/сопровождение цели (бит 4, `$E889`);
     прочие бипы (меню, пауза, старт с уровня) берут пару период/длина из RAM
     на ходу (`$0F3C`, `$C814`, `$8C05`, `$465A`, `$1E9C`);
   - **снятые эталоны**: `sound/title_music.wav` (38.54 с) + `title_music.txt`
     (лог всех переключений бита 4 с `PC` каждой записи в порт),
     `sound/sfx_0..4_*.wav` (одно срабатывание) и `sound/sfx_preview.wav`
     (5 эффектов × 3 повтора) — получены прогоном настоящего кода в SkoolKit
     (`tools/sound_extract.py`, `tools/sound_decode.py`), а не синтезом.

Неизвестное/недоразобранное (из README/ENGINE.MD §8): зачёт завершения миссии,
точная поразрядная раскладка форм, момент перекрутки кольца, роль `$D105`.
При порте эти места проверяются эмпирически в эмуляторе (см. риски, §10).

## 2. Цель порта и рамки

Играбельный ремейк H.A.T.E. на Векторе-06Ц: полный цикл «титул → меню SELECT →
миссия (несколько уровней/техники) → смерть/респаун → конец уровня → GAME OVER»,
DEMO-автопилот, пауза, HUD, звук.

**Технология — обязательна:** двойной буфер `lib/gfx/dblbuf.asm` (как в
`mario-dbl`): буфер A = плоскости E000/C000, буфер B = A000/8000, смена палитры
на VBlank, 4 логических цвета на буфер. Плавность без tearing — критерий №1.
**Область применения — меню и миссия:** заставка статична и выводится
**без dblbuf** (одиночный вывод в буфер A, §3.5); dblbuf включается на входе
в меню: рельеф-фон рисуется один раз в A и копируется в B, поверх него в
back-буфер лягут пункты меню (Stage 3); в миссии — та же схема для динамики.

**Что портируется буквально (алгоритмы и данные):** кольцевой буфер, сборка
страниц `$D51D`, проекция объектов `$EFA5`, вывод объектов `$D9D6/$DD44/$DD6C`,
банк шаблонов, банк геометрии, таблица трассы, данные уровней, шрифт.

**Что переписывается под Вектор:** блиттер экрана (линейная адресация VRAM +
цветовые плоскости), лесенка адресов, атрибутный проход (→ цветовая модель §5.3),
ввод, окна/HUD. **Звук не переписывается по существу:** бипер `$FE` →
TapeOut (PC0 ПИА1, порт `01h`/BSR `00h`) — как на ZX Spectrum; 1-битный
программный синтез сохраняется, ВИ53 в звуковом тракте не участвует (§3.8).

## 3. Ключевые проектные решения адаптации

### 3.1 Память: кольцо уменьшается до 32 страниц

Оригинальное кольцо 16 КБ лежало в `$8000–$BFFF`; на Векторе весь диапазон
`0x8000–0xFFFF` занят видеопамятью двух буферов dblbuf. Нижних ОЗУ только 32 КБ
(ROM + куча + BSS + кольцо). Поэтому:

- **Кольцо: 32 страницы × 256 Б = 8 КБ, по адресу `0x6000–0x7FFF`** (страница =
  16 клеток + сдвинутая копия `+$80` — как в оригинале);
- **Шаг кольца: `+$FC`** (1 страница = 256 Б, минус 4 байта, mod `$2000`)
  вместо `+$1FC` (2 страницы − 4): сохраняет уклон «−4 байта на столбец» и
  даёт полный экранный охват без коллизий (пролёт кадра 31×$FC + 192 =
  8004 Б < 8192 Б);
- все формулы пересчитываются механически: `2*band → band`, `$78 → $3C`,
  `&$3F → &$1F`, высокий байт страницы `$80|idx → $60|idx`, заворот
  `D+=2; RES 6,D → D+=1; RES 5,D`; проекция объекта:
  `page = $60 | (($C32E) + band + $3C) & $1F`.

### 3.2 Блиттер: линейная адресация Вектора

У Вектора столбец VRAM — 256 ПОДРЯД идущих байт (адрес = `base + col*256 +
255 − y`), в отличие от трёхтретевой развёртки ZX. Клетка пишется как в
оригинале: `8 × (LDAX D; STAX H; INX D; DCX H)`, но адрес клетки считается
по формуле выше. Лесенка `$D5B2` (528 слов) заменяется **таблицей столбцов**:
32 записи `(адрес_старта_колонки, число_клеток)`, предвычисленной один раз из
данных лесенки оригинала (утилита `tools/`); перспектива сохраняется как есть.

### 3.3 Цветовая модель (4 цвета → 2 плоскости)

Палитра обоих буферов (маска `0x03`/`0x0C` внутри):

| Лог. цвет | Бит (вес) | Роль |
|---|---|---|
| 0 | 00 | чёрный (небо/пустота) |
| 1 | 01 (w1) | зелёный — рельеф/дорога/ландшафт |
| 2 | 10 (w2) | голубой/белый — текст, кристаллы, HUD |
| 3 | 11 (w1+w2) | красный — враги, огонь, опасность, логотип |

- **Плоскость w1** = полный битмап сцены (всё, что не чёрное).
- **Плоскость w2** = «старший бит цвета»: пишется только там, где цвет 2 или 3.
- Блиттер клетки: 8 байт паттерна → w1 всегда; → w2 если `цвет&2`, иначе
  8 × зачистка w2 (XRA A). Быстрый путь: рельеф почти весь зелёный (w2 пустой),
  и при чистом ландшафте w2 можно не трогать вовсе — зачищать только там, где
  раньше был не-зелёный объект (грязные зоны по списку объектов).
- Цвет клетки определяется **полосой** (как атрибутный проход оригинала):
  таблица «полоса → логический цвет» (4 дороги рельефа) + цвет объекта из его
  записи. Паттерн и цвет кодируются в кольце раздельно: байт паттерна — в
  странице кольца (как в оригинале), цвет — в параллельной карте
  `color_cell[32][16]` = 512 Б (байт на клетку, 16 клеток × 32 страницы).
- **Фон меню (Stage 3) — цвет запечён в данные.** На кадре меню все 24 ряда
  (полосы) дают атрибут `6/0` (жёлтые чернила по чёрной бумаге), поэтому
  `tools/gen_terrain.py` собирает 8-байтные блоки плоскостей сразу в нужном
  варианте (00 / FF / паттерн / ~паттерн) и `include/render.asm` только
  копирует байты: арифметики цвета в рантайме нет. Для порта меню этого
  достаточно; цветовая модель §3.3 остаётся рабочей для миссии
  (`color_cell` + w2-патчи). Палитра буфера — `terrain_pal4`
  (0 чёрный, 0x3F жёлтый, 0xFF белый, 0x07 красный).

### 3.4 Объекты — через кольцо, с w2-патчами

Проекция и вывод объектов портируются буквально (§3.1-пересчёт формул):
объект кладётся в кольцо, фон снимается в буфер кучи (аналог `$F800`), ряды
патча пишутся с шагом `+$FC` (внимание: шаг ряда внутри патча объекта = шаг
кольца, см. §3.1). Цвет объекта пишется в `color_cell`. Движение объекта =
снять-положить в кольцо + переблит затронутых полос — как в оригинале
(§4.4 ENGINE.MD).

### 3.5 Двойной буфер: что рисуется куда

- **Заставка — БЕЗ dblbuf.** Растр титула статичен, свапать нечего: картинка
  рисуется один раз в одиночном режиме (плоскости буфера A, E000/C000, маска
  `0x03`), `gfx_dblbuf_init()`/`gfx_dblbuf_present()` не вызываются, палитра
  статична. Критерий сверки — эталон `assets/hate.png` (Stage 3).
- **Меню — С dblbuf** (уточнение этапа 3, отменяет прежнее «меню без dblbuf»):
  после нажатия клавиши на заставке палитра гасится, затем
  `gfx_dblbuf_init(terrain_pal4)`, `set_planes(0x03)`, рельеф в буфер A
  (`include/render.asm`: плоскости 0xE000/0xC000, 2480 Б данных в
  `include/terrain.inc`), `gfx_dblbuf_copy_ab()` → тот же рельеф в B,
  `gfx_dblbuf_front_pal()` → `gfx_fade_in()`, дальше цикл `present()` +
  `v06_wait_frame()`. Пункты меню (следующий шаг) рисуются в back-буфер и
  появляются на свапе — без мигания оверлея.
- **Статичный слой миссии** (рамки, панель HUD, статичные строки меню):
  рисуется один раз в буфер A, затем `gfx_dblbuf_copy_ab()` → в B;
- **Динамика миссии** (рельеф + объекты): на каждый **скролл-тик** полный
  переблит игрового поля в back-буфер; между тиками — только переблит полос,
  затронутых объектами; затем `gfx_dblbuf_present()` и `v06_wait_frame()`
  (кадровый контракт §7: `frame_handler` = только `gfx_dblbuf_isr()`;
  TapeOut-звук — `sound_service()` в главном цикле, §3.8);
- **HUD-цифры/полосы**: перерисовываются в back-буфере после блита поля каждый
  кадр (как в оригинале — панель поверх рельефа), текст — `gfx_print`
  портированным шрифтом (§3.7);
- fade-in по палитре переднего буфера, как в mario-dbl.

### 3.6 Управление (порт)

| Действие | Клавиши Вектора | В оригинале |
|---|---|---|
| Горизонталь | ← / → | Q/A (+W/S с флагом) |
| Тяга/высота | ↑ / ↓ | ENTER / L |
| Огонь (осн. оружие) | ПРОБЕЛ | SPACE-ряд (bit4) |
| Вторичное оружие | СС (Shift) | «вверх + огонь» |
| PAUSE | P | P |
| ABORT (в миссии) | A | P + ENTER-подтверждение |
| DEMO-секрет | U+G | U+G |
| Меню: ввод | 1..4 / 5 (DEMO) / 6 (START), ПРОБЕЛ | то же |

Снимок матрицы — `kbd_scan_now()` в цикле (как в mario-dbl), режимы
SINCLAIR/KEMPSTON/PROTEK не портируются (пункты меню 2–4 оставить для
совместимости меню, но вести себя как KEYBOARD).

### 3.7 Шрифт и текст

Шрифт оригинала ($6300, 96 слотов по 8 байт, MSB-first) побитово совпадает
с форматом плоскости Вектора (MSB = левый пиксель), но в 96 слотах глифы
занимают только два участка: `$20–$3A` и `$40–$5A`; слоты `$3B–$3F` и
`$5B–$7F` заняты строками движка («BEN DAGLISH», «WRITTEN BY», «COSTA
PANAYI», «MUSIC BY») и графикой, а на месте `$28`/`$29` — не скобки, а UDG;
знак копирайта — код `@` (`$40`).

В порт взяты работающие глифы (пробел, `0–9`, `:`, `@` = ©, `A–Z`, 39 шт.,
312 Б) и подключены как шрифт **по умолчанию** через `-Ca-DFONT_EXTERNAL`
(`font_chars`/`font8x8` в `include/font.asm`, генерируется
`tools/gen_font.py` из `assets/font_6300.bin`), а не через `gfx_select_font()`:
так любая строка интерфейса сразу набирается шрифтом игры и не может
случайно уйти на латиницу дефолтного шрифта. Окна `$EE17` портируются
как C-строки с теми же координатами (структуры окон → массивы строк).

### 3.8 Звук: бипер оригинала → TapeOut (как на ZX Spectrum)

> **Решение обязательное.** Звук выводится **через TapeOut**, как на ZX Spectrum:
> 1-битный программный бипер, **не** ВИ53 и **не** AY. Это сохраняет оба движка
> оригинала один-в-один (порт `$FE` ↔ PC0 ПИА1), снимает пересчёт периодов в
> делители таймера и делает шум воспроизводимым точно, без аппроксимации.

Аппаратура вывода (по `docs/VECTOR_VERIFIED.md` §8.1 и `lib/README.md`):

| Что | ZX Spectrum | Вектор-06Ц |
|---|---|---|
| Линия бипера | порт `$FE`, бит 4 | ПИА #1, **порт `01h`, бит 0** («магн. out», Tape Out) |
| Запись уровня | `OUT ($FE),A` | `OUT (00h),A`: `A=01h` → SET PC0, `A=00h` → RESET PC0 (BSR-форма, D7=0) |

Оригинал озвучен бипером (порт `$FE`), звук портируется, а не пишется заново
(факты — §1.9; формат, адреса данных, извлечение и грабли — SOUND.MD;
эталоны для приёмки — `zx-disasm/games/hate/sound/*.wav`):

- **Мелодия заставки** `$8243` (2 голоса на SMC-ячейках `$82CA/$82CC/$82D0/
  $82D4` и `$832C/$832E/$8332/$8336`; данные: байткод партитуры `$8473`,
  таблицы переходов `$843D`/`$83FC`, потоки событий `$85A3` (A) и `$85B1` (B).
  Порт: алгоритм и данные переносятся как есть; у бипера один выход, поэтому
  оба голоса **сводятся программно в один бит** (чередование во времени, как
  в оригинальном цикле), а не разводятся в два канала.
  **Период — измеренная величина, а не формула:** по логу
  `sound/title_music.txt` полупериод на ZX ≈ `218·D + 830` T, где `D` — байт
  периода из SMC-ячейки; то же звучание на Векторе (3.0 МГц) требует
  `≈ (218·D + 830) × 3.5/3.0` T — потратить на задержку PC0, а не на ВИ53-делитель.
- **Эффекты заставки** (те же коды потока, что у мелодии): пауза
  `$836A/$8375` (`OUT $18` → задержка `DE=$012C` → `OUT $00`); «шум» `$8389`
  (150 пар байт из ROM `$0064`, маска `$18`) — на TapeOut это **тот же
  1-битный поток**, поэтому воспроизводится точно, без свип-аппроксимации
  (AY-вариант не требуется); тональные семейства событий 4/5/6 — обработчики
  `$83A6` (`$839A`), `$83B9` (`$83C6`), `$83D1` (`$8398`) — циклы переключения PC0.
- **Игровые SFX**: 5 слотов `$F2C0` (бит-флаги `$F2BF`, записи `$F2E2` по
  5 Б: `flag, B, C, D, E`; `flag=0` — тон `HL=(C<<8)|B` = `L`-период/`H`-длина,
  иначе — свип `HL=(B<<8)|C`, шаг `H`, `D` — внутренний счётчик, `E` — число
  шагов; слот 3 — единственный тональный, `HL=$0414`). Порт: собственный
  модуль `include/sfx_hate.c` со своим планировщиком PC0; общий тональный
  микшер `lib/snd/sfx.c`/`music.c` (ВИ53/AY) в звуковом тракте не участвует.
  Биты событий — как `EV_JUMP/EV_LAND` в mario-dbl; свип = шаг полупериода
  по кадрам. Короткие бипы `$F288` (выстрел `$8C05`, пауза `$0F3C`, меню,
  конец миссии `$C814`) — те же циклы PC0.
- **ВИ53 — только таймер, не источник тона**: канал 2 (`lib/timer`, `timer_*`)
  задаёт точное время для выдерживания полупериодов и служит кадровым
  синхросигналом; записи в каналы 0/1 как в тональные регистры не делаются.
- **Образец реализации Tape Out в проекте** — `lib/snd/drums.asm`, маршрут
  `drum_route_tape`: один `OUT 00h` на шаг, разделение «движок / маршрут /
  планировщик», гейт по кадрам. Бит-бэнг переносится по этой же схеме.
- **Стоимость в тактах (обязательный учёт):** бипер занимает процессор всё
  время звучания, кадр — 60000 T, поэтому поток PC0 выдаётся порциями:
  (а) заставка/меню — блита нет, под музыку доступен почти весь кадр;
  (б) миссия — бюджет звука ≤ 25 % кадра, порции в окнах после
  `gfx_dblbuf_present()`; (в) при перегрузе — шаг переключения ×2 (ниже
  разборчивость потока) с приоритетом SFX. Замер — Stage 10.
- **Грабли ПИА (проверять трассой, а не по документации):** запись в `00h` —
  это запись в управляющий регистр ВВ55; режимная форма (D7=1, например
  `0x88`) на Векторе сбрасывает скролл (порт A `03h`). BSR-форма (D7=0) по
  коду скролл не трогает, но это подтверждается `debug_get_io_trace` по
  портам `00h/02h/03h` на первом же включённом звуке; при сбросе — вернуть
  скролл (`0xFF` в обоих режимах, 256×256 и 512×256) до ближайшего VBlank.
  PC0 делит порт `01h` с клавиатурными битами СС/УС/РУС — писать через BSR,
  не затирая биты 3/5–7.
- **Приёмка — по эталонам, а не по формулам:** `sound/title_music.wav`
  (мелодия заставки) и `sound/sfx_preview.wav` (5 эффектов × 3 повтора).
  Оба движка — чистый «pulse-proportional synthesis», DSP не нужен; заготовка
  переноса (тон/свип псевдокодом) — SOUND.MD §6. Пересчёт тактов обязателен:
  Z80 3.5 МГц → КР580ВМ80А 3.0 МГц, при переносе счётчиков 1:1 звук станет
  ниже на ≈15 % — масштабировать все задержки/полупериоды на 3.5/3.0;
  сверка — на слух и по `debug_get_io_trace` (последовательность PC0).
- **Опциональный `hate_ay.rom` больше не нужен:** и тон, и шум воспроизводимы
  точно на TapeOut; AY — только как отдельный эксперимент, не путь приёмки.

## 4. Карта памяти порта

| Диапазон | Что |
|---|---|
| `0x0100–~0x4F00` | ROM: код (C + render.asm + lib-модули) + ассеты (шрифт 0.8К, шаблоны 0.5К, геометрия 6.9К, уровни/трасса ~1.5К, таблица столбцов 0.2К, окна/строки ~0.5К) ≈ 18–20 КБ |
| `~0x4F00–0x5FFF` | куча (`heap_alloc`, `heap_top = 0x6000` — не выше кольца): буферы объектов (аналог `$F800`, ~0.2К), списки вывода (~0.3К), w2-патчи, при необходимости — распакованная музыка |
| `0x6000–0x7FFF` | **кольцевой буфер: 32 × 256 Б** (см. §3.1) |
| `0x8000–0xFFFF` | видеопамять: буфер B (8000/A000) + буфер A (C000/E000) |

BSS (записи объектов 16×16 Б, `color_cell[32][16]`, записи столбцов, очереди,
переменные состояния ≈ 1.2–1.5 КБ) лежит сразу за кодом и входит в образ ROM
(как во всех проектах на lib). Образ ROM не должен перерасти `0x5FFF`, иначе
он врежется в кольцо — проверка в Makefile (`romconsist`/размер).

## 6. Этапы реализации

Каждый этап — отдельный заход, критерий приёмки обязателен до перехода дальше.
Промежуточные отчёты/заметки — в `reports/StageN.md` (по факту работ).

### Stage 1. Ассеты
`tools/extract_assets.py`: снять `font_6300.bin`, `bank_653A.bin`, паттерны
`$C400` (из снапшота), таблицу трассы `$6000–$62FF`, части уровня `$C8EA`,
данные лесенки `$D5B2` → `include/*.inc` + `assets/`.
**Приёмка:** байт-в-байт с дампами zx-disasm; `include/ladder.inc` построен из
`$D5B2` по §3.2.

### Stage 2. Каркас сборки
Makefile (по mario-dbl: startup/v06io/v06pal/kbdscan/clr/nextframe/plane/
dblbuf/mode/gfx/fade/pr/keyboard/heap + render.asm + main.c), `main.c` с
одиночным выводом на старте (заставка — без dblbuf, §3.5): модули
`gfx_dblbuf_init()`/`gfx_dblbuf_isr()`/`gfx_dblbuf_present()` подключены, но
включаются только при входе в миссию; чёрная палитра, fade-in пустого экрана.
**Приёмка:** `hate.rom` собирается и крутится в эмуляторе, пустой экран
гаснет/проявляется без артефактов.

### Stage 3. Шрифт, окна, титул, меню SELECT
Свой шрифт (`-Ca-DFONT_EXTERNAL`, §3.7 — сделано в Stage 1 с надписью
«PRESS ANY KEY WHEN READY»), порт оконных структур, титульный экран
H.A.T.E. **без dblbuf** (§3.5): статичная картинка выводится/распаковывается в
плоскости буфера A один раз и остаётся на экране; меню SELECT (пункты 1–6,
гейт SPACE, переход DEMO/START) рисуется поверх и перерисовывается по клавише
без свапа.
**Приёмка:** скриншот титула совпадает с эталоном
`roms/games/hate/assets/hate.png` (раскладка и 4-цветная палитра), текст меню
читается; на входе в миссию dblbuf включается без визуальных артефактов.

**Сделано (этап 2):** меню открывается по любой клавише после мелодии;
фон-рельеф собран из кольца (`tools/gen_terrain.py`: 32×24 клетки, 118
уникальных 8-байтных блоков, 2480 Б) и выведен в двойной буфер
(`include/render.asm`, сверка `assets/terrain_preview.png` — совпадение
байт в байт). Пункты меню поверх рельефа — следующий шаг.

### Stage 4. Кольцо и сборка страниц
Порт `$D51D` под кольцо 32×256 по §3.1 (сдвинутая копия `+$80`, 4 фазы ближней
клетки дороги, очередь `$CA43`).
**Приёмка:** собранные страницы побайтово = клетки банка шаблонов (как
`render/02_ring_page.png`), заворот `RES 5,D` работает.

### Stage 5. Блиттер ландшафта
Порт `$D2E3` (§3.2) + цветовая модель §3.3: полный переблит поля из кольца в
back-буфер по таблице столбцов, статичный тест-кадр.
**Приёмка:** кадр рельефа совпадает с реконструкцией
`render/04_reconstruction.png` (с точностью до палитры 4 цветов), FPS-замер
полного блита ≤ бюджета §9.

### Stage 6. Скролл и камера
Фазы 2px (половина страницы `$00/$80`), тик скролла (2px за N кадров),
поворот кольца (`$C32E`/`$C32F`), пересборка новых страниц на ходу.
**Приёмка:** плавное движение рельефа без tearing (dblbuf), скорость скролла
играбельна; замер — Stage-отчёт.

### Stage 7. Объекты
Порт записей `$C000`, проекции `$EFA5`, вывода `$D9D6/$DD44/$DD6C` (формулы
§3.1), цветовые байты `color_cell`, w2-патчи грязных зон. Тест: расставить
объекты кадра 1600.
**Приёмка:** объекты визуально соответствуют `render/20_crystal_small.png`…
`24_block_edge.png` (5 типов с кадра 1600), тени/перспектива верны.

### Stage 8. Игровая логика
Ввод (§3.6), движение/стрельба игрока, столкновения и клиренс (порт `LE3BF`
по таблице трассы), генераторы → плазменные ячейки → жизни/щит, урон,
смерть/респаун, конец уровня (mothership), счёт.
**Приёмка:** проходится полный цикл миссии «старт → генераторы → ячейки →
конец уровня», HUD-полосы и SCORE обновляются.

### Stage 9. Состояния игры
PAUSE (P), ABORT (A + подтверждение), GAME OVER, DEMO-автопилот (аттракт и
`u+g`), переходы между уровнями/техникой (танк → самолёт → ховеркрафт).
**Приёмка:** все переходы состояний работают из эмулятора, аттракт-демо
крутится бесконечно без зависаний.

### Stage 10. Звук (TapeOut, как на ZX Spectrum)
`include/sfx_hate.c`: тон `$F288`/`$F284` и свип `$F2A3` по 5 записям `$F2E2`
(резолвер `$F2C0`, биты `$F2BF`) — переключение PC0 по триггерам §1.9; затем
мелодия заставки `$8243` (2 голоса, программное сведение в один бит) и её
эффекты, включая точный шум `$8389` (§3.8). Выход — TapeOut (порт `01h`,
уровень через BSR-порт `00h`), ВИ53 — только таймер. Замер бюджета: доля кадра под
бит-бэнг в миссии ≤ 25 % (§3.8, §9).
**Приёмка:** эталоны — `zx-disasm/games/hate/sound/title_music.wav` и
`sound/sfx_preview.wav` (5 эффектов × 3 повтора): высота, длительность и
направление свипов совпадают на слух; мелодия заставки узнаваема; порт-трасса
PC0 (`debug_get_io_trace`) даёт полупериоды, совпадающие с `title_music.txt`
после масштаба 3.5/3.0; картинка и тайминги не страдают.

### Stage 11. Приёмка и полировка
Полный прогон: меню → миссия → смерть → game over → аттракт; замер FPS
(методика mario-dbl: счётчик кадров за окно VBlank); правки под бюджет §9;
README.MD, развёртывание `make deploy`.
**Приёмка:** все критерии §8 выполнены, ROM стабилен ≥ 10 минут прогона.

## 7. Кадровый контракт (по образцу mario-dbl)

```
frame_handler = isr;          // ТОЛЬКО gfx_dblbuf_isr() (палитра ПЕРВОЙ) + frame_count
for (;;) {
    v06_wait_frame();         // сон до VBlank (применит свап палитры)
    kbd_scan_now();           // снимок матрицы (переиспользуем VBlank)
    game_logic();             // фиксированный шаг, догон по frame_count (кламп)
    render_back();            // в back-буфер: скролл-тик? полный блит : патчи
                              // объектов + HUD-поверх
    gfx_dblbuf_present();     // свап на ближайшем VBlank
    sound_service();          // порция TapeOut (PC0): ticks/биты на текущий кадр
}
```

**Звук (TapeOut, §3.8) в ISR не генерируется:** бит-бэнг держит процессор и
чувствителен к джиттеру входа в прерывание. В `frame_handler` остаётся только
кадровый счётчик; поток PC0 выдаёт `sound_service()` из главного цикла — после
`present()`, бюджетом ≤ 25 % кадра в миссии и почти всем кадром на заставке.

Скролл-тик — раз в N кадров (N подбирается по бюджету, старт N=2, т.е. ~25 Гц
обновление поля); между тиками экран статичен → кадры можно не переблитовывать,
но свап палитры всё равно выполняется (синхронизация), как skip-оптимизация
mario-dbl.

**Заставка/меню (без dblbuf, §3.5):** контракт вырождается в
`v06_wait_frame(); kbd_scan_now(); обработка выбора;` — свап не выполняется,
fade-in делается палитрой один раз на входе в экран.

## 8. Критерии приёмки (общие)

1. Полный игровой цикл: титул → SELECT → миссия (≥ 2 уровней, ≥ 2 техник) →
   смерть → GAME OVER → аттракт-DEMO.
2. Без tearing; движение рельефа и объектов плавное (dblbuf-свап каждый VBlank
   в миссии; заставка статична и выводится без dblbuf).
3. Играбельность: 25–50 кадров/с по FPS-замеру; скролл-тик не чаще 1 раза в 2
   кадра при полном блите ≤ 60000 тактов.
4. Визуальное соответствие референсам zx-disasm (`render/*.png`) в 4-цветной
   палитре §3.3; титульный экран — эталону `assets/hate.png`.
5. Управление по §3.6; звук выведен через **TapeOut (PC0 ПИА1)** по §3.8
   (сверка с `sound/*.wav`), ВИ53 в звуковом тракте не звучит; секреты
   оригинала (p/A, u+g) работают.
6. ROM собирается `make`, размер образа < 0x5FFF, куча/кольцо не пересекаются
   (проверка `romconsist`-методом или в Makefile).

## 9. Бюджет производительности (оценка)

- Тактов на кадр: 60000 (3 МГц / 50 Гц).
- Полный блит поля (скролл-тик): ~350 клеток × 8 Б × (чтение 7т + запись w1 7т
  + зачистка w2 7т + инкременты ~10т) ≈ 87 Ктактов — **выше бюджета кадра**;
  поэтому: (а) скролл-тик раз в 2–4 кадра (поле статично между тиками, блит
  только объектных полос — как в оригинале, где блиттер тоже горячий только в
  части кадров); (б) зачистка w2 только в грязных зонах (быстрый путь §3.3)
  → типичный тик ≈ 60–70 Ктактов, укладывается в 2 VBlank при сохранении
  50 Гц свапа; (в) при перегрузе — перенос остатка блита на следующий VBlank
  (поле дорисовывается в back-буфере, front не дёргается — tearing нет).
- Замеры этапов 5–6 обязательны: фактическое число клеток/кадр и такты — в
  `reports/StageN.md`; по факту принимается N скролл-тика и (а)/(б)/(в).
- Звук (TapeOut, §3.8) тратит такты кадра напрямую: в миссии бюджет
  ≤ 15 Ктактов/кадр (25 %), порции выдаются после `gfx_dblbuf_present()`;
  на заставке/меню блита нет — музыке доступен почти весь кадр.

## 10. Риски и их закрытие

| Риск | Митигация |
|---|---|
| Производительность блиттера с 2 плоскостями | §9 (а–в); при крайней необходимости — 25 Гц полный блит; измерять на Stage 5 |
| Кольцо 32 страницы — формулы пересчитаны неверно | Stage 4 принимается только с побайтовой сверкой страниц; все формулы §3.1 в одном месте render.asm с комментарием `; was $…: reason` |
| Банк геометрии 6863 Б не до конца распарсан | переносится verbatim; проверка на тест-кадрах Stage 7; при расхождении — трассировка конкретной формы в zx-disasm (snapshot-сверка) |
| Шаг ряда патча объекта завязан на шаг кольца | при переходе `+$1FC → +$FC` проверить все три класса (4×21/3×17/2×13) тест-кадрами |
| Незавершённый разбор финала миссии/перекрутки кольца | реализуется по здравому смыслу (зачёт при уничтожении генераторов), сверяется с игрой оригинала в эмуляторе ZX |
| Образ ROM перерастёт 0x5FFF | лимит в Makefile; резерв — ZX0-сжатие уровней/форм с распаковкой в кучу |
| Шум бипера (`$8389`) воспроизводится точно на TapeOut | аппроксимация не нужна (1-битный поток, §3.8); сверка по `sound/sfx_preview.wav` и `title_music.wav` |
| Бит-бэнг TapeOut забирает такты кадра | порционный вывод PC0 после `present()`, ≤ 25 % кадра в миссии, приоритет SFX (§3.8, §9); замер на Stage 10 |
| BSR-запись в `00h` задевает скролл/бордюр ПИА | первый же включённый звук проверяется `debug_get_io_trace` по портам `00h/02h/03h`; при сбросе — восстановление скролла (§3.8) |
| Заставка без dblbuf даёт tearing при перерисовке меню | титул статичен; меню перерисовывается только в паузах ввода (VBlank-синхронно), сверка с `assets/hate.png` на Stage 3 |
