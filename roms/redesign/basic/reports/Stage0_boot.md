# Stage 0. Boot-факты: как устроен самораспаковывающийся `bas2997.rom`

Снято шагом в эмуляторе через MCP `v06c-mcp` (единственный источник фактов;
офлайн-декод `utils/zx0.py` — справочно). Все листинги ниже подтверждены
`debug_disassemble_range`/`debug_get_state`, а не чтением байтов «на глаз».

| объект | размер | SHA256 | роль |
|---|---|---|---|
| `src/bas2997.rom` | 13247 | `921c631925936c2703ab5533857df17ef6c0886ee5c18572019676738bebd581` | упакованный исходник: стаб + поток |
| `src/basic.r0m` | 17152 | `6c632f67718a31f0bc2c7cc4142d77bc9454cdc2f76aa6813d94e675530253d9` | распакованный образ интерпретатора — **объект анализа** |

## 1. Адрес загрузки и способ съёма

* `.rom` грузится загрузчиком на **`0x0100`** (соглашение; `.r0m` → `0x0000`).
* После `debug_load_rom` PC=`0x0000`, а `0x0000..0x00FF` заполнены `NOP`
  (`00`): CPU «проскальзывает» по page zero и входит в стаб на `0x0100`.
  Поэтому точка останова на `0x0000/0x0003` ловит **boot**, а не конец
  распаковки — на это провериться нельзя.
* Съём распакованного образа — `tools/dump_interp.py`: BP на **`0x19CC`**
  (первый вход = сразу после распаковки, `LXI SP,7FFF; JMP 19CC` уже отработал,
  инициализация ещё не выполнила ни одной инструкции ⇒ RAM pristine),
  выгрузка `0x0000..0x42FF` → `src/basic.r0m`.
* Съём **детерминирован**: повторная выгрузка побайтово совпала с эталоном
  (`cmp` — 0 расхождений).

## 2. Unpacker-стаб: `0x0100..0x0125` (38 байт, 23 инструкции, 8080)

```
0x0100  DI                 ; прерывания выключены на время распаковки
0x0101  XRA A              ; A = 0
0x0102  OUT 10             ; отключить квазидиск
0x0104  LXI H,4300         ; <- база области программы
        ; --- очистка 0x4300..0x7FFF ---
0x0107  MOV E,A            ; E = 0 (значение очистки)
0x0108  MOV M,E            ;   (HL) = 0
0x0109  INX H
0x010A  ORA H              ;   флаг Z когда H = 00 (переход через 0x7FFF→0x8000)
0x010B  JP 0108            ;   пока H < 0x80 — чистить
0x010E  SPHL               ; SP = HL = 0x8000  (стек растёт вниз от 0x8000)
        ; --- копирование потока в стагинг ---
0x010F  LXI D,0126         ; DE = начало сжатого потока (сразу за стабом)
0x0112  LXI B,3399         ; BC = длина потока = 13209 байт
0x0115  LDAX D             ; --- пересылка потока: (HL)++ = (DE)++, BC-- ---
0x0116  INX D              ; HL здесь = 0x8000 (после цикла очистки),
0x0117  MOV M,A            ; т.е. поток кладётся в 0x8000..0xB398
0x0118  INX H
0x0119  DCX B
0x011A  MOV A,B
0x011B  ORA C
0x011C  JNZ 0115
0x011F  LXI D,805C         ; DE = сжатые данные внутри копии (после декодера)
0x0122  PUSH B             ; B = 0 — аргумент/маркер для декодера
0x0123  JMP 8000           ; в распаковщик второго этапа
```

Проверено на BP `0x0123`: `HL=0xB399` (`0x8000+0x3399` — конец копии),
`DE=0x805C`, `BC=0`, `SP=0x7FFE`.

**Граница «стаб ↔ поток» = `0x0126`** (`debug_disassemble_range` на 39 байт
возвращает `incomplete_instruction: true` — 39-й байт уже не код). Поток —
`0x0126..0x34BE` (весь хвост файла, 13209 байт).

## 3. Распаковщик второго этапа: `0x8000..0x805B` (92 байта)

Копия потока в `0x8000` — это **сам декодер (92 байта) + сжатые данные с
`0x805C`** (отсюда `LXI D,805C`). Разобран полностью:

| адрес | роль |
|---|---|
| `0x8000` | `LXI H,FFFF; PUSH H; INX H` ⇒ **HL = `0x0000`** — база вывода |
| `0x8007`/`0x8010`/`0x8022` | `CALL 803D` — **чтение одного бита** потока в carry (`INR L` — счётчик оставшихся битов текущего байта, `ADD A` — сдвиг, при переполнении — `LDAX D; INX D; RAL` — следующий байт) |
| `0x8046` | `DAD H; ADD A; JNC 803E` — расширенный побитовый сдвиг (чтение multi-bit полей) |
| `0x804E` | `LDAX D; STAX B; INX D; INX B; DCX H; …; JNZ 804F` — **копирование блока** (literal-run) из потока по адресу в BC |
| `0x8029` | `RZ` — выход по достижении признака конца |
| `0x805B` | `RET` — последний байт декодера (рядом начинается поток) |

> **Важно для Stage 9/10.** Change log п.17 заявляет «ZX0 вместо MegaLZ», но
> фактический декодер — **самодельный LZ с явным битовым чтением и
> копированием runs** (структура, близкая к MegaLZ-семейству). У ZX0 другой
> формат (переменные коды с эскейп-байтом `0x00`, без такого bit-reader).
> Следствие: **repack через `utils/zx0.py -c` даст поток, который этот
> декодер не прочитает.** Либо пересобирать вместе с 92-байтным декодером,
> либо менять и декодер, и стаб. Зафиксировать при выборе ветви Stage 9.

## 4. Размещение интерпретатора

* Вывод декодера — **низкая RAM, `0x0000..0x42FF`** (17152 байта). НЕ `0x80xx`:
  `0x8000` использован только как стагинг (и как VRAM — позже затирается
  выводом экрана).
* Reset-вектор образа, `0x0000`:
  `31 FF 7F` `LXI SP,7FFF` · `C3 CC 19` `JMP 19CC`.
* **Entry интерпретатора = `0x19CC`** (инициализация). Проверено на BP:
  `SP=0x7FFF`, `DE=0xB399`, `BC=0x4300`, `HL=0x0100`, первая инструкция
  `MVI A,81`.
* Page zero (`0x0000..0x00FF`) — вектора и служебные ячейки: `RST`-векторы на
  `0x0008`/`0x0010`/…, обработчик прерывания с `0x0038` (`… C3 7F 2C` → `JMP
  2C7F`). Из `0x0000` достижим весь код — поэтому seed_rdb запускается от
  `0x0000`, а не от `0x19CC`.

## 5. Очистка области программы

Двухуровневая:

1. **Стаб** циклом `0x0107..0x010B` выставляет нули в `0x4300..0x7FFF`
   (выход по `ORA H`, когда H переполняется в `0x80`). Это change log п.52
   («инициализатор распаковщика чистит память программы»).
2. **Сам интерпретатор** при инициализации (`0x19CC`) настраивает свои
   указатели программы, начиная с `0x4300` (spec v2.5: `0x4300` — загруженная
   программа).

## 6. Данные в образе

* **Таблица масок точек** — `0x4200..0x42FF`, ровно 256 байт: 32 повтора
  `80 40 20 10 08 04 02 01` (change log п.67 — «gard» PEEK/POKE). Это последний
  заполненный блок образа: последний ненулевой байт — `0x42FF`.
* **Строка автозапуска** `COLOR15,0,1:CLS` + `$0D` — в **`0x4012..0x4021`**
  (перед ней `0x4010: DB 2B`). Ранняя «строка» `BtR15,0,1:CLS` из packed-файла
  была ложным чтением сжатого потока.
  Spec v2.5 ждёт встроенную программу на `0x3C60` — факт против спеки,
  проверять на Stage 5/8.
* После boot REPL печатает `=>` (экранный снапшот подтверждён), прерывания
  включены (`iff=true`), CPU работает в `0x2Bxx..0x2Cxx` (цикл REPL).

## 8. Ограничения и что исправлено по ходу

1. **Экспортёр на момент прогона не был собран:** `export_asm` упал с
   `FileNotFoundError: …/vector-debug/build/v06c-asm-export`, и потому
   `toolchain_lint`, `symbolic_operand_lint`, `syntax_check`,
   `roundtrip_verify` — BLOCKED. Цель CMake `v06c-asm-export` в проекте есть
   (`export/asm_exporter_main.cpp`), бинарь собран перед Stage 1 — эти стадии
   догнаны прогоном `run_pipeline.sh basic --from export_asm` (см. Stage 1).
2. **Баг фреймворка (исправлен):** разрешение имени RDB в
   `pipeline.py` (`re.sub(r"\.(rom|ROM|bin)$", ".rdb", …)`) не знало про
   `.r0m` ⇒ при отсутствующем `basic.rdb` `ctx.rdb` указывал на сам ROM, и
   `coverage` падал с `UnicodeDecodeError` на байте `0xFF`. Добавлено `r0m`
   в список расширений (общая правка, ROM-специфики в `pipeline.py` нет).
3. **Имя RDB.** `debug_save_rdb` не принимает путь — RDB привязан к базису
   ROM. Переход на `basic.r0m` дал ровно `basic.rdb`, как требовал ТЗ
   (раньше получался `bas2997.rdb`).
4. **Объекты packed-части в RDB не заводятся** (`func_unpacker_entry`,
   `data_packed_stream`, `var_unpacked_base`, `lbl_interp_entry`): RDB теперь
   описывает `basic.r0m`, где стаба и потока нет. Их адреса зафиксированы
   здесь (п.2, п.3) — это и есть «якорь» для Stage 9/10 при пересборке
   `bas2997.rom`.
5. `table_shape` и `measure_sizes` почти не дают пользы на интерпретаторе
   (формы таблиц и размеры — семантика, Stage 2/5/8).

## 9. Домен: 8080 (решён по факту Stage 1)

ТЗ требовал решить вопрос домена сборки на Stage 0. Решение — **8080**,
доказательств три:

1. **Таблица дизассемблера — 8080, не Z80:** `vector-debug/src/disassembler.cpp:43—60`
   — строки опкодов с 8080-именами (`SHLD` `22h`, `LHLD` `2Ah`, `DAD`,
   `INX`/`DCX`), а неприсвоенные опкоды ряда `x8h` (`08h/18h/28h/38h`) стоят в
   позиции `[+0]` каждой строки как `"NOP", F_IMP` — однобайтовые no-op по
   спецификации Intel 8080 (в Z80 на этих местах — двухбайтовые
   `JR z/nz/nc/c, e`).
2. **Эмулятор исполняет их как 8080.** Микро-зонд через MCP: в RAM на `0x7000`
   записано `28 05 …`, `PC=0x7000`, шаг при `Z=0` и при `Z=1` — в обоих случаях
   `PC=0x7001` (байт+1), т.е. `NOP`, а не `JR Z` (было бы `0x7007`). То же на
   реальном байте ROM `0x0AA7` (`28 CD`): `PC=0x0AA8` при обоих состояниях
   флага нуля. В образе таких мест ровно три: `0x0AA7`, `0x0AE9`, `0x1CB5`, и
   всюду они стоят сразу после `RST 08`.
3. **Аппаратной Z80-регистрации нет:** `debug_get_registers` отдаёт только
   `PC SP A F B C D E H L AF BC DE HL` — без `AF'`/`BC'`/`DE'`/`HL'`, `IX`, `IY`,
   `I`, `R` (ср. docs/VECTOR_CPU_COMMANDS.md: `RST 5` = `0028h`).

Следствие для Stage 9/10: проверки сборки вести в обычном режиме z80asm,
**без** `-m=8080_strict` — мнемоники экспорта (`rst`, `dad`, `shld`, `inx`) и
так 8080-ные, а strict-режим спотыкается на тех же неприсвоенных опкодах.

### 9.1 Потеря round-trip на этих байтах (дефект экспортёра — исправлен)

Контракт Stage 1 — `0 расхождений`. Первоначальный вердикт: **3 байта**
(`28h` → `00h`) на тех же `0x0AA7 / 0x0AE9 / 0x1CB5`. Первопричина — не
классификация, а экспортёр:

* дизассемблер корректно возвращает `mnemonic="NOP", size=1` для `28h`;
* `vector-debug/export/asm_exporter.cpp:946` печатает `toLower(instr.mnemonic)`
  без сверки с исходным байтом, поэтому `NOP` собирается как `00h`;
* попытка починить своей стороной (завести `data_0aa7`/`data_0ae9`/`data_1cb5`,
  тип `Data`, `size=1`, через `debug_add_rdb_object` + `debug_save_rdb`) дала
  метку в выдаче (`data_0aa7:` напечатана), но сам байт экспортёр по-прежнему
  выводит мнемоникой — вердикт `roundtrip_verify` не изменился. Объекты
  оставлены как маркеры аномалии: на них теперь ссылается поле `rdb_object`
  в diff-отчёте.

Минимальный почин на стороне экспортёра: если `mnemonic == "NOP"`, а байт
образа по этому адресу не `00h`, печатать `defb <byte>` (то же для всего
семейства `x8h`). Потеря универсальна: она возникнет на любом ROM с
неприсвоенными 8080-опкодами, а не только на этом.

**Разрешено (Stage 1).** Баг-репорт ушёл в
`vector-debug/docs/Known_Issue_ASM_Exporter_NOP_Opcodes.md`, экспортёр
исправлен и пересобран. Проверка после патча:

- `roundtrip_verify` → `OK`, вердикт `byte-for-byte identical`,
  `bytes_differing = 0` из `compared_bytes = 17152`, `size_match = true`;
- в выдаче на этих местах стоит
  `; unassigned i8080 opcode, executes as NOP -- emitted as byte` + `defb 28h`;
- контрольная проверка: три объекта `data_0aa7`/`data_0ae9`/`data_1cb5`
  **сняты** из RDB (`debug_remove_rdb_object` + `debug_save_rdb`, объектов
  снова 434), и `defb 28h` печатается по-прежнему — значит почин сверху
  самодостаточен, а ложная классификация «Data» для исполняемого байта в RDB
  не нужна. Итоговый прогон Stage 1: `stages 6, успешных 6, отказов 0`.
