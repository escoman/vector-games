# Stage 8 — Данные BASIC → `keywords.inc` / `messages.inc` / `demo.inc`

ТЗ §8: выгрузить три ROM-блока данных (кроме знакогенератора Stage 7) и
закрепить их в RDB. Итог: **+2 объекта** (`data_error_messages` @ `0x2465`,
`str_autoload` @ `0x4012`), **обогащён** `data_keyword_table` @ `0x256E`,
созданы `asm/keywords.inc` (101 слово), `asm/messages.inc` (23 строки),
`asm/demo.inc` (автозапуск). RDB 552→**554**, `dirty: False`. Round-trip
**byte-for-byte identical** (17152 байт, 6/6 стадий SUCCESS).

Попутно исправлена ошибка Stage 7: коды **104 и 118 были перепутаны**
(104=Х, 118=Ж). См. §5.

---

## 0. Метод: статика + decoding + живой рендер

1. **Статика.** Адреса блоков взяты из потребителей: токенизатор
   `func_tok_tokenize` (`LXI D,256D`) — таблица слов; `func_error_raise`
   (`0x0083`, `LXI H,2465`) — пул сообщений; остров данных сразу за
   `JMP @0x400F` — автозапуск.
2. **Декодирование.** И таблица слов, и пул сообщений — плотные блоки без
   разделителей: граница элемента задаётся **bit7 последнего байта**. Один и тот
   же приём, разная семантика (слово vs строка).
3. **Живой рендер (главное подтверждение).** ROM загружен в эмулятор, на READY
   набрано `NEXT` → экран показал `NEXT БЕЗ FOR ОШИБКА`. Это доказало, что
   сообщения набраны **настоящей кириллицей** через знакогенератор Stage 7, а не
   транслитом.
4. **Пиксельная сверка.** `tools/render_messages_preview.py` печатает все 23
   строки растром `data_glyph_block` — независимо проверяет и порядок строк, и
   карту кодов (именно так всплыл перенос 104/118).

## 1. Таблица ключевых слов — `data_keyword_table` (`0x256E..0x26D6`)

* 361 байт, **101 слово**; байт = символ, bit7 последнего байта = конец слова.
* Токен = `0x80 + номер слова` (`func_tok_tokenize`: `MOV A,B / ORI 80`).
* Потребители: токенизатор (`LXI D,256D`) и детокенизация `LIST`/`LLIST`.
* Объект был в RDB с Stage 2 (тип `table`); здесь обогащён свойствами
  `role/encoding/token_base/listing` и комментарием.
* Полная построчная выгрузка — `asm/keywords.inc`; карта токен↔слово↔обработчик
  — `tools/tokens.md`.

## 2. Пул сообщений об ошибках — `data_error_messages` (`0x2465..0x256D`)

* 265 байт, **23 строки**; плотный пул, terminator = bit7 последнего байта.
* **КОДИРОВКА (находка):** коды `0x60..0x7E` в этом ROM — КИРИЛЛИЦА (Stage 7),
  поэтому сообщения набраны русскими буквами: `62 65 7A` = «БЕЗ»,
  `6F 7B 69 62 6B 61` = «ОШИБКА». Ключевые слова внутри (NEXT/FOR/DATA/GOSUB/
  DEF) — латиницей старшего регистра (`0x41..0x5A`).
* **Вывод:** `func_error_raise` (`0x0083`): `LXI H,2465` (база) и цикл
  `MOV A,M / INX H / ORA A / JP` шагает по строкам, отсчитывая индекс от кода
  ошибки (`MOV A,E / RAR / DCR E`). Коды приходят по путям
  `MVI E,nn / JMP 0x0083`, все чётные: {8,10,12,14,16,22,24,26,30}, модель
  `индекс = (код>>1) − 2`. Точный регистр-источник кода (через CALL 01C5/07B2)
  уточняется при портировании; авторитетно для Stage 8: ПОРЯДОК строк и привязка
  `NEXT → строка #0` подтверждены живьём.

## 3. Строка автозапуска — `str_autoload` (`0x4012..0x4021`)

* 16 байт: `COLOR15,0,1:CLS` + `0D` (CR).
* Природа — **data-остров в кодовой области** (сразу за `JMP @0x400F`), а не код.
* Исполняется при boot до REPL: задаёт палитру и очищает экран.
* Новый объект типа `string` (префикс `str_` ⇔ тип `string` по `naming.py`).

## 5. Попутная коррекция Stage 7: перенос кодов 104/118

При рендере пула настоящим шрифтом (§0.4) строка #3 читалась как «МАЛО
ДАННЫ**Ж**» (#15 «СЛО**В**НО») — бессмыслица. Разбор:

* эталонные слова требуют **Х** в «ДАННЫ**Х**» (код `h=0x68`=104) и **Ж** в
  «СЛО**Ж**НО» (код `v=0x76`=118);
* растр глифа 104 = `C6 28 10 28 C6` — простой крест = **Х**;
* растр глифа 118 = `C6 28 FE 28 C6` — крест с перемычкой = **Ж**.

Значит Stage 7 перепутал подписи. Исправлено: `CYRILLIC` в
`tools/stage7_glyphs.py` (104→«Х», 118→«Ж»), перегенерированы `glyphs.inc`,
`glyphs_chart.png`, карта §2 Stage7.md. Байты образа не тронуты (round-trip
прежний). Это **второй** случай, когда визуальная сверка ловит промах статики.
