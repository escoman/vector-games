# SPR_FORMAT.MD — формат данных спрайтов beam-sprites и asm-ядро вывода

Спецификация нового «готового к выводу» формата спрайтов для подсистемы
beam-sprites ([`../lib/gfx/spr.c`](../lib/gfx/spr.c) +
[`../lib/gfx/spr.asm`](../lib/gfx/spr.asm)) и ассемблерного ядра блита.
Документ — план, **код пока не меняется**: сперва формат утверждается, потом
пишутся ядро и правки планировщика.

Модель вывода — **sprite-major** (весь спрайт одним блитом, запущенным когда
луч прошёл его нижний край). Решения по охвату: формат спрайта + устранение
O(SPR_MAX) скана инстансов + ускорение перекраски фона (BG-тайлмап).

---

## 1. Почему меняем формат (данные замера)

Baseline снят ROM-бенчмарком [`../roms/tests/spr-speed`](../roms/tests/spr-speed)
на живом растре (КР580ВИ53, 96 тиков/строку; методика Э0 из `demo-spr`).
`v06_emu` не считает VRAM-wait-states — только реальный растр.

| Операция (юнит) | тиков/юнит | строк/юнит |
|---|---|---|
| `spr_glyph_at` raw, 4 пл. (8×8 глиф) | 989 | **10.3** |
| `spr_glyph_at` compact-тег (1 пл. + 3 нуля) | 887 | **9.2** |
| `spr_glyph_at_or` raw (RMW-композит) | 1563 | **16.3** |
| 16×16 = 4× отдельных `spr_glyph_at` (на глиф) | 947 | **9.9** |
| путь клетки фона: lookup + адрес + blit (на клетку) | 1501 | **15.6** |
| `spr_update` — скан O(SPR_MAX) (на кадр) | 232 | **2.4** |

Выводы, на которых построен формат:

1. **Setup платится полный N раз.** 4 вызова на глифы 16×16 (9.9 строк/глиф)
   ≈ одиночный вызов (10.3) — амортизации нет. Каждый глиф платит `CALL/RET` +
   разбор стековых аргументов + снятие compact-тега + счётчик плоскостей +
   арифметику stride ([`spr.asm` L33-122](../lib/gfx/spr.asm)). Новый формат:
   **один setup на спрайт**, длинный прогон на столбец.
2. **Compact-тег почти бесполезен** (9.2 vs 10.3): он всё равно **пишет все 32
   байта**, 3 плоскости нулями (`xor a`, [L60-78](../lib/gfx/spr.asm)). Бит
   *наличия* плоскости должен **пропускать** пустую плоскость целиком, а не
   затирать нулём.
3. **Фон — главный расход.** Клетка фона = 15.6 строк, из них ~5 строк — чистая
   арифметика адреса (софтмал `*32`, `ring_dst`). Полноэкранная перекраска
   (1024 глифа) ≈ десятки кадров. BG-тайлы — сплошные прямоугольники → им нужен
   путь **без** по-столбцовой таблицы.
4. **Скан инстансов — не бутылочное горлышко** (2.4 строки/кадр). Его снимает
   sprite-major (инстанс рисуется целиком своим блитом, без поиска «кто
   покрывает клетку» в [`paint_cell` L189-252](../lib/gfx/spr.c)).

## 2. Геометрическая опора: вертикальный прогон непрерывен

Из адресации кольца ([`spr.c` L15-19](../lib/gfx/spr.c),
[`cell_dst` L155-159](../lib/gfx/spr.c)):

```
dst(gcol, grow) = 0x8000 + (gcol << 8) + (248 - 8 * (grow & 31))
```

* один **8px-столбец** (`gcol`) = один 256-байтовый блок VRAM = 32 тайл-ряда;
* глиф = 8 подряд идущих байт, следующий `grow+1` — соседние 8 байт
  (`dst-8`), т.е. **N тайл-рядов одного столбца и одной плоскости лежат в N·8
  подряд идущих байтах**. Экранная строка `Y` ↔ смещение `255 − Y` (адрес
  убывает вниз по экрану) — подробнее в «Порядок байтов прогона» ниже;
* шаг **в соседний столбец** = `+0x100`; шаг **в следующую плоскость** = `+0x2000`
  (П3→П2→П1→П0 при базах 0x8000/0xA000/0xC000/0xE000);
* **шов кольца**: `grow & 31` оборачивается 31→0 каждые 32 ряда (= высота окна
  256px) → адрес прыгает с `+0` обратно на `+248`, непрерывность рвётся.

Отсюда — «данные максимально готовы к выводу»: столбец каждой задействованной
плоскости выливается **одним линейным прогоном**, между столбцами `+0x100`,
между плоскостями `+0x2000`.

### Порядок байтов прогона (важно!)

Экранная строка `Y` (0 = верх) ↔ смещение в блоке столбца `255 − Y`: адрес
**убывает вниз по экрану** (Y-inversion — известный питфолл проекта). Значит
прогон сверху вниз = обход по **убывающему** адресу (`dec HL`), начиная со
смещения `255 − Y_верха`. Никакой перестановки 8-байтовых блоков не нужно:
генератор эмитит строки тайл-ряда в экранном порядке сверху вниз, ядро льёт их
`dec`-прогоном (идиома `dcx h` из `../roms/demos/mario-dbl/include/render.asm`).

Единица длины — **тайл-ряд 8px** (8 байт), поэтому каждый прогон кратен 8 и
всегда выравнивается на границы глифов (см. §3, решение по единицам высоты).

Направление (`dec`, а не `inc`) и привязка `dst` к ВЕРХНЕЙ строке фиксируются
round-trip тестом: сгенерировать тайл → заблитить → снять VRAM-дамп → сверить с
исходником (иначе тихая перевёрнутость). Текущий `_spr_glyph_at` привязан к
НИЗУ глифа и идёт `inc hl` — новое ядро переходит на «верх + `dec`», это надо
учесть в `cell_dst`/planner.

## 3. Формат дескриптора

Заголовок (3 байта + опциональная таблица) описывает весь спрайт:

```
offset  поле     назначение
[0]     FLAGS    битовые флаги (ниже)
[1]     COLS     число 8px-столбцов (=ширина/8)
[2]     DEPTH    dense: высота в ТАЙЛ-РЯДАХ (1..32; 1 тайл-ряд = 8px = 8 байт)
               sparse: игнорируется, высота = max(TOP_i + LEN_i) из таблицы
[3..]   TABLE    только если FLAGS.sparse: COLS пар (TOP, LEN) в тайл-рядах
               TOP — отступ сверху (пустых тайл-рядов), LEN — длина прогона
               в тайл-рядах (см. seam-кап §4.5)
[..]    DATA     блоки данных: для каждой ПРИСУТСТВУЮЩЕЙ плоскости
               (по порядку П3,П2,П1,П0) подряд по COLS прогонов;
               прогон = LEN_i·8 байт (dense: DEPTH·8 байт).
               Если FLAGS.mask — блок П0 (маска) обязателен и идёт отдельно
               в конце (см. §5 OR).
```

### 3.1 FLAGS — байт [0]

```
bit0..3  наличие данных плоскостей:  bit0=П3  bit1=П2  bit2=П1  bit3=П0
bit4     наличие маски (OR-композит; П0 трактуется как маска зачистки)
bit5     SPARSE: есть per-column таблица (TOP,LEN); 0 = dense (единый DEPTH)
bit6     OR-composite: писать через композицию res=(dst AND msk) OR col;
       0 = плоская запись (overwrite)
bit7     резерв (напр. режим 16px-столбца / широкого тайла)
```

Это ровно «5 битов наличия (маска + 4 плоскости)» из исходной идеи +
**два бита режима вывода**, которые дают нужную вилку плотный/разреженный:

* **dense** (bit5=0): один `DEPTH` на все столбцы → путь BG-тайлмапа и
  симметричных спрайтов. Без таблицы, без extra-арифметики на столбец.
* **sparse** (bit5=1): таблица `(TOP,LEN)` на каждый столбец → неровные
  силуэты («хвост» Марио: `XX/XX/XX/XXX/XXX`).

**Почему флаг, а не «универсально таблица на всех»:** baseline §1.3 показывает,
что горячий цикл — перекраска фона, и навязывать ей по-столбцовую таблицу =
чистый оверхед. Спрайтам таблица почти бесплатна (несколько десятков тиков на
столбец против blit 989), а экономия на пропуске пустых строк реальна. Две
ветки в ядре — осознанная плата (см. риск §7).

### 3.2 Примеры

Сплошной BG-тайл 8×8, 1 плоскость (вес-8):
```
FLAGS = 0b0000_0001 (пл.П3 есть; dense)  COLS=1  DEPTH=1   DATA: 8 байт
```
Hero 16×16, 3 цвет. плоскости + маска, OR-композит:
```
FLAGS = 0b0100_1111 (П3,П2,П1 есть + бит6 OR)  COLS=2  DEPTH=2 (=16px)
DATA: 2×2 прогона по 16 байт  (+ отдельный П0-маска, см. §5)
```
Mарио с «хвостом» (sparse), поле 3 столбца × 4 тайл-ряда:
```
FLAGS = 0b0010_0001 (sparse)  COLS=3  TABLE (тайл-ряды): (0,4)(0,4)(1,3)
DATA: прогоны 4·8, 4·8, 3·8 байт (3-й столбец короче и со смещением вниз)
```

## 4. Ядро `spr_blit_sprite` (8080, псевдокод)

Конвенция z88dk classic как у текущих примитивов
([`spr.asm` L8-12](../lib/gfx/spr.asm)): аргументы на стеке, caller-cleanup,
`ret` без трогания SP. Вход: `dst` (база левого-верхнего столбца плоскости П3),
`desc` (указатель на дескриптор).

```
spr_blit_sprite(dst, desc):
  HL = dst                          ; адрес ВЕРХНЕЙ строки левого столбца, П3
  DE = desc
  FLAGS = (DE); COLS = (DE+1); DEPTH = (DE+2)   ; DEPTH в тайл-рядах
  DATA = DE + 3 (+ COLS*2 если sparse)
  ; --- внешний цикл по плоскостям наличия ---
  for plane in {П3,П2,П1,П0}:       ; базовый шаг +0x2000
    if !(FLAGS & plane_bit): DATA += plane_bytes; continue   ; ПРОПУСК пл.
    src      = DATA                 ; курсор данных плоскости
    col_base = HL
    for c in 0..COLS-1:
      (TOP,LEN) = sparse ? TABLE[c] : (0, DEPTH)   ; в тайл-рядах
      run(col_base - TOP*8, src, LEN*8)  ; адрес вниз => минус TOP*8 (§2)
      src      += LEN*8             ; следующий прогон
      col_base += 0x100             ; соседний столбец
    DATA = src                      ; конец данных плоскости
    HL  += 0x2000                   ; следующая плоскость
  ; plane_bytes = (Σ LEN_i)·8 — размер данных одной плоскости (для пропуска)
```

`run(addr,src,len)` — плотный внутренний цикл одного прогона (flat):

```
run:                             ; HL=VRAM (низ прогона), DE=src, B=len
  loop: ld a,(DE); inc DE
        ld (HL),a; dec HL       ; адрес убывает вниз по экрану (§2)
        dec B; jnz loop
```

Композиционная версия `run_or` (бит6): тот же обход, но побайтово
`ldr=(HL); res = ldr ^ ((ldr ^ col) & msk)` — идиома из
[`mario-dbl/render.asm` dr_p0 L335-351](../roms/demos/mario-dbl/include/render.asm)
и текущего [`spr.asm` sgo_blit8](../lib/gfx/spr.asm).

### 4.1 Что это даёт по тактам (ожидание)

* 16×16 hero было: 4 setup + 4×4-плоскостных blit ≈ 4 × (setup + 32 writes) ≈
  4 × 989 = **~3956 тиков**. Станет: **1 setup** + цикл по 3 наличным плоскостям ×
  2 столбцам × 16-байтовый прогон. Setup экономится 3-кратно; пустые плоскости
  (если FLAGS их снимает) не пишутся.
* BG-тайл 1 плоскость: было compact = 887 (пишет 24 нуля). Станет ~прогон 8 байт
  без zero-writes → в разы короче; dense-ветка не платит за таблицу.

### 4.2 Двухфазная модель: преамбула → быстрый путь

Функция `spr_blit` разделена на две фазы:

**Фаза 1 — Преамбула (setup, один раз на вызов):**
1. Разбор аргументов стека: `dst` → HL, `desc` → BC.
2. Чтение заголовка дескриптора: FLAGS, COLS, DEPTH → в bss-переменные.
3. Для sparse (FLAGS bit5): вычисление `tabbase = desc+3`, сдвиг `BC` (DATA)
   на `COLS*2` байт вперёд.
4. Для OR (FLAGS bit6): вычисление `mask_base` — адреса блока П0-маски
   (см. §4.6). Иначе переход к плоскому пути.

**Фаза 2 — Быстрый путь (внутренний цикл, на каждый столбец × ряд × плоскость):**
1. Сброс курсора TABLE (`sbf_tab = sbf_tabbase`) — в начале каждой плоскости.
2. `sbf_getcol`: (TOP,LEN) текущего столбца (из TABLE для sparse, или (0,DEPTH)
   для dense).
3. `sbf_col_geom`: старт прогона = `dst_top - TOP*8`, вычисление `sbf_row`/`sbf_seg`
   (разбиение по шву §4.5).
4. Копирующий цикл: 8 байт/тайл-ряд, `dcx h` (адрес убывает — §2).
5. Переход к след. столбцу: `inr h` (+0x100), декремент счётчика столбцов.
6. Переход к след. плоскости: `adi 20h` на H (+0x2000).

Цена преамбулы платится **один раз** на спрайт, независимо от числа столбцов
и плоскостей. Быстрый путь не содержит обращений к дескриптору (кроме чтения
данных через DE-курсор) — только регистровые операции и запись в VRAM.

### 4.3 Регистровые соглашения (8080)

| Регистр | Фаза 1 (setup) | Фаза 2 (быстрый путь) |
|---------|----------------|----------------------|
| HL | dst (адрес VRAM, верх столбца) | VRAM-курсор: `dcx h` в цикле, `inr h` между столбцами |
| DE | src (указатель на DATA в дескрипторе) | Курсор данных: `inx d` на каждый байт |
| BC | desc (указатель на дескриптор) → после разбора: курсор TABLE | Flat: не используется. OR: BC = курсор маски |
| A | FLAGS, счётчики | Счётчик рядов (`sbf_orow`/`b`), копирование (`mov m,a`) |

**Ключевое свойство:** DE — сквозной курсор данных. Он **не сбрасывается**
между плоскостями — данные в дескрипторе лежат непрерывно в порядке
П3/П2/П1/П0, и DE просто проходит их последовательно. Курсор таблицы
(`sbf_tab`), напротив, **сбрасывается** в `sbf_tabbase` в начале каждой
плоскости (каждая плоскость читает те же пары TOP/LEN).

### 4.4 Внутренний цикл: побайтовый копир (8 байт/тайл-ряд)

Flat-путь (`sbf_plane`), один тайл-ряд = 8 байт:
```asm
    ldax  d          ; байт из DATA
    mov   m,a        ; записать в VRAM
    inx   d          ; следующий байт DATA
    dcx   h          ; VRAM: адрес убывает (к экр. низу, §2)
    ; ... повторить 8 раз ...
    dcr   b          ; счётчик тайл-рядов
    jnz   row_loop
```

OR-путь (`sbf_plane_or`), один байт:
```asm
    ldax  b          ; mask_byte (BC = курсор маски)
    ana   m          ; AND с VRAM
    xchg             ; DE ↔ HL (VRAM-адрес в DE, color-адрес в HL)
    ora   m          ; OR с color_byte
    xchg             ; восстановить
    mov   m,a        ; записать результат в VRAM
    inx   b          ; след. маска
    inx   d          ; след. цвет
    dcx   h          ; VRAM вниз
    ; ... 8 раз ...
```

AND-путь (`sbf_plane_and`, плоскость П0), один байт:
```asm
    ldax  d          ; mask_byte
    inx   d
    ana   m          ; VRAM AND mask
    mov   m,a        ; записать
    dcx   h
    ; ... 8 раз ...
```

### 4.5 Шов кольца (seam) — разбиение прогона

Прогон `TOP..TOP+LEN` (в тайл-рядах) обязан остаться в одном 256-байтовом
блоке (32 тайл-ряда): `(grow_base & 31) + TOP + LEN <= 32`.

* putup-клетка 16px = 2 глиф-ряда — с запасом в 32-рядном кольце; seam-пересечение
  возможно только у самой границы прокрутки (grow 31→0).
* `sbf_rows2seam`: `A = (L >> 3) + 1` — тайл-рядов до шва (offset 255 → 0).
* Если `LEN <= seam` (сравнение в `sbf_col_geom`): прогон не разбивается,
  `sbf_row = LEN`, `sbf_seg = 0` — один цикл.
* Если `LEN > seam`: `sbf_row = seam` (1-й сегмент до шва),
  `sbf_seg = LEN - seam` (2-й сегмент после шва).
* **Ребаза адреса** (2-й сегмент): `H = sbf_blk+1` (старший байт блока
  столбца, сохранён в `sbf_col_geom`), `L = 0xFF` (верх блока, offset 255).
  Далее `dcx h` продолжает прогон с новой базы.
* Seam-кап одинаков для flat, OR и AND путей.

### 4.6 OR-композит: два курсора данных

Для OR-спрайтов (FLAGS bit6) используются **два** курсора данных:

* **DE** — курсор цвета (текущая цветная плоскость: П3, П2 или П1).
* **BC** — курсор маски (блок П0, синхронно идёт по тем же столбцам/рядам).

Маска расположена в дескрипторе **после** всех цветных плоскостей:
```
DATA layout (FLAGS = 0x4E: OR, П2+П1 color, П0 mask):
  [П2 data: COLS*DEPTH*8 байт]
  [П1 data: COLS*DEPTH*8 байт]
  [П0 mask: COLS*DEPTH*8 байт]
```

Вычисление `mask_base` (Фаза 1, `sbf_or`):
```
mask_base = DATA + plane_bytes * popcount(FLAGS & 0x07)
```
где `plane_bytes = (Σ LEN_i) * 8` вычисляется в `sbf_pbytes`.

Перед **каждой** цветной плоскостью BC сбрасывается в `mask_base` (вызывающий
код в `sbf_or` загружает `BC = mask_base` перед `call sbf_plane_or`).
Внутри `sbf_plane_or` BC продвигается синхронно с DE (оба `inx` на каждый байт),
покрывая блок П0 в том же порядке столбцов и рядов.

Плоскость П0 (AND-путь, `sbf_plane_and`): DE загружается из `mask_base`,
продвигается `inx d` — тот же порядок, что и цветные плоскости.

## 5. Маска и OR-композит (семантика)

Семантика putup OR ([`spr.asm` L124-130](../lib/gfx/spr.asm),
[`build_tile_or` demo-spr](../roms/demos/demo-spr/main.c)):
П0 = `¬S` (маска сохранения фона), П3/П2/П1 = цвет. Композиция:
```
П3/П2/П1:  dst = (dst AND П0) OR color
П0:        dst = dst AND П0
```
В новом формате:
* бит4 = «есть маска», бит6 = «OR-режим».
* Блок маски = прогоны П0 по тем же COLS/(TOP,LEN). Ядро читает маску и цвет
  **параллельно** (два DE-курсора) — как `sgo_blit8` буферизует П0 в scratch,
  но теперь прогоном, а не 8 байтами.
* Hero 16×16 = 2 столбца × 16 строк маски + 2×16 цвета — один setup.

## 6. Миграция и совместимость

* **Формат не обратно совместим** с 32-байтовой plane-major записью и
  compact-тегом (бит0 слова-указателя). Планировщик `spr.c` (`tile_word`,
  `paint_cell`) переводится с «слова глифа» на «указатель дескриптора».
* **Генератор ассетов**: нужен скрипт, конвертирующий исходники (BMP/ тайл-карты
  putup/mario) в дескрипторы с корректным §2-порядком байтов и §3 раскладкой
  флагов. Кандидат — расширение `utils/bmp2inc*.py` / новый `utils/sprpack.py`
  по образцу `mario-dbl/tools/gen_assets.py`.
* **Планировщик sprite-major** (решено ранее) заменяет per-cell `paint_cell`-скан:
  на строке плана, когда луч прошёл низ спрайта, вызывается `spr_blit_sprite` для
  каждого пересечённого инстанса поверх перекрашенного BG-фоне.
* **BG-путь**: тайлмап-тайлы получают dense-дескрипторы; `spr_bg_cell` = адрес +
  lookup + `spr_blit_sprite(dense)` — без таблицы, с пропуском пустых плоскостей.

## 7. Риски / что проверить на next spr-speed

1. **Две ветки ядра** (dense/sparse) — поверхность багов; dense покрыть в первую
   очередь (BG = 90% блитов).
2. **Порядок байтов** (§2) — легче всего ошибиться; верифицировать round-trip:
   сгенерировать → заблитить → снять VRAM-дамп → сверить с исходным тайлом
   (метод «эмпирической верификации» из practice-памяти).
3. **Софтмал `*LEN` / `*DEPTH`** внутри ядра на 8080 дорог — курсоры DATA держать
   инкрементами по фикс. шагам (как `dt_rec += 25` в `render.asm`), не умножением.
4. **Новые замеры**: добавить в `spr-speed` сцены `bm_spr16_new` (sprite-major
   16×16) и `bm_bg_dense` (BG-тайл dense 1..2 пл.) и снять до/после — под
   гейтом `-DSPR_CALIBRATE`.

## 8. Итог

Формат = **3-байтный заголовок (FLAGS/COLS/DEPTH) + опц. per-column таблица +
прогоны по наличным плоскостям**. Один setup/спрайт, вертикальные прогоны
максимальной длины, пустые плоскости пропускаются (не затираются), dense-ветка
бережёт горячий BG-путь, sparse-ветка рисует неровные силуэты. Ядро `spr_blit`
разделено на преамбулу (разбор дескриптора, вычисление геометрии) и быстрый
путь (внутренний цикл без обращений к дескриптору). Следующий шаг —
эмпирическая отладка в spr-speed до byte-exact результата.

## 9. Статус реализации и план отладки

### 9.1 Что сделано

* **k1** — ядро `spr_fmt.asm` (798 строк): dense + sparse + OR/маска + шов
  кольца (§4.5). Реализованы: `sbf_plane` (flat), `sbf_plane_or` (OR),
  `sbf_plane_and` (AND), `sbf_col_geom` (геометрия + seam), `sbf_pbytes`
  (размер плоскости), `sbf_or` (setup OR-пути с вычислением `mask_base`).
* **k2** — spr-speed: сцены 8-17 (dense: spr_blit_dense, spr_blit8_smc,
  spr_blit 1пл/4пл/16×16), сцены 18-28 (OR, round-trip, sparse, seam)
  закомментированы до стабилизации.

### 9.2 Известная проблема

**Крах при `COLS≥2` И `DEPTH≥2` одновременно** (сцена 16: `desc_spr16`
2×2, 4 плоскости, FLAGS=0x0F). Симптомы:

* Заполнение VRAM идёт штатно (0xFF фон от `TG_SOLID`).
* После начала `spr_blit` с `COLS=2, DEPTH=2` запись уходит **ниже 0x8000**
  (в RAM, где код), затирая собственную программу.
* `COLS=2, DEPTH=1` — работает. `COLS=1, DEPTH=2` — работает.
  Крах только при комбинации.

Гипотезы (требуют проверки в spr-speed):
1. Неправильный расчёт `plane_bytes` для многоколоночного многорядного
   дескриптора → DE уходит за пределы DATA.
2. Ошибка в адресации при переходе между столбцами после нескольких рядов
   (`inr h` накапливает ошибку).
3. Порча стека в `sbf_col_geom` / `sbf_sub_top_o` при `DEPTH > 1`.

### 9.3 План стабилизации

1. **Очистка:** снести изменения в `lib/gfx/` (spr.c, spr.asm, spr_fmt.asm),
   проекты `demo-spr`, `demo-spr512`, `putup-spr`. Весь полезный код —
   в `spr-speed` (сцены, дескрипторы, бенчмарки).
2. **Минимальный тест:** восстановить `spr_fmt.asm` в spr-speed, оставить
   только сцену 16 (`COLS=2, DEPTH=2`, dense, 4 пл.).
3. **Пошаговая отладка** в v06c-debugger: проверить HL/DE/BC на каждом
   столбце и каждой плоскости; найти момент ухода адреса ниже 0x8000.
4. **Round-trip верификация:** после починки — VRAM-дамп vs. эталонные
   данные дескриптора (byte-exact, §4.4).
5. **Расширение:** постепенно раскомментировать сцены 17-28 (OR, sparse,
   seam), после каждой — проверка в эмуляторе.
