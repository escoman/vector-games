# Исследование ROM ./src/cyberno.rom с помощью mcp-сервиса и python-фреймворка `analyze`

Объект: `./src/cyberno.rom`, 27392 байта, SHA256
`02c769c4e1f6cc6824597511d90ffff7d736dc54dff1a722a704575a45d85ded`.
**Это самораспаковывающийся ROM.** Дальнейший анализ ведётся по
**распакованному образу** — см. раздел «Распакованный образ» ниже.
**Origin/entry = `0x0100` (подтверждено на Stage 0 через `debug_load_rom`):**
загрузчик отображает файл с `0x0100`; `0x0000–0x00FF` — NOP-sled, через который
CPU после сброса попадает в код. Первые байты образа (по адресу `0x0100`):
`31 EE DC` (`LXI SP,0DCEEh`), `21 00 02` (`LXI H,0200h`), `CD E1 01`
(`CALL 01E1h`), далее `3A F9 01 … 32 E2 ED` — инициализация копирует горячий
участок кода в `0xEDE2…` (само-релокация). Верх образа `0x6BFF`
(0x0100 + 27392 − 1); `vram_base = 0xC000`.

**Главный интерес: генератор голоса из текста (текст→речь).** В ROM открыто
читаются транслит-фразы «речи» (это не экранные подсказки):

- `JSEM HLAS VAS'EHO POC'I'TAC'E SPEKTRUM`
- `ESTI DVA STO DVADCATX  GOROD BORISOV  PAVLOWA SEMNADCATX  PODOVDITE MINUTOHKU  POVALUJSTA`
- `GRU  DIL  SOFT  PREDLAGAET  NOWEJSIE  PROGRAMMY  K  WEKTOR  NOL  SESTX C  PISITE NAM PO ADRESU`
- `DIL SOFT PREDLAGAET NOWYE IGRY K WEKTOR NOL SEST C  PISITE PO ADRESU  DWESTE DWADCAT NOL SEMDESUAT ODIN ABANEBENTNYJ IASIK SESDESUAT ODIN`
- `ku~inskomu andre` iwanowi~u` (видимо, дарственная подпись)

**Механизм речи подтверждён на Stage 0:** на заставке ROM непрерывно пишет
1-битные значения в **порт `0x00`** (`OUT 00h`, значения `00h/01h`, шаг ~40
T-состояний ≈ 37 кГц) — это **PDM/PWM-воспроизведение речи через динамик
(TapeOut/beeper)**, а не ВИ53 и не AY. Транслит-фразы выше — исходный текст,
который движок синтезирует в этот поток.

Сама игра — порт ZX-Spectrum-ной Cybernoid (сайд-скроллер со спрайтами) —
**вторична**: спрайтовый движок, коллизии и уровни фиксируются в
RDB на уровне «что где лежит», без глубокой семантики (Stage 8).

Экранные строки (для ориентира): `PLEASE%ENTER%YOUR%NAME`, `THE%FEDERATION%WILL%REWARD`,
`ENTER%PASSWORD`, `1.START` / `2.LOAD` / `3.PASS`, `GET%READY`, `YOU%ARE%DEAD`,
`FUCK%OFF`, `NO%DRIVE%A`, `LOADING%ERROR`, `CONGRATULATIONS%%`, `HI%SCORE:`,
`SCORE:` / `LIFE:` / `STAGE:` / `LEVEL:`, имена `HEWSON`, `DIL%SOFT`, `%MINSK%`.
Разделитель слов `%` (0x25) — вероятно, внутренний терминатор/пробел дисплей-
движка; подтвердить на Stage 6.

Игровой процесс (частично подтверждено на Stage 0): boot → **заставка
«CYBERNOID — THE FATAL RETURN» с меню `1.START` / `2.LOAD` / `3.PASS`** → игра.
**Голос произносится уже на заставке** (порт `0x00` активен с первых секунд,
экран в этот момент может быть затемнён). Дальнейшие экраны — уточнить на Stage 5.

Методика учитывает, что для механических шагов есть готовый детерминированный
фреймворк `utils/analyze` (устройства и команды модулей — в `utils/analyze/README.MD`,
здесь они не дублируются). Все Stage, где нужно лишь «вызвать MCP → посчитать →
оформить», делает фреймворк; ИИ включается только там, где нужна семантика.

## RDB — база знаний по ROM; отчёты краткие (НОВОЕ, действует на всех Stage)

RDB-файл `src/cyberno.rdb` — не «служебный индекс», а **первичная база знаний**
по ROM: имена объектов, комментарии (русский текст), `params`/`reads`/`writes`,
связи `func→data/music/var` — всё это пишется в RDB и там живёт. Следствия:

1. **Отчёт Stage — это обзор, а не свалка.** Формат: цель → 5–15 ключевых
   выводов → ссылки на объекты RDB (`func_speak_engine@0xXXXX`) и
   JSON прогонов → Open questions. Типовый объём ручного отчёта — 0.5–1.5
   страницы. Запрещено дублировать в отчёт то, что уже в RDB/JSON (полные
   таблицы функций, списки параметров, дампы байтов).
2. **Знание, не попавшее в RDB, считается незафиксированным.** Каждый вывод
   уровня C (семантика) оформляется объектом/комментарием/связью в RDB и
   сохраняется `debug_save_rdb` до конца Stage; в отчёте остаётся одна строка
   со ссылкой на объект.
3. **Человекочитаемость — критерий приёмки RDB**, а не отчёта: после каждого
   ручного Stage `debug_get_rdb_info`/`debug_list_rdb_objects` должны показывать
   осмысленные имена и комментарии без пересборки отчётов.

## Распакованный образ — НОВЫЙ рабочий вход (после Stage 8)

`cyberno.rom` самораспаковывается на boot, поэтому статический разбор файла даёт
ложные чтения (файл ≠ exec: resident-блоки лежат со смещением +0x59…+0x138,
`0x1000+` — сжатый стрим). Распакованный образ получен прогоном в эмуляторе и
снятием RAM через **`debug_dump_memory`** (диапазон `0x0000–0x7FFF`, 32768 байт):

- **`./src/cybernoid_unpacked.r0m`**, 32768 байт, SHA256
  `d29d7d813b3add02e94fb3940341a82225d27f77588ad9bbd90637e7c48c9cbf`.
  Расширение `.r0m` → **origin `0x0000`** (соглашение предпоследнего символа
  имени; см. `run_pipeline.sh`/эмулятор). Канонический старт для unpacked-
  анализа: `debug_load_rom(path=…/cybernoid_unpacked.r0m)` — org подставляется
  из имени, `ORG` руками не задаём.
- Карта RAM после распаковки (VERIFIED): `0x0000 = C3 00 01` (JMP `0x0100`,
  вектор пропатчен boot); resident-код/данные `0x0100–0x0FFF`; игра
  `0x1000–0x7FFF`. Распаковщик (`0xEFE0–0xEFFF`) в образ **не** включён — он не
  нужен для анализа игры.

**Разделение RDB (решение исполнителя, проверено `debug_save_rdb`):**

| файл | ROM | содержимое | объектов |
|---|---|---|---|
| `src/cyberno.rdb` | `cyberno.rom` (org `0x0100`) | **только до распаковки**: bootstrap/unpacker (`func_0100`, `func_01be`, `func_01c4`, `func_unpacker_copy_primitive@0x01E1`), векторные EQU-метки, `data_packer_archive@0x0256` | 10 |
| `src/cybernoid_unpacked.rdb` | `cybernoid_unpacked.r0m` (org `0x0000`) | **после распаковки**: весь игровой код и данные (речь, меню, ISR, display-list, таблицы паролей/спрайтов, строки) | 339 |

**Ключевое:** адреса объектов unpacked-RDB = runtime-адреса = смещения в
`.r0m` (перенос выполнен 1:1, без смены ключей). Проверено: разборка
`func_menu_dispatcher@0x018B` в `.r0m` (`CALL 0F15; ORA A; JZ 018B; CPI 11; JZ
02F6; CPI 12; JZ 0FA5`) совпала с комментарием RDB дословно.

**Что это меняет в методике (Stage 9 и далее):**
1. Все последующие ручные Stage (9, 9a, 10) работают с **`cybernoid_unpacked.r0m`**
   и пишут в **`cybernoid_unpacked.rdb`**; `cyberno.rom`/`cyberno.rdb` остаются
   как запись bootstrap'а и точка сборки побайтового двойника (Stage 10).
2. Экспорт кода/данных Stage 9 берётся из unpacked-образа (exec-адреса, без
   фантомов relocation).
3. Профиль `pipeline.json`/`run_pipeline.sh`: для unpacked-анализа ROM =
   `src/cybernoid_unpacked.r0m`, соседний RDB = `src/cybernoid_unpacked.rdb`
   (origin подставляется из имени файла = `0x0000`).
4. **Caveat — не путать роли образов.** В отличие от packed `cyberno.rom`,
   unpacked-`.r0m` — срез RAM после самораспаковки (стек уже инициализирован
   boot'ом, ISR уже в RAM). Поведенческая проверка через MCP (IO-трейс, трассы,
   клавиши) по-прежнему делается **на packed `cyberno.rom`** (он исполняет
   bootstrap и загружает стек); `.r0m` — для статического разбора, экспорта ASM
   и разметки объектов. Побайтовый round-trip Stage 10: либо пересборка packed
   (bootstrap + `INCBIN` сжатый стрим, как в `basic`), либо сборка unpacked-asm
   с последующей упаковкой — решается явно на Stage 10.

## Stage 0. Автоматизированное исследование (главный вход)

Весь детерминированный слой поднимается **одной командой**:

```bash
utils/analyze/run_pipeline.sh cybernoid            # полный прогон (apply по умолчанию)
utils/analyze/run_pipeline.sh cybernoid --dry-run  # строго read-only, ничего не пишет
utils/analyze/run_pipeline.sh cybernoid --resume   # продолжить с чекпоинта
utils/analyze/run_pipeline.sh cybernoid --clean    # стереть чекпоинт и начать заново
```

**Предусловие (разовая регистрация профиля).** В `utils/analyze/run_pipeline.sh`
добавить `cybernoid` в `PROFILES` и в dispatch-`case`:
`ROM=roms/redesign/cybernoid/src/cyberno.rom`, `CONFIG=.../pipeline.json`;
profile-имя даст `RDB=src/cyberno.rdb` (по соседству с ROM). **Origin = `0x0100`
подтверждён — `ORG` не переопределяем** (дефолт пайплайна `0x0100` верен;
отличие от `basic`, где `.r0m` грузится на `0x0000`). Конкретные `stage_args`
профиля — п. «Профильный pipeline.json» ниже.

Launcher прогоняет DAG стадий в топологическом порядке:

`probe → coverage → disassembly → seed_rdb → rdb_lint → memory_diff →
io_signature → abi_scan → strings_scan → table_shape → vram_credits →
export_asm → toolchain_lint → symbolic_operand_lint → syntax_check →
roundtrip_verify → measure_sizes`.

Что даёт автоматика:

- **RDB-файл `src/cyberno.rdb` рождается здесь** (стадия `seed_rdb` досевает
  функции/метки/ссылки до fixpoint и вызывает `debug_save_rdb`); отсутствующий
  `.rdb` — не ошибка;
- **Сырые результаты:** JSON каждой стадии в `.scratch/pipeline/cybernoid/` +
  `statistics.json` + `pipeline.md` + чекпоинт `pipeline_state.json`.

**Профильный pipeline.json (максимальное раскрытие голоса).** `stage_args` —
как в exolon (`seed_rdb --max-depth 12`, длинные трассы 15–30 с, расширенные
`abi_scan`/`table_shape`), плюс ROM-специфика:

- **Клавиши прогона:** `1` (START), `2` (LOAD), `3` (PASS), стрелки (движение),
  `SPACE`/`RUS` (огонь), `ENTER` (имя/пароль). Прогон обязан довести ROM до
  момента произношения — иначе `io_signature`/`memory_diff` не поймают
  порт-сигнатуру и RAM-патчи голосового движка. Если голос звучит только на
  заставке/после смерти (`YOU%ARE%DEAD`) — добавить соответствующую последовательность.
- `strings_scan`: `--allow-ya`, `--min-len 4` — ловит и транслит-фразы речи;
- `probe --snapshot` — RAM-снимок на моменте речи (для diff голосовых указателей).

**Где автоматика упирается (и дальше только ИИ):** статическое покрытие
сходится на достижимом из entry; `table_shape`/`vram_credits`/`music2midi`
молчат, пока ИИ не занесёт в RDB таблицы кодов голоса, строки и спеки
(Stage 6–7, 9a).

## Stage 0'. Принципы и разделение ответственности

Именование объектов в RDB — префиксы `func_`, `data_`, `str_`, `music_`, `var_`,
`lbl_`; суффикс `_unknown` для недообследованного. Единственный источник правил
именования — `utils/analyze/naming.py`. Для голоса зарезервированы имена:
`func_speak_engine`, `func_speak_char` (кодировщик символа),
`data_speak_codes` (таблица кодов/указателей речи), `data_speak_units`
(дифоны/артикулограммы), `var_speak_ptr`, `var_speak_speed`.

| слой | кто | что делает |
|---|---|---|
| **A. Facts** | Python (`utils/analyze`) | загрузка ROM, покрытие, round-trip сборки, VRAM-кредиты, размеры объектов, MIDI по готовой спеке |
| **B. Candidates** | Python находит с пометкой | сигнатуры ABI, форма таблиц, строки транслит/RUS, порт-сигнатуры I/O, границы гэпов |
| **C. Semantics** | только ИИ/человек | «эта функция — движок речи», «эта таблица — коды дифонов», имена и комментарии |

Политика доступа: Python-скрипты идут к эмулятору **только** через MCP
`v06c-mcp`; единственный легальный внешний бинарь — `v06c-asm-export`.
Декодировать опкоды и строить CFG скриптам запрещено. Ad-hoc py-ки в обход
пакета не пишутся: общий алгоритм — в `utils/analyze`, ROM-специфичное
(адреса фраз, спеки) — в `tools/`.

Канонический старт — только `debug_load_rom`. Промежуточные отчёты —
`./reports/StageN.md` (краткие, см. раздел «RDB — база знаний»); RDB —
`./src/cyberno.rdb`; ASM — `./asm/`; спеки — `./tools/`.

**Консолидация экспорта (анти-халтура).** Итоговый `asm/` — НЕ «по файлу на
объект»: весь код — один `code.asm`, все строки — один `strings.asm`, данные —
целевые `.inc`. Полная раскладка — Stage 9.

## Stage 1. Механические факты: карта памяти, посев RDB, round-trip

Полностью делает `run_pipeline.sh cybernoid`. Отчёт `./reports/Stage1.md` —
генерируется `report_gen.py` по всем JSON прогона (краткий, по формату раздела
«RDB — база знаний» выше):

```bash
PYTHONPATH=utils python3 -m analyze.report_gen \
  --results .scratch/pipeline/cybernoid \
  --statistics .scratch/pipeline/cybernoid/statistics.json \
  --stage 1 --title "Stage 1. Механические факты (cyberno.rom)" \
  --out roms/redesign/cybernoid/reports/Stage1.md
```

Фиксирует (всё — ссылками на JSON и объекты RDB, без пересъёмки руками):

- карту памяти: подтверждённые origin/entry, RAM-патчи, порт-сигнатуры IN/OUT
  (`probe`, `memory_diff`, `io_signature`) — **отдельно отметить порты,
  активные только в моменты речи** (кандидаты звуковых портов голосового
  движка: VI53 09h/0Ah/0Bh; AY 14h/15h, если ROM под расширенный звук);
- посев RDB до fixpoint (`seed_rdb` → здесь создаётся `src/cyberno.rdb`);
- экспорт и **побайтовый round-trip** (`export_asm → … → roundtrip_verify`,
  0 расхождений = Fact) — контракт действует до Stage 10;
- candidates c пометкой: ABI (`abi_scan`), транслит-строки (`strings_scan`),
  формы таблиц (`table_shape`), глифы (`glyph_scan`), размеры (`measure_sizes`).

## Stage 2. Подробное исследование функций (семантика — за ИИ)

Для каждой функции из RDB: осмысленное имя, **комментарий-назначение в RDB**
(русский текст), свойства `params`/`reads`/`writes`/`calls`, связи
`debug_add_rdb_link`. Глубоко — только цепочка, ведущая к речи и выводу текста
(`func_speak_*`, движок строк, звуковой вывод, тикер); остальное — до уровня
«назначение угадано, комментарий стоит». Сохранение RDB — только
`debug_save_rdb`. Отчёт `./reports/Stage2.md` — краткий обзор + ссылки.

## Stage 3. Параметры функций

Кандидатов даёт `abi_scan` (`--all --limit …`). ИИ подтверждает и пишет в RDB
`properties.params`. Особое внимание — входным параметрам движка речи
(адрес строки в HL? скорость в регистре?) и способу возврата (по petle-фишке
встречается `RET`-подобный выход после терминатора). Отчёт краткий.

## Stage 4. Прерывания и тикер речи

Векторы: `0x0008/0x0010/0x0018/0x0020` (RST 0/8/16/24), `0x0038` (RST 32),
`0x003C` INTERPT (`docs/VECTOR_VERIFIED.md`). Ключевой вопрос для cybernoid:
**чем тарифицируется речь** — ISR VBlank (`RST 7`, 50 Гц), таймер ВИ53 или
busy-loop c задержкой внутри `func_speak_engine`. Ответ фиксировать в RDB
(`func_irq_*` с комментарием; у движка речи — свойство «шаг = N тиков чего»).
Отчёт `./reports/Stage4.md` — краткий.

## Stage 5. Главный цикл и экраны (обзорно)

Установить маршрут boot → меню (`1.START`/`2.LOAD`/`3.PASS`) → игра и
**момент(ы) произношения голосовых фраз** (заставка? info? death?). Найти
функцию перехода между экранами; игровые переменные — только поверху:
`var_score`, `var_lives`, `var_stage` (парольная система `2.LOAD`/`3.PASS` —
только как данные, Stage 8). Отчёт `./reports/Stage5.md` — обзорный, без
подробного матчера спрайтов (это не scope).

## Stage 6. Вывод текста на экран + каталогизация строк

Строки-кандидатов находит `strings_scan`. ИИ подтверждает, классифицирует,
создаёт объекты `str_*` (комментарий = расшифровка транслита в русский;
для речевых фраз — пометка `str_voice_*`). Установить кодировщик экранного
шрифта (транслит + разделитель `%`) и базовый адрес глифов (`data_glyph_block`,
подтвердить `glyph_scan`/`vram_credits`). Отчёт `./reports/Stage6.md` — краткий.

## Stage 7. ГЕНЕРАТОР ГОЛОСА ИЗ ТЕКСТА (главная цель, обязательный Stage)

Порт Spectrum-ного speech-синтезатора (в духе Speak You! / «говорилки»
Спектрума) или собственный движок — установить по коду. План раскопа:

1) **Точки вызова.** От речевых `str_voice_*` через `debug_get_xrefs` дойти до
   `func_speak_engine`; зафиксировать, в каких экранах/состояниях зовётся
   (сверить с рантайм-трассой `probe` в момент речи).
2) **Кодировщик символ→коды.** `func_speak_char`: таблица перевода букв
   транслита в коды артикулограмм (дифоны/фонемы). Найти таблицу
   (`data_speak_codes` — указатели DEFW или фиксированные блоки `DEB`),
   подтвердить `table_shape` + RAM-диффом; в RDB — комментарий «строка ASCII/
   транслит → последовательность кодов».
3) **Синтез единиц.** Речь идёт **1-битным PDM/PWM-потоком в порт `0x00`**
   (подтверждено Stage 0), значит `data_speak_units` — это не «пары
   регистр→данные» ВИ53/AY, а **форм-фактор сигнала**: либо PCM/PDM сэмплы
   дифонов, либо параметры генератора (частота/форма/длительность),
   оцифровываемые в поток `OUT 00h` на лету. Установить: откуда берутся байты
   потока (таблица в ROM vs генерация), шаг вывода (горячие блоки `0x0600`/
   `0x0700` и само-релоцированный код `0xEDE2…` — кандидаты на выводчик), как
   кодируются длительность/пауза/просодия.
4) **Темп и исполнение.** Цикл выборки: указатель `var_speak_ptr`, шаг
   (VBlank/таймер/busy-loop из Stage 4), терминатор фразы, скорость речи
   (параметр или переменная — отсюда «замедленная речь» на низких частотах).
5) **Доказательная база:** IO-трейс совпадает с последовательностью `OUT`
   движка; RAM-лог показывает чтение таблицы ровно в байты кодов текущего
   символа; скриншоты/видео момента речи через MCP. Каждый вывод — комментарием
   в RDB, в отчёте — строка-ссылка.
6) **Артефакты:** спецификация `./tools/voice_spec.md` (формат: таблица кодов,
   формат единицы, порты, темп — это единственный разрешённый «длинный» кусок
   Stage 7, и он живёт отдельным файлом, а не размазан по отчёту);
   ROM-специфичные скрипты разметки — в `./tools/`.
7) **Критерий приёмки:** по RDB+`voice_spec.md` можно воспроизвести произнесение
   любой фразы ROM'а; опциональный stretch (решается по ходу): порт движка в
   `lib/snd/` (`speak`-модуль) с тестом «свой текст → голос».
   Отчёт `./reports/Stage7.md` — краткий обзор.

## Stage 8. Игровые данные: уровни, спрайты, паттерны (обзорно, минимально)

Спрайтовый движок и уровни в scope'е TZ только как носители данных: каталог
`data_sprites_*`, паттерны врагов/волн, таблица уровней/паролей (`3.PASS`),

подтверждение `table_shape`/`measure_sizes`. Без глубокой семантики движения

> **СТАТУС:** Все Stage 0–10 закрыты. **Stage 10 выполнен**: перекрытия RDB

> (`OUT 0x00` PDM) идентична оригиналу. Отчёт — `reports/Stage10.md`.
> Дефект экспортёра (метки `true+1`) скомпенсирован `defb`-починкой; после
> C++-фикса цикл починки превратится в пустую операцию.

**Главный принцип: экспорт не дробить.** Один логический класс содержимого —
один файл; `func_*.bin`/`lbl_*.bin`/`gap_*.bin` per-object запрещены.

### Развилка: побайтовая идентичность ⟷ раскладка по файлам-классам

Проверено на `z80asm -b -m=8080_strict`: второй `ORG` не переносится, гэпы не
заполняются — байт-в-байт сборка обязана идти строго адресным потоком под
одним верхним `ORG`.

| ветвь | когда выбираем | раскладка `asm/` | round-trip |
|---|---|---|---|
| **A. Монолит (byte-identical)** | нужен побайтовый ROM-двойник | один `code.asm`: весь код мнемониками + строки/таблицы/глифы/гэпы — помеченные секции `DEFB`/`DEFM` по меткам RDB; мастер `cybernoid_new.asm` = `ORG` + `INCLUDE "code.asm"` | 0 расхождений |
| **B. Файлы-классы (релокация)** | допускаем сдвинутое адресное пространство | `code.asm` + `strings.asm` + `voices.inc` (таблицы `data_speak_*`) + `sprites.inc` + `fonts.inc` + `data_*.inc`, каждый класс на своём `ORG` | функционально-эквивалентный, НЕ byte-identical |

Выбор ветви фиксируется в `reports/Stage9.md` явно. Детали (ROM-backed vs
RAM-backed, `INCBIN` только для крупных массивов, починка синтаксиса экспорта
вместо подмены кода блобами) — как в TZ exolon, Stage 8.

## Приоритеты и порядок

- **Stage 0 (`run_pipeline.sh`) — точка входа**: закрывает весь Stage 1 и
  значительную часть 3/6/8/9. Затем ИИ добирает семантику.
- **Сквозной приоритет — голос (Stage 7).** Ручные этапы выстроены вокруг него:
  2 → 3 → 4 → 5 → 6 → **7** → 8 → 9 → 9a → 10. Этапы 5 и 8 — обзорные, их
  глубину сознательно ограничиваем; при конфликте времени жертвуем 8, не 7.
- **Правила исполнения (обязательны для исполнителя):**
  1. **Один Stage = один заход.** Ручные этапы строго последовательно, нельзя
     делегировать пачку Stage агенту за раз. Каждый — отдельный проход и
     отдельный `reports/StageN.md`.
  2. **Сохранять RDB инкрементально.** Каждую пачку правок сразу фиксировать
     `debug_save_rdb`; `.rdb` руками не править.
  3. **Отчёты краткие** (см. раздел «RDB — база знаний»): вывод без объекта в
     RDB не считается сделанным; отчёт не дублирует RDB/JSON.
  4. Механический Stage 1 — отчёт только через `report_gen.py`.
- После ручных правок RDB — пересобрать экспорт/round-trip
  (`run_pipeline.sh cybernoid --from export_asm`) и обновить Stage1.md.

## Примечания по ROM

- **Адресное пространство (Stage 0, VERIFIED)**: образ `0x0100–0x6BFF`
  (27392 байт), entry `0x0100`; `0x0000–0x00FF` — NOP-sled. `vram_base=0xC000`.
  Переменные — в page `0x01` (`0x01F9/0x01FA/…`); инициализация копирует горячий
  код в `0xEDE2…` и исполняет его оттуда (в memory map блок `0xEE00` даёт
  execute-активность). Начальный `SP=0DCEEh` — в области ≥0xC000 (пересечение со
  VRAM-окном эмулятора): уточнить раскладку RAM/стека диагностикой RAM-патчей на
  Stage 1.
- **Две орфографии транслита**: экранная (`V`→Ж, `X`→Ь/Щ-хвосты, как в exolon)
  и речевая (`POC'I'TAC'E`, `DVADCATX`, `SPEKTRUM`) — для Stage 7 нужна полная
  таблица `data_speak_codes` (буква → код), отдельная от экранного кодировщика.
- **Разделитель `%` (0x25)** в экранных строках — вероятно внутренний пробел/
  терминатор; в речевых фразах разделитель — двойной пробел. Не путать при
  классификации `str_*` vs `str_voice_*`.
- **Звук речи = 1-битный порт `0x00`, а не ВИ53/AY** (Stage 0, VERIFIED): на
  заставке ROM бит-бэнгит `OUT 00h` (`00h/01h`, ~37 кГц) — PDM/PWM на динамик.
  ВИ53/AY к речи отношения не имеют; их порты (`09h/0Ah/0Bh`, `14h/15h`)
  проверять отдельно на предмет фоновой музыки (Stage 9a).
