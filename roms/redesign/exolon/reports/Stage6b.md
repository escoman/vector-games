# Stage 6b. Команды интерпретатора списка отображения (exolon.rom)

> Источник фактов — дизасемблирование `func_display_interpreter @0x3CC1` (см.
> [`asm/code.asm`](../asm/code.asm), строки 4463–4629; каждая команда снабжена
> комментарием справа) плюс живой прогон через MCP `vector-debugger`
> (`debug_read_memory_range` display-списков, `debug_get_screen_snapshot`).
> Документ — приложение к [`Stage6.md`](Stage6.md): там — шрифты/кодолист/строки,
> здесь — **система команд** самого интерпретатора.

## TL;DR

Вывод текста рисует не «функция печати строк», а **байтовый интерпретатор списка
отображения** (display-list interpreter) `func_display_interpreter @0x3CC1`. Он читает
команды **из ROM по месту** (копии в RAM нет) и исполняет диспетч по значению байта:
байт `< 61h` — код глифа (рисуется), остальные значения — служебные опкоды
(позиция / цвет / повтор / вложенный список / смена шрифта / флаг / терминатор).

**Практический вывод для гэпов:** байты, стоящие *между* строками в display-списке
(например `DBh`, `D0h` в HUD), — это **не длина строки и не префикс РУС/ЛАТ**, а следующая
команда интерпретатора: в примере ниже это **опкоды цвета** (диапазон `CFh…DEh`).
РУС/ЛАТ — отдельный опкод `E6h` + 2-байтная база шрифта.

## Модель состояния

Интерпретатор — это цикл `while (cmd = *[HL]++),` с одним регистром-курсором списка `HL`
и внешним состоянием, которое команды mutate:

| Регистр / RAM | Роль |
|---|---|
| `HL` | курсор чтения display-списка (в ROM) |
| `D` | строка (row) позиции курсора на экране |
| `E` | столбец (column) позиции; `inr e` — шаг на знак |
| `C` | байт цвета/атрибута, передаётся в `func_draw_glyph` |
| `B` | счётчик цикла повтора (пары `E1`/`E2`) |
| `[3B19:3B1A]` | база шрифта (устанавливается `E6`): `0x2530` лат., `0x732D` кир. |
| `[3B56]` | флаг режима рендера (устанавливается `E8`) |
| `[3B50]` | флаг инверсии/мигания (`E9` → 0, `EA` → FF) |

Диспетч — цепочка `cpi/jnc|jnz`: сначала отделяются текстовые байты (`< 61h`), затем
диапазоны `61…8F`, `90…CE`, `CF…DE`, после `DFh` — поштучная проверка `DF,E0,E1,E2,E3,E4,
E5,E6,E7,E8,E9,EA,EB`; любой неизвестный байт (`≥ ECh`, на практике `FFh`) даёт `rnz → RET`
= **конец списка**.

## Таблица команд

| Опкод | Диапазон | Байт | Действие |
|---|---|---|---|
| `< 61h` | `00…5F` | 1 | код глифа → `call func_draw_glyph` в `(D,E)` цветом `C`, затем `E++` |
| `61h…8Fh` | относит. сдвиг | 2 | `D += cmd−78h` (строка); `E += [HL]` (столбец); `HL++` |
| `90h…CEh` | нов. строка + сдвиг | 1 | `D++`; `E += cmd−AFh` |
| `CFh…DEh` | **цвет/атрибут** | 1 | `idx = cmd−CFh`; `low = idx<8 ? idx : (idx−8) OR 40h`; `C = (C AND 38h) OR low` |
| `DFh` | абсолютный курсор | 3 | `D := [HL]`, `E := [HL+1]` (строка, столбец) |
| `E0h` | цвет напрямую | 2 | `C := [HL]` |
| `E1h` | начало цикла | 2 | `B := [HL]`; `PUSH HL, BC` — точка тела повторения |
| `E2h` | конец цикла | 1 | `B--`; `≠0` → `POP HL`, прыжок на тело; `=0` → `POP PSW`, выход |
| `E3h` | вложенный список | 3 | `HL' = word (младший байт первым)` → `call` рекурсии, возврат контекста |
| `E4h` | глиф ×N горизонт. | 3 | `B := [HL]`, `A := [HL+1]`; печать глифа `B` раз с `E++` |
| `E5h` | глиф ×N вертикальн. | 3 | `B := [HL]`, `A := [HL+1]`; печать глифа `B` раз с `D++` |
| `E6h` | **смена шрифта РУС/ЛАТ** | 3 | `[3B19:3B1A] := word` (`2530h` лат. / `732Dh` кир.) |
| `E7h` | пробел | 1 | временно база `2530h`, глиф `20h`, `E++`, восстановить базу |
| `E8h` | режим рендера | 2 | `[3B56] := [HL]` |
| `E9h` | инверсия выкл | 1 | `[3B50] := 00h` |
| `EAh` | инверсия вкл | 1 | `[3B50] := FFh` |
| `EBh` | спец-команда | 2 | операнд → `[6ADC]`, `jmp label_6ADD` (обработчик, см. §Ограничения) |
| `≥ ECh` (напр. `FFh`) | терминатор | — | `RET` — конец списка |

### Плот цвета `CFh…DEh`

Полуразрядный цвет `idx = cmd − CFh` (0…0x0F). Если `idx ≥ 8`, берётся `(idx−8)` и
выставляется бит `40h` — это **выбор плоскости** (bit6 в байте цвета VRAM). Старшие биты
цвета `C AND 38h` (биты 3…5) при этом **сохраняются** из предыдущего значения `C`. Поэтому
цвет ставится «поверх» уже накопленного атрибута, а не сбрасывает его целиком.

## Разбор HUD-списка `0x3F4A` (иллюстрация)

Сырые байты (MCP `debug_read_memory_range 0x3F4A`) и построчная декодировка:

```
DF 16 00            ; абсолютный курсор (D=16h, E=00h)
E6 30 25            ; шрифт := 0x2530 (латиница)
E8 01               ; [3B56] := 01 (режим)
E9                  ; [3B50] := 00 (инверсия выкл)
DC                  ; ЦВЕТ idx=0D → (0D−08)|40 = 45h      ┐ гэп перед «AMMO»
41 4D 4D 4F 20      ; 'AMMO '                             ┘ (не длина!)
DD                  ; ЦВЕТ idx=0E → 46h                   ┐ гэп перед «GRENADES»
47 52 45 4E 41 44 45 53 20 ; 'GRENADES '                  ┘
DB                  ; ЦВЕТ idx=0C → 44h      — гэп перед «POINTS»
50 4F 49 4E 54 53 20 ; 'POINTS '
D0                  ; ЦВЕТ idx=01 → 01h       — гэп перед «LIVES»
4C 49 56 45 53 20   ; 'LIVES '
DA                  ; ЦВЕТ idx=0B → 43h       — гэп перед «ZONES»
5A 4F 4E 45 53      ; 'ZONES'
DF 17 00            ; новый абсолютный курсор (D=17h, E=00h)
E4 20 20            ; глиф 20h (пробел) ×0 раз… (RLE-заполнение строки)
E3 24 3E            ; CALL вложенного списка 0x3E24 (поле счёта)
FF                  ; конец списка
```

Каждая подпись HUD помечена **своим цветом** (`DC/DD/DB/D0/DA` из диапазона `CF…DE`) — на
живом скриншоте метки AMMO/GRENADES/POINTS/LIVES/ZONES действительно каждая своего цвета.
Это подтверждает: «префиксы строк» — опкоды цвета, а не длина/шрифт.

## Связь с Stage 6

- `func_draw_glyph @0x3B00` / `func_draw_glyph_base @0x3B5B`: адрес источника глифа =
  `[3B19] + code*8` — база ставится только опкодом `E6` (см. Stage 6, §Архитектура).
- Два шрифта (лат. `0x2630`, кир. `0x742D` с учётом виртуальной базы −0x100) выбираются
  тем же `E6`; `E7` печатает пробел всегда латинской базой.
- Вложенные списки (`E3`) объясняют, почему «строки внутри display-списка» оформлены
  отдельными объектами: счёт/поля рисуются вызовом `E3 <addr>` (напр. `0x3E24` — ASCII-decimal
  ADD-ридер поля счёта).

## Ограничения

- **`EB` раскрыт частично:** опкод читает операнд в `[6ADC]` и передаёт управление
  `label_6ADD` → `label_3DD3` (сравнение `[3D9B]` с `3B00h`, `func_scale_de_x8`, запись).
  Это спец-путь (похоже на патч/кастомный рендер), не базовый текстовый опкод; полный
  сценарий не трассирован — помечен как «спец-команда», а не выдуман.
- Диапазон `00h…20h` формально «код глифа», но управляющие/нулевые коды на экран в игре
  не выводились — за рамками наблюдений.
- Точная геометрия `(D,E)` → экран задаётся внутри `func_draw_glyph` (маски `E AND 20h/1Fh`,
  `D AND 0F8h`); здесь `D`/`E` трактуются как строка/столбец, что подтверждено поведенчески
  (`inr e` на знак, `inr d` на строку).
