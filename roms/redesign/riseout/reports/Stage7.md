# Stage 7. Карты уровней (riseout.rom)

> Источник фактов — MCP `vector-debugger`: каноническая загрузка ROM через `debug_load_rom` (org 0x0100, `roms/redesign/riseout/src/riseout.rom`, sha256 `c265014b…a6991`), `debug_disassemble` / `debug_disassemble_range`, `debug_analyze_code`, `debug_find_bytecode_sequence`, `debug_find_immediate_in_range`, `debug_read_memory_range`, живые прогоны `debug_run`/`debug_pause`/`debug_step`/`debug_set_register`/`debug_write_memory`/`debug_set_breakpoint`. Правки RDB — только `debug_update_rdb_object` / `debug_add_rdb_object` / `debug_set_rdb_comment` / `debug_set_comment` / `debug_set_rdb_property` / `debug_add_rdb_link` + `debug_save_rdb`; файл `riseout.rdb` руками не редактировался. `debug_reset` не вызывался (вешает ЦП на busy-wait `OUT 1C`/`IN 1B`). Все адреса — адреса образа ROM.
>
> **Важно про формулу из ТЗ.** ТЗ предполагает `base + (level−1)*stride`. Наблюдение это **опровергает**: постоянного `stride` в ROM нет. Карты лежат плотным блоком, а их адреса берутся из **таблицы слов-смещений**; тождество ТЗ выполняется в обобщённой (префикс-суммовой) форме. Ниже — где именно это видно в коде и байтах.

## Goal (ТЗ, раздел «Stage 7. Карты уровней»)

1. найти `func_level_loader` и в ней — **формулу адреса карты**;
2. разобрать **цикл обхода M×N**: размерность тайлов, 1 или 2 байта на тайл, как тайлы уходят в поле/VRAM;
3. найти **координаты спавна игрока и выхода** на карте;
4. определить в RDB `data_level_maps`, `LEVEL_COUNT`, `stride`, создать `data_level_01 … data_level_NN` (с учётом «один адрес — один объект»), подтвердить границы и **проверить тождество** `LEVEL_COUNT*stride == data_next_addr − data_level_maps_addr` (`table_shape`, `measure_sizes`, прямое чтение);
5. завести связи `func_start_new_level` / `func_level_loader` → `data_level_maps` и комментарии `data_level_*`.

## Method

1. **Предусловие.** `debug_get_rdb_info`: `loaded=true`, `object_count=449` (состояние после Stage 6), `dirty=false`. К концу этапа — **479 объектов**, сохранено 11 пачками.
2. **Якорь вместо перебора.** Статическое покрытие из entry ≈44 %, и блок карт в него не попадает (в достижимых из entry диапазонах `0x3594..0x4BE6` нет ни одной инструкции — только данные), поэтому поиск шёл не по CFG, а от вызывающего кода. Поэтому поиск шёл от объявленного Stage 5 якоря `func_start_new_level @0x1FAD`: `CALL 1FAD` из `func_player_session @0x095C`, внутри — `CALL 0x24CF @0x1FB0`. Дальше только дизассемблирование `0x24CF`.
3. **Поиск «тайла-маркера» по коду.** `debug_find_bytecode_sequence([0xFE,0x64])` (`CPI 0x64`) по 0x0100..0x50FF → **ровно одно** совпадение, `0x213D`. Это закрыло вопрос «чем карта отличается от поля»: маркеры старта/цели ищутся в уже развёрнутом буфере поля сравнением байта, а не вычисляются из упаковки.
4. **Динамика: «вызов функции по адресу» без стекового возврата.** Первый вариант (затолкать адрес возврата в стек и BP на `0x0038`) **не сработал**: BP поймал аппаратный `RST 7` (обработчик прерывания), а не `RET`. Рабочая схема: `[0x7C66]←N`, `SP←0x77FE` (блок 0x7700 — нули, полем/переменными не занят), `PC←0x24CF`, **BP на `0x253A` (сам `RET`)** — снимается состояние в момент выхода загрузчика, возврат выполнять не нужно. Так получены две независимые точки проверки (§5).
5. **Фреймворк.** `analyze.table_shape` (два прогона: таблица `0x253D/40` и блок `0x3594/5715`) и `analyze.measure_sizes` (`--types data,table`) — только как независимая перепроверка; JSON в `/tmp/s7/` (каталог `.scratch/pipeline/riseout` в этом заходе отсутствовал, поэтому ссылки — на файлы прогона в `/tmp/s7/`; см. «Артефакты»).

## 2. Формула адреса карты

```
0x24CF LDA  7C66        ; A = var_level
0x24D2 CPI  15          ; 21?                     ┐ LEVEL_COUNT = 20:
0x24D4 JNZ  24DC        │                         │ после 20-го — снова 1
0x24D7 MVI  A,01        │                         ┘
0x24D9 STA  7C66        │
0x24DC DCR  A           ; A = level − 1            ┐ метка lbl_24dc
0x24DD ADD  A           ; A = 2·(level − 1)        ┘ (запись = слово)
0x24DE LXI  H,253D      ; HL = таблица смещений
0x24E1 MOV  C,A
0x24E2 MVI  B,00
0x24E4 DAD  B           ; HL = 0x253D + 2·(level−1)
0x24E5 MOV  E,M         ; DE = offset[level−1]  (LE-слово)
0x24E6 INX  H
0x24E7 MOV  D,M
0x24E8 LHLD 253B        ; HL = base = 0x3594   (data_level_maps_addr_ptr)
0x24EB DAD  D           ; HL = base + offset   ← МОМЕНТ ВЫЧИСЛЕНИЯ АДРЕСА
0x24EC XCHG             ; DE = источник (ROM), HL = приёмник (RAM)
0x24ED LXI  H,7040      ; буфер поля
```

**Формула:** `addr(level) = [0x253B] + word[0x253D + 2·(level−1)]`, где `[0x253B] = 0x3594`.

Таблица смещений (`debug_read_memory_range 0x253B,46`; байты `94 35 | 00 00 16 01 E1 01 …`):

`0, 278, 481, 800, 1053, 1401, 1713, 2049, 2355, 2675, 3051, 3230, 3584, 3788, 4140, 4345, 4678, 4898, 5119, 5480` — 20 строго возрастающих LE-слов, `0x253D..0x2564`.

*Почему это таблица, а не stride.* `analyze.table_shape` по `0x253D/40`: `monotonic{width:16,endian:little,count:20,up_share:1.0,first:0,last:5480}`, `pointers{stride:2,count:20,distinct:20,rom_share:0.95}`, `linear_fit{slope:292.594,max_residual:148.803,`**`exact_integer_strides:[]`**`} → candidate_kind `pointer_table/CANDIDATE`. Пустой `exact_integer_strides` — это и есть формальное «нет постоянного шага».

*Граница таблицы:* следующий байт `0x2565 = 0xCD` — opcode `CALL`, т.е. там уже код; длина 40 байт подтверждена и `LXI H,253D` (начало) и отсутствием `JNZ`-ветки, читающей дальше.

## 3. Цикл обхода и формат тайла

```
0x24F0 LDAX D           ; P = очередной упакованный байт   ┐ метка lbl_24f0
0x24F1 MOV  C,A
0x24F2 ANI  0F          ; B = P & 0x0F   = ДЛИНА ПОВТОРА (0 ⇒ 256)
0x24F3 MOV  B,A
0x24F4 STA  082A        ; кэш-ячейка (idiom LDA/STA 082A — no-op)
   … 4× (ORA A; RAR; MOV C,A) …   ; C = P >> 4 = КОД ТАЙЛА
0x251D MVI  A,60
0x251E ADD  C           ; глиф = 0x60 + код
0x2521 CPI  6F
0x2523 JNZ  2527
0x2526 MVI  A,20        ; код 0x6F → пробел (пусто)
0x2527 MOV  M,A         ; ┐ метка lbl_2527: внутренняя петля повтора
0x2528 INX  H           ; │
0x2529 PUSH PSW         ; │
0x252A DCR  B           ; │
0x252B JZ   2532        ; │
0x252E POP  PSW         ; │
0x252F JMP  2527        ; ┘
0x2532 POP  PSW         ; ┐ метка lbl_2532
0x2533 INX  D           ; │ следующий упакованный байт
0x2534 MOV  A,H         ; │
0x2535 CPI  73          ; │ стоп, когда HL достиг 0x7300
0x2537 JNZ  24F0        ; ┘
0x253A RET
```

**Размерность и «байт на тайл».** Стоп-условие — старший байт `HL = 0x73` при `L = 00`; старт `HL = 0x7040`, значит записано **ровно 0x2C0 = 704 клетки**. Поле — `22 ряда × 32 клетки`, шаг ряда `0x20`, строка-major, `0x7040..0x72FF` (полные `0x7000..0x72FF` = 768 байт = 24 ряда × 32; первые два ряда — служебные, см. §4). **В RAM 1 байт на тайл**; в ROM — **1 байт на RLE-пару** (не на тайл): мл. ниббл = длина повтора (0 ⇒ 256), ст. ниббл = код тайла, код → `0x60+код`, `0x6F` → `0x20`.

Независимая проверка формата по статистике блока (`analyze.table_shape 0x3594/5715`): `zeros=0`, а топ-значения байт — `0xB1×1501, 0xF1×622, 0x51×455, 0xF2×372, 0x54×280, 0x52×196, 0xD1×187, 0x11×186`. Во всех доминирующих байтах мл. ниббл ∈ {1,2,4} — короткие повторы; старшие нибблы `B,F,5,D,1` = как раз самые частые тайлы (`k`, пусто, `e`, `m`, `a`). Двухбайтовые записи (`period 2`) не подтверждаются: `equality_ratio 0.294`, нулей в блоке нет вовсе.

Алфавит тайлов по всем 20 развёрнутым картам (суммарное число клеток `14080 = 20×704` — т.е. ни одной лишней/потерянной клетки):

`0x20` (пусто) ×5406, `0x60` (маркер старта) ×20, `0x61`×897, `0x62`×507, `0x63`×18, `0x64` (цель) ×36, `0x65`×3440, `0x66`×623, `0x67`×20, `0x68`×307, `0x69`×17, `0x6A`×18, `0x6B`×1639, `0x6D`×359, `0x6E`×773 — итого 14080. Ровно по одному `0x60` на карту (20/20) и 1 или 2 `0x64` на карту (4×1 + 16×2 = 36) — см. §4. Код `0x6C` не встречается, `0x6F` в карты не упакован (он и есть «пусто»-код 15 → `0x20`).

Степень упаковки по уровням: `704/len` = от **1.9×** (L10, 376 байт) до **3.9×** (L11, 179 байт).

**Про растеризацию.** Загрузчик в VRAM/знакостраницу **не пишет** — только коды в поле. Дальше карта живёт как текстовая сетка: обе функции-искателя (§4) для стирания маркера вычисляют адрес знакостраницы **линейно тем же индексом** — `LXI D,5400; DAD D; CALL 0124` (`0x0124` принимает адрес в `HL`, внутри `MOV M,A` и `CZ 0551` при `H∈{54,55,56}`), т.е. буфер поля `0x7000..0x72FF` и знакостраница `0x5400..0x56FF` используются как **линейно-эквивалентные** сетки 24×32 с шагом 32. Сама отрисовка глифа — цепочка Stage 6, здесь не переследовалась.

## 4. Координаты спавна и цели («выхода»)

Маркеры не хранятся в заголовке карты — они **ищутся в развёрнутом поле**:

| | старт игрока | цель / «выход» |
|---|---|---|
| тайл | `0x60` (код 0) | `0x64` (код 4) |
| кто ищет | `func_find_player_start @0x2034` | `func_find_scroll_target_cell @0x2136` (`CPI 64 @0x213D` — единственный в ROM) |
| кодировка | `X = индекс & 0x1F`, `Y = индекс >> 5` (сдвиг через `RAL`, отсчёт от `0x7000`; ряд поля = `Y−2`) | то же |
| куда пишет | `0x7C00` (`var_player_x`), `0x7C01` (`var_player_y`) | scratch `0x7C21/0x7C22` (дубли `0x7C25/0x7C26`) → слоты `0x7D11/0x7D12` и `0x7D31/0x7D32` |
| после чтения | маркер стирается (`MVI A,20; MOV M,A`) + затирка клетки знакостраницы (`CALL 0124`) | то же |
| счётчик | ровно **1 на уровень** (`0x60`×20 по всем картам) | **1 или 2**: `var_scroll_target_count [0x7C55] = 1` на L01..L04, `= 2` на L05..L20; всего `0x64`×36 = 4·1 + 16·2 ✓ |

Менеджер слотов — `func_clear_scroll_params @0x20EC`: очистка `0x40` байт от `0x7D11`, `STA 7C56`, `CALL 2136`, `LXI H,7C56; INR M; RZ`, затем `0x2109 MVI A,01; 0x210B STA 7C55` и копирование `31` байта `0x7C21→0x7D11` (`LXI B,001F; CALL 12E0`); второй проход — `0x211C CALL 2136; 0x211F LDA 7C56; 0x2122 ORA A; 0x2123 RNZ`, `0x2124 MVI A,02; 0x2126 STA 7C55`, `0x212C LXI D,7D31` → `0x7D31/0x7D32`. Если цель не найдена, `0x2136` выставляет `0x7C56=0xFF` и записывает сторож `(X,Y)=(0,24)`.

Потребитель: в области `0x0EC0` позиция игрока сравнивается с `[0x7D12]/[0x7D11]`, затем с `[0x7D32]/[0x7D31]`, и совпадение даёт `JMP 0x106A` — тот же обработчик, что у «разрабатываемых» клеток (`0x65/0x67/0x63`).

**Runtime-подтверждение (уровень 1, естественный проход, BP на `0x253A`):** `[0x7C66]=1`; после загрузчика `HL=0x7300`, `DE=0x36AA` (потреблено 278 байт); `[0x7C00]=2, [0x7C01]=2` ⇒ старт col 2, row 0; `[0x7D11]=15, [0x7D12]=3` ⇒ цель col 15, row 1; `[0x7D31..]=0`, `[0x7C55]=1`, `[0x7C56]=0xFF` ⇒ одна цель; ряды поля `0x7040` и `0x72C0` побайтово совпали с моделью.
**Runtime-подтверждение (уровень 13, форсированный вызов):** `DE=0x4460` (= `0x4394+204`), `HL=0x7300`, ряды 0 и 20 поля — снова побайтовое совпадение с моделью.

## 5. Границы блока и тождество размеров

Длины карт = разности соседних смещений (`len_i = off[i+1] − off[i]`, i=1..19), у последней — по стоп-условию загрузчика и подтверждено runtime:

`278, 203, 319, 253, 348, 312, 336, 306, 320, 376, 179, 354, 204, 352, 205, 333, 220, 221, 361, 235` (min 179 @L11, max 376 @L10); **Σ len = 5715 = 0x1653**.

*Форма ТЗ* `LEVEL_COUNT × stride == data_next_addr − data_level_maps_addr`:
- `stride` как константа **отсутствует** (см. §2) ⇒ в буквальном виде тождество неприменимо: `20 × 285.75 = 5715`, но `stride=285.75` нецелый и в коде не встречается;
- *обобщение префикс-сумм* (то же самое утверждение для таблицы смещений):

```
data_next_addr − data_level_maps_addr = 0x4BE7 − 0x3594 = 5715 = Σ len(level_i)   ✓
offset[19] + len(level_20) = 5480 + 235 = 5715                                    ✓
```

Границы подтверждены тремя независимыми способами:
1. **Прямое чтение**: `debug_read_memory_range 0x253B,46` (смещения + база), дамп `0x3594` и `0x4BE2` (хвост L20).
2. **Выполнением**: BP `0x253A` при `var_level=20` ⇒ `DE=0x4BE7`; при `var_level=13` ⇒ `DE=0x4460`. Т.е. `0x4BE7` — это реально первый байт **после** последней использованной карты, а не оценка «на глаз».
3. **`analyze.measure_sizes --types data,table`**: 33 объекта в окне, `warn=0`, у всех `data_level_*` `declared_end+1 == address` следующего и `slack_bytes=0`, `crosses_end_by=0` (блок `0x36AA..0x4BE6` непрерывен без единого зазора); 19 находок — только INFO `object-nested` («`data_level_maps (0x3594+5715)` накрывает `data_level_02…20` целиком»), что и замыслино правилом «один адрес — один объект». Verdict модуля: «19 расхождений(я) размера из 33 объектов», status `CANDIDATE`.

Что сразу за `0x4BE7`: `debug_find_immediate_in_range(0x4BE7)` → **0 совпадений**; следующий адресный сайт — `LXI H,4BF4` (`0x28A1`, единственный на `0x4BF4`). Зазор `0x4BE7..0x4BF3` (13 байт) ничем не адресован — см. Limitations.

## Verified Facts

1. `func_level_loader = 0x24CF` (size 108); вызывается из `func_start_new_level @0x1FAD` (`CALL 0x24CF` в `0x1FB0`) и из `func_game_over_high_score @0x223C` (`0x226C`).
2. Формула адреса: `addr = [0x253B] + word[0x253D + 2·(var_level−1)]`, `[0x253B] = 0x3594`; момент вычисления — `0x24EB DAD D`, источник/приёмник разведены к `0x24ED`.
3. `LEVEL_COUNT = 20` — двумя независимыми признаками: обёртка `0x24D2 CPI 15` и 20 строго возрастающих слов в таблице `0x253D..0x2564`.
4. Постоянного `stride` нет: длины карт `179..376`; `table_shape.exact_integer_strides = []`.
5. Формат карты — RLE по 1 байту: `count = P & 0x0F` (`0 ⇒ 256`), `tile = 0x60 + (P >> 4)`, `0x6F → 0x20`; в поле — **1 байт на тайл**; сетка `22×32 = 704` клетки, `0x7040..0x72FF`, шаг ряда `0x20`; выход цикла — `HL=0x7300`.
6. Все 20 карт разворачиваются ровно в 704 клетки без переполнения (модель + runtime L01/L13/L20: каждый раз `HL=0x7300`).
7. Координаты: `X = индекс & 0x1F`, `Y = индекс >> 5` от `0x7000`; старт из тайла `0x60` → `0x7C00/0x7C01` (по 1 маркеру на карту, всего 20); цель из тайла `0x64` → `0x7C21/0x7C22` → слоты `0x7D11/0x7D12` и `0x7D31/0x7D32`; количество целей `0x7C55 ∈ {1,2}`, всего `0x64`×36 = 4+32 ✓.
8. Граница блока: `data_next_addr = 0x4BE7` (runtime: `DE` в момент `RET` для L20), тождество `Σ len = 5715 = 0x4BE7 − 0x3594` выполняется в префикс-суммовой форме; `measure_sizes`: 0 warn, `slack=0`, `crosses=0`, непрерывная цепь `0x36AA..0x4BE6`.
9. Байт `0x4BE7` не является операндом ни одной инструкции диапазона `0x0100..0x50FF` (`debug_find_immediate_in_range` → 0 совпадений).
10. RDB сохранён: 11 вызовов `debug_save_rdb`, `dirty=false`, `object_count=479`; связи проверены чтением сохранённого файла и `debug_get_rdb_links`.

## Inferences (не факты, но с указанием опоры)

1. **`0x64` = «выход» уровня.** Доказано: это целевая клетка, позиция игрока сравнивается с `0x7D11/0x7D12` и `0x7D31/0x7D32`, совпадение ведёт в `0x106A` (тот же обработчик, что у разрабатываемых клеток `0x65/0x67/0x63`). Не доказано, что именно это завершает уровень. Косвенный намёк на иной триггер — `LDA 7C01; CPI 01; RZ` в главном цикле (`0x09E0..0x09E5`), т.е. отдельное состояние при `Y=1` (ряд над картой). Трактовка «выход» взята из ТЗ/жанра, а не из байтов.
2. **Семантика остальных тайлов** (`0x61..0x6E`) как «платформа/грунт/бонус» — из частот и из обработчиков `0x0DB0/0x0EC0`; соответствие «код ↔ рисунок глифа» в Stage 7 не проверялось.
3. **Назначение scratch-дублей `0x7C25/0x7C26`** — координаты в составе 31-байтной структуры, копируемой в слоты; почему дублируются — не установлено (объектов не заводил, зафиксировано в комментариях `0x7C21/0x7C22`).
4. **Поле = линейное зеркало знакостраницы** (`0x5400 + индекс поля`) — вывод из `LXI D,5400; DAD D; CALL 0124`, а не из документации по железу.

## Limitations

1. **Зазор `0x4BE7..0x4BF3` (13 байт) не атрибутирован.** Не относится к потреблённому потоку L20 (runtime `DE=0x4BE7`) и не адресовано ни одной инструкцией; следующий адресуемый блок — `0x4BF4` (`LXI H,4BF4 @0x28A1`). Варианты: выравнивающий паддинг, мёртвый хвост записи L20, данные без адресного сайта. *Эксперимент:* трасса `debug_get_memory_access_map`/`debug_get_memory_access_log` полного прохождения 20 уровней (если существует путь загрузки, кроме `func_level_loader`) + поиск вторых источников чтения `0x4BE7..` (например, `INX H`-прогулки по указателю, где базовый регистр загружается из `0x4Bxx` как младшая часть).
2. **Runtime-проверка развёртки сделана для 3 уровней из 20** (L01 побайтово, L13 побайтово + длина, L20 длина/граница). Для остальных 17 длины получены из таблицы смещений и из модели остановки по `HL=0x7300`. *Эксперимент:* цикл «`[0x7C66]←N`, `PC←0x24CF`, BP `0x253A`» для N=2..19 c чтением `DE` и сравнением с ожидаемым `base+offset[N]`.
3. **Координаты спавна/целей 19 уровней — из статической модели**, runtime-подтверждены только L01 (`0x7C00/0x7C01 = 2,2`; `0x7D11/0x7D12 = 15,3`) и косвенно L13/L20 (через `DE`/`HL`). *Эксперимент:* тот же форсированный вызов + `CALL 0x2034`/`CALL 0x20EC` и чтение `0x7C00,0x7C01,0x7D11,0x7D12,0x7D31,0x7D32,0x7C55`.
4. **Линейная vs блочная адресация знакостраницы.** Stage 6 дал формулу `0x5400 + 256·(row>>3) + 32·(row&7) + col`, а загрузчик/искатели используют `0x5400 + индекс` (линейно, шаг 32). Для рядов ≥ 8 это разные клетки. В Stage 7 не разрешалось. *Эксперимент:* уровень с целью в ряду 16 (например L11, цели `(14,16)`/`(16,16)`) — снять `debug_get_vram_bytes`/`debug_get_screen_snapshot` до и после стирания маркера и посмотреть, в какой визуальной строке исчез глиф.
5. **`0x6C` и часть кодов (`0x63,0x67,0x69,0x6A`) встречаются редко** (`18,18,20,17,18` раз); их роль не исследовалась — это не Stage 7 (по ТЗ здесь только адрес карты, цикл и спавн/выход).
6. **Точное число целей, обрабатываемых игроком, ≤ 2** — следует из `func_clear_scroll_params` (два слота). Есть ли карты с третьей клеткой `0x64` — отрицательный факт по текущему разбору (максимум 2 на карту), но «что делает ROM с третьей, если бы она появилась» не проверялось.
