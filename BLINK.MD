# BLINK.MD — исследование остаточного мерцания движущихся объектов (putup)

## Постановка

После внедрения VBlank-синхронизации (`EI; HLT` перед стиранием тайла — см. ниже)
мерцание героя/врагов **уменьшилось, но не исчезло**: при движении всё равно
заметны редкие «помигивания». Нужен детальный разбор — **где именно находится
электронный луч в момент каждой записи в VRAM** при перерисовке движущегося
объекта, и почему всплеск записи не целиком попадает в окно гашения.

Это задача **исследования + доводки**, а не с нуля: текущий механизм синка
оставляем как базу и проверяем гипотезы ниже.

## Что уже сделано (база)

Прямые записи в живую VRAM делают две функции (пишут 4 глифа = 4 плоскости):

| функция | адрес | что пишет |
|---|---|---|
| `func_draw_tile_at_ptr` | 0x0104 | стирание (erase) тайла по прошлой позиции |
| `func_render_tile_vram` | 0x1BA8 | рисование тайла по новой позиции |
| `func_render_glyph` | 0x0803 | низший уровень; внутри `DI … EI; RET` |

`func_render_glyph` защищает запись только от **маскируемых прерываний** (`DI`),
но **не от положения луча** — если луч в этот момент сканирует строку, глаз ловит
незавершённый кадр → мерцание.

Добавлены трамплины в слот `func_load_glyph_block` (@0x0401, мёртвый распаковщик):

```
sync_draw_tile_at_ptr:  EI ; HLT ; JMP func_draw_tile_at_ptr   ; 0x0401
sync_render_tile_vram:  EI ; HLT ; JMP func_render_tile_vram    ; 0x0406  (пока не зовётся)
```

`EI` включает прерывания, `HLT` глушит ЦП до ближайшего кадрового прерывания
`RST7 → func_vblank_isr` (@0x03A4, срабатывает в **начале** вертикального гашения).
Проснувшись внутри blanking, трамплин исполняет оригинал.

Синхронизированы **только erase-вызовы** (стирание), draw идёт сразу за ним без
отдельного `HLT` — чтобы стир+рисование одной ячейки легли в одно окно гашения:

| файл | адрес erase (sync) | адрес draw (без sync) |
|---|---|---|
| `func_game_update.asm` (герой) | 0x0D9B | 0x0DB5 |
| `func_draw_game_objects.asm` (3 объекта) | 0x132C / 0x135C / 0x138C | 0x1346 / 0x1376 / 0x13A6 |
| `func_entity_state10.asm` | 0x193B | 0x1955 |
| `func_level_loader.asm` (статич. сборка уровня) | синка **нет** (0x1AE7/0x1B01/0x1B34/0x1B4E) | |

## Гипотезы остаточного мерцания (проверять по порядку)

1. **Всплеск длиннее окна гашения.** Erase+draw одной ячейки ≈ 4 глифа по 4
   плоскости (в заголовке трамплина оценка ~11K T). Если вертикальное blanking
   короче этого времени, **хвост** записи уже попадает в активную развёртку —
   мерцает нижняя часть тайла. → Замерить: длительность blanking в T против
   длительности burst'а erase+draw.

2. **Разнесение объектов по разным кадрам.** В одном проходе главного цикла
   (`lbl_main_game_loop` @0x0E85) героев/объектов до 4-х, и у каждого **свой**
   `EI; HLT`. Первый erase ждёт vblank N, второй — уже vblank N+1 (спустя ~20 мс),
   третий N+2… То есть за один «тик» обновления разъезжаются по нескольким кадрам,
   а draw каждого объекта стартует из разной точки луча. → Проверить, сколько
   `HLT`/кадр и где луч на каждом.

3. **Прямая запись в отображаемую страницу.** Игра использует переворот страниц
   (`var_page_flip` @0x08FA). Если тайлы пишутся в ту страницу, которую сейчас
   сканирует луч, синк к vblank лишь *уменьшает* окно видимости, но не устраняет
   принципиально. Кандидат на корректное решение — **рисовать в теневой back-buffer
   и сделать полный blit/переворот на vblank** (двойная буферизация), а не патчить
   прямые VRAM-записи. → Оценить объём изменений.

4. **Позиция луча после wake-up не гарантирована.** Возврат из `func_vblank_isr`
   (музыкальный тик, OUT портов) добавляет джиттер: реальная строка, на которой
   возобновляется код, может плыть от кадра к кадру. → Замерить разброс.

## Методика исследования (MCP `vector-debugger`)

Инструменты для съёма доказательств (схема: загрузить `PUTUP_NEW.ROM`, дойти до
геймплея, двигать героя/врагов):

- `debug_set_breakpoint` на `func_draw_tile_at_ptr` (0x0104) и
  `func_render_tile_vram` (0x1BA8) — ловить каждый redraw движущегося объекта.
- `debug_get_screen_info` / `debug_get_raster_events` — **номер строки луча** в
  момент срабатывания брейкпоинта и в момент фактической записи (проверить, в
  blanking ли мы или в активной развёртке).
- `debug_get_cpu_state` — `PC`, `IFF` (включены ли прерывания) на входе в запись.
- `debug_get_memory_access_log` / `debug_get_vram_bytes` — зафиксировать адреса
  плоскостей и порядок байт-записей внутри burst'а (4 глифа × 4 плоскости).
- `debug_get_int_events` — моменты `RST7`/vblank, чтобы привязать burst к кадру.
- Замер длительностей: `debug_get_instruction_history`/счётчик T вокруг burst vs
  расстояние между соседними vblank (окно гашения).

Регрессионная база (не должна сломаться при правке): `make verify`,
`python3 tools/lint_ptrs.py`, `python3 tools/compare_color.py --label <TAG>`,
`python3 tools/compare_behavior.py`. **Важно:** `compare_color` кадрирует только
title/play1/play2 и **не ловит момент мерцания** — он не является мерой успеха
этой задачи; критерий — визуальный + инструментальный (луч в blanking на всех
записях).

## Кандидаты решения (после замеров)

A. **Один vblank-синк на весь кадр:** собрать erase+draw всех объектов в один
   батч после единственного `EI; HLT` (а не по `HLT` на объект) → все записи в
   одном окне гашения, без разъезда по кадрам (снимает гипотезы 2 и частично 1).
B. **Двойная буферизация:** redraw в теневую страницу + blit/`var_page_flip` на
   vblank → eliminate прямых записей в сканируемую VRAM (снимает 1 и 3 полностью;
   дороже по объёму, может изменить поведенческий профиль).
C. **Коррекция тактов:** если burst чуть длиннее blanking — либо разбить burst,
   либо подстроить `func_delay`, либо начать запись раньше (синк на рисовании, а
   не на стирании) — по итогам замеров.

## Acceptance

- При одновременном движении героя и ≥2 врагов **нет видимых помигиваний** на
  глаз и по инструментальной проверке (все VRAM-записи redraw'а падают в окно
  гашения).
- Темп игры приемлемый (не хуже текущего; при необходимости — осознанная
  подстройка `func_delay`).
- Все регрессионные гейты зелёные; расхождения с оригиналом — только разрешённые
  (allow-list в `tools/verify_image.py`).
