# ТЗ: подсистема вывода спрайтов с синхронизацией с лучом (`lib/` — «beam», API-префикс `beam_`)

Документ — задание на проектирование. Цели, правила для игр, контракты и
приемка сформулированы так, чтобы подсистема **прямо сейчас** вобрала весь
наработанный опыт putup-«гонки луча» (BLINK.MD, растер-гарды, Этап 1 огня,
гейты e2/e3/e4, инструменты beam_*).

**Редакция 2.** Пиксельный blit реализован библиотекой
[lib/gfx/spr.asm](../../../lib/gfx/spr.asm) (спека формата —
[docs/SPR_FORMAT.MD](../../../docs/SPR_FORMAT.MD), замеры —
`roms/tests/spr-speed`, потребительское демо — `roms/tests/spr-demo`).
Область ТЗ сужена: **beam — только планировщик/пейсер** (OAM-подобная
таблица экземпляров, тени, diff→план по рядам, behind-the-beam исполнение,
бюджет), а пиксели пишут готовые ядра `spr_blit`/`spr_blit_mask`. Всё, что
в редакции 1 касалось технологии записи байта/композита/pre-shift кешей
сдвигов, — закрыто форматом SPR_FORMAT и из ТЗ исключено.

---

## 1. Постановка задачи

### 1.1 Цели
1. **Гарантия отсутствия мерцания/tearing**: ни одна запись в видимую область
   VRAM не совершается, пока луч сканирует полосу записываемого ряда.
2. **Упрощение разработки игр**: игра объявляет спрайты-дескрипторы один раз
   (загрузка уровня) и в игровом цикле меняет **только позиции и кадры
   анимации**. Вся растер-магия, erase, бюджеты, атомарность — внутри
   подсистемы. Аналог по интерфейсу — аппаратные спрайты NES (OAM), где игра
   пишет 4-байтные записи, а «железо» рисует.
3. **Детерминированный темп**: длительность кадра = высота кадра (312 строк),
   не зависит от числа обновлений; никаких «плавающих» просадок темпа.

### 1.2 Нецели (осознанно вне области)
- **Пиксельная отрисовка спрайта** — не beam: это `spr_blit`/`spr_blit_mask`.
  beam обязан использовать их как единственный writer, а не писать байты сам.
- Аппаратный странипереворот VRAM на Vector-06C **отсутствует** — подсистема
  его не эмулирует «целой страницей», только покадровую консистентность.
- Полноэкранная анимация тайлмапа 50 Гц (бюджет растра это не позволяет,
  см. §7); широкие анимируемые ряды — с частотой, которую задаёт игра.
- Звук/музыка: подсистема только **не мешает** вокабулятору (см. НФ-5).

### 1.3 Известные факты платформы (замерено, не принято на веру)
| Факт | Число | Источник |
|---|---|---|
| Тиков ВИ53 на строку растра / строк в кадре | 96 / 312 (=0x7500) | `lib/timer`, модель beam_state |
| Виден. поле: строки растра | 24..280 | BLINK.MD «Калибровка» |
| Полоса ряда `row` (8 глифов) | растр-линии 48+8·row .. +15 | BLINK.MD, проверено диффом VRAM |
| Фаза: `beam_line − elapsed/96` | мед +5,3 строки, константна | BLINK.MD (ISR ack latency) |
| `spr_blit` 16×24 (3 столбца, 2 плоскости, ~168 записей VRAM) | 4208T = 43,8 строки | spr.asm/шапка, spr-speed |
| `spr_blit_mask` тот же спрайт (~168 записей) | 7274T = 75,8 строки | spr.asm/шапка, spr-speed |
| Удельная цена записи VRAM: blit / mask | ≈25T/байт (24T лесенка) / ≈43T/байт (53T лесенка) | spr.asm (кол_copy/col_or) |
| ОЗУ-собственность spr.asm: лесенки | 0x7000..0x7081, 0x7100..0x7203 | spr.asm/шапка |
| Пределы геометрии спрайта | LEN ≤ 32 (blit), ≤ 28 (mask); x кратен 8; y — пиксельная строка верха | spr.asm, SPR_FORMAT.MD |
| DI дольше ~500..900T ломает музыку (VBlank-секвенсор) | — | история title-music slowdown |

Исторические putup-замеры (func_render_glyph ~12 строк, OR 2×2 ~71, OR3
~105, инстанс героя 101..137 строк) оставлены как справка для этапа
портирования (§9 Э6): путь через spr-ядра дешевле (тот же герой-класс
75,8 строки вместо 101..137).

## 2. Архитектура

### 2.1 Хранилища (как в NES: pattern table / OAM / фон)
1. **Библиотека спрайтов** (ROM уровня): каждый спрайт — дескриптор
   SPR_FORMAT `[FLAGS, COLS, DEPTH] + (TABLE) + DATA`, выводимый
   `spr_blit` (плоский) или `spr_blit_mask` (бит4 FLAGS — OR-композит
   `dst = (dst AND mask) OR color`). **Маска — часть дескриптора** (первый
   блок DATA, TABLE общая): отдельное хранилище масок редакции 1 упразднено,
   плоскость VRAM под маску не занимается. Субпиксельные X-варианты —
   дополнительные дескрипторы, собранные build-time (см. §3.3).
2. **Библиотека фоновых клеток** (ROM уровня): тайл фона 8×8 — плоский
   дескриптор SPR_FORMAT (1 столбец, plane-major, до 32 байт/плоскость),
   индекс = код тайла. Тот же `spr_blit` служит и erase-до-фона: beam
   вызывает его с дескриптором клетки из тайлмапа.
3. **Таблица экземпляров** (RAM, аналог OAM, 4 байта на спрайт):
   `{ u8 y; u8 x; u8 pat; u8 flags; }`, `pat=0xFF` — скрыт. `x` — пиксельный,
   кратный 8; `y` — пиксельная строка верха спрайта (конвенция spr-ядер).
   `flags`: бит0 — путь вывода (0 = `spr_blit`, 1 = `spr_blit_mask`). Плюс
   **тень последнего commit** `{ y, x, pat }` на экземпляр — по ней
   планировать erase.
4. **Тайлмап фона** (RAM/ROM уровня, 1 байт кода на клетку поля 8×8):
   источник erase-до-состояния-фона. Статичен на уровне; правится только
   через `beam_bg_put`.

### 2.2 Конвейер кадра (технология вывода — ядра spr.asm)
```
 VBlank(RST7)  timer_start()                       ── кадр 0
 |             [игра: kbd, логика, анимация — пишет только таблицу экземпляров]
 |  beam_update()  diff(экземпляры vs тень) -> план по рядам:
 |                   на каждый грязный ряд: список erase-записей + draw-записей,
 |                   оценка стоимости в строках растра (см. §4)
 |  beam_render()  ИСПОЛНЕНИЕ ПЛАНА, отсортированное по рядам СВЕРХУ ВНИЗ,
 |                   в такт лучу (см. §3.1): каждый ряд пишется только когда
 |                   луч уже ниже его конца (elapsed >= bot(row)) — «behind-the-beam
 |                   pacing». Пиксели пишет spr_blit/spr_blit_mask. Возврат к
 |                   концу кадра; недописанные ряды — в план следующего кадра
 |                   (флаг перерасхода).
 |  ... остаток бланкинга свободен музыке/вводу ...
 VBlank(RST7) ── кадр 1 (тени обновлены -> вид консистентный кадр)
```
Игровой контракт цикла (и есть «конструктор»):
```c
for (;;) {
    v06_wait_frame();
    game_logic();          // ТОЛЬКО beam_move/beam_show/beam_hide/beam_bg_put
    beam_update();
    beam_render();         // блокирует до конца кадра — темп = 50 Гц всегда
}
```

### 2.3 Что замещает в существующих играх
Подсистема инкапсулирует и обобщает: `func_render_glyph`+`data_vram_col_table`
(адресация — теперь внутри spr-ядер), `func_raster_guard_hero/_enemy/_row`
(+атомарность ряда), `func_hero_repaint_over`/erase-dispatch (тени),
E1/E2/E3 pre-shift кеши (упразднены: субпиксель = варианты дескрипторов,
§3.3), `data_flip_tab`-анимацию (фазы паттернов), chunked-скан (`beam_update`
= diff, не слепой скан), OR-композит героя с маской П0 (маска — блок
дескриптора `spr_blit_mask`, плоскость освобождается).

## 3. Технология планирования: правила принятия решений (НФ-1…НФ-5 = §3.1…§3.5)

### 3.1 Базовое правило записи (НФ-1, ядро гарантии)
Для каждого ряда плана запись разрешена **только** при
`elapsed >= bot(row)`, где `bot(row) = TIMER_LINES(48 + 8·row + 8)`, ИЛИ при
условии `top(row) − elapsed − BEAM_LEAD > row_cost + MARGIN_MIN`
(«успеем до луча» с запасом; `BEAM_LEAD = 6 строк` — калибровочные +5,3,
MARGIN_MIN ≥ 8 строк). **Деградация всегда к behind-the-beam**: если
оценка сомнительна — ждём прохода.

Следствия (все — уроки putup, зашитые как инварианты):
- **Ряд-атомарность по всем полосам спрайта**: спрайт высотой >8 px пересекает
  несколько рядов, но пишется ОДНИМ вызовом ядра (столбец целиком). Решение
  (§3.1) принимается ОДИН раз на спрайт по его **нижней** полосе
  (`row = (y + h − 1) / 8`) и не пересматривается. Никаких per-cell решений —
  они дают «плывущий» двухфазный шов (Этап 0 огня).
- **Целый спрайт за один проход луча**: если спрайт не влезает в остаток кадра
  по бюджету — переносится ЦЕЛИКОМ в следующий кадр; частичная запись спрайта
  запрещена (консистентность важнее отзывчивости; константа задержки +1 кадр
  предпочтительнее рваных швов). Ряд в плане считается грязным, пока хоть один
  его спрайт не закоммичен.
- **Единственное пересечение**: ряды обрабатываются сверху вниз в такт лучу —
  поток записей догоняет луч ровно сзади и никогда не пересекает его
  повторно; «резонанс» из нескольких пауз на кадр структурно невозможен,
  потому что пауза — не блокировка, а пейсинг (логика уже закончена).
- **Широкие анимируемые ряды** (типа огня в putup) попадают в
  behind-the-beam-ветку автоматически и пишутся за второй «хвост» того же
  кадра — с гарантией одной фазы.
- **Стоп-лист**: никакой активной загрузки в бланкинг как основного режима
  (бланкинг мал, ~26+32 строк, и музыкальный секвенсор там же). Бланкинг —
  только для `beam_init`/полных перерисовок уровня.

### 3.2 Erase/draw порядок
В ряду: сначала все erase — `spr_blit` плоских дескрипторов фоновых клеток
(по теням: код из тайлмапа; порядок — чтобы не трогать клетки, которые в этом
ряду же перерисовываются тем же рядом draw), затем draw по приоритету
(младшие — раньше, старшие поверх). Пересечения спрайтов одного ряда
разрешаются:
- плоским overwrite по приоритету (`spr_blit` — дёшево, ~25T/байт записи);
- OR-композитом по маске дескриптора (`spr_blit_mask`, флаг экземпляра):
  erase под таким спрайтом **не нужен** (фон вне силуэта сохраняется самим
  композитом), цена ~43T/байт — **лимит: ≤ 2 mask-инстанса на кадр**
  (паспорт §4).
Маскированная запись требует x кратного 8 и LEN ≤ 28; плоская — LEN ≤ 32
(ограничения ядер, проверяются на загрузке уровня, не в кадре).

### 3.3 Субпиксельные позиции (4 px)
Сдвиги ±4px по X — только **дополнительные дескрипторы, собранные build-time**
генератором спрайтов (модель `gen_spr.py` из `roms/tests/spr-demo`): паттерны,
для которых сдвиги запрошены (`flags` паттерна), получают до 4 вариантов
`[FLAGS, COLS, DEPTH]`-записей; столбцовая геометрия SHIFT/LEN позволяет
сдвигать содержимое без побитовой математики. Запрет на пересборку/перекодировку
в кадре (урок E3: 407 строк). `beam_move(x, y)` принимает байтовую сетку
(x кратен 8); суб-шаг выражается выбором сдвинутого варианта дескриптора —
план для подсистемы неотличим от обычного. Сдвиг по Y ядра принимают напрямую
(y — пиксельная строка), precompute не нужен.

### 3.4 Анимация
Фаза (кадр анимации) — поле экземпляра или per-pattern счётчик каденции
(`anim_every_n_frames` в дескрипторе уровня). Смена дескриптора выполняется
как обычный move: через план, рядом-атомарно. Широкие анимируемые поля
(огонь/мерцание) не требуют игровых сканов — они штатные паттерны.

### 3.5 Защита от аномалий
- `timer_wait` уже завершается при переполнении счётчика (кадр упущен) —
  scheduler обязан корректно перенести хвост плана на следующий кадр
  (done-флаг на ряд), без зависаний и без записи ряда «вразнобод».
- Полный стоп-двигатель (загрузка/сбой секундомера, `var_raster_flag`=0 на
  заставке): режим `BEAM_OFF` — записи только в бланкинг, с полным
  перерасходом кадра (устаревший титульный путь exolon/putup). Явный флаг
  уровня: `beam_sync = 0/1`.
- Антизацикливатели вроде `var_raster_cap` сохраняются как debug-assert
  сборка (в релизе — assertion-free, пейсинг не может зациклиться, см. §3.1).
- **Монополия на ядра**: `spr_blit`/`spr_blit_mask` работают через глобальные
  курсоры spr.asm (`_sb_*`) и не реентерабельны. Единственный вызывающий в
  кадре — `beam_render`; вызовы spr-ядер из игры вне окна рендера запрещены
  (ТФ-1).

## 4. Бюджет растра (паспорт стоимости)

Правило планирования: стоимость записи = ΣLEN дескриптора × удельная цена
(≈0,26 строки/байт записи blit, ≈0,45 — mask; калибруется на Э0 таблицей
`beam_cost`, в прошивке — константы) + накладные плана. Опорные замеры
(уже есть, `roms/tests/spr-speed`):

| Операция | Строки | Комментарий |
|---|---|---|
| `spr_blit` 16×24, 3 столбца, 2 плоскости (~168 записей) | 43,8 | 4208T |
| `spr_blit_mask` тот же спрайт | 75,8 | 7274T |
| фоновая клетка 8×8 (erase, 1 столбец, 1 плоскость, ≤32 байта) | ≤ 8,3 | ~800T |
| guard/план решения на ряд | ≤ 2 | настраиваемый, не >1% бюджета |

Кадровый бюджет: 312 строк; резерв: логика/музыка/опрос клавиатуры ≤ ~90;
=> **потолок спрайт-рендера ≈ 200-220 строк/кадр**. Типовые допущения
конструктора: до ~20-25 движущихся спрайтов «герой-класса» 16×24×2 в
flat-пути ИЛИ до 2 mask-инстансов «герой-класса» + 10-12 flat. Перерасход
-> отброс целых инстансов по политике приоритета round-robin (мерцание всего
спрайта лучше шва на ряду; как 8-на-строку в NES) + `beam_overbudget() != 0`
для диагностики.

## 5. API (декларации в `v06.h`, реализация `lib/gfx/beam.c` + `beam.asm`)

Модуль живёт в `lib/gfx/` — часть графической подсистемы, поверх
существующего `lib/gfx/spr.asm`; линкуется вместе с ним и `lib/timer`.

```c
/* --- загрузка уровня ---------------------------------------------------- */
typedef struct { const beam_pat_t *pats;   /* библиотека дескрипторов SPR_FORMAT */
                 const uint8_t *map;       /* тайлмап (коды фоновых клеток) */
                 uint8_t rows, cols; uint8_t beam_sync;          /* §3.5 */
                 const uint8_t *bg_tiles;  /* плоские дескрипторы клеток фона */
                 const beam_anim_t *anims; } beam_level_t;
void beam_init(const beam_level_t *lvl);   // собирает тени/план; ВНУТРИ вызывает
                                           // spr_init() ровно один раз (лесенки
                                           // 0x7000..0x7203) — игра spr_init НЕ
                                           // зовёт; окном записи = бланкинг
/* --- игровой цикл: эти мутаторы меняют позицию/вид ---------------------- */
void beam_move  (uint8_t id, uint8_t x, uint8_t y); // x кратен 8, y — строка px
void beam_show  (uint8_t id, const beam_pat_t *p);  // новый дескриптор/кадр аним.
// beam_pat_t: { u16 desc (указатель на дескриптор SPR_FORMAT); u8 attr; }
//   attr: бит0-3 приоритет, бит4 = путь spr_blit_mask (см. §3.2)
void beam_hide  (uint8_t id);
void beam_bg_put(uint8_t col, uint8_t row, uint8_t code); // клетка фона
/* --- кадровый контракт --------------------------------------------------- */
void beam_update(void);   // diff -> план по рядам (после game_logic)
void beam_render(void);   // исполнение плана в такт лучу (пишет spr_blit/
                          // spr_blit_mask); возврат = конец кадра
uint8_t beam_overbudget(void);          // байт статуса (для отладки/HUD)
/* --- примитивы для игр, сохраняющие гарантию ---------------------------- */
void beam_blank_wait(void);             // spin до бланкинга (palette/HUD-правки)
```
Соглашения: callee-cleanup для asm-функций с ≤2 параметрами (конвенция
z88dk/ABI), регистровая прозрачность — как у putup-гардов (вызывающий не
теряет DE/HL). Прямые записи в VRAM из игры вне подсистемы **запрещены**,
кроме палитры (`gfx_set_palette` — бланкинг-примитив) и `beam_blank_wait`-окна.

**RAM-бюджет**: ОЗУ 0x7000..0x7203 — собственность spr.asm (лесенки);
данные beam (экземпляры 16×4 + тени 16×3 + план ~24×8 ≈ 350B) размещаются
ВНЕ этого диапазона, куча не должна дорасти до 0x7000.

**Базовая реализация — C** (`beam.c`): горячая часть (пиксельные записи) уже
в asm-ядрах, планировщик/дифф не критичен к скорости; вынос отдельных участков
в `beam.asm` — только по итогам замеров A2/A5 (не самоцель).

## 6. Правила для игр, использующих подсистему (ТФ)

- **ТФ-1 Единственный писатель.** Вся видимая графика уровня — через `beam_*`.
  Прямые вызовы `spr_blit`/`spr_blit_mask`/`spr_init` из игры запрещены
  (ядра не реентерабельны, §3.5). Свой текст/HUD — либо как клетки тайлмапа,
  либо в окне `beam_blank_wait`.
- **ТФ-2 Никаких собственных EI;HLT и ожиданий** внутри кадра, кроме
  контрактных `v06_wait_frame` и `beam_render`. Пауза «до конца кадра» —
  свойство подсистемы, не игра её организует.
- **ТФ-3 Никаких длинных DI.** Критические секции ≤ ~200T. Музыкальный
  секвенсор живёт на VBlank; канал 2 VI53 занят таймером — звуковые движки
  ограничивать маской 0x03 (уже правило `lib/timer`).
- **ТФ-4 Изменения — только таблицы.** В игровом цикле игра пишет
  экземпляры/тайлмап; не читает и не пишет VRAM, не знает про луч, пороги и
  фазы. Единственная видимая обратная связь — задержка отображения ровно 1
  кадр (константа контракта, а не артефакт).
- **ТФ-5 Бюджет — обязанность игры.** Суммарная объявленная динамика
  (движущихся спрайтов × тип пути) обязана влезать в паспорт §4; перегруз
  трактуется как баг игры (детектируется `beam_overbudget`).
- **ТФ-6 Анимация — через фазы дескрипторов**, не через собственные сканы поля.
- **ТФ-7 Переходы уровня** (заставка->игра) — через `beam_init`; режим
  `beam_sync=0` на заставках легитимен (много writes, гарантия не нужна).

## 7. Оптимальные практики реализации (из putup, обязательны к применению)

1. **Precompute вместо runtime-математики**: дескрипторы, субпиксельные
   варианты, фазы — build-time/загрузка уровня. Худшая находка putup —
   пересборка кеша в кадре (407 строк). В beam runtime-математики нет вовсе:
   формат SPR_FORMAT уже хранит геометрию по-столбцово.
2. **Прозрачность гардов** (PUSH/POP PSW,B,D,H) — hot path игр на 8080 живёт
   регистрами; любой сервисный вызов внутри чужого цикла обязан их беречь
   (XCHG-идиомы, DE.H-базы таблиц).
3. **Пороги — только через `timer_*`** (elapsed = 0x7500−count), модель ряда
   `48+8·row` и калибр. BEAM_LEAD=+6 строк из BLINK.MD, а не из головы.
4. **Стоимость каждой операции планировщика измеряется инструментом, а не
   оценивается** (beam_hero/beam_pickup/pipeline). Перед оптимизацией —
   прогон по real-raster; помнить: BP-потоки морозят луч, одинарные trap-замеры
   валидны, потоковые — нет (память tool_experience). Цены spr-ядер уже
   измерены (spr-speed) — перемерять их не нужно, только удельную таблицу §4.
5. **Единица консистентности — ряд глифов (8 строк)**, никогда не «клетка»
   и не «кадр целиком» (широкие ряды не влезают; см. Этап 1 огня). Спрайт
   выше ряда коммитится атомарно по нижней полосе (§3.1).
6. **Fail-safe лучше зависания**: все ожидания ограничены кадром
   (semantics `timer_wait`), перенос хвоста плана на следующий кадр штатный.
7. **Плоский путь — основной**: erase фона и непрозрачные спрайты —
   `spr_blit` (~25T/байт); `spr_blit_mask` (~43T/байт) — только оверлей-класс
   «герой» с лимитом §3.2.
8. **VRAM-адресация скрыта дважды**: плоскости/Y-инверсия/колонки — внутри
   spr-ядер; для 512-режимов ядра сейчас не приспособлены (база 0x8000, шаг
   +0x2000, только 256×256) — обобщение адресации делается в spr-слое на Э5,
   beam знает только конвенцию «x кратен 8, y — строка px».
9. **Тени и diff вместо слепых сканов**: putup-чанки (128 клеток/кадр,
   var_scan_ptr) — обход вслепую; подсистема знает, что изменилось, и
   платит за фактические грязные ряды.
10. **Инструменты принимаются вместе с кодом** (см. §8): без tearing-детектора
    подсистема не считается готовой.

## 8. Гарантии и критерии приёмки

Гарантии контракта (для игр):
- **Г1 Tearing = 0**: нет ни одной записи в видимую VRAM при луче внутри
  полосы записываемого ряда (±0; «успеем»-ветки с запасом не считаются
  нарушением, но должны быть проверяемы).
- **Г2 Консистентность ряда**: на любом кадре каждый видимый ряд однофазен
  (каждая клетка ряда отражает ровно один плановый кадр).
- **Г3 Темп**: период цикла ровно 1 hw-кадр при любом штатном загруженном
  кадре; музыка (VBlank-секвенсор) не пропускает тиков.
- **Г4 Задержка**: изменение позиции видно через ровно 1 кадр; не более.

Гейты (по аналогии с putup e-серией; инструменты — апгрейд `tools/beam_*.py`
в тестовый ROM подсистемы):
- **A1 tearing-детектор**: BP-инструмент на всех writer'ах (входы
  `spr_blit`/`spr_blit_mask`, `gfx_put_char*`, `gfx_plane_or`) + сверка
  полосы ряда vs beam/elapsed на момент записи; синтетика: 12 спрайтов в
  одной строке, широкий анимируемый ряд, sprite на границе видимого поля,
  запись на wrap-рубеже кадра.
- **A2 budget-meter**: распределение строк на кадр на стресс-сцене
  (предел §4), таблица worst-case.
- **A3 consistency-checker**: потактовые снимки VRAM, row-phase униформность
  (обобщение e4 модели «тёмная/светлая фаза == record(кодов)»).
- **A4 byte-exact**: вывод подсистемы побайтово == эталонный ручной render
  того же состояния прямыми вызовами spr-ядер в бланкинг (compare_color-
  подход) — «планировщик не портит картинку».
- **A5 tempo**: 600 кадров стресса, Δframe_count строго 1 на цикл, 0
  пропусков VBlank-тиков музыки.

## 9. Этапы (по одному, с гейтами; дисциплина TZ/TZ2)

- **Э0. Паспорт планировщика + interface draft**: цены spr-ядер уже измерены
  (spr-speed/spr-demo) — перемерить только накладные плана/guard и
  фоновой клетки real-raster-инструментами на тестовом ROM; зафиксировать
  форматы паттернов/экземпляров и таблицу `beam_cost`. Гейт: таблица §4
  подтверждена.
- **Э1. Ядро**: flat-путь (move/hide/erase-из-тайлмапа/plan/behind-the-beam
  pacing, ряд-атомарность по нижней полосе), планировщик на C поверх
  spr_blit; тестовая сцена «шарики» в эмуляторе v06_emu + A1/A3 на flat-наборе.
- **Э2. Анимация и приоритеты**: фазы дескрипторов (kadence), пересечения
  overwrite-порядком, широкий анимируемый ряд (генерализация огня), A2.
- **Э3. Mask-оверлеи**: `spr_blit_mask`-путь (attr бит4), лимит 2
  mask-инстанса, «герой-класс» сцена, A1+A5 с полной нагрузкой.
- **Э4. Субпиксель**: генератор build-time вариантов дескрипторов (расширение
  gen_spr.py) + сцены с 4px-шагом; runtime-перекодировки нет — только выбор
  варианта.
- **Э5. Режимы 512**: обобщение адресации **в spr-слое** (512_4/512_2 под
  `gfx_modes`, col-таблицы на режим); beam получает режим как параметр
  уровня; A4 в каждом режиме.
- **Э6. Порт putup** (доказательство «конструктора»): выровнять putup на API
  подсистемы; сравнить темп/визуал (ориентир §1.3: герой-класс 75,8 строки
  против исторических 101..137); BEAM-заметки перенести в README lib.

## 10. Открытые вопросы (решаются на Э0)
1. Максимальное число экземпляров (предложение: 16, OAM-подобно) и размер
   библиотеки дескрипторов; RAM-бюджет теней/плана (оценка: 16×4 + тени
   16×3 + план ~24×8 ≈ 350B, вне диапазона 0x7000..0x7203).
2. Портировать ли chunked-скан как fallback для гигантских полей анимации,
   или diff-план обязателен (предложение: обязателен; широкий ряд =
   декорированный «паттерн-лента», план один индекс).
3. Текст/HUD: единый тайлмап-слой или отдельный blanking-API (предложение:
   HUD = клетки тайлмапа + `beam_blank_wait` для строковых обновлений).
4. Поведение при намеренной перегрузке (демо-сцены): политика flicker
   round-robin или блокировка move до освобождения бюджета.
5. ~~Materialизация маски~~ — закрыто форматом: маска в дескрипторе
   `spr_blit_mask` (первый блок DATA), streaming AND/OR из ROM уже в ядре;
   VRAM-кеши композитов не нужны.
6. ~~Приоритет по pixel-ne-zero (NES-like)~~ — закрыто: `spr_blit_mask` +
   приоритет инстанса покрывают «герой-класс» semantics без пиксельного скана.
