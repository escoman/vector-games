# mario-8cols: можно ли фонам использовать цвета персонажа

Вопрос: **земля, кирпичи, деревянные бруски и блоки «?»** — тайлы, в которые
Марио никогда не заходит. Можно ли в них применять цвета переднего плана
(`ch` = red / pink / black), то есть писать старшие плоскости
(`0C0h`, `0E0h`) не только спрайту?

**Ответ: да, и это самый дешёвый из вариантов с палитрой.** Палитру менять не
нужно вообще — цвета спрайта уже лежат в таблице **в каждой строке**, а
«расточительное» дублирование как раз и делает трюк рабочим. Ниже — замер,
цена и план.

Механика (см. [`src/palette.json`](src/palette.json), `build_palette()` в
[`tools/gen_assets.py`](tools/gen_assets.py)):

- индекс пикселя = `bg * 4 + ch`, где `bg` — код фона из плоскостей `8/4`,
  `ch` — биты из плоскостей `2/1`;
- `palette[4b+1]` = **красный** при любом `b`, `palette[4b+2]` = **розовый** при
  любом `b`, `palette[4b+3]` = чёрный (он уже есть как `BG_BLACK`, выгоды ноль);
- ⇒ пиксель стены получает нужный цвет **независимо от своего кода фона**, и
  бюджет палитры не тратится: новые записи в порт `0Ch` не нужны;
- спрайт не конфликтует, потому что `ch=0` у него = «показать фон этого ряда», а
  в стены он не заходит (см. «Гарантии» ниже).

## Гарантии изоляции

Стена действительно никогда не под боксом спрайта — это держится на трёх
проверках в [`main.c`](main.c):

```c
if (!(solid_at(edge, r0) & COLL_WALL) && !(solid_at(edge, r1) & COLL_WALL)) wblk = nb;  // в стену не входим
if (solid_at(wblk, brow) || solid_at(wblk + 1, brow)) nmy = brow * TILE_PX - SPR_H;     // ноги на верх опоры
if (solid_at(wblk, trow) & COLL_WALL) nmy = (trow + 1) * TILE_PX;                        // голова: блок сверху отталкивает вниз
```

Замер по модели уровня: бокс 16×16 с учётом прыжка (вершина 66 px ⇒ 11 рядов,
±2 колонки) накрывает **все четыре кода фона** (sky 17 % / black 26 % / white
26 % / green 30 %), то есть все 16 слотов палитры заняты спрайтом. Но это не
мешает фонам брать `ch=1/2`: цвета-то те же самые, занятые слоты просто
переиспользуются. Обратно: идея «освободить слоты под несомкнутые тайлы» цвета
**не даёт** — палитра одна на кадр.

Две дыры в инварианте, которые надо закрыть при внедрении:

1. **Прижим к верху экрана** — `dy = (my < top_px) ? top_px : my`. Единственный
   случай, когда бокс ложится на стену. `_mario_undraw` обнуляет `ch`-плоскости
   по всему боксу, а диф-рендер тайл не перерисует (он не менялся) ⇒ **дыра до
   следующей перепечки**. Лечится сбросом `tile_nz` / поднятием `pair_top` для
   перекрытых клеток в этом редком кадре.
2. **Прочность битов**: `_mario_undraw` затирает плоскости без слепка —
   теневой копии фона под спрайтом у нас нет (и не было, пока фон в `ch`
   плоскости не писался). Пока пункт 1 закрыт и `ch`-биты разрешены только
   на `COLL_WALL`-тайлах (проверка на сборке), затирание безвредно.

## Что даёт: замер по исходникам тайлов

Метрика — средняя евклидова ошибка квантования пикселя исходника
(`src/tiles/tile_NNN.png`) против ближайшего доступного цвета, 4 цвета против 6
(+red, +pink). Всего 33 wall-тайла, 32 с содержимым.

Главная неприятная новость оказалась хорошей: **дорогие по перерисовке тайлы не
нуждаются в новых цветах**. Тайлы 58/61/64/67 — это 45 % всех грязных
wall-клеток на шаг, но они зелёные (`48B600` = наш же `BG_GREEN`) и чёрные,
ошибка 0–37, красного/розового не хотят вовсе. А то, что реально врёт (кирпич
`FF9155`, персиковые «?» `FFDAAA`, дерево), встречается на границах колонок
редко:

| Набор тайлов | Тайлов | Грязных кл/шаг | Цена на шаг |
|---|---|---|---|
| все wall | 32 | 58,8 | +15,3k T (1 пл.) / +30,6k T (2 пл.) |
| **только `err4 > 90` (кирпич, «?», дерево)** | **12** | **13,6** | **+3,5k T / +7,1k T** |
| 4 самых частых (зелёная земля) | 4 | 26,7 | не нужно — цвет уже верный |

Шаг скролла сейчас **210 660 T** (см. [`OPTIMIZATION.MD`](OPTIMIZATION.MD)),
цена за одну доп. плоскость на грязной клетке = `copy8` = 260 T. Итого
**+1,7 %** на шаг за красный, **+3,3 %** за красный + розовый.

Дизер сверху даёт не 2 цвета, а ~6 тонов (всё офлайн, в рантайме стоит те же
биты в плоскостях): red↔black = тёмный кирпич/коричневый, red↔white =
лососево-оранжевый тело кирпича, pink↔black = дерево.

## Цена внедрения

| | Только красный (1 пл.) | Красный + розовый (2 пл.) |
|---|---|---|
| Время на шаг | +3,5k T (+1,7 %) | +7,1k T (+3,3 %) |
| ROM | +2 080 Б | +4 160 Б (запас 32 512 − 17 994 = ~14 КБ) |
| BSS | +1 024 Б (`tile_nz` 2→4 бит/тайл) | +1 024 Б |
| Работа | 1,5–2 дня | +0,5 дня |

Для сравнения: в первой прикидке я считал эти +15…30k T по всем wall-клеткам и
оценил вариант в 1,5–3 дня с сомнительной окупаемостью — после разбивки по
тайлам он в 4–9 раз дешевле.

### План по файлам

1. [`tools/gen_assets.py`](tools/gen_assets.py) — квантование wall-тайлов по
   расширенной палитре (6 цветов + дизер между ними), запись старших
   плоскостей; **жёсткая проверка**: у тайла без `COLL_WALL` старшие биты обязаны
   быть нулём, иначе decor-бит уедет в проходимый тайл и спрайт его сотрёт.
2. `tileset` — записи 16 → 32 Б (4 плоскости). Недекорированные тайлы — нули, но
   маска `tile_nz` говорит их не копировать ⇒ на «пустых» тайлах времени ноль.
   Адресация в `_rw_put_cell`: `4× dad h` → `5× dad h` (+4 T/клетка, тот же
   приём, что в `_mulshift`).
3. `tile_nz` — 2 → 4 бита на тайл (маска ненулевых плоскостей), 16 → 32 Б на
   колонку кольца; `bake_groups` / `bake_shift` сдвигают на один `movdd`
   больше (~+1,3k T/шаг — в шуме).
4. [`mario.asm`](mario.asm) `_rw_put_cell` — цикл по 4 плоскостям через уже
   существующую `_vram_bases` (`defw $+3, 0A0h, 0C0h, 0E0h`), ход в `0C0h/0E0h`
   движок умеет и так.
5. [`main.c`](main.c) — сброс грязных клеток при прижиме к верху экрана (пункт 1
   «Гарантий»).
6. [`tools/level_editor.py`](tools/level_editor.py),
   [`tools/tile_editor.py`](tools/tile_editor.py),
   [`tools/check_parity.py`](tools/check_parity.py) — PNG-раундтрип
   4-плоскостных тайлов. Скучно, но это ~40 % оценки.

### Риски

- **Читаемость.** Красный кирпич рядом с красным Марио. По замеру розовый
  занимает 38–42 % пикселей в «?-тайлах» и ~0 % в кирпичных, поэтому разумная
  политика: тело кирпича/дерева — розовый и его дизеры, красный только контур и
  тени. Правило стоит зафиксировать комментарием в `src/palette.json`, иначе
  следующая правка ассетов съест контраст.
- Порядок: выгоднее делать **после** пунктов #1 (маска грязных рядов) и #7 /
  zero-fill из [`OPTIMIZATION.MD`](OPTIMIZATION.MD) — они дают −70k T/шаг, и
  тогда +3,5k T тонут в запасе. Вариант сам по себе ничего из этого не блокирует.

## Что НЕ даёт цвета

- **«Освободить слоты для тайлов, куда Марио не заходит»** — свободных слотов
  ноль: бокс спрайта за цикл побывал на всех 4 кодах фона ⇒ заняты все 16 слотов
  таблицы, изоляция клеток цвета не освобождает.
- **Маска/слепок спрайта** (+12 цветов) — `+60…90k T/шаг` и `+3…4k T` каждый
  кадр на слепок; съедает бюджет оптимизаций #1+#7+#3 целиком. Отклонено.
- **Чёрный через `ch=3`** — это уже `BG_BLACK`, полезная нагрузка ноль.

## Как воспроизвести замеры

Скрипт одноразовый, в `tools/` не клался; скопировать в `/tmp/pal_plus.py` и
запустить из каталога проекта.

```python
# -*- coding: utf-8 -*-
"""Цвета персонажа для wall-тайлов: выигрыш по цвету и цена по времени."""
import sys, os, json
from collections import Counter
from PIL import Image
sys.path.insert(0, 'tools')
import gen_assets as G

cols, rows, tileset, tilemap, tile_nz, pair_top, model = G.build_level_editor()
solid = G.load_tile_solid(len(tileset)); WALL = 2
cell = lambda cx, cy: tilemap[cx * rows + cy]           # col-major
with open(os.path.join(G.SRC, "tiles.json")) as f:
    names = {t["index"]: t["file"] for t in json.load(f)["tiles"]}

RED, PINK = G.CH_RGB[G.CH_RED], G.CH_RGB[G.CH_PINK]
RGB = {b: G.BG_RGB[b] for b in range(4)}; RGB["R"] = RED; RGB["P"] = PINK
CUR, NEW = [0, 1, 2, 3], [0, 1, 2, 3, "R", "P"]
de = lambda a, b: ((a[0]-b[0])**2 + (a[1]-b[1])**2 + (a[2]-b[2])**2) ** 0.5
near = lambda p, tab: min(tab, key=lambda k: de(p, RGB[k]))

# цена: грязные клетки, в которых НОВЫЙ тайл — стена (один шаг = 32 блока экрана)
VIEW, STEPS, cnt = 32, cols - 33, {}
for cam in range(1, STEPS + 1):
    for bl in range(VIEW):
        cx = cam + bl
        if cx >= cols - 1: continue
        for cy in range(pair_top[cx], rows):
            a2, b2 = cell(cx, cy), cell(cx + 1, cy)
            if a2 != b2 and b2 and solid[b2] & WALL:
                cnt[b2] = cnt.get(b2, 0) + 1

out = []
for t in sorted(set(cnt) | {cell(cx, cy) for cx in range(cols) for cy in range(rows)
                           if cell(cx, cy) and solid[cell(cx, cy)] & WALL}):
    im = Image.open(os.path.join(G.SRC, names[t])).convert("RGB")
    px = [im.getpixel((x, y)) for y in range(8) for x in range(8)]
    px = [p for p in px if p != (41, 88, 124)]          # фон листа
    if not px: continue
    d4 = sum(de(p, RGB[near(p, CUR)]) for p in px) / len(px)
    d6 = sum(de(p, RGB[near(p, NEW)]) for p in px) / len(px)
    out.append((t, cnt.get(t, 0) / STEPS, d4, d6,
                sum(1 for p in px if near(p, NEW) == "R") / len(px),
                sum(1 for p in px if near(p, NEW) == "P") / len(px),
                "/".join(f"{r:02X}{g:02X}{b:02X}" for (r, g, b), _
                         in Counter(px).most_common(2))))
print(f"{'t':>4} {'кл/шаг':>7} {'+T/шаг':>7} {'err4':>6} {'err6':>6} {'red%':>5} "
      f"{'pk%':>5}  цвета исходника")
for t, d, d4, d6, nr, npr, c in sorted(out, key=lambda x: -x[1])[:16]:
    print(f"{t:>4} {d:7.2f} {d*260:7.0f} {d4:6.1f} {d6:6.1f} {100*nr:5.0f} "
          f"{100*npr:5.0f}  {c}")
```

260 T — измеренная в офлайн-профиле цена одного `copy8` (плоскость на клетку);
`err4/err6` считаются без байеровского дизера, поэтому это верхняя граница
искажения, а не то, что видит глаз в эмуляторе.
