# ТЗ: Инструмент трассировки прерываний `int_watch` для v06c-mcp

> Статус: проект. Касается сервера `v06c-mcp` (MCP `vector-debugger`), исходники вне этого репозитория.
> Ключевая идея — **агрегация «сайтов» прерываний** (адрес + байты/опанды прерванной инструкции) + детектор аномалий для отлова «левых» прерываний.

## 1. Контекст и проблема
При отладке ROM на Векторе-06Ц (8080, IM0, кадровое прерывание через `RST 7.0`→`0x0038`) нужно отвечать на вопросы:
- **Откуда** реально приходят прерывания: какой PC прерывается, какая инструкция/опанды исполнялись в момент прихода, был ли CPU в `HLT` (ожидание) или прерывание пришло поверх активной инструкции;
- **Куда** они векторизуются (адрес, взятый с шины в IM0 / из таблицы в IM2) — чтобы ловить «левые»/шумовые прерывания, приходящие не в штатный вектор;
- **Как часто** (число прерываний на кадр) — чтобы отличить штатные 50 Гц от пропусков/задвоения;
- Не ломает ли `DI/EI` критический участок (прерывание внутри защищённого кода / повторный вход в ISR).

Сейчас есть `debug_get_execution_trace`, `debug_get_io_trace`, `debug_get_beam_state`, брейкпоинты, но **нет специализированного сбора именно событий прерывания** с их сайтами/операндами и агрегацией. Ручная работа (breakpoint на `0x0038` → читать `[SP]` → дизасемблировать) медленна и не даёт картину по всему прогону.

## 2. Термины
- **Событие прерывания (IntEvent)** — момент, когда CPU реагирует на INT (INTE=1 и не в машинном цикле `DI`), включая выход из `HLT`.
- **Сайт (IntSite)** — уникальный адрес прерванной инструкции (точнее — address of next-to-execute, «точка возврата»).
- **Вектор (vector_taken)** — фактический адрес перехода по прерыванию (для `RST 7` = `0x0038`; IM2 = `(I<<8)|N`).
- **«Левое» прерывание** — событие, не соответствующее заданному ожиданию (чужой вектор, неверная каденция, прерывание внутри защищённого участка/ISR).

## 3. Цель и критерии успеха
**Цель:** включить дешёвый сбор всех прерываний за прогон и в один вызов получить: гистограмму сайтов (адрес+мнемоника+опанды+сколько раз+сколько из них `HLT`-wake), статистику по векторам и каденции, и список аномалий.

Критерии:
- После `debug_int_watch(enable=true)` и прогона N кадров — `debug_get_int_sites()` возвращает **все** адреса, на которых сработало прерывание, с корректной дизасемблированной инструкцией по каждому.
- Различаются `wake-from-HLT` (прерывание разбудило `HLT`) и прерывание активной инструкции (по признаку: байт по `retPC-1 == 0x76`).
- Аномальные (не в белом списке) векторы/сайты/каденция помечены и вынесены в `debug_get_int_anomalies()`.
- Накладные расходы на эмуляцию ≤ заданного бюджета (§7), память ограничена (dedup/ring).

## 4. Не-цели (out of scope)
- Реализация/починка конкретной демо (mario-dbl) — вне рамок инструмента.
- Точный cycle-accurate raster-timing ISR-реентранс-аппарат сверх текущего ядра эмуляции.
- GUI: только JSON поверх MCP.

## 5. Функциональные требования

### 5.1 Сбор на событие (IntEvent), поля
| поле | тип | смысл |
|---|---|---|
| `seq` | u32 | порядковый номер события |
| `frame` | u32 | кадр из beam-счётчика (§10) |
| `v_cycle_in_frame` | u32 | такт внутри кадра прихода |
| `raster_line` | u16 | строка развёртки на момент прерывания |
| `ret_pc` | u16 | точка возврата = PC после прерванной инстр. (кладётся на стек) |
| `interrupted_pc` | u16 | фактический адрес прерванной инструкции (`ret_pc` − длина, либо адрес `HLT`) |
| `opcode_bytes` | bytes[4] | байты по `interrupted_pc` (для операндов) |
| `mnemonic` | string | дизасемблированная инстр. (reuse дизасемблер сервера) |
| `was_halt` | bool | CPU сидел в `HLT` (wake) |
| `is_hardware` | bool | **флаг `HARDWARE`**: событие вызвано сигналом на линии `INT` (истинное аппаратное прерывание, включая `wake-from-HLT`); `false` — если это программный переход в вектор (`RST n`/`CALL`, исполненный как инструкция потока) |
| `in_post_DI` | bool | INTEGRATE=0 был (тогда прерывание быть не должно — аномалия) |
| `int_taken` | u8 | код векторного байта/инструкции IM0 (`RST n`/`CALL`) |
| `vector_taken` | u16 | куда перешли (`0x0038`, IM2, …) |
| `iff_before` | bool | состояние INTE до |
| `im_mode` | u8 | 0/1/2 |
| `sp` | u16 | SP на момент (для in-ISR-реентранс-детекта) |
| `vector_cycles` | u8 | такты на векторинг (для бюджета) |

### 5.1.1 Флаг `HARDWARE` (`is_hardware`)
Главный признак для отличия «левых» прерываний. Определяется **по источнику события, а не по адресу перехода** (переход на `0x0038` + PC в стек одинаковы и для аппаратного `INT`, и для программного `RST 7` — по стеку они неразличимы):
- `is_hardware = true` — CPU отреагировал на **сэмпл линии `INT`** при `INTE=1` в конце машинного цикла (IM0/IM1/IM2) либо вышел из `HLT` по этому сигналу (`was_halt=true` ⇒ всегда `is_hardware=true`).
- `is_hardware = false` — в потоке кода исполнилась инструкция `RST n`/`CALL` в вектор прерывания; линию `INT` это не касается, `EI/DI` не влияет.
Трассировщик обязан засчитывать событие как прерывание **только при `is_hardware=true`**; программные `RST` в ту же ячейку помечать `is_hardware=false` (и по умолчанию не включать в `per_frame`-каденцию, иначе кадровый счётчик завышается).

### 5.2 Агрегация сайтов (IntSite) — «по адресу и опандам»
Dedup по `interrupted_pc`. По каждому сайту:
- `addr`, `opcode_bytes`, `mnemonic` (с одной нормализацией);
- `count`, `halt_wakes`, `active_hits` (`count − halt_wakes`), `hw_count` / `sw_count` (разбивка по `is_hardware` — программный `RST` и аппаратный `INT` на одном адресе не должны смешиваться в один счётчик);
- `vectors` (set `vector_taken`, если на одном сайте ловились разные векторы — красный флаг);
- `first_frame`, `last_frame`;
- `flags[]`: `foreign_vector`, `inside_protected`, `nested_isr`, `not_hlt_expected`, `software_rst` (сайт порождён преимущественно программным `RST`/`CALL`, а не линией `INT`).

### 5.3 Каденция и статистика
- `per_frame` гистограмма: число прерываний на кадр (ожидаемое — конфигурируемо, по умолчанию 1).
- `total`, `by_vector` (счёт по каждому `vector_taken`), `distinct_sites`.

### 5.4 Детектор «левых» прерываний (anomalies)
Пользователь задаёт ожидание: `expected_vector` (напр. `0x0038`), `expected_per_frame` (1), `expected_sites` (опц. белый список адресов, где прерывание легально — напр. точки `ei/halt`). Аномалия, если:
1. `vector_taken != expected_vector` → чужой источник/шум;
2. число в кадре ≠ `expected_per_frame` (пропуски/задвоение);
3. прерывание при `IFF==0` (`INTE` снят) → баг ввода прерываний/эмуляции;
4. `nested_isr`: прерывание, когда PC уже внутри диапазона ISR (пересечение со стеком возврата ISR) — реентранс;
5. `site not in expected_sites` (если список задан).

Отдельный вызов возвращает список с контекстом (кадр, сайт, тип).

### 5.5 Управление (API)
Новые MCP-инструменты (префикс `debug_`, согласованно с существующими):
- `debug_int_watch{ enable: bool, mode: "sites"|"events"|"both", cap: int, ring_events: int, reset: bool }` — включить/настроить; `mode=sites` — только дедуп-агрегация (дёшево, неограниченно по времени прогона), `events` — кольцо последних `ring_events` событий (детальный разбор порядка), `both`.
- `debug_get_int_sites{ sort_by: "count"|"addr"|"frame", min_count: int, reset: bool }` → таблица сайтов (§5.2).
- `debug_get_int_trace{ recent: int }` → последние события (кольцо), только в `events/both`.
- `debug_get_int_summary{}` → `total/by_vector/per_frame/distinct_sites/im_mode`.
- `debug_get_int_anomalies{ reset: bool }` → список (§5.4) + счётчики по типам.
- `debug_clear_int_watch{}` → сброс всей накопленной статистики.

Семантика `reset`/`clear` — как у существующих `debug_clear_breakpoints`/`debug_clear_memory_access_map`.

## 6. Модель данных/хранение
- Сайты: хэш-таблица `addr → IntSite` (память ~ O(distinct_sites), ограничить `MAX_SITES`, по умолчанию 4096; при переполнении — вытеснять LeastFrequent + флаг `overflow`).
- События: ring buffer фикс. размера (по умолчанию 2048, настраиваемо `ring_events`), overwrite-oldest.
- Аномалии: отдельный bounded-лог (256) + полные счётчики, даже если тела отброшены.

## 7. Производительность
- В `sites`-режиме overhead на событие должен быть сопоставим с одним `PUSH` в trace (не писать опкоды в плоскую память на каждое событие; нормализация mnemonic — ленивая, при `get`).
- `enable=false` → нулевая стоимость (полный пропуск hook'а).
- Бюджет: прогон типового ROM 10 000 кадров не должен замедлять реальное время эмуляции >20% в `sites`, >50% в `both`.

## 8. Точность эмуляции прерываний (важно)
Инструмент обязан корректно моделировать 8080-семантику, иначе «левые» прерывания будут артефактом эмулятора:
- Различать **IM0** (устройство кладёт инструкцию на шину → `RST n`/`CALL`), **IM1** (fixed `RST 7`), **IM2** (`JP (I<<8|N)`); поле `im_mode`.
- Корректный **wake-from-HLT**: при `HALT` прерывание не векторизируется «поверх» — CPU зависает до INT; `ret_pc` = адрес после `HLT`, `was_halt=true`.
- **Не брать** прерывание при `INTE=0` (между `DI` и `EI`) — и если источник дёрнул линию в этом окне, это фиксируется как аномалия типа 3, а не тихо игнорируется.
- Векторинг в середине машинного цикла (не между инструкциями на границе) — зафиксировать как есть и пометить `mid_instruction` в `flags`.

## 9. Интеграция с текущим сервером
- Переиспользовать: дизасемблер (`debug_disassemble`), `beam_state` (frame/raster/v_cycle), naming `debug_*`, формат JSON-ответов, `max_entries`-идиому как в `*_trace`.
- События прерываний — новый источник рядом с `execution_trace`/`io_trace`; `debug_get_state` мог бы показывать `int_watch: {enabled,total,anomalies}`.

## 11. Приёмочные тесты
1. **Штатный ROM**: кадр-ISR через `RST7@0x0038`, цикл `ei/halt`. Ожидание: 1 сайт-`wake-from-HLT`, `per_frame=1`, `vector=0x0038`, 0 аномалий.
2. **Двойной `halt`**: ROM с двумя последовательными `ei/halt` за кадр → `per_frame=1`, но два разных wake-сайта (регресс на наш mario-dbl кейс).
3. **Левое при `INTE=0`**: ROM, где источник дёргает INT при `INTE=0` → аномалия тип-3 с адресом сайта.
4. **Чужой вектор**: инъекция INT с векторным байтом, задающим `CALL`/`RST` не в `0x0038` → `flags: foreign_vector`, попадание в `debug_get_int_anomalies`.
5. **Реентранс**: INT внутри тела ISR → `nested_isr`.
6. **Нагрузочный**: 10k кадров в `sites` → в бюджете §7, `overflow=false`.
7. **Корректность операндов**: `mnemonic/opcode` на каждом сайте совпадает с `debug_disassemble(addr)` офлайн.
8. **Hardware vs Software**: ROM с явным `RST 7` в коде и внешним INT в тот же `0x0038` → у сайта `RST` `hw_count=0`/`sw_count>0`/`software_rst`, у реального INT — `is_hardware=true`; программные `RST` не влияют на `per_frame`.

## 12. Граничные случаи
- Прерывание на границе `RESET` (trace не должен нестись через reset — автосброс по `debug_reset`).
- `RST n`, исполняемый **программно** (не по INT): не учитывать как прерывание (лишь по факту аппаратного INT) — различать источник через флаг `is_hardware` (`HARDWARE`) (§5.1.1): hardware-int (сэмпл линии при `INTE=1`) vs instruction fetch (`RST`/`CALL` в коде).
- Переполнение кольца/хэша → флаги `overflow`, но счётчики полные.
- Несколько INT в одном машинном цикле → слить/пометить.

## 13. Этапы и объём
- **M1**: `int_watch(sites)` + `get_int_sites`/`clear` + `wake-from-HLT` детект + корректный IM0/IM2 `vector_taken`. (~1 день)
- **M2**: `per_frame`/`by_vector` summary + аномалии тип 1–3. (~0.5 дня)
- **M3**: `events`-ring + `get_int_trace` + аномалии 4–5 (реентранс/защищённый участок). (~0.5–1 день)
- **M4**: приёмка (§11), документация инструмента (`tools/debug_int_watch.json` и др.), интеграция в `debug_get_state`.

## 14. Open questions

- IM2 нужен ли (8080-режимы), или достаточно IM0/RST — по фактическим ROM.
- Должен ли `int_watch` учитывать прерывания, отбрасываемые из-за DDT/DMA-подобных пауз, если таковые моделируются.
