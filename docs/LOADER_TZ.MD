# ТЗ: Второй загрузчик (stage-2 tape loader) — `lib/boot/loader*.asm`

> **Цель:** ROM-заставка умеет отдавать управление следующему ROM по ленте,
> не полагаясь на внешний начальный загрузчик Вектора. Пользователь загружает
> ROM заставки (штатным способом), смотрит её, нажимает любую клавишу — и
> встроенный **второй загрузчик** стирает машину до чистого состояния, рисует
> карту загрузки (образ — `kish1_src_/boot.png`) и принимает основной ROM с
> порта магнитофона по протоколу **v06c-rom**, после чего передаёт ему
> управление.
>
> **Аппаратура:** Вектор-06Ц (КР580ВМ80А, 3 МГц, только штатные 8080-команды),
> ПИА КР580ВВ55, порт C (01h): бит 0 — Tape Out, бит 4 — Tape In.
>
> **Кодирование операндов:** модуль загрузчика собирается строго в системе
> команд i8080 (пп. 3, 9): z80asm по умолчанию принимает и Z80-расширения,
> которые на 8080 читаются другими командами, — финальный контроль идёт по
> байтам готового бинарника, а не по тому, что сборка прошла без ошибок.
>
> **Эталоны:**
> • начальный загрузчик NEWROM v2.0 (TMK Soft'91) — `kish1.asm` / `newrom2.asm`
>   (протокол ленты, карта, палитра, стек 0xDCF0);
> • кодировщик ленты — `utils/rom2mp3.py::maketape_v06c_rom` (норматив формата,
>   переписан с bin2wav.c);
> • целевой экран — `kish1_src_/boot.png`.

---

## 1. Сценарий и границы ответственности

```
┌ ROM заставки ────────────────────────────────────────────────┐
│ заставка → любую клавишу → loader_boot()                     │
└──────────────────────────────┬───────────────────────────────┘
                               │ stub (lib/boot/loader.asm):
                               │  DI, копирует blob в 0xE000 (+ конфиг и панели
                               │  для loader_boot_cfg), JP 0xE000
┌ stage-2 (blob @ 0xE000) ──────▼──────────────────────────────┐
│ DI → SP=0xDCF0 → очистка 0x0000..0xDFFF → JMP 0xE000 в 0x0000  │
│ → рестарт ПИА → панели (§5.2) → карта загрузки (OR поверх)          │
│ → палитра «виден только C000» цветами из конфига → приём v06c-rom   │
│ → PCHL на addrhi:0000 (§3.8)                                        │
└──────────────────────────────┬───────────────────────────────┘
                               │ управление идёт на фактический старт образа
                               │ (для .rom — 0x0100, для .r0m — 0x0000);
                               │ hardware reset — снова в загрузчик по
                               │ заглушке JMP 0xE000 в 0x0000 (§3.8-reset)
┌ ROM основной игры ───────────▼───────────────────────────────┐
```

Заставка обязана **до** вызова `loader_boot()`:
• дождаться нажатия клавиши (свой `kbd_scan`/`kbd_read` — в stage-2 клавиатуры
  нет);
• заглушить звук (`music_stop`/`sound_stop`/`drum_mute`) — PCM-щелчки из
  Tape Out помехой не являются (вход — бит 4, выход — бит 0), но прерывание
  звукового движка во время загрузки ломает тайминг декодера;
• не держать своих переменных в 0xC000..0xDFFF, если они нужны после
  загрузки (эта область стирается и становится картой/стеком).

`loader_boot()` **не возвращается**: память заставки будет стёрта.

## 2. Карта памяти stage-2

### 2.1. Диапазоны

| Область | Назначение |
|---------|-----------|
| 0x0000..0x0002 | `JMP 0xE000` (`C3 00 E0`) — заглушка `reset`→загрузчик (§3.8-reset); ставится после очистки, для `.r0m` (старт 0x0000) её затирает сам образ |
| 0x0003..0x00FF | нули после очистки; управление сюда НЕ скользит (выход — `PCHL` на `addrhi:0000`, §3.8). Вектор 0x0038 не переставляется и прерываний нет (§3.1) — нули в нём просто `NOP` |
| 0x0100..0xBFFF | приём следующего ROM (линейно, от `addrhi:0000`) |
| 0xC000..0xDFFF | единственная видимая плоскость (вес 0, бит 1 адреса): карта загрузки §5 **и панели §5.2**, линии OR-ом поверх арта; здесь же живут «живые» ячейки — приёмный буфер, переменные и стек (раскладка NEWROM) |
| 0xE000..0xE2FF | код stage-2 (blob; бюджет кода 768 Б, сейчас 712 Б) |
| 0xE300..0xEEFF | слот данных панели 1 (3 КБ) — сразу за кодом; стаб РАСПАКОВЫВАЕТ в него ZX0-поток из ROM (`zx0_decompress`) |
| 0xEF00..0xFAFF | слот данных панели 2 (3 КБ). Адрес слота — ФОРМУЛА `LOADER_PANEL_BASE + номер·LOADER_PANEL_STRIDE` (0xE300 + i·0xC00): рост одной панели в пределах stride не сдвигает соседнюю и не требует правки адресов ни в `loader.asm`, ни в `v06.h` |
| 0xFB00..0xFB0F | рабочее поле `drawp` (панели §5.2) |
| 0xFB10..0xFB1F | **блок конфига** (§4.2, §7): два цвета и дескрипторы панелей; его пишет копир заставки |
| 0xFB20..0xFFFF | резерв под рост арта (1248 Б) |
| 0xDC00..0xDCFF | **стек, вершина `SP = 0DCF0h`** (`LXI SP,0DCF0h`) — ровно как STEK у NEWROM; PUSH пишет return-адреса в плоскость, точки стека видны на экране |
| 0xDED0..0xDEF2 | `ABUFF[35]` — приёмный буфер READB (35 байт после E6). Он тоже в плоскости: принятые записи мелькают в правом верхнем углу столбца 0x1D, как в оригинале |
| 0xDEF4..0xDEF8 | переменные **после** буфера: `PRINV`=0DEF4h (`ABUFF+36`), `CONR`=0DEF6h (`ABUFF+38`), `STARTHI`=0DEF7h (`ABUFF+39`, slot `VAR`; addrhi первого заголовка — адрес старта, §3.8), `SBCNT`=0DEF8h |

Раскладка буфера/переменных/стека — как у NEWROM (`docs/etalon/newrom2.asm`
11..17: `ABUFF=0DED0h`, `PRINV=ABUFF+36`, `CONR=ABUFF+38`, `VAR=ABUFF+39`;
`kish1.asm` — `STA 0DEF6H`). Именно поэтому они **внутри** стираемой
области: их запись сразу видна на экране — «живые» байты приёма и точки
стека. Оффсеты переводятся как **десятичные**: 35-байтный буфер занимает
`DED0h..DEF2h`, а переменные начинаются сразу за ним (ошибиться на
`ABUFF+36 → 14h` — значит положить `PRINV` в середину буфера, и первый же
принятый блок перезапишет его своими данными).

Жёсткие следствия:
• **следующий ROM ≤ 0xC000 − 0x0100 = 48896 байт** (совпадает с лимитом
  `ROM_MAX` в `finally.mk`); образ, дорастающий до 0xE000, затрёт работающий
  загрузчик — это не обнаружимая никак ошибка, лимит проверяется кодировщиком;
• адрес загрузки в заголовке ленты — кратный 0x100 (`addrhi:00`), стандартный
  `.rom` = 0x0100;
• **переменные в 0xDEF4.. обнуляются самой очисткой** (§3.2 доходит до
  0xDFFF), но `PRINV` всё равно инициализируется в точке входа явно: очистка
  идёт ПОСЛЕ `STA PRINV`, а NEWROM обнулял все 64 КБ целиком, и его `PRINV`
  (0xDEF4) получался нулевым «сам». Без явной инициализации каждый принятый
  байт XORится с мусором от предыдущего ROM (в тесте это был `AA^A5 = 0F` —
  байт не проходил gates синхробайта, и приём зацикливался на калибровке;
  по времени это выглядит как «не захлопывается фазировка», хотя с ней всё
  хорошо). Рабочее поле `drawp` и конфиг §4.2 лежат выше 0xE000 — очистка до
  них не доходит, конфиг пишет заставка перед прыжком в stage-2.

## 3. Конвейер stage-2 (порядок нормативен)

1. **DI.** Прерываний stage-2 не использует совсем: `EI`/`HLT` нигде,
   вектор 0x0038 не пишется. «RST 7» из NEWROM (задержка + чтение уровня
   ленты в E) становится внутренней подпрограммой blob **с двумя входами**
   (`SAMPLE` — задержка+выборка, `RDATAP` — только выборка; §6), декодер зовёт
   их прямым `CALL` (§3.1, §6). Причина запрета: в стёртую 0x0000..0xDFFF
   область линейно грузится новый ROM (`.r0m` — с 0x0000, `.rom` — с 0x0100);
   живое прерывание в момент приёма увело бы управление в мусор.
2. **Очистка 0x0000..0xDFFF + заглушка сброса.** Цикл `STAX B` парами без
   стека (вершина уже выставлена в 0xDCF0, пункт 3, но в самой петле CALL/PUSH
   нет — стек она не затирает); остановка по `B == 0xE0`. Сразу после очистки в
   `0x0000..0x0002` пишется `JMP 0xE000` (§3.8-reset): аппаратный `reset`
   возвращает в загрузчик. ~0.7 с на 3 МГц — допустимо (однократно, экран
   ещё не показывает ничего важного).
3. **Рестарт ПИА** (как NEWROM): `00h←88h`, `04h←81h`, `03h←FFh`, `05h←FFh`,
   `06h←FFh`, `07h←FFh`, `02h←00h` (бордюр — слот 0, режим 256×256; запись CW
   сбрасывает PA — скролл восстанавливается 0xFF сразу после).
4. **SP ← 0xDCF0** (§2.1, как STEK у NEWROM): выставляется сразу после `DI`,
   до очистки. Стек внутри стираемой области — это сознательно: точки
   PUSH/POP видны на экране. Глубина загрузчика — единицы вызовов (SPmin в
   тесте 0xDCE2), до ROM-области стек не дотягивается.
5. **Панели (§5.2), затем карта загрузки (§5).** Сначала `drawp` пишет арт
   панелей OR-ом в 0xC000 по дескрипторам из конфига (панель с `wb = 0` не
   рисуется — дефолт `loader_boot`), потом линии карты простреливаются тоже
   OR-ом: в точках пересечения с артом остаётся светиться и то, и другое.
   Данные панелей к этому моменту УЖЕ распакованы в слоты стабом (ZX0,
   §5.2) — в blob декодера нет и быть не может: бюджет кода 768 Б,
   свободных 56 Б.
   Всё это пишется в VRAM ДО цветов.
6. **Палитра** (§4, §4.2) — трюк бордюра (порт 02h → номер слота, 0Ch → байт
   цвета), но БЕЗ синхронизации с лучом, — поэтому она требует ПУСТУЮ
   плоскость C000 (§4.1): при nonzero-пикселе под лучом номер ячейки задаёт
   сам пиксель, и слепой обход раскидал бы цвета по чужим слотам (отсюда
   «чёрные» 2/3, если рисовать до палитры и не прятать картинку). Схема:
   картинка уже нарисована (п. 5) → §4.1a уводит C000..DFFF в stash
   0100..2FFF и гасит плоскость → обход 15..0 кладёт цвета по гашению
   (индекс ∈ {0,8}) → §4.1c возвращает картинку из stash (и обнуляет stash).
   Так экран вспыхивает картой СРАЗУ своими цветами, непосредственно перед
   приёмом, а не показывается чужой палитрой ROM заставки в момент отрисовки.
7. **Приём ленты** (§6), мотор: `01h←02h` на входе в приём, `01h←00h` перед
   прыжком (бит 1 — реле двигателя, как NEWROM; бит 0 — Tape Out — в тишине).
8. **PCHL на addrhi:0000** — переход на фактический адрес старта
   загруженного образа (§3.8). `addrhi` ПЕРВОГО заголовка ловится в `STARTHI`
   при разборе (в `B` к выходу остаётся страница последнего блока — для
   перехода он непригоден). Выход адресный, а не скольжением, поэтому
   заглушка `JMP 0xE000` в `0x0000` не мешает: `.rom` (старт 0x0100) её
   минует и стартует, а `reset` по ней попадает в загрузчик; `.r0m` (старт
   0x0000) затирает заглушку собственным кодом при приёме, и `reset` ведёт
   прямо в него (иначе нельзя: 0x0000 — одновременно вектор сброса и его
   точка входа). Универсально: один и тот же выход запускает и `.rom`, и
   `.r0m`.

Требование самодостаточности: blob не ссылается ни на что вне 0xE000..0xE2FF
(кроме портов, плоскости 0xC000 вместе с «живыми» окнами стека/буфера
0xDC00..0xDEF8 и ячеек слотов панелей/рабочего поля/конфига 0xE300.., 0xFB00..0xFB1F) —
все данные (константы палитры, таблицы задержки) внутри кода; никаких EXTERN
из ROM заставки. Панели и конфиг приходят из high RAM, куда их кладёт (панели —
распакованными из ZX0) копир заставки (§7), а не из самого blob. Blob собирается
**отдельным модулем с `ORG 0xE000`** (отдельный прогон z80asm): все метки
(CALL/JP/адреса переменных) разрешаются в абсолютные адреса того места, где
blob будет исполняться, — копир в stub'е остаётся побайтовым без релопации
(проверено: `z80asm -b` с `ORG` не дополняет файл нулями — bin начинается
сразу с кода).

Кодовое покрытие модуля — только i8080 по
[VECTOR_VERIFIED.md §2](VECTOR_VERIFIED.md) (запрещены `IX`/`IY`, `IN/OUT
(C)`, `IN/OUT r,(c)`, блочные, `DD/FD/ED`-расширения, 16-битные
`ADD/ADC HL,ss`, `INC/DEC (HL)` как отдельные опкоды допустимы — они общие).
`IN`/`OUT` с непосредственным портом (`out (2h), a`) разрешены: их код
совпадает с 8080. Контроль — по п. 9.4 (дизассемблирование бинаря).

Ловушки z80asm, которые проходят сборку без единого предупреждения (обе
найдены на реализации, обе видно только по байтам бинаря):

• `jp метка` **без запятой** ассемблируется как безусловный `JMP` (C3), а не
  «переход, если знак плюс»; условный переход пишется с запятой и условием:
  `jp p, метка` (F2). То же касается `call`/`jr` без условия;
• имена символов **регистрозависимы**: `equ`-константы в репозитории пишутся
  ЗАГЛАВНЫМИ (`STACK_TOP`, `CW_CH2_M0`, `LOADER_STAGE2_SIZE`) — ссылка на
  `conr` вместо `CONR` даёт «undefined symbol», а не тихую ошибку.

## 4. Палитра «видна только плоскость 0xC000»

Индекс палитры = биты плоскостей (бит 1 = вес 2 = 0xC000). Маскировка —
цветом, а не маской planes. Два цвета берутся из конфига (§4.2), а не
вшиты: фон — слоты с битом 1 = 0, линии/арт — с битом 1 = 1:

| слот | бит 1 | роль | байт |
|------|-------|------|------|
| 0,1,4,5,8,9,12,13 | 0 | `cfg.bg` — фон (он же бордюр) | дефолт `0x80` |
| 2,3,6,7,10,11,14,15 | 1 | `cfg.line` — линии и арт | дефолт `0x2D` |

Бордюр = слот 0 (порт 02h, биты 0-3 = 0, бит 1 = 0) — автоматически цвет
`cfg.bg`, отдельного бордюрного слота нет. Дефолтные `0x80`/`0x2D` —
голубой фон и жёлтые линии, как на эталоне.
Плоскости 8000/A000/E000 при такой палитре не видны (их биты не меняют цвет),
об этом этапе рисования/записи они не заботятся.

### 4.1. Выставление палитры без прерываний

По docs/BEAM_TIMING.MD §6 запись в 0Ch идёт в ячейку `палитра[индекс бордюра]`,
пока луч в гашении, и в ячейку `палитра[цвет под лучом]` (т.е. в ячейку, номер
которой задают 4 бита плоскостей под пикселем) на видимой части строки.
`EI/HLT` запрещены (§3.1) — поэтому запись идёт вслепую, но с гарантией
покрытия — и только при пустой видимой плоскости C000:

1. на этом шаге плоскость C000..DFFF СПРЯТАНА в stash 0100..2FFF (§4.1a),
   а A000/8000 уже обнулены boot-erase'ом (§3.2) — из четырёх весов индекса
   остаётся только E000 (вес 8, наш код), поэтому «промахи» по лучу бьют
   только в ячейки 0 и 8, а обе — фонового цвета; NEWROM достигает того же
   тем, что ставит палитру сразу после стирания всех 64 КБ (мы рисуем карту
   ЗАРАНЕЕ, поэтому прячем её на время цветов и возвращаем обратно);
2. цикл `02h←N; 0Ch←color[N]` для N = 15..0 крутится непрерывно ~1 кадр
   (≥ 20 мс): гасящих интервалов за кадр достаточно, чтобы каждая ячейка
   получила свою запись многократно; порядок обхода и последний победивший
   байт задаются таблицей §4 (цвет зависит только от бита 1 индекса);
3. завершающий цикл — только бордюр 0 и цвет `0x80`, ~2 мс: он перекрывает
   ячейки 0 и 8 (последние попадания луча — фон и бордюр голубой), а
   жёлтые ячейки с битом 1 к этому моменту не трогаются.

Процедура одноразовая, идёт ПОСЛЕ отрисовки панелей и карты (§3, п. 6):
картинка уводится в stash (ниже 0x8000 — он не отображается и не индексирует
палитру), плоскость гасится, ставятся цвета, картинка возвращается (stash при
этом обнуляется, чтобы для мелких ROM в 0100..2FFF не осталось мусора). ~25 мс
самих цветов плюс по ~0,1 с на прятанье/возврат — всё это ДО включения мотора.

### 4.2. Конфиг цветов

Два байта в начале блока конфига (0xFB10, §2.1 и §7): `bg` и `line`. В
цикле палитры §4.1 вместо `MVI A,080h`/`MVI A,02Dh` стоит `LDA CFG_BG` /
`LDA CFG_LINE` (выбор по биту 1 индекса сохраняется), завершающий проход —
`LDA CFG_BG`. Стаб записывает конфиг в high RAM до прыжка в stage-2, а
`loader_boot` без конфига даёт дефолт `{0x80, 0x2D}` — картинка identical
прежней. Отдельного цвета у панелей (§5.2) не бывает: светящийся пиксель
плоскости C000 один и для арта, и для линий.

## 5. Карта загрузки (образ — boot.png)

Адресация плоскости C000 (256×256, проверено, `docs/VECTOR_VERIFIED.md` §7.1.3):
байт (col, row) лежит в `0xC000 + col*0x100 + (255 − row)`, бит 7 = левый
пиксель. Строка экрана = 32 байта со stride 0x100.

### 5.1. Нормативная геометрия сетки

Адресация та же, что в §5: байт (col, row) лежит в `0xC000 + col*0x100 +
(255 − row)`, строка — 32 байта со stride 0x100.

• **8 групп линий**, g = 0..7, базовая строка `r0 = 54 + 24·g`:
  – строка `r0`: **пунктир** — во всех 32 байтах `0x81` (по одному жёлтому
    пикселю на 8 с обоих краёв блока: бит 7 — левый, бит 0 — правый, ровно
    как `MVI M,81H` в очищающей петле CLEA3 у NEWROM);
  – строка `r0 + 1`: **сплошная** — `0xFF`;
  – строка `r0 + 10`: **сплошная** — `0xFF`;
• остальной C000 стёрт в 0 → голубой фон.

Разметка снята с boot.png: группы периодом 24 строки, в группе пунктир +
сплошная рядом и сплошная через 9 строк; линии на всю ширину.

**Не воспроизводится:** fade-in (15 кадров `WRCLR`) — палитра выставляется
слепым циклом за ~1 кадр (§4.1). Угловой блок меток и столбики приёма —
СМ. §5.3, они у нас воспроизведены портом `AKART`.

### 5.2. Панели (картинки в углы экрана)

Панель — 2-цветное изображение, которое stage-2 рисует В УГОЛ экрана до
сетки §5.1; сверху линии ложатся OR-ом, поэтому арт под ними не исчезает
(из 4352 пикселей сетки на арт попадают 107 — при безусловной записи они бы
пропали). Формат данных — плоскость C000 «как есть» (§5): байт = 8
**горизонтальных** пикселя, бит 7 = левый, строки сверху вниз, ширина
дополняется до кратной 8 нулями. Тогда `drawp` — чистое копирование байтов
в `0xC000 + (x/8)·0x100 + (255 − y)` с OR, без сдвигов и маскирования.

Геометрия задаётся дескриптором в блоке конфига (§4.2, §7): `x`, `y`, `wb`
(байт в строку), `h` (строк). `x` ОБЯЗАТЕЛЬНО кратен 8 (выравнивание по
блоку плоскости); `wb = 0` значит «панели нет» — она не рисуется (дефолт
`loader_boot`). Данные лежат в fixed-слоте high RAM по ФОРМУЛЕ
`LOADER_PANEL_BASE + номер·LOADER_PANEL_STRIDE` = `0xE300 + i·0xC00` (панель 1 —
0xE300, панель 2 — 0xEF00, по 3 КБ), куда их РАСПАКОВЫВАЕТ копир заставки
(§7); слот в стираемую 0x0000..0xDFFF область не попадает. Именно формула,
а не перечисление адресов, держат lib универсальной: если одна панель
дорастёт в пределах stride, соседняя не сдвинется и заголовок править не
потребуется. Верхняя граница stride — из геометрии high RAM: после кода
(768 Б) остаётся 0xE300..0xFFFF = 7424 Б, два слота + `drawp`/конфиг
умещаются при stride ≤ ~0xE70, 4 КБ на панель уже не влезают.

В ROM панели лежат СЖАТЫМИ ZX0 (`png2panel.py --zx0`), распаковывает их
стаб `boot/loader.asm` вызовом `zx0_decompress` (`lib/unpack/zx0.asm`, чистый
8080) ДО прыжка в stage-2 — в самом blob декодера нет (бюджет 768 Б, свободно
56 Б). Прямой порядок распаковки: сжатый поток в ROM лежит НИЖЕ слота
назначения (src < dst), области не пересекаются, конец потока — EOF-маркер
Elias(256), длину декодер не знает.

Конвертер — `utils/png2panel.py`: 2-цветный PNG (фон = самый частый цвет,
светится всё, что ему не равно — инверсная картинка тоже годится) в
`.inc`-массив DB и/или C-заголовок (`--emit h`) с геометрией. Режимы
`--corner top-left` / `bottom-right` / `xy,X,Y`. Ворота: РАЗУПАКОВАННАЯ
панель > `--slot` (по умолчанию 3072 Б) или `x` не кратен 8 — ошибка сборки;
в заголовок пишутся и `_SIZE` (размер в слоте), и `_CSIZE`/`_ZX0` для
сжатого потока. Демо-ассеты: `panel_top.png` 172×88 → 22×88 = 1936 Б
(ZX0 658 Б) в (0,0); `panel_bottom.png` 144×72 → 18×72 = 1296 Б (ZX0 419 Б)
в (112,184). Та же `pack_panel()` переиспользуется тестом раунд-трипа, чтобы
ожидание не расходилось с генерацией.

Ограничение: отдельного цвета у панелей не бывает (§4.2) — пиксель
плоскости C000 один и для арта, и для линий. Сжатие экономит ROM, а не
ОЗУ игры: слот всё равно вмещает РАЗУПАКОВАННЫЕ `wb·h` байт, зато в образе
заставки две панели весят 1077 Б вместо 3232 Б.

### 5.3. Прогресс приёма: порт `AKART`

Оригинал NEWROM в пути приёма LOA14-15 после копирования 32-байтного
подблока делал `POP B` / `MOV L,C` / `MOV H,B` / `CALL AKART` / `MOV M,E`,
где `E = 7Eh` из `LXI D, 207Eh` (D — счётчик байт, E не меняется в цикле).
Именно от этого на boot.png растёт «столбик» в группе и появляется
угловой блок меток в правом верхнем углу (страницы с большим `addrhi`
попадают в последние байты блока). Мы воспроизводим этот эффект портом
`AKART` (`newrom2.asm` 277..297) один-в-один в хвосте `sbc`.

Формула (8080-ротейты `RLC`/`RAR` — ЧИСТЫЕ 8-битные: bit7<->bit0
замыкаются внутри A, CY = выходящий бит, вход CY не участвует; отсюда
безопасность `RAR → ANI 70h` в листинге):

```
col      = addrhi & 1Fh
row_byte = 24 + 24*(addrhi>>5) + (addrlo>>5)
addr_vram = 0xC000 + col*0x100 + row_byte
```

8 подблоков страницы (offset 0x00..0xE0 шаг 0x20) дают 8 РАЗНЫХ байт
внутри группы — байты 24..31 группы (VRAM-строки 8..15 в нумерации
«255 − row»), то есть ровно между двумя линиями сетки §5.1 (пунктир
на `r0` = 54+24g и сплошные на `r0+1`, `r0+10`). Столбик заполняется
сверху вниз по мере приёма подблоков; страница целиком = 8 жёлтых
«засечек» 6×1 пиксель в своей колонке `addrhi & 1Fh`.

Запись `MOV M, E` — безусловная (не OR): там, где ячейка столбика
совпала с артом панели, стоит именно 7Eh. Раунд-трип моделирует это
в `screen_expect(panels, rom)`: сначала OR линий сетки и панелей,
затем безусловная расстановка принятых ячеек; расхождение — FAIL.

Fade-in (15 кадров `WRCLR`) остаётся не воспроизведённым: у нас палитра
готовится за ~1 кадр слепым циклом (§4.1), поэтому «проявления» карты
нет — столбики просто дорисовываются по мере приёма.

## 6. Протокол ленты v06c-rom (нормативно)

Физический уровень. Порт 01h бит 4 — вход с магнитофона (меандр,
`vio.h: tape.sample() << 4`). Кодировщик — `utils/rom2mp3.py`:
• уровни в PCM: «низкий» 32, «высокий» 223 (unsigned 8-bit), тишина 0x80;
• полупериод (фаза) = `SPEED` = **8 сэмплов @ `SAMPLE_RATE` = 22050 Гц** =
  363 мкс = **1088 t-состояний** на 3 МГц; бит = 2 фазы = 16 сэмплов =
  726 мкс = 2177 t; байт = 8 битов = 16 фаз = 128 сэмплов;
• бит 1 = «низкий→высокий» (начинается с низкого), бит 0 = «высокий→низкий»;
  байт = 8 бит MSB-first; стыки однополярных половин дают импульс удвоенной
  длины — декодер различает 0/1 по **фазе** последовательности переходов,
  поэтому декодер обязан быть самокалибрующимся по первому переходу
  (реализация TSBIT/MITAP из NEWROM — эталонная, переносится как есть,
  кроме `RST 7` → прямой `CALL` внутренней задержки, §3.1);
• **у узла выборки два входа — это не косметика.** В newrom2.asm обработчик
  `RST 7` = `LDA CONR → DELAY → REATP` (`IN/ANI/MOV E,A/RET`), и `MITAP` на
  входе зовёт `CALL REATP` — **без задержки**; с задержкой работает только
  `RST 7` внутри цикла битов (и в `TBIT`). Если задержку оставить и на входе
  в `MITAP`, она набегает ещё раз после 0.75T, отработанных на последнем бите
  предыдущего вызова: фронт на границе байта теряется, и разбивка по байтам
  уплывает на бит каждый байт — синхробайт не набирается никогда. У нас тот же
  двухвходовый узел: `SAMPLE` (задержка+выборка) и `RDATAP` (только выборка);
  как опкод `RST` не используется — прерываний нет (§3.1), самомасштабирование
  TSBIT покрывает изменившуюся длину цикла;
• окно захвата: выборка обязана попадать между первым и вторым фронтом после
  обнаруженного, то есть `1 фаза < CONR·(dcr a + jnz) < 2 фазы`. При
  плотности потока 8080 (15 t на итерацию задержки, 39 t на итерацию
  счётного цикла `RTF11`) калибровка `RCON3` даёт `CONR ≈ 75..90` — задержка
  1.08..1.30 фазы: в густых сериях (байты 0x00 — фронты каждую фазу) чётность
  пропущенного фронта неустойчива и байт читается как 0F/FF, в редких (0x55 —
  фронт на бит) всё ровно; это поведение оригинала, синхробайт и ловится
  только внутри групп 0x55 (см. п. 1 приёма);
• задержка между выборками — `CONR` (ячейка 0xE224), калибруется по
  измеренному периоду, как `RCON3` в newrom2.asm; важно: `STA CONR` в калибровке
  — это `ADD D` без переноса, то есть намеренное (унаследованное) 8-битное
  переполнение: сумма двух замеров ~334 даёт 78, что и попадает в окно захвата.

Поток (для одного ROM, кодировщик `maketape_v06c_rom(rom, 0x0100, name)`):

```
преамбула 200 Б: 25×0x00, 25×0x55, … (8 групп)
для каждого блока b = 0..N-1 (N = ceil(size/256), rev = N−b):
  заголовок 56 Б: 16×00 | 4×55 | E6 | 4×00 | name[25] | 00 00
                  | addrhi | N | rev | cs0        (cs0 = sum(name)+addrhi+N+rev)
  8 подблоков s = 0x80..0x87, по 40 Б: 4×00 | E6 | s | cs0 | payload[32] | cs
                  (cs = s + cs0 + sum(payload))
```

Длина записи после E6 — 35 байт и в заголовке, и в подблоке (поле `name[25]`
считается как данные). Блок целиком — 56 + 8×40 = **376 байт ленты** = 2,18 с;
максимальный образ (191 блок) — 191×376 + 200 = 72 016 байт ≈ **419 с**. Эти
числа важно не путать: в записях «заголовок 40 Б» и «подблок 37 Б» (так считали
по документации формата, а не по кодировщику) блок выходил 336 Б, и тестовый
«запас по времени» оказывался короче самой ленты — на 191 блоках не хватало
44 с, и провал выглядел как «загрузчик не успел», хотя он просто ещё не
дослушал последние страницы.

Приём (порт логики newrom2.asm; поля записей нумеруются от первого байта
после E6):
1. синхробайт: 12 подряд байт `0x55` или `0xAA` (смесь разрешена); срыв —
   перекалибровка CONR и заново;
2. `READB`: синхронизация по паттерну `0xE6` (паттерн потребляется в
   процессе посимвольно, в буфер не кладётся; инверсия ленты автодетектится
   по `0x19`);
   принять 35 байт после E6 в ABUFF; контрольная сумма: кумулятивная
   с нуля, последний байт == сумма предыдущих 34; не совпало — READB
   пересинхронизируется и принимает запись заново (внутренний цикл, как
   оригинал);
3. заголовок: первый байт == 00 (отличие от подблока, у которого там id);
   сверка `N == rev` (это первый блок — иначе полная ресинхронизация),
   E ← cs0 заголовка (он же поле cs0 подблоков), D ← N (счётчик блоков),
   адрес загрузки addrhi — страница приёма (B); addrhi ПЕРВОГО заголовка
   дополнительно сохраняется в `STARTHI` — это адрес старта образа, на
   который уйдёт выходной `PCHL` (§3.8);
4. подблоки: id 0x80..0x87, cs0 поля == E; 32 байта пишутся **линейно** в
   `addrhi:0000 + (id−0x80)*32 + i`; после записи байт буфера ленты обнуляется
   (гигиена оригинала сохранена);
5. cs0 заголовков убывает на 1 по блокам (кодировщик: cs0 =
   sum(name)+addrhi+N+rev, а rev убывает) — расхождение признаётся
   ошибкой: полный рестарт приёма; каждый новый заголовок уменьшает
   счётчик блоков D; конец загрузки: 8 подблоков последнего блока
   (D == 1, SBCNT досчитан до нуля);
6. отбраковки NEWROM не переносятся: сверка «0x81 в VRAM» (TESTL) и отметки
   прогресса в плоскости — в §5 помечены как невоспроизводимые.

Восстановление после помех: любая ошибка контрольной суммы/номера блока →
полный рестарт приёма с поиска синхробайта (как `JMP LOADF`). Поток
переписываемый: блоки независимы, повторная запись страницы допустима.

## 7. API (v06.h)

```c
/* Высокая RAM загрузчика (§2.1): конфиг и слоты данных панелей. Слот —
 * ФОРМУЛА base + номер·stride, а не перечень адресов: lib остаётся
 * универсальной при росте любой панели в пределах stride. */
#define LOADER_CFG_ADDR     0xFB10u   /* struct loader_cfg как есть, 14 Б */
#define LOADER_PANEL_BASE   0xE300u   /* слот панели 0 — сразу за кодом blob */
#define LOADER_PANEL_STRIDE 0xC00u    /* 3 КБ на панель (бюджет png2panel --slot) */
#define LOADER_PANEL_ADDR(i) (LOADER_PANEL_BASE + (i) * LOADER_PANEL_STRIDE)
#define LOADER_PANEL1_ADDR  LOADER_PANEL_ADDR(0)
#define LOADER_PANEL2_ADDR  LOADER_PANEL_ADDR(1)

/* Одна панель (§5.2): геометрия; данные — плоскость C000, их генерирует
 * utils/png2panel.py. wb = 0 значит «панели нет». */
struct loader_panel { unsigned char x, y, wb, h; };

/* Конфиг: два цвета и до двух панелей, 14 байт. Указатели на данные —
 * адреса ZX0-потоков внутри ROM заставки; стаб РАСПАКОВЫВАЕТ картинки
 * в слоты сам, в stage-2 указатели не попадают. */
struct loader_cfg {
    unsigned char bg, line;      /* фон/бордюр и линии+арт (§4.2) */
    struct loader_panel p1, p2;
    const unsigned char *p1_data, *p2_data;
};

/* LOADER — второй загрузчик (boot/loader.asm). Вызывается ROM-заставкой
 * после нажатия клавиши. НЕ ВОЗВРАЩАЕТСЯ: копирует stage-2 в 0xE000, стирает
 * 0x0000..0xDFFF, рисует карту и принимает следующий ROM (v06c-rom), затем
 * PCHL на addrhi:0000 — переход на фактический старт образа (§3.8).
 * Прерываний нет; hardware reset попадает в заглушку JMP 0E000h в 0x0000. */
extern void loader_boot(void);

/* То же, но цвета и панели из cfg; дефолтный loader_boot эквивалентен
 * cfg = {0x80, 0x2D, панели пустые}. Панели рисуются до сетки, линии — OR. */
extern void loader_boot_cfg(const struct loader_cfg *cfg);
```

`loader_boot` без аргументов: имя ленты и адрес берутся из заголовка
потока; заставка решает сама, когда звать. Точка входа следующего ROM
задаётся переходом `PCHL` на `addrhi:0000` (§3.8) — addrhi первого заголовка
ловится в `STARTHI`; один и тот же выход запускает и `.rom` (0x0100), и
`.r0m` (0x0000). `loader_boot_cfg` принимает указатель на
`struct loader_cfg` в ROM заставки: стаб (`boot/loader.asm`) до прыжка в
stage-2 копирует в high RAM blob, 14 байт конфига (в 0xFB10) и для каждой
панели с `wb ≠ 0` — РАСПАКОВЫВАЕТ её ZX0-поток (`zx0_decompress`,
lib/unpack/zx0.asm) в слот `LOADER_PANEL_ADDR(i)`. Картинки и конфиг лежат
выше 0xE000, куда очистка §3.2 не доходит,
поэтому доживают до приёма ленты (§2.1). Указатели `p*_data` смотрят в ROM
(адреса ниже слотов) — это требование прямого ZX0-декодера: src < dst,
области не пересекаются.

ссылается стаб): blob он тянет `INCLUDE`'ом из `.inc` внутри этого
модуля — тот же порядок, что у шрифтов (`default_8x8.inc` подключён из
`gfx/pr.asm`, в `SRCS` проектов его нет). `.inc` при этом — prerequisite цели
сборки (`GEN_INC` в `boot-demo/Makefile`), иначе пересобранный stage-2 не
перетригнет ROM. `boot-demo` — в общий список `TESTS` корневого Makefile.

Ограничения размера: код blob ≤ 768 Б (область 0xE000..0xE2FF, проверяется
целью `loader2` через `bin2inc.py --max 768`; сейчас ~712 Б; сразу за ней —
слоты панелей 0xE300/0xEF00, рост кода сверх бюджета упрётся в панели и
будет отвергнут сборкой), стаб —
порядка 90 Б + ZX0-декодер (он в бюджет blob не входит). Панели — до
`LOADER_PANEL_STRIDE` = 3 КБ каждая в своём слоте, ворота `png2panel.py
--slot` (§5.2).

## 9. Верификация

1. **Сборка:** `make loader2` — z80asm без предупреждений, размер кода ≤ 768.
2. **Раунд-трип протокола (главный критерий), Python:**
   `v06_emu.py::CPU8080` имеет хуки `io_read`/`io_write`, но **t-состояния не
   считает** (у него только счётчик команд) — виртуальные такты тесту придётся
   копить самим по таблице opcode→t (для 8080 она конечна и известна). Тест
   (`.scratch/rt/loader_rt.py`, диагностик приёма `.scratch/rt/diag2.py` —
   точки наблюдения выводятся из `.scratch/loader_stage2.sym`, а не прописаны
   числами):
   – модель ленты: по текущему t-состоянию вычисляется сэмпл потока
     (`3 000 000 / SAMPLE_RATE = 136,05 t на сэмпл; фаза = 8 сэмплов =
     1088 t), его уровень → бит 4 порта 01h;
     вход теста — поток `maketape_v06c_rom` из `rom2mp3.py`, а не сам WAV;
   – прерываний в модели теста не нужно: stage-2 не включает `EI`, не
     выполняет `HLT` и не пишет вектора (§3.1); гонка идёт при DI до JP;
   – в эмулятор грузится stage-2 blob по 0xE000 + следующий ROM «в ленте»;
   – **размер образа в тесте обязан быть не меньше ~2 КБ (8 страниц).**
     Калибровка `RCON3` — дорогая: TSBIT усредняет 32 интервала, а любой
     интервал, отклонившийся больше чем на T/2, начинает усреднение заново
     (`JNC TSF10`), поэтому один замер съедает ~150 фронтов; на успех
     `RCON1` (второй замер ≥ 1.5× первого — ловля границы групп 0x00/0x55)
     уходит ~16 замеров ≈ 3 с ленты на раунд. Преамбула же — 200 байт =
     0,73 с, и группы 0x55 в ней по 25 байт: одностраничный ROM 256 Б
     (поток ~3 с) физически не может дать 12 подряд синхробайтов — это
     ограничение теста, а не загрузчика. Точка, в которую приходит конец
     калибровки, детерминирована (наблюдение: байты 33,6 / 83,6 / 133,6 /
     183,6 — каждые 50 байт);
   – после `PCHL` на `addrhi:0000` — сравнение RAM 0x0100.. с исходным
     образом **байт-в-байт**, проверка карты (пиксели §5 и панели §5.2) и
     стёртой области: 0x0000..0xDFFF обязан быть нулём, кроме ROM,
     нарисованного экрана и заглушки сброса `C3 00 E0` в 0x0000..0x0002
     (§3.8-reset). Стек и приёмный буфер stage-2 лежат ВНУТРИ стираемой
     области (SP = 0DCF0h, ABUFF = 0DED0h..0DEF2h, переменные 0DEF4h..0DEF8h),
     поэтому проверка делает исключение для этих «живых» окон: их содержимое
     зависит от порядка вызовов и принятых записей; отдельно проверяется,
     что ABUFF содержит хвост последней записи (id=0x87) и что STARTHI=01h,
     палитра и бордюр — по хукам io_write (содержимое ячеек 0/8 в слепом
     методе §4.1 зависит от луча — в эмуляторе проверяется только факт
     записей в 02h/0Ch, корректность цветов — на реальном железе).
   – путь `.r0m` (addrhi=0x0000) проверяется отдельным прогоном
     (`.scratch/rt/probe_r0m.py`): `PCHL` приводит в 0x0000, приём затирает
     заглушку своим кодом, образ побайтово верен.

   Эталон переноса — исходники NEWROM v2.0 (TMK Soft'91): `kish1.asm` (сырая
   разметка адресов) и `newrom2.asm` (та же программа с метками TBIT/TSBIT/
   READB/MITAP/REATP/RCON3, кодировка CP866). Правки, отличающие наш приём от
   оригинала, допустимы только те, что тут перечислены: `RST 7` → `CALL`
   двухвходового узла (§6), явная инициализация `PRINV` (§2; сам буфер и
   переменные стоят на адресах NEWROM), отбраковка TESTL (п. 6 приёма), счётчик
   подблоков `SBCNT` вместо скана карты, выход `PCHL addrhi:0000` вместо
   `JMP 0000H` (§3.8). `AKART` и метки прогресса карты ПЕРЕНЕСЕНЫ один-в-один
   (§5.3) — это не «правка», а порт; в листинге их отсутствие было бы
   расхождением.
   Всё остальное — включая порядок `PUSH`, значения констант (`MVI E,12`,
   `LXI B,0023h`, `LXI D,207Eh`) — обязано совпадать байт в байт по логике:
   расхождение в одну выборку уровня ломает приём так, что по таймингам это
   не выглядит ошибкой.
3. **Статическая:** каждая команда blob — 8080 (таблица
   `docs/VECTOR_CPU_COMMANDS.md`); ссылок вне разрешённых областей нет —
   проверяется тем же обходом, что и п. 9.4: `disasm8080.py --refs
   0e000-0e2ff --ref-allow 0000-0002,0c000-0dfff,0fb00-0fb0f,0fb10-0fb1f`
   собирает 16-битные адресные операнды всех `LDA/STA/SHLD/LHLD/JMP/CALL/
   Jcc/Ccc` и ругается на попадание вне диапазонов (`refs_out_of_range=0`);
   `--ref-allow` принимает и одиночные адреса, и диапазоны `lo-hi`. `LXI` в
   список не входит сознательно: это непосредственное значение регпары, а не
   обращение, и оно легально указывает в стираемую область (`LXI SP,0DCF0h`,
   цикл очистки, `LXI B,0023h`); в листинге нет `EI`, `HLT`, `RST`, а
   обращения к низкому региону — только заглушка сброса `STA 0000h..0002h`
   (§3.8-reset) и выходной `PCHL` (§3.8); вектор 0x0038 не пишется.
4. **Дизассемблирование бинаря (операнды Вектора-06Ц).** `loader_stage2.bin`
   целиком прогоняется через дизассемблер 8080 (скрипт по таблице
   `docs/VECTOR_CPU_COMMANDS.md`), байт за байтом от 0xE000: поток должен
   декодироваться валидными командами i8080 от первого до последнего байта,
   без `DD`/`FD`/`ED`/`CB`-префиксов **на позициях опкодов** и без смещения
   («висящих» операндов) — иначе код, собранный как Z80, на 8080 исполнялся
   бы другими командами. Те же байты внутри непосредственных значений и
   адресов законны (например `FD` — старший байт `JNZ E0FDh`), поэтому
   критерий проверяется обходом команд, а не поиском по сырым байтам.
   Проверяется именно бинарь: z80asm собирает Z80-расширения молча, и чистая
   сборка (§9.1) об ошибке ничего не сообщает. В том же обходе контролируется
   отсутствие `EI`, `HLT` и `RST` (§3.1) и адреса ссылок (п. 9.3) — цель
   `make loader2` запускает дизассемблер с обоими флагами и падает на любой
   из претензий.
5. **Ручная (реальный Вектор/эмулятор с лентой)** — вне объёма автоматизации,
   сценарий из `roms/tests/boot-demo/`: загрузка `.rom` заставки штатным
   способом → клавиша → карта → `rom2wav.py` второго ROM → приём → вход в
   него. Сравнение экрана с `docs/etalon/boot.png` (кроме углового блока,
   §5).

## 10. Критерии приёмки

• [ ] `loader_boot()` объявлен в `v06.h`, реализован в `lib/boot/loader.asm`;
• [ ] blob собирается из `lib/boot/loader_stage2.asm` отдельным модулем с
      `ORG 0xE000`, ≤ 512 Б, самодостаточен (ни одного EXTERN);
• [ ] конвейер §3 соблюдён дословно, включая DI-до-очистки;
• [ ] прерываний нет нигде: в листинге ни `EI`, ни `HLT`, ни `RST`, вектор
      0x0038 не пишется (§3.1, §4.1, §6);
• [ ] бинарь stage-2 целиком декодируется как валидный i8080 (§9.4): без
      DD/FD/ED-префиксов и без смещения потока — операнды Вектора-06Ц, а не
      другого процессора;
• [ ] карта §5 совпадает с boot.png по геометрии (угловой блок отсутствует
      осознанно);
• [ ] раунд-трип §9.2 проходит на эталонном потоке `maketape_v06c_rom`
      (многостраничный ROM ≥ 2 КБ — см. требование к размеру теста — и
      48896 Б);
• [ ] следующий ROM > 48896 Б не может быть принят молча: кодировщик/тест
      документирует лимит (сам stage-2 его не проверяет — физически не может);
• [ ] докованы: `lib/README.md`, `docs/README.MD`, цель `make loader2`;
• [ ] собран `roms/tests/boot-demo/` (заставка → `loader_boot()`), добавлен
      в `TESTS` корневого Makefile, сценарий ручной проверки §9.5 проходит.
