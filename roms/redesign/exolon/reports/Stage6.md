## Goal

Закрыть Stage 6 из `TZ.md` (строки 198–206):

1. найти функцию вывода строк и её базовый адрес глифов (`data_glyph_block`);
2. подтвердить растровую сетку глифов `glyph_scan` (PNG на адресе блока);
3. предсказание картинки сверить с реальностью `vram_credits`;
4. ИИ подтверждает и классифицирует строки, создаёт объекты `str_*` (комментарий = расшифровка
   транслита в русский);
5. определить кодировщик — таблицу соответствия ASCII-кодов и кириллических глифов. TZ
   утверждает: `[`→Ш, `]`→Я, `^`→Ч, `Q`→Я, `X`→Ь, `Y`→Ы, `V`→Ж, `W`→Щ.

## TL;DR (вердикт)

Текст рисует **интерпретатор списка отображения** `func_display_interpreter @0x3CC1`: он читает
display-list **из ROM по месту** (копии в RAM нет) и на текстовых байтах вызывает рендер глифа
`func_draw_glyph_base @0x3B5B`. Адрес источника глифа = **`[3B19] + code*8`** (трассировка:
`ADD A; DAD H ×2` ⇒ 8·code, затем `LHLD 3B19; DAD B`). Базовый регистр `[3B19]` по умолчанию
равен **0x2530** (`LXI H,2530 / SHLD 3B19`) и переключается опкодом **0xE6** (2-байтный
little-endian операнд). В игре **два шрифта**: латиница/цифры (база-регистр 0x2530) и кириллица
(база-регистр 0x732D). Оба регистра указывают на **0x100 байт НИЖЕ** реальных растров
(«виртуальная база»: коды 0x00–0x1F не рендерятся и алиасились бы в код), поэтому фактические
блоки битмапов: **латиница 0x2630–0x282F**, **кириллица 0x742D–0x762C**. Сетка — 8 байт/глиф
(8×8 моно), подтверждена `glyph_scan`. Кодолист восстановлен по растрам и **опроверг TZ** в двух
позициях: `]` = **Щ** (не Я), `W` = **В** (не Щ). Создано **33 объекта `str_*`** + 2 блока
глифов; побайтовый round-trip совпал (SHA идентичен).

## Архитектура вывода текста

```
func_display_interpreter @0x3CC1   ; читает display-list из ROM, RLE-опкоды позиции/цвета/повтора/текста
  │  опкод 0xE6 <lo> <hi>          ; смена базового регистра глифа [3B19] := word  (кириллица/латиница)
  │  байт < 0x61                   ; текстовый код глифа
  └─▶ func_draw_glyph @0x3B00 / func_draw_glyph_base @0x3B5B / func_draw_glyph_masked @0x3BA2
          адрес источника = [3B19] + code*8        ; 8 байт = 8 строк по 8 пикселей (моно)
          побитовый blit в overlay-буфер (0x8E30) → экран
```

Дефолт базы ставится в boot-коде: `LXI H,2530 / SHLD 3B19`. Далее:

| Display-list | Опкоды базы | Шрифт | Блок битмапов |
|---|---|---|---|
| info `0x7890` | `E6 2D 73` → **[3B19]=0x732D** | кириллица | `0x742D–0x762C` |
| title `0x7782` | `E6 30 25` (лат.) + `E6 2D 73` (кир.) | оба | оба блока |
| HUD/round-end/bonus/game-over | дефолт **0x2530** | латиница | `0x2630–0x282F` |

### Виртуальная база (почему блок не по адресу регистра)

Регистр базы на 0x20·8 = 0x100 ниже начала растров: `0x2530 + 0x20·8 = 0x2630`,
`0x732D + 0x20·8 = 0x742D`. Коды 0x00–0x1F (управляющие, на экран не выводятся) при таком
раскладе попадают в предыдущий код — это **не данные шрифта**, поэтому объекты `data_glyph_block_*`
заведены на **фактические** адреса растров (0x2630 / 0x742D), а не на значения регистра. Это же
спасло от ошибки: область 0x732D–0x742C формально «попадает» в формулу, но содержит реальный код
(`func_blink_toggle @0x7335`, `func_poll_rus_continue @0x73FD`) — дизасемблирование 0x2638 (битмап:
паттерны `38/6C`) против 0x2568 (код: `LXI H,252B …`) подтвердило границу.

## Растровая сетка (glyph_scan)

`analyze.glyph_scan --rom exolon.rom --address 0x742D --width 8 --height 8 --layout mono`
→ вердикт `32 глиф(а) из 32, групп повторов 0, источник IMAGE`, `rdb_object =
data_glyph_block_cyrillic` (аналогично `0x2630 → data_glyph_block_latin`). Сетка подтверждена:
**stride = 8 байт, 8×8 моно, 1 глиф на код**, дублей нет. Тайлы PNG — в `.scratch/`.

Пример растров (ASCII-арт прямо из ROM, `#` = бит), спорные коды кириллицы:

## `vram_credits`: почему no_prediction

`analyze.vram_credits --string 0x77AA --run 3` → вердикт
`no_prediction: строка не найдена в текстовом буфере RAM`, `cursors_found = []`,
`column_table = null`, `glyph_table = null`, `base_low@0x08D0 = 0x00`.

Модель `vram_credits` предполагает **RAM-буфер символов** (0x5000–0x5400), который покадрово
рендерится в VRAM через `func_render_glyph` + таблицы баз столбцов/указателей глифов (это
механика **Stage 7**, на что указывает докстринг модуля: «Stage 7, Finding 2»). У Exolon путь
вывода иной: `func_display_interpreter` читает display-list **из ROM по месту** и растеризует
глифы сразу в overlay/VRAM — промежуточного знакобуфера в RAM нет, поэтому предсказывать
адрес не по чему. **Сверка предсказания с реальностью для Stage 6 выполнена живым скриншотом**
(§выше); полную адресную реконструкцию VRAM осмысленно отложить до Stage 7, где появится
`func_render_glyph` и таблицы.

## Расхождения с TZ (важно)

| Утверждение TZ (стр. 205–206) | Факт по растровым битмапам ROM |
|---|---|
| `]` → **Я** | `]` (0x5D) = **Щ** (Ш с хвостом вправо-вниз). Я — это `Q` (0x51) |
| `W` → **Щ** | `W` (0x57) = **В** (B-форма с двумя чашками). Щ — это `]` |
| `[`→Ш, `^`→Ч, `Q`→Я, `X`→Ь, `Y`→Ы, `V`→Ж | подтверждены побитово |

Ошибка TZ, похоже, — транспозиция: `]` и `W` перепутаны местами (TZ дал Я/Щ вместо Щ/В).
Решение принято по растрам, не по тексту ТЗ.

## Limitations / открытые вопросы

- **`vram_credits` не дал адресного предсказания** (нет RAM-знакобуфера на этом пути) — полная
  VRAM-реконструкция отложена до Stage 7 (`func_render_glyph` + таблицы столбцов/глифов).
  Реальность на Stage 6 подтверждена живым скриншотом, а не арифметикой адресов.
- **`syntax_check`: 180 «undefined symbol» (90 `rst <символ>` × 2) — наследные, НЕ Stage 6.**
  Все это ссылки `rst` на векторы 8080 (`label_0008/0010/0018/0020/0028/0030`, адреса < origin
  0x0100, потому в ASM не эмитируются как метки) и на `func_irq_vblank @0x0038` (объект Stage 4).
  К строкам/глифам Stage 6 отношения не имеют; побайтовый round-trip от них не зависит
  (SHA совпадает). Это артефакт символьной аннотации человекочитаемого ASM.
- `conflicts: 1` в отчёте экспорта — поле внешнего `v06c-asm-export`; побайтовых пересечений
  по адресным интервалам между всеми 452 объектами RDB — **0** (проверено подинтервально), в том
  числе мои 35 объектов (2 блока + 33 строки) не пересекаются ни с чем. Природа этой единичной
  метки экспорта не расшифрована (вне Stage 6), на побайтовый round-trip не влияет (SHA совпадает).
- Латинский блок 0x2630–0x282F и кириллический 0x742D–0x762C перекрываются по кодам 0x20–0x5F,
  но это два разных шрифта (разные базовые регистры) — не конфликт, а штатный выбор гарнитуры
  опкодом 0xE6.
- Строчные кириллические глиф-коды (0x61+, малые буквы) на скриншотах не встречались — в игре
  текст верхним регистром; нижний регистр кодовой страницы в отчёте не исчерпывающе проверен.
