# TZ2. Редизайн `riseout`: основной цикл на C, примитивы — ASM самой игры

Документ продолжает `TZ.md`. **TZ закрывается на Stage 10** — побайтовой
реконструкции `RISEOUT_NEW.ROM ≡ riseout.rom` из дерева `./asm/` и RDB
`src/riseout.rdb`. TZ2 — **следующий, вне-TZ этап**: превратить разобранную ROM
в поддерживаемую пересборку, где **основной цикл заставки и основной цикл игры
написаны на C**, а все примитивы ввода-вывода — **перенесённый ASM самой игры**.

> **Рамка.** Это **редизайн, а не реконструкция**. Контракт «RDB → ASM → ROM
> byte-for-byte» держится только до Stage 10 и здесь **осознанно ломается**:
> C-код даёт другую раскладку кода и допустимо другие адреса.
> Критерий приёмки TZ2 — **семантическое** поведение (играется как оригинал), а не
> хеш. Исходник-эталон `src/riseout.rom` и RDB не правятся — они только источник
> истины по адресам/форматам данных.

---

## 0. Главный принцип: `lib/` и `v06.h` не используются

**Всё, что нужно игре, уже есть в игре.** Вектор-06C-специфичный код
(вывод глифов, бит-плоскости, палитра, клавиатурная матрица, VI53/AY, ISR)
в TZ2 **переносится из `asm/` оригинала**, а не берётся из `lib/`.

Запрещено подключать в сборке редизайна:

| Не используется | Почему |
|---|---|
| `lib/v06.h` | описывает API `lib/`, которого в редизайне нет |
| `lib/gfx/*` (`gfx_print`, `gfx_put_char`, `pr.asm`, `mode.c`, `clr.asm`) | в ROM есть свой рендер глифов и своя заливка плоскостей |
| `lib/kbd/*` (`kbd_scan`, `keyboard.c`) | в ROM свой строб rows и кольцо клавиш |
| `lib/snd/*` (`music.c`, `sound.c`, `vi53`, `ay`) | в ROM свой музыкальный драйвер и воркеры |
| `lib/sys/startup.asm`, `v06io.asm`, `v06pal.asm` | в ROM свой `func_boot_init` + ISR с палитровой рампой |

`lib/` остаётся источником только **тулчейка** (`z88dk/`, `config.mk`,
`finally.mk`, target `+vector06c`) и **формата ROM-контейнера**
(`utils/romconsist.py`). Из `docs/` остаются нужными только `Z88DK_CALL.md` (§4 ниже)
и `VECTOR*.MD`.

Единственный заголовок с прототипами в редизайне — `remake/inc/riseout.h`.
Он объявляет **ASM-шов игры**, а не API библиотеки.

## 2. Шов C ↔ ASM

C **принимает решения, ASM исполняет их над железом**. При этом ASM — это
функции оригинала, у которых уже есть свои контракты (входы `A`/`HL`/`DE`/`BC`,
выходы, side-effects). Редизайн эти контракты **сохраняет**, а не изобретает
свои: C подстраивается под игру, а не игра под C.

### 2.1 Инвентарь переносимых примитивов

| Модуль редизайна | Что переносится из ROM | Адреса |
|---|---|---|
| `remake/boot_riseout.asm` | `func_boot_init`, `func_install_vectors`, `func_irq_vblank_dispatcher`, `func_irq_frame_service` (палитра OUT 02/0C, строб rows, кольцо клавиш, скролл), `func_irq_scroll_deferred`, `func_irq_sound_one_shot` | 0x0100, 0x04B5, 0x04D6, 0x04F7, 0x03D7, 0x035E |
| `remake/font_riseout.asm` | `func_render_glyph_vram`, `func_write_plane_run`, `func_put_char_glyph`, `func_fill_char_glyph`, `func_copy_text_block` | 0x0551, 0x05B7, 0x0124, 0x0142, 0x017C |
| `remake/text_riseout.asm` | `func_draw_text_records`, `func_draw_text_record`, `func_draw_text_record_safe`, таблицы записей, HUD-цифры | 0x2D1B, 0x16F3, 0x2D2F, 0x2B8B |
| `remake/gfx_overlay_riseout.asm` | оверлей заставки: `func_attract_load_overlay`, `func_attract_draw_window`, `func_attract_draw_row`, `func_attract_plot_bits`, обработчики плоскостей, `func_attract_plane_shift` (звёзды), таймер/RNG | 0x2893, 0x265B, 0x2680, 0x27E1, 0x284A, 0x2A9A, 0x2A4D, 0x2A7C |

| `remake/snd_riseout.asm` | `func_music_start/stop`, `func_music_load_track`, воркеры голосов, `func_sound_cmd_dispatch`, диспетчер VI53/AY | 0x2D7A, 0x2D72, 0x2E2E, 0x2FA6, 0x0206 |

| `remake/data_*.asm/.h` | шрифт, карты, партитуры, палитры, таблицы плоскостей/масок | `asm/data/data.asm` |

### 2.2 Что уезжает в C

Только управляющая логика, без единого `OUT` и без адресов VRAM:

- `attract_screen()` — автомат заставки (`var_menu_state` титул → HOW MANY
  PLAYERS → SELECT SPEED LEVEL), выбор числа игроков/скорости по слотам,
  мигание подсказки, выход по подтверждению всех слотов, вызовы примитивов
  оверлея/текста/музыки.
- `game_loop()` — счётчики проходов (поле «раз в 3», клавиши «раз в 5»),
  round-robin игроков, счёт/жизни/уровень, события уровень-пройден/смерть,
  game-over/high-score, вызовы blitter/HUD/SFX.
- `level.c` — чтение карт уровней, спавн, проверка «на верхней строке»,
  генерация поля (решение), плюс вызов ASM-исполнения.

Признак правильности шва: **в C нет ни одного literal-адреса VRAM, порта или
`var_*`-ячейки ROM**. Если C приходится писать в `0x8000` или дёргать
`OUT 0Ch` — этот кусок ошибочно не донесли в ASM.

## 3. Память и размещение

Примитивы оригинала работают с фиксированными ячейками (`[0x081C]`, `[0x082A]`,
`[0x0834]/[0x0836]/[0x0838]`, кольцо `[0x081F+A]`, курсор `[0x082E]`,
`[0x083C]`, RAM-буферы `0x6000`/`0x6400`/`0x6700`/`0x7000`/`0x7500`, текстовые
страницы `0x5400..0x56FF`, таблица режимов `0x5800..0x5FFF`, `var_*` в
`0x7Cxx..0x7Dxx`, временный байт `0xFFFE`). Поэтому:

1. **Ячейки ROM-примитивов сохраняют свои адреса.** Они объявляются в
   абсолютном сегменте (`SECTION ... AT 0xnnnn`, у z80asm флаг `-a`) ровно тем
   же именем, что в `asm/` (`var_scratch_word`, `var_menu_state`, …). Порт
   функции при этом остаётся **дословным** — правки только в именах меток и в
   базах данных, перенесённых в ROM-образ.
2. **Текстовые страницы и таблица режимов остаются в `0x5400..0x5FFF`.**
   Рендер глифов выводит адрес как `(текстовый адрес) + 0xAC00`, то есть
   страница `0x54/0x55/0x56` → плоскости `0x8000/0xA000/0xC000/0xE000` со
   смещением строки из `[0x081C]` (= `0xE0`, ставится инициализацией). Сдвиг
   этих страниц ломает побайтовый порт рендера — не делаем.
3. **VRAM — `0x8000..0xFFFF`**, все четыре плоскости активны: режим 256×256,
   16 цветов, индекс пикселя = вес плоскости (`0xE000`→1, `0xC000`→2,
   `0xA000`→4, `0x8000`→8). Разделение по плоскостям в заставке:
   **звёзды — `0xE000`** (единственное, что скроллится `func_attract_plane_shift`),
   **текст — `0xA000` + `0x8000`**, **точечная надпись RISEOUT —
   `0xC000` + `0xA000` + `0x8000`**. Палитра загружается своей рампой из ROM,
   как в оригинале.
4. **Стек.** Оригинал: `LXI SP,0100h` (растёт вниз от `0x0100`, до `0x5100`).
   Редизайн оставляет ту же схему: CRT0 задаёт `SP` в нижней части RAM, выше —
   код, данные и BSS компилятора, затем `var_*`, затем текстовые страницы и
   буферы. Проверка на каждом этапе: `SP` не уходит ниже `0x0100` и не задевает
   ROM-слоты.
5. **C-глобальные (BSS компилятора) могут лежать где угодно** — они не
   участвуют в побайтовом порте. Единственное требование: не пересекаться с
   абсолютными сегментами п.1–3.

Итог требования: размещение редизайна **совместимо с оригиналом по адресам
железо-зависимых ячеек**, но свободно по расположению C-кода и C-данных.

## 4. Соглашения о вызовах C ↔ ASM

Полный текст — [`docs/Z88DK_CALL.md`](file:///home/alexey/Projects/vector-games/docs/Z88DK_CALL.md).
Обязательны правила ниже (адаптированы под **i8080/KR580VM80A**, не Z80).

### 4.1 Как C зовёт ASM-примитивы

Тонкую обёртку `__z88dk_fastcall`/`__z88dk_callee` получает **только те
примитивы, у которых есть параметрический контракт** (`A`, `HL`, `DE`, `BC`).
Функции оригинала без параметров (`func_attract_plane_shift`,
`func_attract_load_overlay`, `func_attract_overlay_driver`) объявляются как
`extern void f(void);` — их тела не правятся вообще.

- **Один аргумент → `__z88dk_fastcall`.** Аргумент и возврат — в `HL`
  (`L` 8-бит, `HL` 16-бит). Никакого push/pop.
- **Много аргументов → `__z88dk_callee` (предпочтительно).** Callee читает
  параметры и **сама чистит стек**; caller не пукает лишнее.
- **Стандартный `__smallc`** — только для variadic/указателей на функцию.
- Порядок аргументов на стеке: пуш **слева направо**, первый аргумент лежит НИЖЕ:
  ```
  SP+0: адрес возврата   SP+2: 1-й аргумент   SP+4: 2-й аргумент
  ```
  При `pop` первым снимается **последний** аргумент.
- ⚠️ Расхождение с общей документацией (подчёркнуто в Z88DK_CALL): `sccz80` для
  `__z88dk_callee` пушит **справа налево**, для стандартного C — **слева направо**.
  Порядок разбора параметров в ASM обязан соответствовать атрибуту объявления.
- **Сохранение регистров:** `BC` — callee-saved (примитив обязан вернуть как
  получил); `AF`, `DE`, `HL` — caller-saved. **Исключение:** примитивы оригинала,
  которые по договору сохраняют `HL`/`DE` через `PUSH`/`POP` (например
  `func_put_char_glyph`) — их контракт переносится как есть и documented в
  `inc/riseout.h`.

Канонический пролог ASM-примитива под `__z88dk_callee` (8080-синтаксис):
```asm
; extern void write_tile(unsigned int addr, const unsigned char *src) __z88dk_callee;
_write_tile:
    pop  h            ; HL = адрес возврата
    pop  d            ; DE = src  (второй аргумент, наверху)
    pop  b            ; BC = addr (первый аргумент)
    push h            ; вернуть адрес возврата — стек очищен
    ; ... BC=addr, DE=src
    ret
```

### 4.2 i8080-специфика

- **Единственный адресат памяти — `(HL)`.** Нет `ld a,(de)` / `ld (de),a`.
  Чтение из `DE` — `LDAX D`, запись в `DE` — `STAX D`. Код оригинала этому
  следует, поэтому портится дословно.
- **Нет условных переходов `JR cc`** — только `Jcc` (16-бит). Нет `DJNZ`.
- **Нет битовых инструкций** (`BIT/SET/RES`) — маскирование через `ANA/ORA/RAL/RAR`.
- `PUSH PSW / POP PSW`, `PUSH rp / POP rp`, `INX/DCX`, `XTHL`, `SPHL`, `DAD` — есть;
  именно на них держится идиома оригинала «обмен регистрами через RAM-слот»
  (`LHLD`/`XTHL`/`SHLD` в `func_attract_plot_bits` и цикле анимации). **Три
  слова слота `0x0834/0x0836/0x0838` обязаны оставаться отдельными от
  `var_scratch_word` (`0x082A`)** — иначе регистровая ротация затирает
  промежуточное значение внутри той же функции.
- Синтаксис ассемблера — Intel/8080 (`MOV`, `MVI`, `LXI`, `CALL`, `RET`), как в
  `asm/`. z88dk-расширения (`ld`, `ex`) не использовать: сборка идёт с `-m8080`.

### 4.3 Ресурсные ограничения

- **Стек ограничен** (см. §3 п.4). `sccz80` активно использует стек для
  выражений. => глубина вызова ограничена; помощники — `__z88dk_fastcall`
  (0 слотов стека на 1 аргумент) и `__z88dk_callee` (нет паразитных `pop` у
  caller). Не раздувать вложенность C-выражений; сложные вычисления — через
  локальные переменные, а не цепочки в одной строке.
- **Ре-ентрантность ISR.** Примитивы, вызываемые из C, **не должны включать
  прерывания** (`ei`) и не должны зависеть от того, что ISR перезапишет порты.
  ISR оригинала (`func_irq_frame_service`) сам грузит палитру, стробит rows и
  крутит звук — C читает результат только через функции-аксессоры шва
  (`kbd_*`, счётчик кадров), а не по адресам.

## 5. Пошаговая методика (обязательна)

1. **Один подэтап = один заход = один коммит.** Никогда не переносить всю игру разом.
2. **Каждый шаг заканчивается тремя воротами:** (а) линковка `zcc/sccz80` + `z80asm`
   без ошибок; (б) запуск собранного ROM в MCP-отладчике (`debug_load_rom` →
   `debug_run`, без CPU/MEM/WARNING, старт/аттракт реагирует на клавиши);
   (в) кросс-чек поведения по py-движку там, где тайминг критичен. Только затем —
   `git commit`.
3. **Сначала ASM-шов, потом C-логика.** Примитив оборачивается и проверяется
   вызовом из тонкого C-обходчика ДО того, как пишется настоящая логика поверх него.
4. **Порт примитива = дословный порт.** Правки в теле разрешены только трёх
   видов: (а) абсолютный адрес данных → метка; (б) вызов удалённой функции →
   `PUBLIC`-символ другого модуля; (в) удаление побочных вызовов, которые в
   редизайне делает C (например `func_attract_input_update` внутри цикла
   отрисовки окна). Каждая такая правка фиксируется комментарием `; was <адрес>:
   <что и почему изменено>`.
5. **Эталон поведения — оригинал.** Сверка не по байтам, а по наблюдаемым
   эффектам: состав экрана заставки (7 записей + 2 кредит-полосы), позиции
   записей `[x,y]` из `data_title_records`, шаги меню, переход SPACE→игра,
   HUD (`SCORE/MEN/LEVEL`), скорость `[0x7C6A]=(4−speed)·4`, обе мелодии.
6. **Gradual:** если кусок C-логики не влезает в бюджет кадра по профилированию
   (§ Stage R5) — он откатывается/остаётся ASM, а не «дожимается» в C.

## 6. Этапы TZ2

### Stage R1. Каркас сборки на ASM игры
- `remake/Makefile` на `zcc +vector06c --no-crt` + `z80asm`, **без `$(LIB)` в
  `SRCS`**: свои `boot_riseout.asm` (crt0-часть: `SP`, вектора, ISR) и
  `main.c` (пустой `main`).
- Фиксация раскладки: абсолютные сегменты под `var_*`, текстовые страницы и
  таблица режимов; BSS компилятора — вне них.
- Конвертация образа в формат ROM Вектора (`utils/romconsist.py`) в `make full`.
- **Accept:** ROM грузится в MCP, ISR работает (счётчик кадров виден), экран
  очищен, ни одного предупреждения эмулятора.

### Stage R2. Перенос примитивов из ROM
- Ports по инвентарю §2.1: `font_riseout.asm`, `text_riseout.asm`,
  `gfx_overlay_riseout.asm`, `gfx_field_riseout.asm`, `snd_riseout.asm`,
  `kbd_riseout.asm` + `data_*` (шрифт, таблицы плоскостей/масок, партитуры).
- Для каждого — прототип в `inc/riseout.h` с атрибутом вызова по §4; проверка
  разбора порядка аргументов прогоном.
- **Accept:** из тестового C-обходчика каждый примитив вызывается с известными
  аргументами и даёт верный визуал/звук в MCP; стек чист (SP вернулся);
  вывод глида совпадает с оригиналом побитово в соответствующих плоскостях
  (сверить `debug_get_vram_bytes` 0x8000/0xA000/0xC000/0xE000 на одинаковых
  координатах).

### Stage R3. Заставка: `attract_screen()` на C
- Цикл заставки целиком в C: инициализация сцены, генерация звёзд, загрузка и
  прогон точечной анимации RISEOUT, 7 записей титула + 2 кредит-полосы,
  мигание подсказки, опрос клавиш, автомат `титул → HOW MANY PLAYERS →
  SELECT SPEED LEVEL`, фиксация выборок по слотам, выход в игру.
- Музыка заставки — вызовом перенесённого драйвера (партитуры как данные).
- **Accept:** заставка воспроизводит оригинал (тексты на своих местах, точечная
  надпись собирается, звёзды скроллятся, остальные плоскости статичны), реакция на
  SPACE/ENTER, шаги меню, мелодия играет; поведение сверено трассой MCP.

### Stage R4. Игра: `game_loop()` на C
- Счётчики проходов (поле «раз в 3», клавиши «раз в 5»), отложенная
  перерисовка поля (вызов ASM-blitter), события уровень-пройден/смерть,
  SFX-триггеры.
- Сессии/round-robin игроков, счёт/жизни/уровень, чтение карт уровней
  (`level.c`), спавн/коллизии сетки, win/lose-исходы, game-over/high-score,
  возврат на аттракт.
- Тяжёлый рендер/музыка — только вызовами ASM-примитивов.
- **Accept:** уровень играется (прокрутка поля, продвижение, смерть/прохождение),
  HUD обновляется, цикл возвращает управление корректно, game over → аттракт.

### Stage R5. Профилирование реального времени
- Замер T-стейтов на кадр (методика `utils/analyze/measure_cycles.py` / профиль
  `roms/demos/demos/fire2`): бюджет 50 Гц.
- Решение «остаться в ASM»: что не влезает (скорее всего пер-тайловый blit,
  растер-зависимые палитра/скролл, музыкальный воркер) — закрепляется ASM и
  НЕ переносится в C.
- **Accept:** все кадры укладываются в бюджет; задокументирован список
  «осталось ASM».

### Stage R6. Финальная ROM и приёмка
- `make full` → `remake/riseout_redesign.ROM`; запуск в MCP + кросс-чек py; deploy.
- Семантическая сверка с оригиналом (не по байтам): заставка, переход в игру,
  HUD, обе мелодии, скорость, game over → возврат на аттракт.
- **Accept:** играется как оригинал; отчёт `reports/TZ2.md` (Stage R1..R6) +
  фиксация известных расхождений.

## 8. Риски и открытые вопросы

1. **Бюджет i8080.** `sccz80` медленнее ручного asm; узкое место — покадровая
   перерисовка поля. Митигация: blit остаётся ASM, логика в C; R5 — профиль до
   переноса.
2. **Абсолютное размещение vs линкер.** Порт примитивов предполагает фиксированные
   адреса ячеек (§3). Если линкер/CRT0 z88dk конфликтует с `-a`-сегментами —
   раскладка выносится в отдельный `layout_riseout.asm`, а C-BSS стартует
   выше верхней абсолютной зоны. Проверяется на R1 по карте `*.map`.
3. **Дословность порта vs переносимость.** Искушение «сдвинуть базу плоскости»
   в примитиве (например писать точки RISEOUT в `0xE000`, потому что так
   удобнее C-слою) — **запрещено**: примитив сам знает свою плоскость, C его
   только вызывает. Расхождение с оригиналом по плоскостям = ошибка переноса.
4. **Конвенция вызова vs 8080:** обязательна вычитка каждого ASM-примитива на
   `(HL)`-only модель и отсутствие `JR`/битовых инструкций (§4.2).
5. **Открыто:** объём переноса — только ли аттракт+цикл в C, или и генератор
   поля тоже; решать по итогам R5 (профиля), не заранее.
