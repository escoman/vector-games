# mario-8cols: универсальный блокировщик горизонтального скроллинга (screen lock)

**Статус: идея, не реализовано.** Касается [`../main.c`](../main.c) (логика камеры),
[`../tools/gen_assets.py`](../tools/gen_assets.py) (ассет) и
[`../tools/level_editor.py`](../tools/level_editor.py) (инструмент). Скорость
рендера не трогает: hot path остаётся тем же `_render_window`, см.
[`OPTIMIZATION.MD`](OPTIMIZATION.MD).

## Постановка

Уровень состоит из экранных ячеек 32×32 тайла двух сортов:

```
  XXX        X — обычный экран: камера ходит за Марио по горизонтали
  Y Y        Y — залоченный экран: камера стоит, Марио ходит только вверх/вниз
  Y Y
  Y Y
  Y Y
XXXXXXX
```

Сценарий: Марио идёт вправо по нижнему `X`-прогону, упирается в препятствие и
поднимается вверх по башне `Y`, наверху снова попадает в `X`-прогон, позже
опускается по другой башне. Механика — классическая для 8-битных аркад
(SMB/DK): «camera anchor», экран-лифт.

## Ключевое решение: lock — на ячейку, НЕ на колонку

В схеме выше колонковый блок 2 занят сразу тремя сортами экранов: снизу `X`
(низ уровня), посередине `Y` (башня), сверху снова `X`. Флаг «залочить
мировую колонку 2» загонит в стопор и верхний `X`-прогон. Значит карта
блокировок двумерна по обеим осям:

```c
COL_BLKS = ceil(LEVEL_COLS / 32)          /* 10 для текущего 320x64 */
ROW_BLKS = ceil(LEVEL_ROWS / 32)          /*  2 для текущего 320x64 */
unsigned char scr_lock[COL_BLKS * ROW_BLKS];   /* 1 = экран без гор. скролла */
```

20 байт ROM для текущего уровня, 128 байт на максимум (512×255 = 16×8).
Искомая ячейка — по столбцу и строке Марио:

```c
cb = wblk >> 5;  rb = (unsigned int)(my / TILE_PX) >> 5;
```

Якорь камеры для залоченной ячейки — **её левый край**: `anchor = cb * 32`.
Он кратен `OBJ_WIN_STEP`, поэтому база окна `tile_win_base = cam & ~31`
совпадает с якорем: **пока Марио лазает по башне, перепечек нет вообще**
(`bake_shift` не вызывается), вертикаль работает штатным
`render_rowband`/аппаратным скроллом регистра порта 03h.

## Ключевое решение: сближение по 1 колонке за кадр, не прыжок

Весь пайплайн заточен под `|Δcam| ≤ 1`: diff-скан `_rw_block`, быстрая ветка
`refwalk = newwalk ∓ stride` (есть только при `delta = ±1`), `bake_shift`
(только `±32`). Мгновенная установка `cam = anchor` даёт `|Δcam| ~ 10…28` ⇒
полный редрав `CAM_NO_REF` (~9,8 кадра) плюс иногда полная `bake_window`
(~33 кадра) — фриз на каждом входе в башню.

Плавно: каждый кадр камеру сдвигаем к цели **не более чем на одну колонку**.
Тогда

* каждый кадр — обычный diff-шаг (~204k T, тот же хот-путь, ничего нового);
* переход базы окна через `bake_shift` происходит «по расписанию», как при
  обычном скролле;
* визуально — классический эффект «экран едет под Марио».

Скорость сближения 1 колонка/кадр = 8 px/кадр, вдвое быстрее шага ходьбы
(`MOVE_DELAY 2`), т.е. догон ~15 колонок ≈ 15 кадров ≈ 0,3 с. Числом можно
рулить (`LOCK_STEP`).

## Врезка в движок

Единственное место, где `cam` меняется при ходьбе, — блок «держим Марио в
окне `[CAM_MIN..CAM_MAX]`» ([`../main.c`](../main.c), следует за
`old_cam = cam`). Заменяется так:

```c
/* ---- камера: экранные залоченные ячейки => якорь, else follow ---- */
{
    unsigned int want;
    unsigned char locked;

    cb = (unsigned int)(wblk >> 5);
    rb = (unsigned int)(((unsigned int)my / TILE_PX) >> 5);
    locked = scr_lock[cb * ROW_BLKS + rb];

    if (locked) {
        want = cb << 5;                    /* якорь: левый край экрана */
        if (want > (unsigned int)MAX_CAM)
            want = MAX_CAM;                /* последний неполный блок   */
    } else {
        unsigned int rel = wblk - cam;     /* прежняя логика мёртвой зоны */
        if (rel > CAM_MAX_BLK && cam < MAX_CAM) {
            want = wblk - CAM_MAX_BLK;
            if (want > (unsigned int)MAX_CAM) want = MAX_CAM;
        } else if (rel < CAM_MIN_BLK) {
            want = (wblk > CAM_MIN_BLK) ? (wblk - CAM_MIN_BLK) : 0;
        } else {
            want = cam;
        }
    }

    /* ИНВАРИАНТ: за кадр камера сдвигается не более чем на одну колонку.
     * При обычной ходьбе он не виден: Марио идёт 1 колонку за MOVE_DELAY
     * кадров, поэтому follow-цель всегда отличается от cam на 0 или 1.
     * Работает он только на входах/выходах лока (и на любом будущем
     * «хотим cam далеко») — там, где иначе был бы полный редрав. */
    if      (want > cam + 1) cam++;
    else if (cam > want + 1) cam--;
    else                     cam = (unsigned int)want;

    mblk = (unsigned char)(wblk - cam);
    if (mblk >= VIEW_BLOCKS) wblk = cam + VIEW_BLOCKS - 1;   /* страховка края */
}
```

Почему инвариант, а не «сглаживать только кадры перехода»: при **выходе** из
башни в обычный экран Марио стоит у левого края (`cam = anchor`, `mblk` ≈ 0),
а follow-правило хочет отпустить камеру на `wblk − CAM_MIN_BLK`, т.е.
`Δcam ≈ −10…−20`. Один кадр `prev_locked` здесь не спасает — после него
остался бы недогон, и на втором кадре всё равно прыжок. Инвариант
«≤ 1 колонки/кадр» закрывает оба конца сразу, а респаун не ломается: он
выставляет `cam` сам (вне этого блока), а после него `want` уже совпадает с
`cam` (`wblk = 4`, `CAM_MIN_BLK = 10` ⇒ `want = 0`).

Марио при сближении не убегает с экрана: встречные случаи (`cam` догоняет
якорь, Марио идёт навстречу) сами собой держат `mblk ∈ [0..31]`, но clamp
в коде выше — страховка от вырожденных входов (прыжок в башню сбоку на
полной скорости).

## Данные и ассет

`../src/level.json`:

```json
"locks": [[2,1],[2,2],[2,3],[2,4],[4,1],[4,2],[4,3],[4,4]]
```

пары `(colblk, rowblk)`; `[]` = пусто. Компактный вариант — строка
по экранным рядам, `"locks": ["..X.X.", "..X.X."]` (пока `ROW_BLKS ≤ 8`
читаемо и валидируется односимвольно; что выбрать — решить при реализации).

[`../tools/gen_assets.py`](../tools/gen_assets.py) разворачивает в
`src/level.inc`:

```c
#define COL_BLKS   10
#define ROW_BLKS    2
unsigned char scr_lock[COL_BLKS * ROW_BLKS];
```

Валидация в [`../tools/prefablib.py`](../tools/prefablib.py)`validate_locks`:

* `0 ≤ cb < ceil(cols/32)`, `0 ≤ rb < ceil(rows/32)`;
* **предупреждение**: две залоченные ячейки подряд по горизонтали — Марио
  два раза подряд «прилипнет к краю»; разрешить, но не поощрять;
* **предупреждение**: залоченная ячейка, у которой соседняя по вертикали в
  том же `cb` не залочена, — законно (вход/выход по вертикали), но стоит
  проверить геометрию: без стены на стыке камера «отпустится» посередине
  башни.

## Редактор

В [`../tools/level_editor.py`](../tools/level_editor.py) сетка экранов уже
рисуется (полосы по 32 тайла для блоков/префабов). Добавляется:

1. инструмент-переключатель «Lock» (кнопка на баре или хоткей) — клик по
   экранной ячейке инвертирует бит; залоченная ячейка — затемнение/штриховка
   поверх карты и рамка;
2. состояние — в `LocksVar`, сериализация в `level.json` тем же форматом,
   что выше; проверка при сохранении та же `validate_locks` (редактор и так
   обязан отсеять всё, что ломает `make`, — см. его docstring про лимиты);
3. в статус-баре — счётчик `lock: N ячеек` и предупреждения про соседей
   (подсказка в `tooltip`, если ячейка граничит с X по горизонтали).

## Что остаётся проверить тестами

* `check_render_regress.py` — добавить сцену «сближение камеры»: `cam`
  меняется на `+1`/`−1` несколько кадров подряд внутри залоченного экрана,
  хэш VRAM сверить с эталонной полной перепечкой (`bake_window` +
  `render_window(cam, CAM_NO_REF, …)`); это тот же класс проверок, что
  уже есть для `cam_row`;
* `check_bake.py` — не затронут (лок ничего не меняет в модели окна);
* ручной кейс на эмуляторе: вход в башню слева (камера догоняет якорь),
  подъём доверху, выход в `X` сверху, обратный спуск справа налево;
* RAM/ROM-цена: +20…128 байт ROM, `scr_lock` в BSS не нужен (константа).

## Риски и границы

* **Камера «в залоченном экране» не обязана быть кратной 32** в момент
  сближения — база окна в этот момент ещё старая; `render_window` это
  выдерживает (он и сейчас работает при любом `cam` внутри окна).
* Последний неполный блок: `anchor = cb*32` может превысить `MAX_CAM` —
  clamp на месте (в коде выше).
* Ширина прохода башни меньше 32 колонок — это геометрия уровня, лок на
  неё не влияет; но если проход шире экрана, Марио в залоченной ячейке
  упрётся в край экрана, а не в стену: это и есть желаемое поведение
  («дальше путь только наверх»).
* `solid_at` возвращает 0 за пределами окна — прижим к краю не должен
  выдать «стену нет»; проверять `solid_at(edge, …)` только при
  `mblk < VIEW_BLOCKS`.
