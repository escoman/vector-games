# Stage 4. Прерывания (exolon.rom)

> Источник фактов — MCP `vector-debugger`: статический дизасемблер (`debug_disassemble`), поиск байтовых последовательностей (`debug_find_bytecode_sequence`), кросс-ссылки (`debug_get_xrefs`) и **живой прогон** (`debug_run` + `debug_type_key` + breakpoints + снимок CPU). ROM загружен `debug_load_rom` (org 0x0100), `debug_reset` не вызывался. Единственный канал записи RDB — `debug_save_rdb`; `.rdb` руками не правился. Порт-сигнатуры взяты из механики Stage 0/1 (`io_signature`); факты руками не переснимаются — здесь только семантика прерываний (Level C).

## Goal

Закрыть вопрос Stage 4 из TZ.md:

1. какие векторы прерываний ROM вообще использует;
2. что за `RST` на `0x7893` «прямо в инициализации» — переход в прерывание или установка вектора;
3. является ли кадровой/звуковой тикер аппаратный `RST 7` (VBlank ~50 Гц) или движок синхронизируется поллингом;
4. оформить каждый обработчик отдельным объектом `func_irq_*` с комментарием и связями;
5. сохранить инкрементальность RDB и не нарушить побайтовый round-trip.

## TL;DR (вердикт)

**Exolon не является прерывательно-управляемой программой.** Единственный включённый прерыванием момент — однократный `EI / HLT / DI` в `func_init_palette_vblank` (0x1DFB), который ждёт **первый** VBlank (`RST 7` → вектор 0x0038, содержащий один `RET`) просто чтобы привязаться к началу кадра при старте. Дальше прерывания навсегда замаскированы (`DI`), и весь покадровый/растровый тайминг (в т.ч. звук на заставке) делается **поллингом** счётчиков КР580ВИ53 и гонок с лучом. Блок установки «постоянного» VBlank-обработчика на 0x795A существует в образе, но **недостижим** и в рантайме не выполняется.

## Verified Facts (подтверждено вживую и статикой)

### F1. Единственный используемый вектор — 0x0038 (RST 7 / VBlank)

- Аппаратный источник: VBlank ~50 Гц инжектирует опкод `0xFF` = `RST 7` → вектор `0x0038` (`docs/VECTOR_VERIFIED.md §VBlank: RST 7 → 0038h`).
- Статика: поиск `STA` в страницу 0 (маска `[32,??,00]`) даёт `STA 0038` **ровно в двух местах** — `0x1DFE` и `0x7964`. Остальные RST-векторы (`0x0008/0x0010/0x0018/0x0020/0x0028/0x0030`) и `0x003C INTERPT` в образе **никогда не пишутся**.
- Содержание вектора после `0x1DFE`: `MVI A,0C9h / STA 0038h` → по адресу `0x0038` лежит один байт `0xC9` = **`RET`**.
- Живое подтверждение: BP на `0x0038` сработал один раз при инициализации — снимок CPU: `pc=0x0038, a=0xC9, iff=true, current_instruction=RET`. Это момент выхода из `HLT` по первому VBlank.

### F2. Прерывания включаются ровно один раз и сразу гасятся

`func_init_palette_vblank` @0x1DFB (вызывается из инициализации `0x7877: CALL 1DFB`):

```
DI
MVI A,0C9h      ; RET
STA 0038h       ; вектор VBlank = пустой RET
EI              ; ← единственный EI во всём ROM (достижимый код)
HLT             ; встать; разбудит первый VBlank (RST 7 → RET → продолжение)
DI              ; ← обратно замаскировать
LXI H,1E2Ch …   ; загрузка палитры (OUT 02h индекс + OUT 0Ch строб, 16 цветов)
RET
```

- Поиск байта `EI` (0xFB) по образу дал 116 совпадений, но подавляющее большинство — операнды/данные (напр. маски клавиатурной строки `0FBh` из TZ). Реальный исполняемый `EI` в покрытом коде — только `0x1E01`.
- В игровом цикле (после инициализации) CPU-флаг `IFF=false` (подтверждено снимком на `pc=0x7358`, экран мигания звёзд) — прерываний нет.

### F3. Тайминг кадра/растра — поллинг, не прерывание

- `func_frame_sync` @0x0147: `IN 0Ah / IN 0Ah / CPI …` — читает счётчик канала 1 КР580ВИ53 (порт 0Ah) как ход луча и ждёт нужную фазу кадра; ставит палитру (`CALL 2142`), стробирует клавиатуру.
- `func_beam_delay` @0x1E2F: `IN 09h / RRC / ANI 01h / OUT 00h` + внутренние счётчики — задержка «гонок с лучом» через порты 09h (счётчик канала 2) и 00h (управление видео). Это и есть источник `OUT 00`-шума в `io_signature`-трассе (ring-buffer показывал ~4000 `OUT 00` подряд именно из этого цикла).
- Вывод: и кадровая синхронизация, и (по той же схеме) тон/музыка на заставке заводятся явным тикером в основном цикле, а не из `RST 7`. Это перекликается с планом Stage 9a («драйвер: RST 7 **или** явный тикер в цикле» — здесь зафиксировано: **явный тикер**).

### F4. «RST» на 0x7893 — артефакт дизасемблирования данных, а не код

Инициализация `0x787A: LXI H,7890 / CALL 3CC1` передаёт область `0x7890`… дисплейному интерпретатору `func_display_interpreter` (0x3CC1). Байты там — **display-list**, который линейный дизассемблер ложно читает как команды: на `0x7893` (и далее `0x78CB`, `0x78DF`…) стоит байт `0xDF`, который 8080-декодер трактует как `RST 3` (вектор `0x18`). Отсюда две правки к тексту TZ:
- `0xDF` — это `RST 3`, **не** `RST 7` (TZ §«RST 7 (0xDF)» ошибся в нумерации; `RST 7` = опкод `0xFF`);
- он **не исполняется** — это данные. Открытый вопрос TZ §«уточнить на Stage 4» закрыт: ни переход в прерывание, ни установка вектора — просто байт управляющего слова дисплей-листа.

## Inference / Dead code: бутстрап установки векторов @0x795A

В хвосте образа есть связный блок, не видимый как код ни из одного достижимого пути:

```
0x795A …
LXI SP,8000h
MVI  A,0C3h          ; JMP
STA  0000h           ; reset-вектор: C3 …
STA  0038h           ; VBlank-вектор: C3 …
LXI  H,0103h
SHLD 0002h           ; 0x0000 = JMP 0103h
LXI  H,5567h
SHLD 0039h           ; 0x0038 = JMP 5567h   ← «постоянный» VBlank-обработчик
JMP  795A            ; вечный цикл (схема «всё крутится от прерываний»)
```

Докладываем как **кандидат/остаток загрузчика**, а не рабочий механизм:
- `debug_get_xrefs(0x795A)` = 0 (кроме собственного `0x7973 → 0x795A`); в достижимый граф из entry не входит;
- BP на `0x795A` и на его цель `0x5567` **не сработали** за полный прогон через все экраны; `IFF` в игре остаётся `false`;
- цель `0x5567` по телу — обычный подпроцесс рендера (`XTHL`-трюки, `CALL 3CB5/4514/3CC1`), **без** `PUSH PSW`/`EI` как полагается ISR. То есть даже этот мёртвый вектор указывает не на обработчик прерывания.

## Что занесено в RDB

Сохранено `debug_save_rdb`; итог: **408 объектов**, `dirty=false`, sha256 ROM `92be64d1…` без изменений.

| Объект | Адрес | Тип | Смысл |
|---|---|---|---|
| `func_irq_vblank` | `0x0038` | function | Реальный обработчик VBlank: 1 байт `RET`, устанавливается в `func_init_palette_vblank`; однократный `EI/HLT/DI`. Свойство `irq_role`. |
| `func_irq_vblank_install` | `0x795A` | function | Мёртвый бутстрап установки reset/VBlank-векторов (`JMP 5567`). Свойство `reachability=dead`. |
| `func_init_palette_vblank` | `0x1DFB` | (правки) | Комментарий + `properties.interrupts`, ссылка → `0x0038`. Единственный EI/HLT/DI. |
| `func_frame_sync` | `0x0147` | (правки) | `properties.timing` — polled (IN 0Ah). |
| `func_beam_delay` | `0x1E2F` | (правки) | `properties.timing` — polled beam-racing (IN 09h + OUT 00h). |

Связи: `0x1DFB → 0x0038`, `0x795A → 0x0038`.

**Почему нет объекта на `0x5567`.** Попытка завести `func_irq_vblank_alt` как `function` на `0x5567` **ломала побайтовый round-trip** (`roundtrip_verify` падал в `MISMATCH`, 9757 расхождений в 282 диапазонах): адрес лежит внутри уже покрытой кодовой области, и новый function-границей экспортёр начинал заново дизасемблировать/пересобирать соседние байты как код со сдвигом целей переходов на +1. Изолировано проверено на копии RDB: `0x0038` и `0x795A` — `diffs=0`, `0x5567` — `diffs=9757`. Поскольку `0x5567` — не настоящий ISR и всё равно недостижим, объект убран, а его описание перенесено в комментарий `func_irq_vblank_install`. **Сквозной контракт побайтовой идентичности соблюдён.**

## Round-trip после правок

`utils/analyze/run_pipeline.sh exolon --from export_asm --apply` (без `--resume` — правки вне pipeline): все 6 стадий успешны, 0 отказов; `roundtrip_verify = OK, byte-for-byte identical`.

> Примечание по окружению: бинарь `v06c-asm-export` отсутствовал в `vector-debug/build` и был дособран целевым `cmake --build build --target v06c-asm-export` (иначе `export_asm` падал с `FileNotFoundError`). Это инфраструктура, не артефакт ROM.

## Limitations

- `io_signature`-трасса не несёт PC, поэтому привязка «порт ↔ функция» статическая; вывод «звук — поллинг» опирается на дизассемблирование `func_beam_delay/func_frame_sync` + снимок `IFF=false`, а не на динамический трассировщик.
- Полная партитура/драйвер музыки на заставке — предмет Stage 9a; здесь зафиксировано лишь, что тикер не прерывательный.
- Точное назначение `0x5567` (какой именно рендер) не раскрыто — область мёртвая, отдельного разбора не делал.
