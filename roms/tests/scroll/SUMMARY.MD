# SUMMARY: Синхронизация скролла и позиции луча на Вектор-06Ц

## 1. Аппаратная модель скролла

### 1.1. VRAM и регистр скролла

- **VRAM**: 256 строк × 32 байта = 8 КБ, кольцевой буфер.
- **Регистр скролла** (порт 03h, PIA Port A): 8 бит, значение `S` = VRAM-строка, которую луч читает на **физической линии 0** (верх экрана).
- **Формула чтения**: на физической линии `y` (0 = верх, 255 = низ) луч читает VRAM-строку:
  ```
  vram_row = (S - y) & 0xFF
  ```
  Луч сканирует **убывая** адрес VRAM: от `S` вниз до `S - 255`.

### 1.2. Кадр и бланкинг

- **Кадр**: 312 строк растра (96 тиков таймера ВИ53 на строку = 29952 тика/кадр).
- **Видимая область**: строки 0–255 (физические линии экрана).
- **Верхний бланкинг**: строки 256–287 (32 строки, VBlank начинается на строке 288).
- **Нижний бланкинг**: строки 288–311 (24 строки).
- **VBlank (кадровое прерывание)**: на строке 288, RST 7.

### 1.3. Тайминги

| Параметр | Значение |
|----------|----------|
| Тактов CPU на строку | ~192 (при 9 МГц) |
| Тиков таймера на строку | 96 (ВИ53 тактируется 1.5 МГц = 12 МГц / 8) |
| Строк в кадре | 312 |
| Видимых строк | 256 |
| Длительность кадра | ~20 мс (50 Гц) |
| Длительность строки | ~64 мкс |

## 2. Формула D2SCROLL в mario-8cols

```c
#define D2SCROLL(cam_y) (0xFF - ((cam_y) & 0xFF))
```

Если `cam_row = 8` (верх камеры в мировых координатах), то `cam_y = 8 * 8 = 64`:
```
S = 0xFF - (64 & 0xFF) = 0xFF - 0x40 = 0xBF
```

На физической линии 0 луч читает VRAM[0xBF], на линии 8 — VRAM[0xBF - 8] = VRAM[0xB7].

**Проверка**: `cam_row = 8` означает, что мировая строка 8 должна быть на физ. линии 0. Мировая строка 8 хранится в VRAM[8 & 0xFF] = VRAM[8]. Но при скролле 0xBF на физ. линии 0 читается VRAM[0xBF], а не VRAM[8].

**Уточнение**: в mario-8cols VRAM-кольцо построено так, что мировая строка `W` хранится в VRAM[`W & 0xFF`]. При `cam_row = 8` и `S = 0xBF`:
- Физ. линия 0 → VRAM[0xBF] = мировая строка 0xBF (это **над** камерой, небо).
- Физ. линия 8 → VRAM[0xBF - 8] = VRAM[0xB7] = мировая строка 0xB7 (тоже небо).

Это не совпадает с ожидаемым. **Требуется уточнение формулы D2SCROLL** — возможно, в оригинальном коде `cam_y` считается иначе, или VRAM-кольцо имеет смещение.

## 3. Когда менять регистр скролла

### 3.1. Проблема

Если изменить `S` во время видимого сканирования (строки 0–255), то:
- Часть кадра **выше** луча прочитает старое `S_old`.
- Часть кадра **ниже** луча прочитает новое `S_new`.
- На границе (физ. линия = текущая позиция луча) будет **разрыв**: строки VRAM, которые раньше были невидимы, suddenly станут видимы.

Если новая VRAM-строка ещё не нарисована, на экране появится **артефакт** — мусор из старой памяти.

### 3.2. Безопасные моменты для смены скролла

| Момент | Позиция луча | Риск |
|--------|--------------|------|
| **VBlank** (строка 288+) | Вне экрана | **Нет риска**: луч не сканирует видимую область. |
| **Сразу после VBlank** (строка 0–N) | Вверху экрана | Риск: нижняя часть кадра (строки N+1–255) прочитает новое `S`. Если VRAM[N+1..255] не готов — артефакт внизу. |
| **Середина кадра** (строка 128) | В центре | Риск: верх (0–127) показывает старое, низ (128–255) — новое. Разрыв на строке 128. |
| **Перед следующим VBlank** (строка 255) | Внизу экрана | Риск: весь кадр уже прочитан, новое `S` применится только на следующем кадре. **Безопасно**, но с задержкой 1 кадр. |

### 3.3. Вывод

**Единственный безопасный момент** для смены регистра скролла без артефактов — **VBlank** (строка 288+). В это время:
1. Луч находится в бланкинге, не сканирует экран.
2. Можно записать новое `S` в порт 03h.
3. На следующем кадре (строка 0) луч сразу прочитает новое `S`.

**Альтернатива**: сменить `S` сразу после отрисовки новой VRAM-строки, но **до** того, как луч дойдёт до неё. Это требует точного знания позиции луча и таймингов отрисовки.

## 4. Стратегии синхронизации

### 4.1. Стратегия "Отложенный скролл" (gfx_set_scroll)

```c
gfx_set_scroll(new_S);   // Записать в gfx_scroll_row
// ... отрисовка ...
// На следующем VBlank ISR запишет gfx_scroll_row в порт 03h
```

**Плюсы**:
- Простота: не нужно следить за лучом.
- Безопасность: смена происходит в VBlank.

**Минусы**:
- **Задержка 1 кадр**: между отрисовкой VRAM и сменой регистра.
- Если камера двигается быстро, за 1 кадр луч может прочитать старую VRAM-строку из нового места — артефакт.

### 4.2. Стратегия "Немедленный скролл" (v06_out)

```c
v06_out(V06_PIA_PA, new_S);  // Сразу записать в порт 03h
```

**Плюсы**:
- Нет задержки: регистр меняется сразу.

**Минусы**:
- **Риск артефакта**: если луч уже сканирует экран, он прочитает новое `S` с текущей строки.
- Если новая VRAM-строка не готова — мусор на экране.

### 4.3. Стратегия "Скролл после отрисовки" (рекомендуемая)

```c
// 1. Дождаться VBlank
gfx_next_frame();

// 2. Отрисовать новую VRAM-строку (пока луч в бланкинге)
render_rowband(new_row);

// 3. Сменить скролл (луч ещё в VBlank или только начал новый кадр)
gfx_set_scroll(new_S);  // Применится на следующем VBlank
```

**Плюсы**:
- VRAM готова до смены регистра.
- Смена происходит в VBlank — нет артефактов.

**Минусы**:
- Задержка 1 кадр (между отрисовкой и применением скролла).
- Если отрисовка занимает много времени, можно выйти за пределы VBlank.

### 4.4. Стратегия "Точная синхронизация с лучом"

```c
// 1. Дождаться, пока луч пройдёт опасную зону
timer_wait(TIMER_REMAIN(TIMER_LINES(safe_line)));

// 2. Отрисовать новую VRAM-строку
render_rowband(new_row);

// 3. Сменить скролл (луч уже прошёл эту строку)
v06_out(V06_PIA_PA, new_S);
```

**Плюсы**:
- Нет задержки: скролл меняется в том же кадре.

**Минусы**:
- Сложность: нужно точно знать `safe_line` и тайминги отрисовки.
- Риск: если отрисовка займёт больше времени, чем осталось до прохода луча — артефакт.

## 5. Анализ артефакта в mario-8cols

### 5.1. Симптом

При скролле вверх/вниз на 1 строку появляется **полоса** (8 пикселей) с противоположного края экрана:
- Скролл вниз → полоса вверху (из нижней части VRAM).
- Скролл вверх → полоса внизу (из верхней части VRAM).

### 5.2. Причина

**Гипотеза 1**: Регистр скролла меняется **до** отрисовки новой VRAM-строки.

Если `gfx_set_scroll(new_S)` вызывается сразу после изменения `cam_row`, но **до** `render_rowband`, то:
1. На следующем VBlank регистр меняется на `new_S`.
2. Луч начинает сканировать кадр с `new_S`.
3. Новая VRAM-строка ещё не нарисована — луч читает старое содержимое.
4. `render_rowband` дорисовывает строку, но луч уже прошёл — артефакт виден 1 кадр.

**Гипотеза 2**: `render_rowband` вызывается **после** VBlank, но регистр скролла уже изменился.

Если порядок такой:
```
VBlank → gfx_set_scroll(new_S) → render_rowband(new_row)
```
То:
1. VBlank: ISR записывает `new_S` в порт.
2. Луч начинает новый кадр, читает VRAM с `new_S`.
3. Новая строка ещё не нарисована — артефакт.
4. `render_rowband` заканчивает отрисовку, но луч уже прошёл эту строку.

### 5.3. Решение

**Правильный порядок**:
```
1. gfx_next_frame()         // Ждать VBlank (луч в бланкинге)
2. render_rowband(new_row)  // Отрисовать новую строку (пока луч не видит)
3. gfx_set_scroll(new_S)    // Поставить скролл в очередь (применится на след. VBlank)
```

Тогда:
- Кадр N: VBlank → отрисовка → скролл в очереди.
- Кадр N+1: луч читает старое `S_old`, VRAM уже готов.
- Кадр N+1 VBlank: ISR записывает `new_S`.
- Кадр N+2: луч читает `new_S`, VRAM готов — артефакта нет.

**Цена**: задержка 2 кадра (40 мс) между изменением камеры и отображением.

## 6. Формулы для расчёта

### 6.1. Позиция луча в тактах таймера

```c
unsigned int elapsed = timer_elapsed();  // 0..29952
unsigned int line = elapsed / 96;        // 0..311 (физ. строка растра)
```

### 6.2. VRAM-строка на физической линии

```c
unsigned char S = gfx_scroll_row;        // Текущий регистр скролла
unsigned char y = line;                  // Физ. строка (0..255 — видимая)
unsigned char vram_row = S - y;          // VRAM-строка, которую читает луч
```

### 6.3. Безопасная строка для отрисовки

Если отрисовка занимает `T` тиков таймера, то безопасная строка:
```c
unsigned int safe_line = current_line + (T / 96) + 1;
```

Менять скролл можно, когда `elapsed >= TIMER_LINES(safe_line)`.

## 7. Тестовый проект roms/tests/scroll

### 7.1. Описание

Тест рисует **градиент**: каждая VRAM-строка `i` заполнена цветом `(i & 15)`. При скролле видно, какие строки попадают на экран.

### 7.2. Управление

- **UP/DOWN**: сдвиг скролла на ±1.
- **LEFT/RIGHT**: сдвиг на ±16.
- **F1**: пометить кадр (белая полоса на VRAM-строке 128).
- **ESC**: выход.

### 7.3. Наблюдения

1. **При смене скролла в VBlank**: градиент сдвигается плавно, без разрывов.
2. **При смене скролла в середине кадра**: виден **разрыв** на границе: верхняя часть показывает старый градиент, нижняя — новый.
3. **При быстром скролле (LEFT/RIGHT)**: разрыв более заметен, т.к. меняется много строк.

### 7.4. Использование с отладчиком

## 8. Выводы

1. **Регистр скролла можно менять только в VBlank** (строка 288+) или когда луч **гарантированно** прошёл опасную зону.
2. **Отрисовка новой VRAM-строки должна завершиться до смены регистра**.
3. **Безопасная стратегия**: `gfx_next_frame()` → `render_rowband()` → `gfx_set_scroll()`.
4. **Цена безопасности**: задержка 1–2 кадра. Для плавной анимации нужно предсказывать движение камеры.
5. **Артефакт "полоса с противоположного края"** возникает, когда регистр скролла меняется до отрисовки новой VRAM-строки, и луч читает старое содержимое VRAM.

## 9. Рекомендации для mario-8cols

Использовать **отложенный скролл** с правильным порядком:

```c
if (dv != 0) {
    // 1. Ждать VBlank (луч в бланкинге)
    gfx_next_frame();
    
    // 2. Отрисовать новую полосу (пока луч не видит)
    render_rowband(revealed_row, cam);
    
    // 3. Поставить скролл в очередь (применится на след. VBlank)
    gfx_set_scroll(D2SCROLL(cam_row * TILE_PX));
}
```

**Альтернатива** (если задержка критична): использовать `v06_out` сразу после отрисовки, но **только** если луч уже прошёл опасную зону:

```c
render_rowband(revealed_row, cam);
if (timer_elapsed() > TIMER_LINES(safe_line)) {
    gfx_scroll_row = D2SCROLL(cam_row * TILE_PX);
    v06_out(V06_PIA_PA, gfx_scroll_row);
} else {
    gfx_set_scroll(D2SCROLL(cam_row * TILE_PX));  // Отложить до VBlank
}
```
