## Метод: address-exact реконструкция
Идея: собрать все 126 экспортированных .asm в ОДИН мастер-файл и разместить
каждый объект СТРОГО по его оригинальному адресу (`defs addr-$`). Тогда абсолютные
адреса/операнды совпадают с оригиналом автоматически, а поведение — по построению.

Пайплайн (`tools/gen_layout.py`, конвертер — не постобработка MCP):
1. Читает адреса/типы объектов из `src/putup.rdb` (RDB — источник истины по адресам)
   и заголовоки `; Адрес/; Размер` из каждого `asm/*.asm`.
2. Берёт фактические (замеренные) длины эмитов из `tools/sizes.json` (см. ниже) —
   заголовочные `Размер` местами недостоверны.
3. Кладёт эмиты по адресам; всё, что НЕ эмитируется (незахватанный код, in-image
   хранилище RAM-переменных, музыкальные данные Stage 11 без .asm), заполняет
   ВЛОБ байтами из образа `src/putup.rom` → `asm/bin/gap_*.bin` (21 файл). Это ДАННЫЕ.
4. Генерирует мастер `asm/putup_new.asm` (110 эмитов + 21 пропуск = 17664 байт).

Замер длин (`tools/sizes.json`): мастер `asm/measure.asm` (плотная склейка эмитов без
defs) собран с `z80asm -s`; истинный размер каждого объекта = дельта соседних меток
в .sym. Это закрыло каскад ошибок «defs<0» от недостоверных заголовочных размеров.

Toolchain: `z88dk-z80asm -b -m=8080_strict -s -o=...` (`/…/vector-games/z88dk/bin`).

### Особенности тулчейна, найденные и обошённые (Fact)
- **двойное применение org:** `z80asm -b` с ненулевым `org 0100h` прибавлял смещение
  к АБСОЛЮТным операндам (+0x100; напр. `JMP func_main_init` → 0x0C57 вместо 0x0B57),
  хотя .sym показывал верные значения. **Решение:** `org 0h` + обрезка выхода
  `bin[0x100 : 0x100+17664]` в Makefile.
- **литералы 8080:** hex-константы, начинающиеся с A–F, требуют ведущего 0
  (`DFh`→`0DFh`, `B6h`→`0B6h`), иначе трактуются как метки.

  Доказательство кода (MCP `debug_analyze_code` от 0x3858): code-range `0x3890..0x3BC7`,

  Это подпрограмма проигрывателя голоса, которую экспорт оставил внутри пропуска
  (`gap_388C_3902.bin`). Добавлена ссылка `func_music_tick(0x3858) → func_music_sub_3890(0x3890)`.
  Точная семантика — UNKNOWN (имя — временная метка по адресу, как предписано).
  В сборке область закрыта адресно-точным вербатим-пропуском, поэтому сырой операнд
  `CZ 3890h` резолвится корректно без символической метки (TZ Stage 12 п.3 учтён).

## Поведенческая верификация (MCP-first)
Оригинал и сборка грузились раздельно `debug_load_rom(org=256)` (чистый boot; `debug_reset`
НЕ эквивалентен — см. ниже). Сравнивались одинаковые проявления.

| Проявление | Оригинал | PUTUP_NEW | Вердикт |
|---|---|---|---|
| Чистый boot → заставка | bp 0x0C65, `sp=0x0100`, `LXI B,0C00`, a00 b00 c00 dFF eF6 h09 l85 f96 | **тот же PC/SP и побайтово те же регистры** | Совпало (Fact) |
| Музыка на заставке | порты 0x0B/0x0A/0x09 (2-байт периоды), control 0x08 = 36h/76h/B6h (Stage 11) | те же порты; control 0x08 = 36h/76h; ch0/1/2 writes | Совпало по паттерну (Fact) |
| SPACE → игра | PC уходит из 0x0C65 в игровой код (0x0DBF) | PC уходит в игровой код (0x0EFC, sp=0x00F8) | Совпало: переход есть (Fact) |
| Геометрия экрана | 576×288, vis 256×256, mode512=false, vram_base 0xC000, ppb 8 | идентично | Совпало (Fact) |
| Рендер уровня 1 в VRAM | (0xC000 заполнен тайлами) | 0xC000: повторяющиеся 2×2 стеновые/половые тайлы `FDFE…`/`FF7F` + спрайт `78CC183060CC78` | Рендер присутствует (Fact) |

Важное наблюдение (Fact): после SPACE заставка-музыка **прекращается** (io_trace в игре
содержит только опрос клавиатуры портов 0x00–0x03, без 0x08–0x0B) — воспроизводится на сборке.

### Ложная тревога, разобранные честно (Inference → разрешено)
При проверке сборки `debug_reset` (после долгого прогона оригинала) оставлял CPU в
хардвеерном busy-wait `OUT 1C / IN 1B` (ожидание сброса бита 7 порта 0x1B, ~0x0377) при
аномальном `sp=0xDCEC`, и точка останова 0x0C65 не достигалась. Это **артефакт состояния
периферии эмулятора после reset**, а НЕ свойство ROM: идентичный исходник
(`debug_load_rom`) стартует чисто и достигает 0x0C65 с `sp=0x0100`. Вывод: корректный
чистый boot в MCP — через `debug_load_rom`, а не `debug_reset`.

## Почему equivalence доказана (Fact, сильнейшее)
`PUTUP_NEW.ROM` **побайтово равен** `putup.rom` (SHA256 совпадает, `make verify` = 0 diffs,
воспроизводимо из чистого `make full`). Загрузка в `debug_load_rom(org=256)` даёт
**тот же обраc памяти** ⇒ ЦП исполняет те же инструкции ⇒ рантайм-поведение (заставка/музыка/
SPACE/рендер) идентично по построению. Прямые MCP-наблюдения выше это подтверждают независимо.

## Неизвестное / расхождения
- **Байт-в-байт идентичность получена «без намерения»**: address-exact компоновка + вербатим
  пропуски + byte-exact DEFB→INCBIN привели к точному совпадению. Это НЕ редизайн-«сдвиг
  адресов»; это ровно оригинал. Если требуется именно перекомпонованный ROM (сдвиги), —
  отдельная итерация; текущая цель «вести себя как оригинал» выполнена с запасом.
- `func_music_sub_3890`: точная роль внутри музыкального движка — UNKNOWN (маркер по адресу).
- Замеренные длины (`tools/sizes.json`) отличаются от заголовочных `; Размер` у нескольких
  файлов; эталон — RDB-адрес + измеренная длина. Заголовочные размеры в .asm не правились
  (кроме 4 явно обрезанных адресов) — они не участвуют в сборке (генератор RDB-driven).
- Прочее: расхождений в поведении не обнаружено.
