# BEAM_TIMING.MD — Луч, кадр и окна безопасной перерисовки (Вектор-06Ц)

> Модель видео-тракта «Вектора-06Ц» по исходникам эталонного эмулятора
> **vector06sdl (VSDL, ветка 4write)** — он же используется в проекте
> `vector-debug` как видеомодель (`vendor/v06c-emu/src/filler.cpp`,
> `board.cpp`, `vio.h`, `keyboard.h`).
>
> **Статус:** VERIFIED_BY_CODE (всё выведено из кода эмулятора и его тестов).
> На реальном железе не перепроверялось — см. §12 «Ограничения».

## 0. TL;DR (для ассемблерного кода)

| Вопрос | Ответ |
|---|---|
| Есть ли у луча своё время? | Нет. Луч двигается **ровно на такты, которые потратил CPU**. Нет кода — нет развёртки. |
| Кадр | 312 строк × 768 тактов = **239 616 тактов 12 МГц = 19.968 мс** (50.08 Гц) |
| Строка | 768 тактов = **64 мкс** (15.625 кГц); из них 512 активных, 128+128 служебных |
| Кадровое прерывание | **строка 0, такт 174** (14.5 мкс от начала кадра) |
| Первый видимый пиксель | строка 40, такт 152 → после INT остаётся **30 698 тактов = 2.56 мс ≈ 7 700 T** |
| Окно, когда VRAM не читается | строки **296…311 + 0…39** = 56 строк = **43 008 тактов ≈ 3.58 мс** |
| Сколько туда влезает | ~10 750 T-состояний ≈ **~450 байт** копирования (24 T/байт). 16 КБ буфер — **не влезает** |
| Палитра в гашении | Пишется **только в ячейку с номером = индекс бордюра** (адрес ячейки берётся из пикселя под лучом) |
| Скролл (порт 03h) | Защёлкивается на **строке 40, такт 150** — менять в гашении безопасно |
| Клавиатура | Читается комбинационно, к лучу не привязана. **Но порт 03h общий со скроллом** |

## 1. Базовые единицы времени

| Единица | Значение | Откуда |
|---|---|---|
| Видео-такт (такт луча) | 1/12 МГц = **83.33 нс** | `instr_time << 2` в `Board::single_step()` |
| Такт CPU (T-состояние КР580ВМ80А) | 3 МГц = **4 видео-такта** = 333.3 нс | `i8080_execute()` возвращает `cpu_cycles` |
| Строка | 768 видео-тактов = **64 мкс** | `VideoTiming::lineVCycles` |
| Кадр | 312 строк = **239 616 тактов = 19.968 мс** (50.08 Гц) | `VideoTiming::frameVCycles` |

**Ключевое следствие:** у видео нет собственных часов и нет отдельного потока.
`PixelFiller::fill(clocks)` вызывается из `Board::single_step()` с
`clocks = instr_time << 2`, то есть луч продвигается на время выполненной
инструкции. Поэтому:

- пауза / брейкпоинт останавливают луч вместе с CPU;
- одиночный шаг в отладчике = 16…92 такта = **1.3…7.7 мкс** развёртки (2–12 % строки);
- инструкция, «перелезшая» через конец кадра, досчитывается до конца, лишние такты
  переносятся в следующий кадр (`afterbrk12`) — время не теряется и не удваивается.

## 2. Раскладка одной строки (768 тактов = 64 мкс)

Видео-путь считает горизонтальную координату пикселя как `rpixel = raster_pixel − 24`
(смещение нужно для точной привязки коммитов портов к позиции луча).
Активная (видимая) часть строки — строго `raster_pixel ∈ [152, 664)`.

| Участок (`raster_pixel`) | Тактов | Что делает видео-путь |
|---|---|---|
| 0 … 151 | 152 | бордюр/гашение: индекс = бордюр, **VRAM не читается** |
| 152 … 663 | 512 | активная часть: 256 пикселей (в 256-режиме каждый = 2 такта) |
| 664 … 767 | 104 | бордюр/гашение: VRAM не читается |

Итого на строке **256 служебных тактов из 768 (33 %)** — в это время картинка
не формируется (это и есть строчное гашение + бордюр).

### Телевизионный буфер эмулятора

- размер буфера — **576 × 288** (`Options.screen_width/height` по умолчанию);
- `bmp_x = raster_pixel − 120`, `bmp_y = raster_line − 24`;
- значит в буфер попадает `raster_pixel ∈ [120, 696)`, т.е. 576 тактов;
- внутри буфера: **32 такта бордюра слева + 512 тактов картинки + 32 такта бордюра справа**;
- остальные 192 такта строки (120 слева и 72 справа) — вне экрана (аналоговое гашение).

## 3. Раскладка кадра (312 строк)

| Строки | Кол-во | Что происходит | В буфере ТВ? |
|---|---|---|---|
| 0 … 21 | 22 | кадровый синхроимпульс (КСИ) | нет |
| 22 … 23 | 2 | верхнее гашение | нет |
| 24 … 39 | 16 | верхний бордюр (сплошной цвет) | да |
| **40 … 295** | **256** | **изображение** (чтение плоскостей из VRAM) | да |
| 296 … 311 | 16 | нижний бордюр (сплошной цвет) | да |

Порог включения вывода: `first_visible_line = 312 − screen_height = 312 − 288 = 24`.
Флаг вертикального бордюра: `vborder = (raster_line < 40) || (raster_line >= 296)`.

**Главный вывод:** VRAM читается только на строках 40…295. На всех остальных
строках (0…39 и 296…311) видео-путь её не касается вообще: в бордюре
`getColorIndex(border=true)` сразу возвращает индекс бордюра и обнуляет счётчик
байт-столбца, а на строках 0…23 работает быстрый путь `fill()`, который просто
прибавляет такты к счётчику (`raster_pixel += clocks`).

## 4. Кадровое прерывание 50 Гц

```cpp
// filler.cpp, внутри fill1()
if (this->raster_line == 0 && this->raster_pixel == 174) {
    this->irq = true;
    this->irq_clk = clk;
}
```

- Запрос выставляется на **строке 0, такт 174** = 14.5 мкс от начала кадра,
  т.е. в начале кадрового синхроимпульса (КСИ идёт 22 строки).
- CPU принимает его только при `INTE` (после `EI`), на границе инструкции
  (`Board::check_interrupt()`); если запрос «не успел» внутри M-цикла, он
  откладывается до следующей инструкции (`irq_carry`) — джиттер до ~23 T.
- При приёме `INTE` сбрасывается (D65.2 снимает запрос), поэтому вложенных
  прерываний в обработчике нет до следующего `EI`.
- `RST 7` (0x38) добавляет 16 T, плюс сам вход в обработчик.

### Бюджет от INT до первого видимого пикселя

| Событие | Позиция | Тактов от INT | Время от INT |
|---|---|---|---|
| Запрос INT | строка 0, такт 174 | 0 | 0 |
| Начало записи в буфер ТВ | строка 24, такт 0 | 18 258 | 1.52 мс |
| Защёлка скролла | строка 40, такт 150 | 30 696 | 2.558 мс |
| Первый активный пиксель кадра | строка 40, такт 152 | 30 698 | 2.558 мс |

**Практически:** ≈30 700 тактов = 2.56 мс = **≈7 700 T-состояний** на всю работу
обработчика до того, как луч начнёт показывать содержимое VRAM.

## 5. Безопасное окно перерисовки VRAM

Если программа **не меняет цвет бордюра и палитру**, то запись в VRAM не видна
в текущем кадре на участке, где луч вообще не читает VRAM:

| Границы | По строкам | По тактам |
|---|---|---|
| Консервативно: строка 296, такт 0 → строка 40, такт 0 | 56 строк | 43 008 тактов = **3.584 мс** |
| Точно: строка 295, такт 664 → строка 40, такт 152 | 55.8 строки | 43 264 такта = **3.605 мс** |

Это **18 % кадра** (≈10 800 T-состояний). Внутри окна кадр меняется «атомарно» —
без разрыва, как на реальной машине.

### Сколько кода влезает в окно

| Действие | Тактов на байт | Влезает в 10 800 T |
|---|---|---|
| Минимальный цикл `MOV A,M / STAX D / INX H / INX D` (7+7+5+5) | 24 | ≈ 450 байт |
| То же, но после INT (7 700 T) | 24 | ≈ 320 байт |

Полный экран 256×256 — это **8 192 байта на плоскость** (32 байта на строку),
в двух плоскостях — 16 КБ. При 24 T/байт это ≈393 000 T ≈ **131 мс** (≈6.6 кадра).
То есть **перерисовать весь кадр в окне гашения невозможно физически**.
Варианты, которые применяются в проекте:

- двойная буферизация / маскировка палитрой (см. [DBLBUF.MD](DBLBUF.MD));
- частичная перерисовка только изменившихся участков;
- переключение кадра через `ScrollStart`, а не перерисовка;
- «догон луча» построчно — но тогда нужен расчёт бюджета на каждую строку.

### Оговорки к окну

1. **Бордюр в окне всё-таки рисуется.** Строки 24…39 и 296…311 заполняются
   сплошным цветом бордюра, строки 0…23 в буфер вообще не попадают. Поэтому
   запись в порт 02h (бордюр/режим) или в 0Ch (палитра) в этом окне **видна сразу** —
   это не «мёртвое» время для цвета, только для VRAM.
2. **Префетч.** Строка читается планами вперёд, группами по 16 тактов (≈1.3 мкс)
   на 8 пикселей. Значит запись в активной зоне проявляется не мгновенно, а
   со следующей группы, и заканчивать работу надо чуть раньше входа луча в картинку.
3. **Синхронизация только по INT.** Прочитать позицию луча из портов нельзя.
   Если `EI` не сделан или обработчик длинный — запись «поедет» по экрану.

## 6. Палитра (порты 0Ch…0Fh)

Механизм — не «номер ячейки + цвет», а «цвет в ячейку, адрес которой задаёт луч»:

1. 4 бита пиксельных данных (плоскости) → адрес ячейки палитры 0…15;
2. `OUT 0Ch` → запись физического цвета в ячейку по этому адресу.

Формат байта цвета: `RRR GGG BB` (биты 0–2 — красный, 3–5 — зелёный, 6–7 — синий).

Коммит привязан к лучу: внутри инструкции `OUT` обычный I/O применяется на такте
`commit_time = (instr_time − 4) << 2`, а палитра — на `commit_time_pal = commit_time − 20`
(на 20 тактов ≈ 1.7 мкс раньше), с индексом того пикселя, который в этот момент под лучом.

### Следствия для гашения

- В бордюре и на строках гашения «под лучом» находится **индекс бордюра**
  (`border_index = PB & 0x0f`). Значит `OUT 0Ch` в окне гашения пишет
  **в ячейку палитры с номером = индекс бордюра** (обычно 0 или 15).
- «Прошить все 16 ячеек» в гашении нельзя. Остальные ячейки пишутся тогда,
  когда пиксели нужного цвета находятся под лучом (racing the beam).
- Если бордюр и фон используют один и тот же индекс — смена цвета фона в гашении
  работает как надо. Если нет — верхняя видимая полоса бордюра (строки 24…39)
  уже покажет новый цвет.
- Цвет бордюра — **отдельный 4-битный регистр** (`PB & 0x0f`), но берётся он из
  палитры по этому индексу: `Palette(border_index)`. В режиме 512 бордюр
  раскладывается на две 2-битные группы: `index & 0x03` и `index & 0x0c`.

## 7. Скролл (порт 03h, Port A)

- `ScrollStart() = PA`; защёлкивается в видео-путь на **строке 40, такт 150** —
  ровно за 2 такта до первого активного пикселя.
- Первая строка кадра = `PA`, далее счётчик идёт вниз (`fb_row--` в `advanceLine()`),
  в активной зоне переход `0 → 0xFF`.
- Запись `PA` в гашении гарантированно действует **в этом же кадре**.
- Запись позже тоже безвредна (нет разрыва), но подействует только со следующего кадра.
- Менять `PA` каждый кадр в обработчике INT — штатный механизм вертикальной прокрутки.

---

## 8. Клавиатура (порты 02h/03h)

- Чтение матрицы — чисто комбинационное: `keyboard.read(~PA)` при `CW & 0x02`.
  Никакой привязки к лучу, защёлок и тайминговых требований нет.
- Опрос 8 строк ≈ 250 T — в окне гашения влезает с большим запасом.
- **Ловушка:** `PA` — одновременно селектор столбцов клавиатуры **и** регистр скролла.
  Скан пишет в `PA` маски (`FE/FD/FB/…`), а защёлка скролла читает `PA` на
  строке 40, такт 150. Скан, попавший в эту точку, защёлкнет маску столбца как
  первую строку кадра → картинка «прыгнет».
  - сканировать сразу по INT — безопасно (до защёлки ~30 600 тактов);
  - сканировать рядом со строкой 40 — нельзя, либо после скана переписать `PA`
    значением скролла.
- `SS / US / RUS` читаются из старшего полубайта порта 01h при `CW & 0x08`
  (активный уровень — 0; в эмуляторе инвертируется при чтении).

## 9. Бордюр и режим 512 (порт 02h, Port B)

- Биты 0…3 — индекс цвета бордюра, бит 4 — режим 512×256.
- Применяются на такте `OUT` (обычный I/O-коммит), т.е. строго в привязке к лучу.
- В гашении менять безопасно и правильно: смена бордюра сразу видна на верхней
  полосе (24…39) и далее, смена режима 512 действует на весь кадр. Отдельной
  защёлки «по началу кадра» в этой модели нет.

## 10. Готовый рецепт обработчика кадрового прерывания

```asm
        org     0038h
isr:    push    psw
        push    b
        push    d
        push    h               ; ~45 T на сохранение контекста

        ; --- до первого видимого пикселя ~7 600 T ---

        ; 1) скролл: действует в этом кадре (защёлка позже, строка 40/такт 150)
        mvi     a, SCROLL_ROW
        out     03h

        ; 2) бордюр / режим 512 — если нужно
        ; mvi   a, 10h          ; 512-режим, бордюр 0
        ; out   02h

        ; 3) палитра: попадёт в ячейку с номером = индекс бордюра
        ;    (остальные ячейки — только когда их цвет под лучом)
        ; mvi   a, 0E4h         ; RR RGGGBB
        ; out   0Ch

        ; 4) перерисовка VRAM — успеть до строки 40, такт 152
        ;    ~450 байт максимум; лучше — двойная буферизация/скролл

        ; 5) клавиатура: до строки 40 или с восстановлением PA после скана

        pop     h
        pop     d
        pop     b
        pop     psw
        ei
        ret
```

## 12. Ограничения

- Всё выведено из кода VSDL (`vendor/v06c-emu` в `vector-debug`), а не из
  измерений на железе. Реальный экземпляр Вектора может отличаться по:
  стабильности записи палитры «в луч», длительности КСИ/гашения, джиттеру
  кадрового прерывания.
- Числа привязаны к `Options.screen_height = 288`, `screen_width = 576`,
  `center_offset = 120` (значения по умолчанию). Границы **активной зоны**
  (строки 40…295, такты 152…663) от этих опций не зависят, а вот попадание
  в телевизионный буфер — зависит.
- В ванильном эмуляторе частота кадров подстраивается под монитор (`cadence`,
  пропуск кадров при 60 Гц); в сборке с отладчиком пейсинг фиксирован 50 Гц,
  каденция отключена.
- Механика палитры и раздельность регистра бордюра подтверждены также
  перекрёстной проверкой с EMU80 — см. `agent/knowledge/vector06c/verification.md`
  в репозитории `vector-debug`.
