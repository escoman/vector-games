# Stage 17 — Явный `size` для всех функций (Phase C: размеры по CFG-границам)

ТЗ Phase C / §Gate. Вход: CODE ∪ RDB = **100.00%**, но **208 из 233 функций с
`size=0`** (`measure_sizes`: 504 `size-unknown`, RDB-extents покрытие **27.99%**).
Выход: функций с `size=0` — **2**; RDB-extents покрытие **85.87%**; CODE ∪ RDB
по-прежнему **100.00%**; round-trip **byte-for-byte** (`make verify` diffs=0,
`run_pipeline --from export_asm` **6/6**). Инструмент:
`tools/stage17_function_sizes.py` (`--check` / `--apply`).

---

## 0. Метод границы

Размер функции = длина её тела в байтах, измеренная **разборкой**, а не угаданная:

1. Для каждой функции с `size=0` берём **per-entry линейную разборку**
   `debug_disassemble_range(entry, окно)` — рекомендация ТЗ: точные длины по
   отдельному диапазону, а не по одному большому `debug_analyze_code`
   (глобальная разборка расходится с entry на `PCHL`-островках).
2. **Граница** = адрес следующего *реального* объекта
   (`function`/`data`/`table`/`string`/`variable`). `label` — внутренняя цель
   перехода, границу **не задаёт** (входит в тело функции).
3. `size` = сумма длин целых инструкций от entry, **не пересекающих границу**
   (инструкция, полезшая за следующий объект, отбрасывается → накладов нет).

**Почему round-trip безопасен.** `asm/code.asm` — линейный вывод экспортёра
`v06c-asm-export` (по байту на адрес окна); классификация код↔`DEFB` задают
**data-объекты**, а не declared `size` функции. Типы не менялись, extent не
посягает на чужой объект → `layout.asm` неподвижен → `make verify` остался
byte-for-byte (оракул подтвердил).

## 2. Попутно устранено реальное наложение (данные ↔ доказанный код)

`measure_sizes` после простановки размеров вскрыл **`objects-overlap`**
(warn): `data_irq_palette_table @0x2C7E` (заявлены 16 Б из Stage14) перекрывал
`func_irq_handler @0x2C7F` на 15 байт. Проверка опровергла таблицу:

* `func_irq_handler @0x2C7F` — **доказанный код**: xref `0x0038 → 0x2C7F`
  (RST 38 = вектор прерываний), пролог `SHLD 2D07 / POP H / SHLD 2D0B /
  PUSH PSW / LXI H,0002 / DAD SP / SHLD 2D04` — сохранение контекста в
  `var_irq_context_block @0x2D04` (size 8). Это точный вход обработчика.
* `data_irq_palette_table @0x2C7E` — **0 xrefs**, байт `0xAD`; 15 из его
  «табличных» байт на самом деле исполняемый код обработчика.

Решение: `data_irq_palette_table` сжат **16 → 1** (накрывает только осиротевший
байт `0xAD` на `0x2C7E` перед входом обработчика); наложение снято, round-trip
не затронут. Свойство `size_source=stage17_overlap_fix` + комментарий фиксируют
доказательство. Истинная таблица палитры — вопрос **Phase D (Stage19)**.

## 3. Два пропуска (оставлены `size=0`, честно)

| адрес | функция | причина |
|---|---|---|
| `0x1ED9` | `func_cmd_verify` | окно до соседа `func_cmd_cload @0x1EDA` = 1 байт; entry-разборка не даёт целой инструкции, не пересекающей сосед → нечего записать без наложения |
| `0x3F20` | `func_3f20` | `0x3F20` лежит в коридоре workspace/`data_bit_clear_masks` (`0x3F20..0x40FB`); per-entry разборка не стартует от адреса как от кода → вероятно данные/выровненная граница, а не функция |

Оба остаются `size=0` и покрыты CODE∪RDB (дыр нет). Их переклассификация
(verify — тривиальный переход; `0x3F20` — данные vs код) отнесена к Phase C/D
семантике, а не угадана размером.

## 5. Limitations

* **RDB-extents 85.87% (не 100%)** — остаток 1424 Б накрнут только CFG-разбором
  и/или лежат внутри extent'ов функций как `label`-объекты (у меток размера нет
  по определению). Это не дыра атрибуции (CODE ∪ RDB = 100%); доподлинно
  подняться к 100% по extents можно лишь сольев метки в тела функций — семантика
  Stage18.
* `measure_sizes` post-stage показывает: `size-unknown` 298 = **метки** (им размер
  не нужен), `object-nested` 207 = **метки внутри тел функций** (intentional),
  `entry-not-on-instruction-boundary` 2 = расходимость ОДНОЙ глобальной линейной
  разборки инструмента с per-entry размерами (`func_rst_fac_sign`, `func_amp`) —
  обе уже имеют честный `size`, warning артефакт метода measure, не дефект.
* Sizes отражают **границу следующего объекта**, а не всегда логический `RET`:
  функция может «дотянуться» до следующего entry, включив хвост-данные-как-код,
  если сосед не размечен. Это осознанный консервативный выбор (extend-to-boundary
  без наложений); семантическое сужение до реальных `RET`/границ подпрограмм —
  Stage18 (rename + calls + links).
* Имена функций (технические `func_XXXX` и описательные без ABI) не менялись —
  это **Stage18**. `func_3f20`/`func_cmd_verify` требуют переклассификации.
