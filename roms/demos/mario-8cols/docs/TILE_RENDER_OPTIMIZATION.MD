# ТЗ: Оптимизация вывода тайлов через раздельные фазы «запечённый src → динамический dst → копирование»

## 1. Текущее состояние

### 1.1. Архитектура рендера

Горячий путь демки — `render_window` в [mario.asm](../include/mario.asm).
Функция сравнивает новую тайлкарту (`tile_win[cam]`) с эталоном (`tile_win[old_cam]` или `tileset[0]` для первого экрана) и пишет разницу в VRAM.

**Текущий цикл `_rw_block`** (инлайн в `rw_scan`, оптимизации #7/#9/#4):

```
for each screen row (32 - top):
    if tile_new != tile_old:              ← сравнение (скан)
        nz_mask = (nz[old]<<2) | nz[new]  ← разбор плоскостей
        tileset_addr = tile + tile*16      ← ← 4× dad h (адрес данных)
        for each plane (weight 8, weight 4):
            if copy:  8× (mov a,m / stax d / inx h / dcx d)   ← 192 T
            if erase: xra a + 8× (stax d / dcx d)             ← ~96 T
            if skip:  lxi d,8 / dad d                          ← переход
```

### 1.2. Замеры (profile_scroll, 288 шагов, после #9)

| Участок | T/шаг | Доля |
|---|---:|---:|
| Скан/сравнение (`rw_scan`, `rw_scan_next`) | 70 409 | 34 % |
| Инлайн-копия (`_rw_put_cell`, copy+erase+skip) | 116 941 | 57 % |
| Прочее (пролог, walk-и, pair_top) | ~17 600 | 9 % |
| **Итого средний шаг** | **~204 951** | **3,42 кадра** |

Теоретический пол: 2 283 байт VRAM × ~12 T ≈ **27 000 T** (0,46 кадра).

### 1.3. Спрайт Марио (`mario_draw` / `mario_undraw`)

| Операция | T/кадр |
|---|---:|
| `mario_undraw` + `mario_draw` | 7 596 (0,13 кадра) |

Спрайт — 4 прогона × 16 байт = 64 записи VRAM. Адреса прогонов вычисляются
в преамбуле (`md_vtab[4]`), затем цикл `md_px` пишет побайтно с `dcr e`
(кольцевой переход).

### 1.4. Вертикальный скролл (`render_rowband`)

| Операция | T/вызов |
|---|---:|
| 32 колонки × 2 плоскости × `_rw_copy8` | 30 840 (0,53 кадра) |

## 2. Идея оптимизации

### 2.1. Ключевое наблюдение

Источник данных (плоскости тайлов в ROM) **статичен** для каждого варианта
префаба: мы заранее знаем, из каких тайлов состоит префаб, и можем вычислить
адреса данных плоскостей **на этапе генерации ассетов** (в `gen_assets.py`).
Динамичны только VRAM-адреса назначения — они зависят от текущей позиции
камеры и скролла.

Следовательно, массив `src_ptrs[]` можно **запечь в ROM** для каждого
варианта префаба, а в преамбуле строить только `dst_ptrs[]` в RAM.

### 2.2. Принцип разделения фаз

```
ROM (статика, gen_assets.py):
  src_ptrs[] — указатели на данные плоскостей тайлов префаба
               (запечены один раз, не меняются в рантайме)

RAM (динамика, преамбула каждый кадр/шаг):
  dst_ptrs[] — VRAM-адреса, куда копировать данные
               (вычисляются из позиции камеры / Марио)

Копирование (плоский цикл):
  читает src из ROM, dst из RAM, копирует 8 байт в VRAM.
  Завершение по нулю в src_ptrs[].
```

Ключевое отличие от текущего инлайна: **на этапе копирования алгоритм не
занимается никакими подготовительными работами и вычислениями, а просто
копирует по двум спискам из памяти в VRAM**. Вся адресная арифметика
(tileset lookup, `4× dad h`) уже сделана — на этапе запекания ассетов.

### 2.3. Аналогия со spr-speed

В [spr_smc.asm](../../tests/spr-speed/spr_smc.asm) тот же принцип: обработчик
столбца (`col_copy`) читает SHIFT/LEN из данных, входит в «лесенку» (развёрнутый
код копирования), и каждая строка — это чистые `ldax d / mov m,a / inx d / dcx h`
без ветвлений и счётчиков. Вся подготовительная работа (разбор дескриптора,
вычисление адресов плоскостей) сделана ДО входа в лесенку.

Наш случай — та же архитектура, но для **фонового рендера** (тайлы + спрайт):
- Запечённый `src_ptrs[]` в ROM = аналог дескриптора спрайта (данные готовы)
- Динамический `dst_ptrs[]` в RAM = вычисляется из позиции камеры
- Копирование = плоский цикл по двум массивам (аналог `plane_smc` через `col_copy`)

## 3. Формат данных

### 3.1. Два массива — ROM и RAM

```
src_ptrs[]  (ROM, запечён gen_assets.py, статичен на вариант префаба):
  Указатели на данные плоскостей тайлов в tileset.
  Для варианта V с N тайлами: N × 2 записей (по одной на плоскость веса 8 и 4).
  Завершающий ноль: src_ptrs[last] = 0x0000.

dst_ptrs[]  (RAM, строится преамбулой каждый кадр/шаг):
  VRAM-адреса (0x8000–0xFFFF), куда копировать данные.
  Одна запись на каждую запись src_ptrs.
  Завершающий ноль не нужен — конец определяется по нулю в src_ptrs[].
```

Каждый элемент — 16-битный указатель. Пара `(src_ptrs[i], dst_ptrs[i])` =
одна операция записи 8 байт из ROM в VRAM.

### 3.2. Запечённый src_ptrs[] (генерация ассетов)

Для каждого варианта префаба `V` `gen_assets.py` генерирует:

```c
// Вариант V: префаб из тайлов {t0, t1, t2, ...}
const unsigned int pf_V_src[] = {
    (unsigned int)&tileset[t0 * 16],       // плоскость веса 8
    (unsigned int)&tileset[t0 * 16 + 8],   // плоскость веса 4
    (unsigned int)&tileset[t1 * 16],       // плоскость веса 8
    (unsigned int)&tileset[t1 * 16 + 8],   // плоскость веса 4
    ...
    0x0000,                                 // завершающий ноль
};
```

Эти данные **не меняются в рантайме** — они одинаковы для каждого
экземпляра префаба V, независимо от позиции на экране.

### 3.3. Динамический dst_ptrs[] (преамбула в рантайме)

Преамбула вычисляет VRAM-адреса для каждого тайла префаба в текущей позиции:

```c
// Для каждого тайла preфаба на позиции (col, row):
dst_ptrs[i*2]   = (vram_bases[0] + col) << 8 | (255 - (cam_row + row) * 8);
dst_ptrs[i*2+1] = (vram_bases[1] + col) << 8 | (255 - (cam_row + row) * 8);
```

Преамбула строит dst_ptrs[] только для **видимых** и **изменившихся** тайлов
(diff-оптимизация: если тайл не изменился, запись пропускается — но тогда
нужно согласование индексов src/dst, см. §3.5).

### 3.4. Цикл копирования

Концептуально цикл читает пару `(src, dst)` и копирует 8 байт:

```asm
; HL = &pf_V_src[0] (ROM), DE = &dst_ptrs[0] (RAM)
copy_loop:
    ; Загрузить src из ROM (2 байта)
    ; Проверка: src == 0x0000 → конец (завершающий ноль)
    ; Загрузить dst из RAM (2 байта)
    ; Копирование 8 байт: src (ROM) → dst (VRAM)
    ; Advance HL, DE на 2
    jmp     copy_loop
```

Детальная реализация с раскладкой регистров — в §5.1.

### 3.5. Согласование src/dst при diff-рендере

Запечённый `src_ptrs[]` статичен — он содержит записи для **всех** тайлов
префаба, независимо от diff. Преамбула строит `dst_ptrs[]`, пропуская
неизменившиеся тайлы. Возникает рассинхронизация индексов.

Два варианта решения:

**Вариант A: Полная перезапись** (простой)
Преамбула строит `dst_ptrs[]` для **всех** тайлов префаба (без diff).
Копирование пишет всё, включая неизменившиеся тайлы.
Плюс: индексы src/dst всегда совпадают, цикл прост.
Минус: лишние записи VRAM (но wait states всё равно ограничивают пропускную
способность, поэтому на практике может быть не хуже diff-варианта).

**Вариант B: Diff-фильтрация** (сложный, но экономит VRAM-записи)
Преамбула сравнивает `tile_win[new]` с `tile_win[old]`. Для неизменившихся
тайлов — пропускает запись в `dst_ptrs[]`, но **всё равно продвигается**
по `src_ptrs[]` (т.к. он статичен и содержит все тайлы).
Минус: нужен промежуточный индексный массив или смещение, чтобы
копирование знало, какие src-записи пропущены.

**Рекомендация**: начать с Варианта A (полная перезапись), замерить
производительность. Если упирается в VRAM-записи — перейти к Варианту B.

### 3.6. Кодирование erase

Для **erase** (старый тайл имел плоскость, новый — пуст): запечённый
`src_ptrs[]` уже содержит адрес `&tileset[0]` (тайл 0 = 16 нулей) для
пустых тайлов префаба. Копирование пишет нули — **без отдельной ветки
erase**.

Если префаб не содержит «дырок» (все тайлы непустые), а erase нужен (тайл
стал пустым из-за diff) — преамбула подставляет в dst_ptrs[] адрес, но
src указывает на tileset[0] через отдельный механизм:
- Либо: специальный маркер в dst_ptrs[] (бит = «писать нули»)
- Либо: отдельный src-массив для erase-случаев
- Либо: Вариант A (полная перезапись) решает проблему автоматически

### 3.7. Размер данных

**ROM (src_ptrs[], статика):**
- Один вариант префаба: N_тайлов × 2 записи × 2 байта + 2 байта (ноль)
- Пример: префаб 3×3 = 9 тайлов × 4 + 2 = 38 байт
- 61 вариант × ~38 байт ≈ **2,3 KB ROM** (оценка)

**RAM (dst_ptrs[], динамика):**
- Максимум записей на шаг скролла: ~286 (143 клетки × 2 плоскости)
- 286 × 2 байта = **572 байта RAM**

**Итого**: ~2,3 KB ROM + ~0,6 KB RAM.

## 4. Фаза 1: Преамбула

Преамбула строит **только `dst_ptrs[]`** (VRAM-адреса). Массив `src_ptrs[]`
уже запечён в ROM для каждого варианта префаба.

### 4.1. Преамбула `render_window`

Вход: `cam`, `old_cam`, `blk0`, `nblk` (те же, что у текущего `_render_window`).

```
; Предусловие: для текущего варианта префаба V уже известен
; запечённый src_ptrs_V[] в ROM (генерируется gen_assets.py).

for blk = blk0 .. blk0+nblk-1:
    compute newwalk, refwalk (адреса в tile_win)
    compute dst_low (кольцевой адрес VRAM)
    compute pair_top → rw_top (пропуск неба)

    for row = rw_top .. 31:
        tile_new = tile_win[newwalk + row]
        tile_old = (old_cam == CAM_NO_REF) ? 0 : tile_win[refwalk + row]

        if tile_new == tile_old:
            continue                        ← пропуск (diff-оптимизация)

        ; --- Только VRAM-адрес, БЕЗ lookup tileset ---
        dst = (vram_bases[plane] + blk) << 8 | dst_low
        dst_ptrs[cur++] = dst

        ; (src уже в запечённом массиве — просто идём по нему)

        dst_low -= 8                        ← кольцевой переход
        newwalk++; refwalk++
```

**Что делается в преамбуле (и НЕ делается в копировании):**
- Сравнение тайлов (diff) — как и раньше
- Вычисление VRAM-адреса (`vram_bases[p] + blk`, `dst_low`)
- Кольцевая арифметика `dst_low -= 8`

**Что УБРАНО из преамбулы (по сравнению с текущим инлайном):**
- Lookup `tile_nz` — не нужен, запечённый src_ptrs[] уже содержит только непустые плоскости
- Вычисление `tileset_addr` (`4× dad h`) — не нужно, адрес уже в src_ptrs[]
- Ветвление copy/erase/skip — не нужно, цикл копирования всегда copy8

### 4.2. Преамбула `mario_draw`

Для спрайта Марио `src_ptrs[]` запечён в ROM для каждого кадра анимации
(16 кадров × 2 направления = 32 варианта). Преамбула вычисляет только
`dst_ptrs[]` из текущей позиции (x, y):

```
; src_ptrs_MARIO[frame][dir] — запечён в ROM
; Преамбула строит dst_ptrs[]:
for run = 0..3:
    dst = char_bases[plane] + blk + (y_offset)
    dst_ptrs[cur++] = dst
    dst_ptrs[cur++] = dst - 8     ; вторая половина прогона
```

### 4.3. Преамбула `render_rowband`

Аналогична преамбуле `render_window`, но без diff-сравнения — все клетки
пишутся безусловно. `src_ptrs[]` запечён для набора тайлов горизонтальной
полосы.

## 5. Фаза 2: Копирование VRAM

### 5.1. Универсальный цикл копирования

Один цикл для всех типов рендера (фон, спрайт, rowband).
Источник (src) читается из **ROM** (запечённый массив), назначение (dst) — из
**RAM** (динамический массив):

```asm
; HL = &pf_V_src[0] (ROM, запечён), DE = &dst_ptrs[0] (RAM, построен преамбулой)
vram_copy_loop:
    ; Загрузить src из ROM
    mov     a, m             ; src_lo (из ROM)
    inx     h
    mov     b, m             ; src_hi (из ROM)
    inx     h                ; HL = следующий элемент src

    ; Проверка на ноль (конец): src == 0x0000?
    ora     b
    jz      copy_done        ; оба == 0 → конец

    ; Сохранить src в стеке
    push    h                ; сохранить HL (src_cur)
    mov     h, b
    mov     l, a             ; HL = src адрес (ROM tileset)
    xchg                     ; DE = src, HL = dst_cur

    ; Загрузить dst из RAM
    mov     a, m             ; dst_lo
    inx     h
    mov     b, m             ; dst_hi
    inx     h                ; HL = dst_cur (продвинут на 2)

    ; Теперь: DE = src (ROM), BC = dst (VRAM)
    ; Копирование 8 байт (подробнее — §5.2)
    push    h                ; сохранить dst_cur
    ; ... 8× ldax d / stax b / dcx d / dcx b ...
    pop     h                ; HL = dst_cur
    xchg                     ; DE = dst_cur
    pop     h                ; HL = src_cur (ROM)
    jmp     copy_loop
```

**Ключевое**: в цикле нет вычисления `tileset_addr` (4× `dad h`), нет lookup
`tile_nz`, нет ветвлений copy/erase/skip. Только загрузка пары указателей +
8 байт копирования.

### 5.2. Оптимизация: развёрнутый копирователь

По аналогии с «лесенкой» spr_smc.asm, цикл копирования можно развернуть:

```asm
vc_copy8:
    ldax    d               ; байт из src
    stax    b               ; байт в dst
    dcx     d               ; (или inx d — зависит от порядка)
    dcx     b
    ; ... ×8 ...
    ret
```

Или использовать `LDIR`-подобную идиому (если есть свободная пара регистров).

### 5.3. Побайтовое vs поплоскостное копирование

Два варианта granularity:

**Вариант A: 8-байтные записи** (как сейчас в copy8)
- `src_ptrs[i]` = адрес 8 байт плоскости тайла
- `dst_ptrs[i]` = VRAM адрес
- Цикл: загрузил пару → скопировал 8 байт → следующая пара
- Записей: ~286/шаг

**Вариант B: 1-байтные записи** (максимально гибкий)
- `src_ptrs[i]` = адрес одного байта
- `dst_ptrs[i]` = адрес одного байта VRAM
- Цикл: `LDAX D / STAX B / INX D / INX B / DCX H` × N
- Записей: ~2283/шаг (2 283 байта VRAM)
- Нет необходимости в `inx h / dcx d` внутри — просто линейный массив

**Вариант B** ближе к идее spr-speed (лесенка копирует побайтно без
внутреннего цикла), но требует больше RAM под массивы (~9 KB). **Вариант A** —
компромисс.

## 6. Применение к функциям рендера

### 6.1. `render_window` (горячий путь, 57 % времени)

**Текущая схема:**
- Скан + инлайн-копия в одном цикле
- Адресная арифметика на каждую грязную клетку (4× `dad h`, lookup `tile_nz`)

**Новая схема:**
1. Фаза скана: только сравнение `tile_new == tile_old`, без копирования
2. Фаза преамбулы: для грязных клеток — **только вычисление VRAM-адресов**
   (src уже запечён в ROM!)
3. Фаза копирования: плоский цикл по массивам

**Ожидаемый эффект:**
- Скан упрощается → можно оптимизировать (до ~50–60k T)
- Преамбула: ~20–25k T (только VRAM-адреса + запись в dst_ptrs[])
- Копирование: ~20–30k T (чистый цикл, без branching)
- **Итого: ~90–115k T** вместо 204k (−43…−56 %)

### 6.2. `mario_draw` (спрайт, 0,13 кадра)

**Текущая схема:**
- Вычисление `md_vtab[4]` (VRAM-адреса 4 прогонов)
- Цикл `md_px`: 16× (`mov a,m / stax d / inx h / dcr e / dcr b / jnz`)

**Новая схема:**
1. `src_ptrs[]` уже запечён в ROM для каждого кадра анимации
2. Преамбула: заполнить только `dst_ptrs[8]` (4 прогона × 2 плоскости)
3. Копирование: универсальный цикл (тот же, что для фона)

**Ожидаемый эффект:**
- Унификация кода (один цикл для фона и спрайта)
- Минимальный выигрыш в T (спрайт и так быстр)
- Возможность: преамбулу спрайта делать **один раз** при смене кадра/позиции,
  а не каждый вызов

### 6.3. `render_rowband` (вертикальный скролл, 0,53 кадра)

**Текущая схема:**
- 32× (`_rw_copy8` через `call`) для каждой плоскости

**Новая схема:**
1. Преамбула: 64 записи (32 колонки × 2 плоскости)
2. Копирование: универсальный цикл

**Ожидаемый эффект:**
- Убирается 64× `call _rw_copy8` (18 T × 64 = 1 152 T только на CALL/RET)
- Копирование становится линейным (нет переходов между колонками)

|---|---:|---:|
| Текущий (baseline) | 204 951 | 3,42 |
| Раздельные фазы (оценка) | ~115 000–140 000 | 1,92–2,33 |
| Теоретический пол | 27 000 | 0,46 |
| SMC-лесенка (spr-speed) | 4 208 (спрайт) | — |

Раздельные фазы дают **−32…−44 %** к среднему шагу. До теоретического пола
далеко — ограничивает скан diff (~55k T) и преамбула (~20–35k T).

### 7.4. С амортизацией bake_shift

| | T/шаг | Кадров |
|---|---:|---:|
| Текущий с амортизацией | ~268 000 | 4,48 |
| Раздельные фазы + #3 (ASM bake) | ~65 000–85 000 | 1,1–1,4 |

Комбинация с #3 (перепечка на ASM) даёт **суммарно ~1,2 кадра на шаг** —
близко к целевым 0,5 кадра.

## 8. Интеграция с существующими оптимизациями

### 8.1. Совместимость с #7/#9 (инлайн copy8/put_cell)

Текущий инлайн (#7/#9) **полностью заменяется** новой схемой:
- Инлайн-тело в `rw_scan` убирается
- Вместо него — вызов преамбулы + копирование

### 8.2. Совместимость с #4 (zero-fill erase)

Естественным образом встраивается: для пустых тайлов запечённый `src_ptrs[]`
уже указывает на `&tileset[0]` (нули). Отдельная ветка zero-fill не нужна —
копирование само пишет нули.

### 8.3. Совместимость с #5 (_mulshift)

`_mulshift` используется в преамбуле для вычисления `newwalk`/`refwalk`.
Остаётся без изменений.

### 8.4. Совместимость с #1 (dirty_mask — откачена)

Раздельные фазы **не совместимы** с dirty_mask в её исходном виде, потому что
скан diff всё равно нужен для построения массивов. Однако можно комбинировать:
если dirty_mask пропускает группу строк — преамбула не добавляет записей для
этих строк. Но #1 уже откачена из-за низкой доли чистых строк (65,8 %).

### 8.5. Отношение к SMC-лесенке (spr-speed)

Лесенка spr_smc.asm — это **развёрнутый цикл копирования** (нет DCR/JNZ на
каждую строку). В нашем случае для тайлов 8×8 это менее применимо (фиксированная
длина 8), но принцип «подготовительная работа ДО цикла копирования» — общий.

Можно использовать развёрнутый копирователь (8 инструкций без цикла) как
внутреннее тело фазы 2:

```asm
; Развёрнутое копирование 8 байт (как текущий copy8, но через пары указателей)
    ldax    d       ; src[0]
    stax    b       ; -> dst[0]
    dcx     d
    dcx     b
    ldax    d       ; src[1]
    stax    b       ; -> dst[1]
    dcx     d
    dcx     b
    ; ... ×8 ...
```

## 9. План реализации

### Этап 0: Генерация запечённых src_ptrs[] (Python)

**Цель:** модифицировать `gen_assets.py` для генерации статических массивов
источников для каждого варианта префаба.

1. Для каждого варианта V: пройтись по тайлам префаба, вычислить
   `&tileset[tile_idx * 16 + plane * 8]` для каждой непустой плоскости.
2. Сгенерировать `pf_V_src[]` в `level.inc` (массив 16-битных указателей).
3. Добавить завершающий ноль.
4. Для спрайта Марио: сгенерировать `src_ptrs_MARIO[frame][dir]` аналогично.
5. Замержить с текущим `tileset[]` — оба массива в ROM.

**Критерий:** `level.inc` содержит дополнительные ~2,3 KB ROM данных.

### Этап 1: Исследовательский прототип (Python)

**Цель:** подтвердить оценку T/шаг на модели.

1. Написать Python-модель преамбулы: на вход — состояние `tile_win` (из
   `profile_scroll`), на выход — массив `dst_ptrs[]` (src уже запечён!).
2. Подсчитать количество записей для каждого шага скролла.
3. Оценить T преамбулы и T копирования раздельно.
4. Сравнить с текущим профилем.

**Критерий:** оценка показывает < 140k T/шаг (−30 % к baseline).

### Этап 2: ASM-реализация преамбулы

1. Выделить из `_rw_block` фазу скана (сравнение + пропуск неба).
2. Написать `_rw_preamble`: скан + заполнение **только `dst_ptrs[]`**.
3. Использовать существующие регистровые приёмы (#2: `B` = nzmask, `C` = dst_low).
4. Курсор dst_ptrs[] в регистрах (DE или HL), запись через `STAX D / INX D`.

### Этап 3: ASM-реализация копирования

1. Написать `_vram_copy`: плоский цикл по запечённому src (ROM) и dst (RAM).
2. Развёрнутое тело копирования (8 байт без внутреннего цикла).
3. Завершение по `src == 0` (нулевой элемент в запечённом массиве).

### Этап 4: Интеграция и паритет

1. Заменить `_render_window` на связку «скан → преамбула → копирование».
2. Прогнать `check_render_regress` — VRAM должен быть побайтово идентичен.
3. Прогнать `profile_scroll sweep` — замерить реальные T.

### Этап 5: Распространение на спрайт

1. Адаптировать `mario_draw` под ту же схему (запечённый src + динамический dst).
2. Преамбула спрайта — один раз при смене кадра/позиции (кэширование).

### Этап 6: Распространение на rowband

1. Адаптировать `render_rowband` (преамбула тривиальна — нет diff).

## 10. Риски и митигации

| Риск | Вероятность | Митигация |
|---|---|---|
| Преамбула дороже ожидаемого (запись dst_ptrs[] в RAM через LHLD/SHLD) | Средняя | Использовать регистры для курсора массива; писать парами `STAX D / INX D` |
| Не хватает ROM под запечённые src_ptrs[] | Низкая | ~2,3 KB — посильно для ROM-бюджета |
| Не хватает RAM под dst_ptrs[] | Низкая | Максимум ~572 байта; можно перекрывать с tile_win |
| Паритет VRAM ломается на граничных случаях (кольцо, cam_row ≠ 0) | Средняя | `check_render_regress` на полном покрытии (cam_row, render_rowband) |
| Выигрыш меньше 30 % — не стоит усложнения | Низкая | Этап 1 (Python-модель) даст ответ до написания ASM |
| Несовместимость с будущими оптимизациями скана | Низкая | Скан остаётся отдельной фазой; его можно оптимизировать независимо |

## 11. Критерии приёмки

1. **Паритет VRAM**: `check_render_regress` — SHA-1 идентичен baseline на всех
   288 шагах скролла (включая `cam_row`, `render_rowband`, первый экран).
2. **Производительность**: средний шаг ≤ 140 000 T (−32 % к baseline 204 951 T).
3. **ROM-бюджет**: запечённые src_ptrs[] добавляют ≤ 3 KB ROM.
4. **RAM-бюджет**: dst_ptrs[] занимают ≤ 1 KB RAM.
5. **Код**: горячий цикл копирования не содержит ветвлений (кроме завершения по нулю).
6. **Унификация**: один цикл копирования используется для `render_window`,
   `render_rowband`, `mario_draw`, `mario_undraw`.

## 12. Открытые вопросы

1. **Гранулярность записи**: 8 байт (плоскость тайла) или 1 байт (отдельный
   пиксель)? 8 байт — меньше записей, но копирование менее гибкое. 1 байт —
   больше записей, но можно копировать произвольные блоки.

2. **Кэширование преамбулы спрайта**: если позиция Марио не меняется между
   кадрами, dst_ptrs[] можно не перестраивать. Нужен флаг «спрайт изменился».

3. **Перекрывание dst_ptrs[] с tile_win**: dst_ptrs[] используется только
   в копировании, tile_win — только в преамбуле. Можно ли разместить их
   по одному адресу? Это экономит RAM, но требует осторожности.

4. **Комбинация с SMC-лесенкой**: можно ли использовать лесенку spr-speed
   для копирования 8-байтных записей? Лесенка работает с переменным LEN,
   а у нас фиксированные 8 — но можно адаптировать.

5. **Порядок записей в запечённом src_ptrs[]**: плоскости одного тайла идут
   подряд (weight 8, потом weight 4)? Или все weight 8 сначала, потом все
   weight 4? Первый вариант проще (один курсор tileset), второй — лучше
   для cache locality VRAM.

6. **Diff-оптимизация**: если преамбула пропускает неизменившиеся тайлы,
   как согласовать индексы src/dst? Варианты:
   - Полная перезапись (Вариант A из §3.5) — просто, но больше VRAM-записей
   - Промежуточный индексный массив — сложнее, но экономит VRAM

7. **Генерация src_ptrs[] в gen_assets.py**: как лучше интегрировать
   генерацию запечённых массивов в существующий конвейер? Отдельная функция
   на каждый вариант префаба или универсальная?
