# Проблема: убрать теневой буфер рельефа (8KB RAM)

## Контекст

Движок рельефа H.A.T.E. хранит 32 столбца мира в кольцевом буфере в RAM:
- 32 страницы × 256 байт = **8KB RAM**.
- Каждая страница = 16 клеток × 8 байт = 128 байт (используется нижняя половина).
- Кольцо выделяется из кучи (`heap_alloc(RING_BYTES)` в `main.c`).

Для Vector-06C это слишком расточительно — впереди ещё много контента,
память уже на исходе.

## Идея

Vector-06C поддерживает **dblbuf** (переключение палитры между плоскостями).
Front-плоскость видна пользователю, back-плоскость скрыта. Можно рисовать
рельеф прямо в back-плоскость VRAM, без промежуточного буфера в RAM.

На ZX Spectrum теневой экран использовался потому, что там нет dblbuf.
На Vector-06C этой проблемы нет — надо использовать возможности по полной.

## Архитектура оригинала

```
m_assemble → кольцо (RAM) → m_blit → VRAM (back-плоскость)
```

- `m_assemble`: генерирует столбец из кодов клеток + банка шаблонов (`lv_data`).
  Пишет 128 байт в страницу кольца. Вызывается 1 раз за тик камеры (раз в 4 кадра).
- `m_blit`: копирует M_CHUNK=8 столбцов из кольца в VRAM.
  Адрес VRAM: `(m_pbase + m_draw) × 256 + m_start`, где `m_start = lv_geom[m_draw].start = 4 × m_draw`.
- `m_draw`: номер столбца в полосе (0..31), инкрементируется внутри `m_blit`.
- `m_col`, `m_lcol`: абсолютные счётчики столбцов мира, инкрементируются внутри `m_assemble`.

## Желаемая архитектура

```
m_assemble → VRAM (back-плоскость, напрямую)
```

- Убрать кольцо в RAM (экономия 8KB).
- Убрать `m_blit` (не нужен).
- `m_assemble` пишет прямо в VRAM по адресу `(m_pbase + m_draw) × 256 + 4 × m_draw`.
- `mission_frame` вызывает `m_assemble` M_CHUNK=8 раз за кадр (вместо `m_blit`).

## Бюджет тактов

- `m_assemble`: 16 клеток × (2 байта код + 8 байт шаблон + 8 байт запись) = 288 байт операций.
- 288 × 24T = 6,912T на столбец.
- 8 столбцов: 8 × 6,912T = **55,296T**.
- Бюджет кадра: 59,904T (3 МГц).
- **Укладывается (92%)** ✓

## Попытки решения

### Попытка 1: упаковка страниц 256→128 байт

**Цель:** сэкономить 4KB RAM (32 × 128 вместо 32 × 256).

**Результат:** ❌ Не удалось.

- Изменил stride в `m_blit` и `m_assemble` с 256 на 128.
- Данные кольца байт-идентичны оригиналу (проверено дампом страниц 0-3).
- Но VRAM вывод отличается: packed = `96,16,100,16,...`, original = `192,112,172,87,...`.
- Баг в `m_blit` — не удалось найти причину. Reverted.

### Попытка 2: прямое рисование в VRAM из `m_assemble`

**Цель:** убрать кольцо полностью, рисовать прямо в VRAM.

**Изменения:**
1. `main.c`: убран `RING_BYTES`, `heap_alloc`, параметр `ring` в `mission_start`.
2. `mission.asm`:
   - `mission_start`: собирает 32 столбца прямо в обе плоскости (A и B).
   - `mission_frame`: вызывает `m_assemble` 8 раз вместо `m_blit`.
   - `m_assemble`: адресация VRAM вместо кольца:
     ```asm
     lda     m_pbase
     mov     b, a                        ; B = m_pbase
     lda     m_draw
     add     b
     mov     b, a                        ; B = m_pbase + m_draw
     lda     m_draw
     add     a                           ; A = m_draw × 2
     add     a                           ; A = m_draw × 4
     mov     c, a                        ; C = m_start = 4 × m_draw
     ```
   - Добавлен инкремент `m_draw` в конец `m_assemble`.
   - Убраны `m_blit`, `m_full`, `m_ring`, `m_loop`, `m_left`, `m_todo`.

**Результат:** ❌ Код падает.

- Адресация VRAM правильная (проверено breakpoint'ом: BC = 0xE000).
- Но код падает после первого вызова `m_assemble` (PC уходит в 0x0129).
- `m_pbase` установлен правильно (0xE0 для A, 0xA0 для B).
- `m_draw` сбрасывается между буферами A и B.

**Гипотезы о причине падения:**
1. `m_assemble` вызывается 64 раза в `mission_start` (32 для A + 32 для B).
   Возможно, очередь `m_win` не готова к такому темпу.
2. `m_cell` или `m_pop` падают из-за неправильных данных.
3. Переполнение стека или другая системная ошибка.

**Проверено:**
- Адресация VRAM: BC = (m_pbase + m_draw) × 256 + 4 × m_draw = 0xE000 для m_draw=0, m_pbase=0xE0. ✓
- `m_pbase` в памяти: 0xE0 (правильно). ✓
- `m_draw` в памяти: 0 (правильно). ✓

## Что известно точно

- VRAM на Vector-06C = обычная память (нет wait states, нет разницы в скорости с RAM).
- `lv_geom[x] = (4x, 16)` — start = 4×x, cnt = 16. Это подтверждено в `gen_levels.py`.
- Адресация VRAM в оригинальном `m_blit`: `BC = (m_pbase + m_draw) × 256 + m_start`.
- `m_start = 4 × m_draw` — вычисление напрямую должно давать тот же результат.
- Оригинал работает: полная полоса рельефа (32 столбца) с диагональным наклоном.

## Следующие шаги

1. **Пошаговая отладка:** найти точное место падения в `m_assemble` через
   `debug_step` или breakpoint'ы внутри функции.
2. **Проверить очередь `m_win`:** убедиться, что `m_pop` и `m_prime` корректно
   работают при вызове `m_assemble` 8 раз за кадр.
3. **Альтернатива — уменьшенное кольцо:** хранить только 8 страниц (видимые
   столбцы) вместо 32. Экономия: 6KB RAM. Но нужен сдвиг каждый кадр.
4. **Альтернатива — гибридный подход:** оставить кольцо, но уменьшить размер
   страницы (попытка 1 с более тщательной отладкой `m_blit`).
