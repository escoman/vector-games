# Stage 8. Выгрузка кода и данных в ASM (консолидированный монолит, exolon.rom)

> **Ретро-нота.** Первый экспорт Stage 8/10 был халтурой: ROM распался на 502
> `.bin`-блоба (`154 func_*.bin` + `258 lbl_*.bin` + `39 gap_*.bin`) плюс 33 файла
> `str_*.asm`. Дерево нельзя было ни читать, ни править. Сейчас `asm/` — это **ОДИН
> монолит `code.asm`** + мастер `exolon_new.asm`. Ниже — почему именно монолит.

## Железобетонное ограничение тулчейна

Проверено эмпирически (`z80asm -b -m=8080_strict`):

- **второй `ORG` не переносится** — «ORG redefined», гэпы не заполняются;
- **код и данные в ROM перемешаны** — в `exolon.rdb` 25 стыков код↔данные
  (`data_sprites@0x01FF`, `data_wave_table@0x2188`, `data_score_table@0x3E33`,
  `str_hud_ammo@0x3F54`, глифы `@0x2630/0x742D`, `str_title_copyright@0x77EA`, …).

Следовательно побайтовая пересборка обязана идти **строго адресным потоком**
(один верхний `ORG 0100h` + последовательный вывод). Разложить содержимое по
отдельным файлам-классам (`strings.asm`, `sprites.inc`, `fonts.inc`, `data_*.inc`)
и остаться байт-в-байт — **невозможно без релокации**. Пользователь выбрал
побайтовую идентичность → экспорт = один монолит, а требования TZ 2–5
(строки/спрайты/шрифты/данные) выполняются как **помеченные секции внутри
`code.asm`** (`defb`/`defm` по меткам RDB), не отдельными файлами.

## Goal

Закрыть Stage 8 из `TZ.md`: весь код — в одном файле, данные — читаемыми
директивами, побайтовый round-trip сохранён.

## TL;DR (вердикт)

`tools/gen_layout.py` порождает **`asm/code.asm` (9779 строк, 641 метка)** —
адресно-упорядоченный образ: функции/межфункциональные метки — **мнемониками**
(из disassembly `v06c-asm-export`), данные/строки/шрифты/спрайты/гэпы — секциями
`defb`/`defm` с именами-метками RDB. Мастер `asm/exolon_new.asm` = `org 0100h` +
`include "code.asm"`. Сборка `make layout all verify` → `src/EXOLON_NEW.ROM`
32512 B, **0 расхождений**, SHA `92be64d1…`. RDB на этом Stage **не изменялся**.

## Как это работает (алгоритм `gen_layout.py`)

1. **Экспортёр, не Python:** запустить `v06c-asm-export` (ROM+RDB) → адресный
   `layout.asm` (мнемоники кода + `defb` размеченных данных/гэпов). Правила
   форматирования листа пишет экспортёр (политика пакета).
2. **Чинка синтаксиса:** `rst <символ>` → `rst <addr>h` (операнд `RST` обязан быть
   константой `00h..38h`; z80asm отвергает символьные цели `rst func_irq_vblank` и
   `rst label_0008…0030` — 90 ошибок). Маппинг по адресу метки, валидация
   «кратно 8, ≤ 0x38».
3. **Собрать и посчитать расхождения.** Голый лист даёт 199 расхождений: disassembler
  decodeировал как код куски **данных** (битмапы `label_0260`, таблицы,
   `str_*`, `data_music_seq_*`, display-list) — мнемоника не рекодируется байт-в-байт.
4. **Починка data-прогонов.** Для каждого label-прогона, внутри которого есть
   расхождение, тело заменяется на `defb` фактических байтов ROM (`rom[addr-ORG …]`;
   для `str_*` печатаемое → `defm`, иначе `defb`). Прогоны сегментируются по всем
   меткам — внутренние метки сохраняются. Реальные функции (0 расхождений) не
   трогаются → максимум читаемого кода. Итог: **23 прогона → 1564 байт `defb`/`defm`**.
5. **Утверждение:** пересобрать, добить `assert` побайтовой идентичности.

## Limitations / открытые вопросы

- **Секции, а не файлы.** Требования TZ 2–5 (отдельные `strings.asm`/`sprites.inc`/
  `fonts.inc`/`data_*.inc`) в побайтово-идентичном режиме недостижимы (см. выше).
  Если для следующего ROM захочется настоящей раскладки по файлам — нужна **релокация**
  (функционально-эквивалентный ROM, не byte-identical); TZ фиксирует этот выбор явно.
- **`defb`-златки вместо мнемоник.** 23 mis-decoded-прогона выгружены байтами. Это
  корректнее, чем псевдо-код, но читается хуже ассемблерных листков; для строк —
  `defm` с текстом.
- **Символьные цели `jmp/call`** резолвятся внутри монолита (все метки в одном
  адресном потоке), отдельных линко-артефактов нет.
- Правка кода теперь возможна прямо в `code.asm` (мнемоники) с последующим
  `make verify`; при рассогласовании с реальным поведением — сверять через MCP (Stage 10).
