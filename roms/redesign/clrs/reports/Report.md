# Анализ "хитрости" clrs.rom

## В чём "хитрость" clrs.rom?

**clrs.rom использует технику "racing the beam" (гонка за лучом)** — динамическую смену палитры во время развёртки кадра.

### Основная идея

Вся видеопамять (VRAM 0x8000–0xFFFF) **очищена нулями** — все пиксели имеют цветовой индекс 0. Но программа **многократно меняет саму палитру** (запись в порт 0x0C) в течение кадра, синхронизируя изменения с позицией луча развёртки.

**Результат:** хотя все пиксели имеют индекс 0, разные строки экрана отображают **разные цвета**, потому что палитра для индекса 0 меняется по мере движения луча сверху вниз.

---

## Как он рисует >16 цветов на экране?

### Парадокс

Вектор-06Ц в режиме 256×256×16 имеет палитру из 16 цветов. Но clrs.rom отображает **больше 16 видимых цветов** на экране.

### Решение

**Временное мультиплексирование палитры:**

1. Все пиксели = индекс 0 (VRAM очищена)
2. VBlank-прерывание (~50 Гц) вызывает ISR
3. Внутри ISR программа **9 раз за кадр** меняет палитру через `OUT 0x0C`
4. Каждое изменение палитры происходит в момент, когда луч рисует определённую строку
5. Результат: экран разделён на **горизонтальные цветовые полосы**, каждая полоса — свой цвет

**Математика:**
- 1 начальное значение палитры (до первого изменения в ISR)
- 9 изменений палитры внутри ISR (9× `OUT 0x0C`)
- Итого: до **10 различных цветов** за один кадр

Если учитывать, что значения палитры циклически повторяются (F8h…FFh, 00h) и комбинируются с XOR-арифметикой, программа создаёт **анимированный градиент** из ограниченной палитры.

### Ключевой код

```asm
; func_isr_palette_cycle (0x0152)
POP PSW          ; Загружаем цвет палитры из стека в A
ORA M            ; Задержка (чтение [HL])
ORA M
ORA M
NOP
OUT 0Ch          ; ← Запись цвета в палитру (луч рисует строку N)
XRA D            ; Модификация цвета (XOR с D=01h)
OUT 0Ch          ; ← Следующий цвет (луч рисует строку N+1)
XRA C            ; XOR с C=03h
OUT 0Ch          ; ← Ещё один цвет
...              ; Повтор 9 раз
RET
```

Каждый `OUT 0Ch` происходит в момент, когда луч рисует очередную строку. Поскольку все пиксели имеют индекс 0, изменение палитры мгновенно меняет цвет **всех** пикселей на экране, но только для текущей строки развёртки.

## Каким образом программе удаётся точно позиционировать цветные блоки на экране?

### Механизм синхронизации

**1. Аппаратное прерывание VBlank (RST 7)**

- Вектор 0x0038 = `JP 0x013F` (устанавливается при инициализации)
- Срабатывает ~50 раз в секунду (начало обратного хода луча)
- ISR начинается с цикла задержки для калибровки тайминга

**2. Калиброванный цикл задержки**

```asm
; func_isr_delay_and_setup (0x013F)
LXI B, 00ECh     ; Счётчик = 236
delay_loop:
DCX B             ; Уменьшить BC
MOV A, B
ORA C             ; Проверить BC == 0
JNZ delay_loop    ; Повторять ~236 раз
NOP               ; Дополнительные такты для точной подстройки
NOP
```

Этот цикл (~236 итераций × 10 тактов ≈ 2360 тактов CPU) создаёт **фиксированную задержку** между моментом VBlank и началом вывода палитры. За это время луч проходит определённое количество строк обратного хода и выходит на видимую область экрана.

**3. Стековая машина состояний**

Палитры хранятся в стеке (SP = 0x0177 после инициализации):

```
Стек (сверху вниз):
[PSW=F8h] [RET=0152h]  ; Первый цвет + возврат в ISR
[PSW=??h] [RET=0152h]  ; Второй цвет + возврат
...
[PSW=??h] [RET=0172h]  ; Последний цвет + возврат в rearm
```

Каждый `POP PSW` извлекает цвет и адрес возврата. После `RET` управление возвращается в ISR для следующего цвета. Это создаёт **программируемую последовательность** из 9 цветов с точными интервалами.

**4. XOR-арифметика для генерации последовательности**

Вместо хранения всех 9 цветов в стеке, программа **вычисляет** промежуточные значения:

```asm
OUT 0Ch          ; Вывод цвета A
XRA D            ; A = A XOR 01h
OUT 0Ch          ; Вывод A XOR 01h
XRA C            ; A = A XOR 03h
OUT 0Ch          ; Вывод A XOR 01h XOR 03h
XRA D            ; A = A XOR 01h
...
```

Параметры: `D=01h`, `C=03h`, `B=07h` — создают паттерн XOR-модификаций, генерирующий **8 дополнительных цветов** из начального значения.

### Точность позиционирования

**Разрешение:** ~1 строка экрана на каждое изменение палитры.

**Как достигается:**
1. VBlank даёт **точную точку отсчёта** (начало обратного хода луча)
2. Калиброванный цикл задержки выравнивает тайминг с точностью до тактов CPU
3. 9× `OUT 0Ch` выполняются с минимальными задержками между ними (только XOR + OUT = ~14 тактов)
4. За 14 тактов CPU (~4.7 мкс при 3 МГц) луч проходит ~1 строку (288 строк / 50 Гц / ~6000 тактов на кадр ≈ 1 строка за 20 тактов)

**Результат:** каждая смена палитры попадает на **конкретную строку экрана**, создавая чёткие горизонтальные границы цветовых блоков.

## Итог: архитектура эффекта

```
Инициализация (0x0100):
  ├─ Очистка VRAM (все пиксели = 0)
  ├─ Установка вектора RST 7 → JP 0x013F
  ├─ Заполнение стека палитрами (F8h..FCh)
  ├─ OUT 02h (border = 0)
  └─ HLT-цикл (ожидание прерываний)

Каждый кадр (VBlank ISR, 0x013F):
  ├─ Задержка ~2360 тактов (калибровка)
  ├─ Настройка регистров (BC=0703h, D=01h, SP=0177h)
  ├─ 9× [POP PSW → OUT 0Ch → XOR-модификация]
  └─ EI + RET (возврат к HLT или самоповтор)

Визуальный эффект:
  Экран разделён на 9+ горизонтальных полос разных цветов,
  хотя все пиксели имеют индекс 0. Палитра меняется 9 раз
  за кадр, синхронно с лучом развёртки.
```

## Почему это работает на реальном железе

**Вектор-06Ц:** порт 0x0C записывает значение в **текущую ячейку палитры**, индекс которой определяется данными пикселя (в данном случае 0). Изменение палитры происходит **мгновенно** — как только луч рисует следующую строку, она использует новое значение палитры.

**Эмулятор (PPSSPP):** эмулирует эту технику корректно, так как моделирует поведение палитры в реальном времени.

**Альтернативный подход (не работает):** если бы программа пыталась рисовать разные цвета, записывая разные индексы в VRAM, ей потребовалось бы 32 КБ данных (256×256 пикселей / 2 пикселя на байт). Но VRAM всего 32 КБ, и это не оставило бы места для кода. Техника "racing the beam" позволяет обойти это ограничение, используя **временное** мультиплексирование вместо **пространственного**.
