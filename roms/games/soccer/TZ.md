# ТЗ: «SOCCER» — футбольный симулятор на Вектор-06Ц (алгоритмический racing-the-beam рендер, 16 цветов)

> **Жанр:** аркадный футбольный симулятор, вид сверху (top-down). Матч
> «стенка на стенку»: две команды, судья, мяч; ворота с двух сторон, поле
> прокручивается аппаратно вверх-вниз вслед за мячом.
>
> **Целевая платформа:** Вектор-06Ц (КР580ВМ80А, 3 МГц, 60000 тактов/кадр,
> 50 Гц), библиотека `lib` ([`v06.h`](../../../lib/v06.h)).
> **Экран:** `GFX_MODE_256_16` — 256×256 пикселей, **16 цветов** (4 битовые
> плоскости, все активны). Ширина поля = 256 px = один экран (горизонталь не
> скроллится); длина поля больше экрана — **аппаратный вертикальный скролл**
> (регистр строки, порт `03h`).
>
> **Движок отрисовки — СОБСТВЕННЫЙ, АЛГОРИТМИЧЕСКИЙ (ревизия 2).** Никаких
> спрайтов, дескрипторов, тайлмапа и подсистемы `beam.c`. **Все** объекты —
> поле, полосы травы, разметка, ворота, угловые флаги, футболисты, судья, мяч —
> рисуются **процедурным кодом напрямую в VRAM**: каждый объект имеет свою
> функцию отрисовки, вычисляющую пиксели по алгоритму (примитивы: строка,
> прямоугольник, окружность, дуга, линия). Никакого промежуточного буфера (не dblbuf) и
> никаких блитов битмапов «память → VRAM». Единственный инструмент синхронизации
> с лучом — **растровый секундомер ВИ53** ([`lib/timer/timer.asm`](../../../lib/timer/timer.asm)).
>
> **Размещение:** `roms/games/soccer/` (этот файл — точка входа проекта).
> **Образцы:** [`roms/games/hate`](../hate) (формат ТЗ, «прозрачная» раскладка),
> [`roms/demos/mario-timer`](../../demos/mario-timer) (эталон потребления
> `lib/timer` — racing-the-beam), [`lib/gfx/plane.asm`](../../../lib/gfx/plane.asm)
> и [`lib/gfx/pr.asm`](../../../lib/gfx/pr.asm) (адресация VRAM, порядок битов).

## 1. Постановка задачи и рамки

### 1.1 Цель
Играбельный футбольный симулятор: полный цикл «титул → выбор формата/команд →
матч (два тайма) → гол/аут/угловой/штрафной → финальный свисток → итог».
Плавное движение всех объектов без tearing, темп ровно 50 Гц, отзывчивое
управление, читаемая полноцветная графика (16 цветов).

### 1.2 Ключевые требования (из задания, редакция 2)
1. **Экран 256×256×16 цветов** — режим `GFX_MODE_256_16`, все 4 плоскости.
2. **Футболисты 8×8 пикселей** — процедурная фигура в футпринте 8×8.
3. **Поле скроллится аппаратно вверх-вниз** — регистр строки (порт `03h`);
   содержимое кольца VRAM при этом не сдвигается, перерисовывается только
   открывшаяся полоса.
4. **ВСЕ объекты рисуются АЛГОРИТМИЧЕСКИ.** Поле, полосы разной травы,
   разметка, угловые флаги, ворота, футболисты, судья, мяч — каждый рисуется
   своим кодом по заданному алгоритму (геометрические примитивы), **не**
   спрайтами/тайлами и **не** копированием готовых битмапов.
5. **Никакого копирования «память ↔ VRAM».** Нет off-screen буфера (dblbuf),
   нет блитов дескрипторов; есть только *вычисление* значений пикселей и
   *запись* их в VRAM. Данные (координаты, цвета, параметры фигур) — это
   скалярные константы/таблицы, а не кадровый буфер.
6. **Синхронизация с лучом — ТОЛЬКО таймер.** ВИ53-канал 2 как растровый
   секундомер; `beam.c`/`spr.asm` в сборку не входят.
7. **Полноцветные 16 цветов** — любой пиксель может быть любым из 16 цветов
   (в отличие от прежней схемы 2+2 плоскости). Никакого «плоскостного»
   ограничения на число цветов спрайтов.
8. **Не dblbuf** — рисуем прямо в персистентную VRAM (что не записали —
   хранится с прошлого кадра).

### 1.3 Нецели (осознанно вне области первой версии)
- Тактика/формации уровня реального симулятора (AI — упрощённый, §7).
- Горизонтальный скролл и масштабирование (поле = 256 px по ширине, фикс.).
- Полная процедурная симуляция правил (офсайд, все виды розыгрышей) — упрощённо.
- Лицензированные составы/лиги; звук — базовый (свисток, удар, толпа), §3.12.
- Сеть/онлайн (только 2 игрока на одной клавиатуре или игрок vs AI).

## 2. Аппаратная основа (факты, на которые опирается рендер)

### 2.1 Плоскости VRAM, адресация, порядок битов
Режим `GFX_MODE_256_16` активирует все четыре плоскости (маска `0x0F`,
[`lib/gfx/mode.c`](../../../lib/gfx/mode.c)). Базы и веса (подтверждено
[`clr.asm`](../../../lib/gfx/clr.asm), [`pr.asm`](../../../lib/gfx/pr.asm),
[`spr.asm`](../../../lib/gfx/spr.asm)):

| Плоскость | База | Вес в индексе цвета | Бит маски `plane_mask` |
|---|---|---|---|
| П3 | `0x8000` | 8 | bit3 |
| П2 | `0xA000` | 4 | bit2 |
| П1 | `0xC000` | 2 | bit1 |
| П0 | `0xE000` | 1 | bit0 |

**Индекс цвета пикселя (0..15)** = `8·П3 + 4·П2 + 2·П1 + 1·П0`.

**Адрес байта** для пикселя `(x, y)` в плоскости `p` (подтверждено
[`spr.asm:503`](../../../lib/gfx/spr.asm) и [`pr.asm:31`](../../../lib/gfx/pr.asm)):
```
addr(p, x, y) = (0x8000 + p·0x2000) + (x >> 3)·256 + (255 − y)
```
- `(x >> 3)·256` — номер 8-пиксельного колонкового блока (в старшем байте);
  переход к следующему блоку вправо = `INR H` (+256).
- `(255 − y)` — смещение строки внутри блока; **строки вниз = уменьшение
  адреса** (`DCR L`). Байт хранит **8 горизонтальных пикселей** одной строки.
- **Порядок битов в байте:** старший бит (bit7, `0x80`) = ЛЕВЫЙ пиксель
  (`x & 7 == 0`), bit0 = правый (`x & 7 == 7`) ([`plane.asm:25`](../../../lib/gfx/plane.asm)).
- Выровненный по `x>>3` объект 8×8 = один колонковый блок = 8 байт на
  плоскость = **32 байта на все 4 плоскости**.

### 2.2 Таймер ВИ53 — растровый секундомер ([`lib/timer/timer.asm`](../../../lib/timer/timer.asm))
Канал 2 (порт `09h`), режим 0 (CW `0xB0`), перезагрузка `TIMER_FULL = 0x7500`
(29952 тика = 312 строк × 96 тиков/строку при 1.5 МГц) на каждый VBlank →
счётчик монотонно убывает в фазе с лучом. API:
- `timer_start()` — пуск на кадр (единственная ISR-безопасная; зовётся из
  `frame_handler`).
- `timer_start_sync()` — `EI; HLT;` затем пуск: одноразовая фазовая привязка к
  VBlank (схема exolon) — для инициализации ядра.
- `timer_read()` — остаток (HL); **больше — луч выше**.
- `timer_elapsed()` — сколько тиков луч прошёл от начала кадра.
- `timer_wait(value)` — спин, пока остаток ≤ `value` (или счётчик перезагрузится
  → всегда выходит внутри кадра). Макросы: `TIMER_LINES(n)`, `TIMER_LINE(t)`,
  `TIMER_REMAIN(elapsed)`, `TIMER_TICKS_PER_LINE = 96`, `TIMER_FRAME_LINES = 312`.
- Ждать строку `y`: `timer_wait(TIMER_REMAIN(TIMER_LINES(y)))`.

**Канал 2 занят таймером** → звуковые движки ограничить каналами 0/1
(`sfx_set_channel_mask(0x03)`, `music_set_channel_mask(0x03)`).

### 2.3 Стена пропускной способности VRAM — **центральный факт ТЗ**
Видимый экран 256×256×4 плоскости / 8 = **32768 байт**. Замеренная цена записи
байта VRAM с продвижением указателей ≈ **24–25 T** («лесенка» `spr.asm`:
`ldax d / mov m,a / inx d / dcx h` = 24 T/строку); голая `STA` = 13 T;
процедурная запись (вычислить значение + `STA` + адрес) ≈ **25–40 T**.

- **Полный перезапуск экрана каждый кадр** = 32768 записей ≈ `32768·24 ≈ 786 000 T`
  (без вычислений), с вычислениями — за миллион. Бюджет кадра = **60 000 T**.
  → полная регенерация в **~13–20 раз дороже всего кадра**: на 50 Гц
  **физически невозможна**.
- Даже **одна полная строка** (32 блока × 4 плоскости = 128 байт) ≈ `128·24 ≈ 3000 T`
  ≈ 32 строки растра, тогда как луч проходит строку за 96 тиков (~192 T CPU):
  регенерация строки **в ~16 раз медленнее** её сканирования.

**Следствие (обязательное):** VRAM — это **персистентный кадр**, а рендер —
**инкрементальный**: пишем только те байты, которые изменились с прошлого кадра.
Это полностью соответствует заданию (без dblbuf, без блитов, процедурно, полная
палитра, только таймер), но исключает наивное «перерисовать всё каждый кадр».
Инкрементальность — не оптимизация, а физическая необходимость.

### 2.4 Аппаратный вертикальный скролл и кольцо
- VRAM-кольцо = 256 px по вертикали; экран показывает кольцо целиком, скролл
  лишь **вращает** его регистром строки (порт `03h`). Адресация контента
  **мировая**: `ring y = world_y & 0xFF`.
- Значение регистра: `scroll = 0xFF − (cam_y & 0xFF)` (конвенция проекта);
  пишется в порт **на VBlank** (луч в гашении). Эмулятор читает порт `03h`
  один раз за кадр (строка ~40) — запись вне VBlank игнорируется до след. кадра.
- **ПИТАНИЕ-ловушка:** запись управляющего слова в порт ПИА `00h` (и опрос
  клавиатуры) **сбрасывает регистр скролла в 0**. Штатный `lib/sys/startup.asm`
  восстанавливает `0xFF`; `gfx_set_scroll(row)` лишь кладёт значение в
  `gfx_scroll_row`, а в порт его выпишет `kbd_scan_now` на ближайшем VBlank.

### 2.5 Стоимость записи и бюджет растра (сводно)
- Кадр = 60000 T = 312 строк таймера (96 тиков/строку); видимых строк 256.
- Резерв на логику/звук/ввод ≤ ~90 строк → **потолок рендера ≈ 200–220 строк**.
- Один объект 8×8 (выровнен по `x>>3`): отрисовка 32 байта (4 плоскости),
  восстановление фона под старым футпринтом ещё ~32 байта; при малом шаге
  (1–2 px/кадр) старый и новый футпринты перекрываются → слитный dirty-rect
  ≈ 40–64 байта ≈ **12–20 строк растра** на ДВИЖУЩИЙСЯ объект.

## 3. Ключевые проектные решения

### 3.1 Модель рендера: персистентный кадр + процедурные примитивы + racing-the-beam
Три столпа:
1. **Персистентная VRAM как кадр.** Никакого второго буфера. Каждый кадр
   перерисовываются только (а) объекты, которые двинулись/изменились, и
   (б) участки фона, которые они открыли, и (в) полоса, открытая скроллом.
2. **Процедурная отрисовка.** Каждый объект — функция, вычисляющая пиксели
   геометрическими примитивами (§3.3, §3.4) и пишущая байты прямо в 4 плоскости
   VRAM. Цвет пикселя (0..15) раскладывается на биты 4 плоскостей и пишется
   побайтово (целые байты для выровненных участков, read-modify-write для
   невыровненных краёв).
3. **Racing-the-beam (без tearing).** Каждая запись делается ПОСЛЕ того, как
   луч прошёл записываемую строку в текущем кадре (wake-phase): изменения
   невидимы до следующего сканирования → нет разрыва. Порядок обработки —
   по возрастанию экранного `y` (§3.6).

### 3.2 Палитра — 16 цветов без ограничений (главный выигрыш ревизии 2)
Процедурная запись снимает прежнее ограничение «2+2 плоскости = 3 цвета
спрайтов». Любой пиксель — любой из 16 цветов. Распределение (16-байтная
палитра `soccer_pal16`, `gfx_set_palette`):

| Индекс | Назначение |
|---|---|
| 0 | тёмная трава |
| 1 | светлая трава |
| 2 | белая разметка (линии, круг, дуги) |
| 3 | сетка/стойки ворот |
| 4 | акцент (угловые флаги, второй тон разметки) |
| 5 | Команда A — форма |
| 6 | Команда A — трусы/деталь |
| 7 | Команда B — форма |
| 8 | Команда B — трусы/деталь |
| 9 | Вратарь (отдельный цвет) |
| 10 | Судья |
| 11 | Кожа (головы/ноги) |
| 12 | Мяч |
| 13 | Тень мяча/игроков |
| 14 | Чёрный (контур, HUD-фон) |
| 15 | Белый (HUD-текст, блики) |

Цвета — данные (§3.3/§3.4 пишут индекс, ядро раскладывает его на плоскости).
Палитра проявляются через `gfx_fade_in` (§3.9). Конкретные RGB — в
`assets/pal.png`/`field_geom.inc`, уточняются на Stage 2.

### 3.3 Процедурное поле (геометрия, не тайлы)
Поле описывается **списком геометрических примитивов** в мировых координатах
(`field_geom.inc`), а НЕ тайлмапом и НЕ битмапом. Покраска — функция
`paint_field(rect)` (мировой прямоугольник): для каждой строки `wy` в `rect`:
1. **Трава:** цвет строки = полоса. Период полос **64 px**: `tone = ((wy >> 6) & 1)`
   → индексы 0/1. Заполняется `hspan` (целые байты — дёшево).
2. **Разметка/ворота/флаги:** для каждого примитива, пересекающего строку,
   вычислить пересечение и наложить `hspan`/`px` нужным цветом:
   - **Линии** (боковые, лицевые, центральная, стенки штрафных/вратарских) —
     отрезки: горизонтальные = `hspan`, вертикальные = `px`/`vline`.
   - **Центральный круг, угловые дуги, штрафные дуги** — окружности/дуги:
     построчно вычисляем полуширину `dx = isqrt(r² − dy²)` и кладём `hspan`.
   - **Отметки пенальти** — короткие `hspan`/`px`.
   - **Ворота** (стойки + перекладина + сетка) — прямоугольники + сетчатый
     узор (чередование пикселей индексами 3/14) в области ворот.
   - **Угловые флаги** — 4 маленьких процедурных маркера (цвет 4) по углам.

Геометрия поля генерируется `tools/gen_field.py` из `assets/field.png`/описания
разметки в компактный список примитивов (отрезки/окружности/прямоугольники с
мировыми координатами и цветом) — это ДАННЫЕ (координаты), а не кадр и не битмап.

Размер поля: `FIELD_W = 256` px (вся ширина), `FIELD_H = 384` px (длина; окно
256 px, скролл ~128 px). Ворота у верхней (`y ≈ 0`) и нижней (`y ≈ 368`) кромок.

### 3.4 Процедурные объекты (игроки, судья, мяч)
Каждый динамический объект: `{ world_x, world_y, type, team, dir, phase, z }`
(`z` — только у мяча). Функция `draw_object(obj)` вычисляет пиксели и пишет их
в 4 плоскости по адресу кольца. **Без готовых битмапов** — фигура строится
арифметически из параметров:
- **Полевой игрок / судья (8×8):** топ-даун фигура из примитивов — тело
  (`fill_rect` цветом формы 5/7/10), голова (`fill_circle` малым радиусом,
  кожа 11), трусы/гетры (2–3 px, цвет 6/8), ноги — две короткие строки,
  смещаемые по `phase` (кадр бега) и ориентируемые по `dir` (8 направлений).
  Все координаты — относительно якоря `(world_x & 0xF8, world_y)`; `phase`
  переключает 2–3 кадра бега (чередование ног), вычисляемых на месте.
- **Вратарь:** тот же механизм, цвет 9, чуть шире стойка.
- **Мяч:** `fill_circle(cx, cy, r, 12)` где `r = f(z)` (§7.6) — PROCEDURAL,
  поэтому любой радиус без «тиров/дескрипторов»; 1–2 px блика (индекс 15).
- **Тень мяча:** `fill_circle`/`hspan`-эллипс малой высоты в точке `(x, y)`,
  цвет 13, рисуется ДО мяча (под ним).

> **Опция (если арифметика силуэта окажется дороже бюджета):** хранить
> компактную маску-контур «1 байт на строку» (8 бит = 8 px строки) и
> разворачивать её процедурным кодом с наложением цвета. Это НЕ битмап-блит
> (цвет и композиция вычисляются, off-screen буфера нет), но читает 8 байт
> формы из ROM. Решение принимает Stage 3 по замеру; по умолчанию — чистая
> арифметика (§3.4).

### 3.5 Стирание, dirty-прямоугольники и восстановление фона
Так как кадр персистентный, «стереть» объект = **восстановить под ним поле**:
- При движении объекта его СТАРЫЙ футпринт добавляется в список dirty-
  прямоугольников; перед redraw он закрашивается `paint_field(old_rect)`
  (процедурно пересчитанная трава + разметка) — никакого «захвата фона» и
  никаких заранее заготовленных тайлов.
- **Перекрытие объектов:** если в dirty-прямоугольник попадает другой объект,
  он тоже перерисовывается (иначе останется «дыра»). Ядро ведёт список
  объектов и для каждого dirty-rect выбирает пересекающиеся (их единицы).
- **Слияние:** dirty-прямоугольники одного кадра сливаются по строкам, чтобы не
  красить одно место дважды. При малом шаге объекта старый и новый футпринты
  перекрываются → слитный rect мал (§2.5).
- **Композиция за один проход (оптимизация):** для НОВОГО футпринта строка
  считается сразу как «поле, если пиксель не принадлежит объекту, иначе цвет
  объекта» — одна запись байта вместо «стереть + нарисовать».

Порядок отрисовки внутри dirty-области — **painter's algorithm по `y`**
(объекты с меньшим `y` рисуются раньше, большие — поверх): «кто ниже по экрану,
тот ближе» (§3.10).

### 3.6 Racing-the-beam планировщик (tearing = 0)
Кадр ядра (`render_frame`):
1. Игра помечает изменённые объекты; ядро строит список dirty-областей
   (старые+новые футпринты + открытые скроллом полосы), переводит мировые `y`
   в **экранные** `sy = (world_y − cam_y) & 0xFF`.
2. Сортирует области по возрастанию `sy_bottom`.
3. Для каждой области: `timer_wait(TIMER_REMAIN(TIMER_LINES(sy_bottom + 1)))` —
   ждём, пока луч ПРОЙДЁТ нижнюю строку области; затем `paint_field` +
   `draw_object` по всем пересекающим объектам. Запись идёт строго позади луча.
4. Полоса, открытая скроллом, красится в **blanking** (строка ≥ 288) до записи
   регистра скролла на VBlank (§3.7).
5. Конец `render_frame` — `timer_wait(0)` (блокирует до конца кадра → темп
   50 Гц). Дополнительный `v06_wait_frame()` в главном цикле **запрещён**.

Это wake-phase алгоритм (память-инвариант проекта): ждать, пока луч пройдёт
**низ** объекта (не верх), затем erase+draw без промежуточных операций.

### 3.7 Аппаратный скролл и камера
- Камера следует за мячом: `cam_y` кратен 8, диапазон `0 .. (FIELD_H − 256) =
  0..128` px. `gfx_set_scroll(0xFF − (cam_y & 0xFF))` → порт на VBlank.
- Позиции объектов — **мировые** `y` (0..383); ядро берёт `y & 0xFF` для кольца.
  Объекты вне текущего окна 256 px **не рисуются** (иначе их алиас «протечёт»
  в видимое кольцо) — флаг `hidden` на стороне игры.
- При шаге камеры на 8 px открывается новая полоса кольца, содержащая СТАРОЕ
  содержимое (алиас из точки на 256 px дальше). Ядро перерисовывает её
  `paint_field` (трава почти бесплатна; разметка/ворота — по геометрии) в
  бланкинге, затем пишется регистр скролла → полоса видна уже новой, без разрыва.
- Период травы 64 px делит 256 → алиас полосы травы совпадает по тону и
  перерисовка сводится к разметке/воротам (дешёвый скролл).

### 3.8 Число объектов и бюджет движения
- Составы: **11v11** = 22 игрока + судья + мяч = **24 объекта**; **7v7** = 14+1+1
  = 16; **5v5** = 10+1+1 = 12.
- Движущийся объект ≈ 12–20 строк растра (§2.5, полная палитра = 4 плоскости,
  вдвое дороже прежних 2-плоскостных спрайтов). Потолок ~200–220 строк →
  **~12–16 одновременно движущихся объектов в кадр**.
- Для 24 объектов (11v11) обязательны:
  (a) **стаггеринг** AI — дальние игроки пересчитываются раз в 2–4 кадра
      (движутся не каждый кадр → меньше dirty-областей);
  (b) **приоритетный перенос** — мяч и 3–5 ближайших/активных игроков рисуются
      каждый кадр, остальные круговой очередью (round-robin) по кадрам; на глаз
      незаметно (обновление 30–37 Гц для дальних);
  (c) **оптимизация записи** — писать только плоскости, где цвет объекта
      отличается от фона под ним (предвычисленный mask для частых пар
      «форма/трава»), целые байты для выровненных участков, RMW только по краям.
- **Запасной вариант:** если Stage 9 покажет, что 11v11 не держит 50 Гц даже со
  стаггерингом, целевым форматом становится 7v7 (16 объектов). Выбор формата —
  в меню (§7.1); данные поля от него не зависят.

### 3.9 Инициализация и проявление экрана
```c
gfx_set_mode(GFX_MODE_256_16);
gfx_set_black_palette();          // экран чёрный — первая покраска не видна
frame_handler = on_frame;         // timer_start() + kbd_scan_now() (+flush scroll)
timer_start_sync();               // фазовая привязка секундомера к VBlank (1 раз)
render_init(&field_geom);         // красит ВСЁ поле один раз (несколько кадров,
                                  // чёрная палитра — не видно); сбрасывает dirty
// ... расставить объекты, cam_y ...
gfx_fade_in(soccer_pal16, 2);     // проявление палитры (fade.c)
for (;;) {
    game_logic();                 // движение/физика/AI/свечи -> помечает dirty
    render_frame();               // §3.6; завершается timer_wait(0)
}
```
`render_init` рисует поле целиком без пейсинга (экран чёрный) — занимает
несколько кадров CPU-времени, но невидимо; допустимо.

### 3.10 Приоритеты и перекрытие
Порядок отрисовки в пределах dirty-области — painter's algorithm:
- Фон (поле) — всегда первым.
- Тень мяча — поверх поля, под объектами.
- Объекты — по возрастанию мирового `y` (нижние = ближние = поверх).
- Мяч: на земле (`z` мал) — **под** игроками (игрок «накрывает» мяч при ведении);
  в воздухе (`z` велик, §7.6) — **поверх** игроков (мяч выше их). Порядок по
  «экранной глубине» = `y − z_vis`.
- Судья — средний приоритет.

### 3.11 Управление
Опрос матрицы — `kbd_scan_now()` в `frame_handler` (снимок в гашении, не задевает
защёлку скролла). Читаем `kbd_rows[]`, фронты снимаем сами (нужно несколько
клавиш одновременно).

| Действие | Игрок 1 | Игрок 2 (опц.) |
|---|---|---|
| Движение выбранного игрока | ← → ↑ ↓ | F/H/T/B (или СС+стрелки) |
| Удар / пас | ПРОБЕЛ | СС (Shift) |
| Смена активного игрока | ЗАБ (Backspace) | — |
| Подкат / отбор | СС + направление | — |
| Пауза | P | — |
| Меню/старт | любая клавиша / ПРОБЕЛ | — |

Точная раскладка уточняется на Stage 8; коды — `KBD_KEY_*` из `v06.h`.

### 3.12 Звук (базовый)
Канал 2 ВИ53 занят таймером → звуковые движки ограничить каналами 0/1
(`sfx_set_channel_mask(0x03)`, `music_set_channel_mask(0x03)` — правило
`lib/timer`). Набор эффектов (`lib/snd/sfx.c`): свисток (старт/гол/фол), удар по
мячу, отдельный «свист» высокого удара/свечи (§7.6), короткая мелодия титула
(`music.c`), опционально шум толпы (`drums`). Звук выдаётся из главного цикла
ПОСЛЕ `render_frame` (в бланкинге есть запас ~90 строк, §2.5); длинные `DI`
запрещены. Бюджет звука — в пределах резерва, не в ущерб пейсингу.

## 4. Кадровый контракт и псевдокод ядра

```c
/* ISR (VBlank): */
void on_frame(void) {
    timer_start();        /* перезапуск секундомера на кадр (ISR-safe) */
    kbd_scan_now();       /* снимок клавиатуры + flush gfx_scroll_row в порт 03h */
}

/* Главный цикл: */
for (;;) {
    game_logic();         /* физика, AI, коллизии, свечи; помечает moved-объекты */
    render_frame();       /* ниже */
}

/* render_frame(): */
void render_frame(void) {
    build_dirty();                 /* старые+новые футпринты moved-объектов */
    if (cam_moved) add_scroll_band(cam_old, cam_new);   /* открытая полоса */
    to_screen_y_and_sort();        /* sy = (world_y - cam_y) & 0xFF, sort by bottom */
    for_each_dirty_region(reg) {
        timer_wait(TIMER_REMAIN(TIMER_LINES(reg.sy_bottom + 1)));  /* луч прошёл */
        paint_field(reg.world_rect);                 /* восстановить фон */
        for_each_object_intersecting(reg, by_y)      /* painter's algorithm */
            draw_object(obj);
    }
    if (cam_moved) {                /* полоса скролла — в бланкинге */
        timer_wait(TIMER_REMAIN(TIMER_LINES(288)));
        paint_field(scroll_band_rect);
    }
    timer_wait(0);                  /* до конца кадра -> 50 Гц */
}
```

Ядро пишется на **ассемблере** (`kernel.asm`) для горячих примитивов
(`hspan`, `fill_rect`, `fill_circle`, запись 4 плоскостей) и на **C**
(`render.c`) для планировщика dirty-областей и `draw_object`. Критичные
по тактам участки — только ASM (соответствует практике проекта).

## 5. Карта памяти

| Диапазон | Что |
|---|---|
| `0x0100–~0x4FFF` | ROM: код (`main.c`, `render.c`, `kernel.asm`, `game.c`, `ai.c`, `sound.c` + `lib`: startup/v06io/v06pal/mode.c/gfx.c/fade.c/clr.asm/pr.asm(шрифт HUD)/timer.asm/kbdscan.asm/keyboard.c + sfx/music) + данные: `field_geom.inc` (список примитивов разметки/ворот ≈ 0.5–1 КБ), палитра 16 Б, шрифт/строки/звук ≈ 1–2 КБ. Итого ≈ 10–14 КБ |
| `~0x4FFF–0x6FFF` | куча (`heap_alloc`, `heap_top` по умолчанию `0x8000`): распакованная музыка (ZX0) при необходимости, буферы AI, dirty-списки |
| BSS (за кодом, входит в образ) | состояние игры (позиции/скорости/`z` 24 объектов, счёт, таймер, фазы матча ≈ 0.5–1 КБ) + статика ядра (dirty-rects, cam, палитра-тень ≈ 0.2 КБ) |
| `0x7000–0x7FFF` | свободно (лесенки `spr.asm` НЕ нужны — движок не используется); держать запас до кучи |
| `0x8000–0xFFFF` | видеопамять: 4 плоскости (П3 `0x8000`, П2 `0xA000`, П1 `0xC000`, П0 `0xE000`) — персистентный кадр |

**Ограничение:** образ ROM + BSS + куча не должны перерасти VRAM (`0x8000`).
Проверка размера — в Makefile. При нехватке — ZX0-сжатие ассетов/музыки с
распаковкой в кучу.

## 7. Геймплей-спецификация (симулятор)

### 7.1 Форматы и меню
- Титул → меню: выбор формата (**11v11 / 7v7 / 5v5**), режим (1 игрок vs AI /
  2 игрока), длительность тайма, цвет команд (A/B). Старт матча.
- `NUM_PLAYERS` влияет только на число объектов и расстановку; геометрия поля
  (`field_geom.inc`) общая.

### 7.2 Матч
- Два тайма по N «минут» (ускоренное игровое время; матч-таймер в HUD).
- Розыгрыш: начальный удар в центре, мяч в центре, команды на своих половинах.
- Гол: мяч полностью пересёк линию ворот между стойками → счёт +1, розыгрыш
  с центра, короткая анимация/свисток.
- Выход мяча: аут / угловой / удар от ворот — упрощённо: мяч возвращается в
  поле ближайшим «вбрасыванием» (без полной процедурной симуляции правил; риск §11).

### 7.3 Физика мяча и игроков
- Игрок 8×8, шаг по пикселям (мировые `x,y`); ядро пишет по адресу кольца
  `(world_x & 0xF8, world_y & 0xFF)` для выровненных байтов (невыровненный
  `x` — RMW по краям, §3.4). Скорость/ускорение, инерция при ударе.
- Мяч: отдельная позиция `x,y` + высота `z` и вертикальная скорость `vz`
  (§7.6), скорость/трение, отскок от границ и ворот; при контакте игрока —
  ведение (мяч «прилипает» к ведущему) или удар (импульс; при сильном ударе
  вплотную к объекту — «свеча», §7.6).
- Коллизии игрок↔игрок (отбор/подкат), игрок↔мяч, мяч↔ворота/границы — на
  стороне `game.c` (логика до `render_frame`).

### 7.4 ИИ и стаггеринг обновлений (важно для бюджета §3.8)
- Каждый объект имеет роль (вратарь/защитник/полузащитник/нападающий) и цель
  (держать зону, бежать к мячу, атаковать ворота, защищать).
- **Стаггеринг:** активные (мяч, 3–5 ближайших к мячу игроков, активный игрок
  пользователя) пересчитываются и рисуются каждый кадр; дальние — раз в 2–4
  кадра (реже `moved` → меньше dirty-областей → меньше строк растра). Это
  удерживает кадр в бюджете 200–220 строк при 24 объектах и даёт штатный, а не
  аварийный, перенос (round-robin, §3.8).

### 7.5 HUD
Счёт, таймер матча, номер тайма — текст `gfx_print` (шрифт `pr.asm`) в
фиксированной полосе окна (не скроллится с полем) либо в окне бланкинга.
HUD статичен по позиции; перерисовывается только при изменении значений
(инкрементально, как и всё остальное).

### 7.6 Высота мяча, масштаб и «свечи»
Мяч — не плоский объект: есть высота `z` (0 = на газоне) и вертикальная
скорость `vz`. Физика: сильный удар сообщает `vz > 0`, гравитация тянет вниз
(`vz −= G` каждый кадр), при `z ≤ 0` — отскок с затуханием (`vz = −vz·k`) и
переход в качение. Высота влияет на игру: низкий мяч подбирается/ведётся,
высокий — пролетает над игроками, пока не опустится (перехват — только при
малом `z`; игра головой в прыжке — как расширение).

**Масштаб от высоты (визуальная высота).** Так как мяч рисуется процедурно
(§3.4), его **радиус вычисляется из `z`**: `r = clamp(R_MIN + z / Z_DIV, R_MIN,
R_MAX)` (напр. `R_MIN = 2`, `R_MAX = 8` px) — без «тиров» и дескрипторов,
`fill_circle` берёт любой радиус. Мяч рисуется выше по экрану: центр
`(world_x, world_y − z_vis)`, `z_vis ≈ z`. Dirty-прямоугольник мяча растёт
вместе с `r` (учтено в бюджете §3.8).

**Тень и смещение по экрану.** Тень мяча — процедурный эллипс малой высоты в
МИРОВОЙ точке `(x, y)` (где мяч фактически над газоном), цвет 13, рисуется под
мячом (§3.10). С ростом `z` тень остаётся на месте, мяч уходит вверх и
растёт — расхождение «тень внизу — мяч выше и крупнее» однозначно читается как
высота и служит индикатором точки падения.

**«Свечи» (candles).** Свеча — высокий дуговой мяч; в топ-даун читается по
большому радиусу + далёкой тени. Trigger-условия:
- **Сильный удар вплотную к объекту:** если в момент удара
  `dist(ball, obj) ≤ THRESH` для другого игрока (блок/рикошет) ИЛИ для
  стойки/перекладины ворот — удар вместо плоского даёт большой `vz` (мяч
  «взмывает») при сохранении горизонтальной скорости → дуга.
- **От перекладины/штанги:** попадание в перекладину/стойку отбивает мяч вверх
  (`vz += IMPACT`), часто с последующим добиванием или сейвом вратаря.

Свеча драматична: мяч подолгу в воздухе (крупный радиус, тень далеко внизу),
вратарь/игроки успевают подстроиться под точку падения; звук — отдельный sfx
«свист» высокого удара (§3.12).

### Stage 1. Примитив записи VRAM + racing-the-beam (tearing = 0)
`kernel.asm`: `vram_addr(x,y,p)`, `px`, `hspan`, `fill_rect`, `fill_circle`
(раскладка цвета на 4 плоскости, целые байты + RMW по краям). Тест: движущийся
тестовый прямоугольник/круг по экрану, `render_frame` с `timer_wait` по нижней
строке (§3.6).
**Приёмка:** примитивы пишут корректные 16-цветные пиксели (сверка с эталоном);
движущийся объект **без tearing** (BP на запись + `debug_get_raster_events`:
ни одной записи в строку, которую луч ещё не прошёл); темп 50 Гц.

### Stage 2. Процедурное поле и палитра
`tools/gen_field.py` → `field_geom.inc` (полосы травы 64 px, отрезки/дуги/круги
разметки, ворота с сеткой, угловые флаги). `paint_field(rect)` (§3.3),
`render_init` красит всё поле. Палитра §3.2 (16 цветов).
**Приёмка:** статичный кадр поля совпадает с эталоном `assets/field_preview.png`
(с точностью до 16-цветной палитры); разметка/ворота/флаги/полосы на месте;
`paint_field` произвольного прямоугольника восстанавливает тот же участок
(тест «покрасить → перекрасить под-прямоугольник → байты identical»).

### Stage 3. Процедурные объекты, стирание, dirty-rects
`draw_object` (§3.4): игрок (параметрическая фигура, 8 направлений, 2–3 кадра
бега), вратарь, судья, мяч (`fill_circle`), тень. Стирание через `paint_field`
по старому футпринту, dirty-rects + слияние + перерисовка пересекающихся
объектов (§3.5), painter's order по `y` (§3.10).
**Приёмка:** объекты видны поверх поля в полной 16-цветной палитре; при движении
**не оставляют «призраков»** (старый футпринт восстановлен `paint_field`,
VRAM-дамп); перекрывающиеся объекты не «дырявят» друг друга; порядок перекрытия
по `y` верен.

### Stage 4. Аппаратный вертикальный скролл
Камера вслед за мячом (§3.7), диапазон 0..128 px, шаг 8 px; перерисовка
открытой полосы в бланкинге; скрытие объектов вне окна (алиас); полоса травы
64 px.
**Приёмка:** плавная прокрутка вверх-вниз без tearing и без разрыва полосы;
трава при скролле почти не перерисовывается (замер числа redraw-байтов в
отчёте); разметка/ворота появляются корректно; объекты вне окна не «протекают».

### Stage 5. Управление, активный игрок, физика мяча и «свечи»
Ввод (§3.11): движение активного игрока, удар/пас, смена активного. Физика мяча
базовая (удар → импульс → трение) + высота `z`, гравитация/отскок, масштаб
радиуса и тень (§7.6); «свечи» при сильном ударе вплотную к объекту и от
перекладины.
**Приёмка:** игрок управляется с клавиатуры, мяч бьётся и катится; высокий мяч
растёт в радиусе, тень отстаёт внизу, мяч опускается по дуге; «свеча»
воспроизводится при сильном ударе рядом с игроком/штангой; отклик ≤ 1 кадр;
темп не проседает.

### Stage 6. Игровая логика матча
`game.c`: коллизии, ведение/отбор, гол, розыгрыш с центра, счёт, матч-таймер,
границы поля/аут/угловой (упрощённо, §7.2).
**Приёмка:** забивается гол (счёт +1, розыгрыш), мяч не проходит сквозь
границы/ворота, матч-таймер идёт, HUD обновляется.

### Stage 7. ИИ команд и судья
`ai.c`: роли, движение к мячу, атака/защита, вратарь, судья следует за мячом;
стаггеринг обновлений (§7.4).
**Приёмка:** команды играбельно атакуют/защищаются без участия пользователя,
кадр держит 50 Гц при 24 объектах (замер бюджета в отчёте); судья не «тонет» в
игроках (приоритет/позиция).

### Stage 8. Состояния: титул, меню, два тайма, итог
Титул, меню выбора формата/команд (§7.1), переход таймов, финальный свисток,
экран итога (HUD/текст — `gfx_print`).
**Приёмка:** полный цикл «титул → меню → матч (2 тайма) → итог» работает из
эмулятора; смена формата (11/7/5) корректно меняет число объектов.

### Stage 9. Звук, HUD-полировка, замеры бюджета
`sfx`/`music` (§3.12, маска каналов `0x03`), HUD (счёт/таймер/тайм),
окончательные замеры растер-бюджета на стресс-сцене (24 объекта + скролл +
звук). При нехватке бюджета — включить формат 7v7 по умолчанию (§3.8), усилить
стаггеринг, включить запись только отличающихся плоскостей (§3.8c).
**Приёмка:** звук не ломает пейсинг (нет пропусков VBlank-тиков, Δ`frame_count`
= 1); worst-case кадр ≤ 220 строк рендера (замер в отчёте); все критерии §9
выполнены.

### Stage 10. Приёмка и полировка
Полный прогон ≥ 10 минут, README.MD, `make deploy`.
**Приёмка:** ROM стабилен, все гейты §9 зелёные, размер образа < `0x8000`.

## 9. Критерии приёмки (общие)

1. Полный цикл: титул → меню → матч (≥ 2 тайма) → гол/аут/угловой → итог.
2. **Tearing = 0:** ни одной записи в VRAM-строку, которую луч ещё не прошёл в
   текущем кадре; проверяется BP на примитив записи + `debug_get_raster_events`.
3. **Темп ровно 50 Гц:** период цикла = 1 hw-кадр при любой штатной загрузке;
   музыка не пропускает тиков; дополнительный `v06_wait_frame` в цикле
   отсутствует (§3.6, §4).
4. **Задержка отклика ≤ 1 кадр.**
5. **Алгоритмичность:** поле и все объекты рисуются процедурным кодом прямо в
   VRAM; в сборке НЕТ `beam.c`/`spr.asm`/`dblbuf.asm`; нет off-screen буфера и
   блитов битмапов (проверка map-файла + отсутствие `spr_blit`/`bg_tiles` в коде).
6. **Полноцветность:** используется вся палитра 16 цветов (§3.2); объект может
   быть любого цвета независимо от фона — без «плоскостного» ограничения.
7. **Аппаратный скролл вверх-вниз** работает, полоса не рвётся, трава при
   скролле перерисовывается минимально (замер redraw-байтов).
8. **Масштаб:** 11v11 (24 объекта) держит 50 Гц со стаггерингом; при
   недостижении — целевым становится 7v7 (16 объектов), зафиксировано в отчёте.
9. **Высота мяча (§7.6):** радиус мяча растёт с высотой, тень остаётся на газоне
   (индикатор точки падения), мяч опускается по дуге; «свеча» воспроизводится
   при сильном ударе вплотную к игроку/перекладине.
10. ROM собирается `make`, образ < `0x8000` (не врастает в VRAM).

## 10. Бюджет производительности (сводно)

- Кадр: 60000 T (3 МГц / 50 Гц) = 312 строк таймера (96 тиков/строку), видимых 256.
- Потолок рендера: ~200–220 строк; резерв логика/звук/ввод ≤ ~90.
- Запись байта VRAM ≈ 24–40 T (§2.3/§2.5); строка растра = 96 тиков таймера.
- Движущийся объект 8×8 (4 плоскости, erase+draw со слиянием): ~40–64 байта ≈
  **12–20 строк**. Полная палитра вдвое дороже прежних 2-плоскостных спрайтов.
- Кадр при 11v11: ~12–16 активных объектов × ~14 ≈ 170–220 строк (в бюджете);
  остальные — стаггер/round-robin перенос (§3.8).
- Полоса скролла: alias-skip травы → обычно перерисовка лишь разметки/ворот в
  открытой полосе, в бланкинге (строка ≥ 288); пик учитывается в замере.
- `render_init` (полная покраска поля) — одноразово, ~несколько кадров, при
  чёрной палитре (невидимо); в кадровой бюджет не входит.
- Звук: ≤ ~90 строк резерва, выдаётся после `render_frame`; канал 2 ВИ53 не
  трогать (таймер).
- Замеры обязательны на Stage 1, 4, 9: фактические строки/кадр и redraw-байты —
  в `reports/StageN.md`.

## 11. Риски и их закрытие

| Риск | Митигация |
|---|---|
| **Стена пропускной способности:** наивная полная регенерация экрана невозможна (~13–20× бюджета кадра, §2.3) | Персистентная VRAM + ИНКРЕМЕНТАЛЬНЫЙ рендер (пишем только изменённые байты). Инкрементальность — физическая необходимость, не оптимизация |
| Полная палитра (4 плоскости) вдвое дороже 2-плоскостных спрайтов → ~12–16 движущихся объектов/кадр | Стаггеринг AI (§7.4), round-robin перенос дальних (§3.8), запись только отличающихся от фона плоскостей (§3.8c), запасной формат 7v7 |
| Tearing при записи в ещё не пройденную лучом строку | Wake-phase racing-the-beam: `timer_wait` по НИЖНЕЙ строке области, запись строго позади луча (§3.6); гейт Stage 1 |
| «Призраки» после ухода объекта (персистентная VRAM) | Стирание = `paint_field` по старому футпринту (§3.5); перерисовка всех объектов, пересекающих dirty-rect; гейт Stage 3 (VRAM-дамп) |
| Процедурный силуэт игрока дороже бюджета (много примитивов/кадр) | Параметрическая фигура из немногих `fill_rect`/`fill_circle`; опция — маска-контур «1 байт/строка» (§3.4), решение по замеру Stage 3 |
| Невыровненный `x` объекта → RMW по краям байтов (дороже) | Якорь `x & 0xF8` для игроков (целые байты); мяч — RMW только по краям круга; §3.4/§7.3 |
| Открытая скроллом полоса содержит алиас-мусор | Перерисовка полосы `paint_field` в бланкинге до записи регистра скролла (§3.7); период травы 64 px делит 256 → alias-skip |
| Объекты вне окна «протекают» алиасом в видимое поле | Игра помечает `hidden` для объектов вне текущего окна 256 px (§3.7) |
| Запись управляющего слова ПИА / опрос клавиатуры сбрасывает регистр скролла (`03h`) в 0 → съезжает изображение | `gfx_set_scroll` + flush `kbd_scan_now` на VBlank; `startup.asm` восстанавливает `0xFF`; до первой камеры держать `gfx_scroll_row = 0xFF` (§2.4) |
| Звук (канал 2) конфликтует с таймером | Маска каналов `0x03` (§3.12); звук после `render_frame`; длинные `DI` запрещены |
| Образ ROM перерастёт `0x8000` (VRAM) | Лимит в Makefile; ZX0-сжатие ассетов/музыки с распаковкой в кучу; лесенки `spr.asm` не нужны — `0x7000–0x7FFF` свободен |
| Упрощённые правила (аут/угловой/офсайд) далеки от «симулятора» | Первая версия — упрощённо (§7.2); ofsайд/полные процедуры — как расширение после Stage 10, помечено в README |
| Мяч меняет радиус (рост с `z`) → dirty-rect растёт | Процедурный `fill_circle` любого радиуса (§7.6); dirty-rect по габариту круга; учтено в бюджете (§3.8) |
