# Stage 2. Семантика функций (riseout.rom)

> Источник фактов — MCP `vector-debugger` (дизассемблирование, трассы, RDB). Механические цифры Stage 1 здесь не дублируются, взяты только те, без которых неотличим результат Stage 2.

## Goal

Дать всем 95 функционным объектам RDB осмысленное имя по правилам `utils/analyze/naming.py`, русскую формулировку назначения в `comment`, подтверждённые свойства (`params`, `reads`, `writes`, `io`, `hook_slot`, `returns`) и связи `function → function / data` — с сохранением результата в RDB пачками. Ничего, выходящее за Stage 2 (метки `lbl_*`, data-объекты, экспорт ASM), не затрагивалось.

## Method

1. **Канал данных — только MCP.** ROM загружен `debug_load_rom` (org 0x0100); `debug_reset` не вызывался (после сброса CPU зависает в busy-wait `OUT 1C / IN 1B`). Для тел функций использованы `debug_disassemble` / `debug_disassemble_image` (пакетный дамп) / `debug_get_function_context` / `debug_get_call_graph` / `debug_analyze_code`; для данных — `debug_read_memory_range`; для состояний — `debug_get_state` перед каждой зависимой от состояния CPU операцией.
2. **Кандидаты брались из сырых JSON прогона** (`.scratch/pipeline/riseout/abi_scan.json`, `io_signature.json`, `disassembly.json`) и из `.scratch/pipeline`-кэша дизассемблирования; повторного «ручного» декодирования байтов не было — свои вычисления применяли только как сверку уже полученных MCP-данных.
3. **Порядок обхода** — адресами сверху (0x0100 → 0x50FF) по кластерам: entry/инициализация → вывод текста и глифов → клавиатурное кольцо и опрос → звуковой тракт КР580ВИ53 → генерация/прокрутка поля и коллизии → HUD (score/men/level) → состояния игры → аттракт-режим (заставка) → музыкальная подсистема. В конце — утилиты-заглушки и обёртки.
4. **Точность как приоритет.** Там, где ранний (batch 1/2) комментарий противоречил найденным доказательствам, комментарий **переписывался** — см. раздел «Уточнённые комментарии». Гипотезы в комментариях помечены словами `предположительно` / `недообследовано`, установленные факты — адресами и мнемониками.
5. **Пачки и сохранения.** Правки шли пачками по ~10 объектов: `debug_update_rdb_object` (только `name`; `address`/`type`/`size` сохранялись как в RDB, размер остался неподтверждённым) → `debug_set_rdb_comment` → `debug_set_rdb_property` → `debug_add_rdb_link` → **`debug_save_rdb`** → проверка `debug_get_rdb_info` (`dirty=false`, `object_count=360`). Итого 10 сохранений; `.rdb` руками не редактировался.
6. **Техническая тонкость:** все аргументы `address`/`source`/`target` в MCP — **десятичные**; одна связь, записанная из-за этого не туда (`0x2565 → 0x29FF`), снята и записана заново (`0x2565 → 0x2AFF`).

## Что установлено по кластерам (кратко)

* **Аттракт-режим (заставка)** — отдельная подсистема: `func_attract_mode_loop` (0x2565) → `func_attract_init_scene` (0x2AFF) → `func_music_start` (трек 1) → `func_attract_draw_title` (0x2B61) → `func_attract_overlay_driver` (0x25FF) построчно через `func_attract_draw_window` / `func_attract_draw_row` → `func_attract_plot_bits` (0x27E1) c OR маски в битплоскость и `func_attract_plane_shift` (0x2A9A) как сдвиг четвёртой плоскости VRAM 0xE000.
* **Музыка** исполняется **из цепочки кадрового прерывания через self-modifying слот 0x04EE**: `func_music_start` пишет туда `0C3h` (JMP) + адрес обработчика 0x2EFB, `func_music_stop` — `0C9h` (RET). Треки: 1 — заставка (ROM 0x4E23/0x4CC4/0x4FB4), 2 — уровень (0x3112/0x3112/0x30D2), 3 — финал (0x4E63/0x4CFC/0x4FE4); команды канала уходят в КР580ВИ53 (`0x08/0x09/0x0A/0x0B`) через `func_music_sound_cmd` → `func_sound_cmd_dispatch` (0x0206).
* **Клавиатура**: кольцо опроса `[0x081F+A]`; `func_key_strobe_state` (0x01A8) и `func_key_code_decode` (0x01BC) содержательно обрабатывают **только A=0** (при A>0 возвращают 0), поэтому сканы аттракта `func_attract_key_row_scan` / `func_attract_key_code_scan` фактически опрашивают одну линию; коды клавиш — таблица 0x01D5 по старшему нибблу кольца.
* **Кандидат Stage 1 «probe» на 0x2AAB переосмыслен**: это не цикл ожидания клавиши, а внутренняя петля копирования `func_attract_plane_shift` (`LDAX D / MOV M / INX H / INX D / JNZ 2AA4`) — CPU долго находится в ней, отсюда и впечатление «пауза вне функции».
* **Вывод текста**: `func_draw_text_record` (0x16F3) рисует одну запись `[x, y, текст..00]`, `func_draw_text_records` (0x2D1B) — B записей из таблицы, `func_draw_text_record_safe` (0x2D2F) — та же с сохранением H/D/B; очистка оверлейной страницы — `func_clear_overlay_page` (0x2D39) / `func_clear_overlay_page_tail` (0x2D45) через `func_fill_char_glyph` (0x0142).

## Open questions

1. **Размеры функций** остались неподтверждёнными (`size = -1`): тела многих функций продолжаются за метками `lbl_*` (например, `func_attract_draw_title` дописан циклом 0x2B71..0x2B8A, `func_blink_step_delay` — до 0x2D71). Пересчёт extent — Stage 5/6.
2. **`func_find_free_record_slot` (0x1E75)** — единственный объект с явной пометкой «недообследовано»: назначение таблицы 0x1E9C (30 байт) статически не подтверждено, кто и что в неё кладёт — из трассы не следовало.
3. **Формат нотных потоков** (0x30D2, 0x4C.., 0x4E..) и точный смысл длин/темпов в `[0x7DC3]..[0x7DDE]` не расшифрованы — Stage 2 зафиксировал лишь только структуру «три голоса + указатели + флаги запуска». Треки 2/3 названы «уровень»/«финал» по адресам вызовов (`0x0964`, `0x0989`), а не по звучанию.
4. **Нумерация команд ВИ53** (0x06/0x07/0x08/0x0A/0x0C/0x0D и параметры) — mapping на режимы КР580ВИ53 не проверялся живой трассой портов; для `func_sound_cmd_dispatch` это помечено как observation, а не как подтверждённое поведение «железа».
5. **Слоты-заглушки** 0x0121 / 0x01A3 / 0x01A4 / 0x01A5 / 0x01A6 / 0x01E5: имена описывают их как RET-вставки; какие обработчики в них устанавливаются в рантайме (в частности, что занимает 0x01E5 при активном мигании `func_blink_overlay_pulse`) — не установлено, в текущем снимке CPU слоты пустые.
6. **`func_attract_plane_shift` (0x2A9A)**: сохранение `[0xE000]` в `[0xFFFE]` и шаг-copy «через 2 байта» описаны механически; зачем нужен именно такой сдвиг четвёртой плоскости (эффект прокрутки оверлея по строкам) — требует проверки сравнением VRAM-снимков до/после кадра.
7. **Вторая графическая полоса `func_attract_draw_title`** (15 байт из 0x2C13 в 0x5729) — значения не выглядят корректной последовательностью глифов (в отличие от 0xE0..0xFD из 0x2C04); возможно, это не данные глифов, а смежный код/структура — требуется разбир на Stage 5 (data-объекты).
8. **`func_hl_eq_de` (0x04F1)** оставлен с функциональной формулировкой «сравнение HL и DE» и привязкой к проверке рекорда (0x22A1) как **предположительной**; прямых доказательств «рекорд» нет.
9. **Покрытие**: функции вне достижимого из 0x0100 графа (остатки 34 промежутков из Stage 1) не обследовались — это не объекты функций RDB, их семантика — задача последующих стадий.
