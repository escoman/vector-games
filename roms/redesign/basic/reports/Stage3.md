# Stage 3. ABI сквозных точек интерпретатора (basic.r0m, RAM-образ)

> Разбор живого образа через MCP-отладчик (тела функций — `.scratch/dis.py`,
> fan-in по экспорту `.scratch/export/pipeline/layout.asm`). Модульные verdict'ы
> (`report_gen.py`) — в `.scratch/pipeline/basic/pipeline.md`. Здесь — контракт
> помощников, на которые опираются все обработчики Stage 2, и три ключевые точки
> из ТЗ: `func_putchar`, `func_eval_expression`, `func_var_lookup`.
> Дата прогона: 2026-10-17. Имена и адреса не изобретаются — каждое подтверждено
> телом и(или) местами вызова.

## 1. Три сквозные точки из ТЗ (доказаны)

### 1.1 `func_eval_expression` — `0x09B1` (указатель на текст → значение)

Точка входа вычисления выражения. Тело:

```
0x09B1  DCX H
0x09B2  MVI D,00 / PUSH D / XCHG
0x09B6  LXI H,FFD1 / DAD SP          ; глубина стека относительно 0xFFD1
0x09BC  LHLD 0CB3 / SUB L / SBB H    ; сравнить с нижним краем занятой памяти
0x09C2  JC 0069                       ; не хватило → OUT OF MEMORY
0x09C6  CALL 0A43                     ; ядро разбора
0x09DD  ...                           ; цепочка реляционных операторов (>0xAB)
```

Вход — `HL` = текстовый указатель; выход — значение в FAC `0x404F..0x4052` и
сдвинутый `0x404D`. Страховка стека (`LHLD 0CB3 / JC 0069`) объясняет, почему
рекурсивный вызов оценщика из `func_eval_ref` безопасно вложен.

Ядро — **`func_eval_primary` `0x0A43`**: сбрасывает строковый флаг (`STA 0C8C`),
двигает указатель (`RST 0x10`), различает литерал/оператор по диапазону токенов
(`CPI 3A/20/30/41/5B/A4/A5/A2/A0/CA/D5…`) и рекурсируется. Сюда же приходит
разбор чисел (`→ 0x15A9`) и переменных/функций (`→ 0x0ABF`).

### 1.2 `func_var_lookup` — `0x0BCD` (имя → слот переменной)

```
0x0BCD  MOV B,M / MVI A,BF / ADD B / CPI 1A / JNC 0074   ; байт-токен имени, плохой → stub
0x0BD7  XRA A / STA 0C8C                                  ; сброс строкового флага
0x0BDA  INX H / MOV A,M / CPI 3A / JNC 0BF5 / CPI 20 / JZ 0BDA / CPI 30 / JNC 0BFC
0x0BEB  CPI 24                                            ; '$' — строковая переменная
0x0BFC  MOV C,M / ... / CPI 41 / JC 0C1B / CPI 5B / JC 0BFD ; вторая буква A–Z
```

Разбирает имя по `(HL)`: код буквы, модификатор `$`/целое, опциональную вторую
букву → поиск/создание слота; двигает текстовый указатель. Вызывается из ветки
ссылок оценщика **`func_eval_ref` `0x0ABF`** (была меткой `lbl_0abf`): там же
`JMP 0x0B09` — вычислительный прыжок в таблицу встроенных функций (Stage 2).

### 1.3 `func_putchar` — `0x1C95` (символ → экран)

```
0x1C95  PUSH B / MOV C,A / CALL 3E9F / POP B / RET
```

Тонкая обёртка: код символа в `A` → `C`, сохранение `BC`, вызов терминального
бэкенда **`func_term_putc` `0x3E9F`** (`EI / PUSH PSW,B,D,H / ANI 7F / …` —
аппаратный вывод символа в область BIOS `0x3EXX`). Его зовёт печатающая петля
строк `0x00A1` (`MOV A,M / ANI 7F / CALL 1C95 / INX H / JP 00A1`) и boot-сообщения
(`LXI H,2544 / CALL 00A1`).

## 2. Page-zero RST-векторы (доказаны по телам)

| адрес | RST | имя | контракт |
|---|---|---|---|
| `0x0008` | 1 | `func_rst_fetch_sep` | сверить ожидаемый разделитель; при совпадении fall-through в RST 2 |
| `0x0010` | 2 | `func_rst_advance_text` | продвинуть `HL` на следующий непробельный символ (стоп на `:`/`0x3A`) |
| `0x0020` | 4 | `func_rst_cmp_dehl` | сравнить `HL`==`DE`, выставить Z |
| `0x0028` | 5 | `func_rst_fac_sign` | тест знак/ноль FAC: RZ если 0; A=0 «+», A=FF «−» |
| `0x0038` | 7 | `func_rst_irq` | `JMP 0x2C7F` — VBlank/IRQ тикер (смена стека `0x26F7`, счётчик `0x3A1F`, `OUT 00`/`IN 01`) — **Stage 4** |

## 3. Горячие помощники числового и строкового путей

Именование по fan-in из `layout.asm` (статика `abi_scan` даёт лишь кандидатов —
у каркасных функций размер неизвестен, поэтому решение принято по дизасму тел).

### 3.1 Числовой путь / FAC (`0x404F..0x4052`)

| адрес | имя | fan-in | контракт |
|---|---|---:|---|
| `0x14AB` | `func_fac_continuation` | **12** | сохранить FAC/текст в стек + self-modified `JMP` в `0x14B8` (трамплин продолжения) |
| `0x1493` | `func_fac_store_int` | 3 | записать `A` как целое FAC (шкала `B`); общий хвост `0x0D95` |
| `0x14BB` | `func_fac_fetch_operand` | 3 | загрузить inline 4-байтную константу → FAC, сдвинуть `0x404D` |
| `0x1183` | `func_fac_normalize` | — | нормализация FAC, underflow → `0x4050=0` |
| `0x0531` | `func_fac_require_int` | PEEK/USR | требовать целое (эксп. <0x91), иначе ошибка 08 |
| `0x10CA` | `func_fac_require_byte` | INP/POINT/CHR$ | eval числа → байт в `A` + контроль диапазона (была метка) |
| `0x15A8` | `func_num_digitize` | VAL | парсер числового литерала из текста → FAC (был меткой) |

### 3.2 Строковый путь

| адрес | имя | fan-in | контракт |
|---|---|---:|---|
| `0x09A1` | `func_str_flush_guard` | 4 | если `0x0C8C<>0` — доделать временную строку (`JMP 0x1E6D`) |
| `0x0E65` | `func_str_make` | 4 | собрать дескриптор (dim `0x4049`, data-ptr `0x404B`); внутренний хвост `0x0DF9` не плодим |
| `0x0E97` | `func_str_return` | 8 | вернуть временную строку: обновить `0x0F07`/`0x404D`, флаг `0x0C8C=1` (была меткой) |
| `0x0ECE` | `func_str_window` | 3 | выделить/заокнировать окно строки (`0x0ED3/0x0ED6`) |

### 3.3 Ошибки (page-zero)

| адрес | имя | был | контракт |
|---|---|---|---|
| `0x0074` | `func_error_stub` | `lbl_0074` | «не реализовано»/синтаксис: `MVI E,02 / XRA A / STA 03E7`; запись AT таблицы функций |
| `0x0083` | `func_error_raise` | `lbl_0083` | единое поднятие ошибки: вызывающий грузит `E`=код (`MVI E,nn / JMP 0083`); коды 08/16/1A/1E |

## 4. Применённые изменения RDB

Инструмент — `tools/stage3_abi_helpers.py` (повторяет `_ensure_function` из
`stage2_dispatch_table.py`). Результат `--apply`:

```
план: 24 сквозных объекта
итог: actions=181 {add:3, comment:24, link:12, property:120, rename:18, retype:3, save:1}
объектов: 462, dirty: False
```

- **создано 3** новых функции: `func_str_return`, `func_fac_require_byte`,
  `func_num_digitize` (в образе были только как `label_*`, объектов RDB не было);
- **переквалифицировано 3** метки → функция (одним `debug_update_rdb_object`,
  links/properties сохранены): `lbl_0074`→`func_error_stub`,
  `lbl_0083`→`func_error_raise`, `lbl_0abf`→`func_eval_ref`;
- **переименовано 18** `func_*` → осмысленные имена;
- каждому записаны `role`/`params`/`reads`/`writes`/`calls`, комментарий и
  **12 связей** (`func_eval_expression→func_eval_primary`,
  `func_eval_ref→func_var_lookup/func_eval_expression`,
  `func_putchar→func_term_putc`, `func_str_make→func_str_window`,
  `func_fac_store_int→func_fac_normalize`, `func_rst_fetch_sep→…`, и др.).

Round-trip: `run_pipeline.sh basic --from export_asm` — **6/6 стадий SUCCESS,
`roundtrip_verify: byte-for-byte identical`**. `measure_sizes: 458 расхождений
из 462` — ожидаемо PARTIAL (каркасные функции без известного `size`), не
регрессия этого этапа.

## 5. Открытые пункты (не выдуманы, отложены)

- **Контракт обработчиков КОМАНД** (`CLS..CLEAR`, токены `0x80..0x99`) не
  вскрыт: диспетчер команд не найден (единственный вычисляемый переход —
  `0x0B09`, это функции). Переносится в **Stage 5** (архитектура интерпретатора:
  REPL/токенизатор/диспетчер/исполнение).
- **`func_rst_irq` (`0x0038` → `0x2C7F`)** — прерывания/VBlank-тикер: детальное
  описание ABI и контракта сохранности HL/SP — **Stage 4**.
- Внутренние хвосты `func_str_make` (`0x0DF9/0x0DFF`) намеренно не заведены
  отдельными объектами (один адрес — один объект; они не вызываются извне).

## 6. Следующие шаги

- Stage 4: прерывания (`0x2C7F`), контракты сохранения контекста.
- Stage 5: общая архитектура — цепочка REPL → токенизатор → диспетчер команд →
  оценщик (`func_eval_expression`/`func_eval_primary`/`func_eval_ref`), хранение
  переменных (`func_var_lookup`), подсистемы ввода/вывода (`func_putchar`).
