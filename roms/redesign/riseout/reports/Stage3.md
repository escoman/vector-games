# Stage 3. Параметры функций (riseout.rom)

> Источник фактов — MCP `vector-debugger` (тела функций, места вызова, побайтовый поиск паттернов, дампы RAM/ROM). Механика Stage 0/1 и переименование Stage 2 здесь не пересказываются: цитируются только те адреса и строки, на которых держатся вердикты.

## Goal

Превратить кандидатов `abi_scan` (32 функции, 97 кандидатов) в подтверждённое описание ABI: для каждой функции записать в RDB структурированный `properties.params` (имя, носитель, размер, русская семантика); **каждый кандидат должен получить вердикт** «подтверждён / изменён / отвергнут»; отвергнутые не удаляются молча — итоговое состояние пишется в `params` (вплоть до `(нет)`), а причина — в комментарий функции. Заодно закрыть параметры там, где сканер их не поймал, но они видны из тела и мест вызова (в том числе 15 функций, получивших в Stage 2 неформальную строку `params`).

## Method

1. **Только MCP.** ROM загружен `debug_load_rom` (org 0x0100), `debug_reset` не вызывался. Тела — `debug_disassemble_range` и пакетный `debug_disassemble_image` (4 куска 0x0100..0x50FE, 13 281 инструкция), места вызова — CALL-мишени из этого же дампа плюс `debug_get_xrefs`, данные — `debug_read_memory_range`, спорные паттерны — `debug_find_bytecode_sequence`.
2. **Отвергнутые «фантомы» проверены побайтово.** Два кандидата `memory_argument` оказались следствием раскодирования данных как кода: поиск паттернов `32 E7 25` (`STA 0x25E7`) и `22 3B 03` (`SHLD 0x033B`) в 0x0100..0x50FF дал **0 совпадений** — таких инструкций в ROM нет; по адресу 0x25E7 в реальности стоит `SHLD 0827h`.
3. **Критерий подтверждения параметра.** Регистр или пара — параметр, если читается в теле **до первой своей записи** на пути от входа И место вызова реально его задаёт (проверено для каждого CALL-сайта с контекстом по 4 инструкции в обе стороны). Только это сочетание: тело без вызова или вызов без чтения в теле давало «изменён»/«отвергнут», а не «подтверждён».
4. **Что параметром не является** (эти правила и дали массовые отказы):
   * `PUSH B/D/H/PSW` первой инструкцией — сохранение контекста вызывающего, а не приём значения (симметричный `POP` в хвосте снимает и претензию на «выход»);
   * 16-битный возвратный адрес в стеке — **стековых параметров в этом ROM нет ни у одной функции**. Проверено по достижимому из 0x0100 коду (`debug_coverage_report`, 4663 инструкции, 34 code-диапазона): `SP` появляется всего в четырёх инструкциях — `LXI SP,0100h` @0x0101 (инициализация) и `DAD SP` @0x2608/@0x260C → `SHLD 7DF0` … `LHLD 7DF0` → `SPHL` @0x264C внутри `func_attract_overlay_driver` (0x25FF). Второе — сохранение и возврат «страховочного» значения стека (описано ещё в Stage 2), а не приём аргументов; ни одна функция не читает данные по смещению от `SP`.
   * регистр, перезаписанный `LXI`/`MVI`/`LHLD`/`MOV r,A` до первого чтения;
   * `STA`/`LDA` служебных ячеек 0x082A (кэш A), 0x0834/0x0836/0x0838 (обмен через `XCHG`/`XTHL`), а также запись результата в переменную игры (0x7C01, 0x7C06) — это `reads`/`writes`, не ABI;
   * «выход» регистра — это результат, он живёт в отдельном свойстве `returns`.
5. **Формат записи** (единый для всех 47 объектов):

   ```
   pN{name=<имя>;carrier=reg:A|pair:HL|mem:0x7DE5|flags:Z,P;size=8|16;sem=<русское пояснение>}
   ```

   несколько параметров через ` | `; параметров нет — `(нет)`; `size=0` (в таблице «—») — для немасштабного носителя `flags:`. Результат — в `returns`, побочные эффекты памяти — в `reads`/`writes`.
6. **Пачки и сохранения.** 6 пачек по ~10 объектов: `debug_set_rdb_property` (+ `debug_set_rdb_comment`, где нужен вердикт-пояснение) → `debug_save_rdb` → `debug_get_rdb_info`. Единственный канал записи — `debug_save_rdb`; файл `.rdb` руками не правился. Финал: `dirty=false`, `object_count=360`, связей 164 (не менялись), имён не менял, новых объектов не создавал, `lbl_*`/`data_*` не трогал.
7. **Технические грабли** (для следующих прогонов): аргумент `address` в MCP — **десятичный** (первая пачка частично не прошла из-за 290/418 вместо 289/292); `debug_set_rdb_property` не экранирует HTML-сущности — `&gt;` и подобное попадает в файл буквально, текст надо писать без них; `debug_save_rdb` и `debug_get_rdb_info` нельзя слать одним параллельным блоком — проверка успевает зафиксировать `dirty=true`.

## Вердикты по 97 кандидатам `abi_scan`

Колонки «Канд./Подтв./Измен./Отверг.» сверены со структурой `abi_scan.json` программно: сумма кандидатов по строкам = 97, расхождений с файлом нет.


### Как читать «изменён»

«Изменён» = кандидат реален, но описан неточно. Три типовых случая:
* `input H` + `input L` — это одна пара, записана как `pair:HL` (два кандидата → один параметр);
* `output A` — регистр действительно меняет состояние вызывающего, но это результат: он описан в отдельном свойстве `returns` (таких объектов стало 12 вместо 1);
* `input D`/`input E` внутри функции, где `PUSH D` стоит первой инструкцией, — сохранение контекста, снято.

### Замечание к выходным данным `abi_scan`

У **всех 32** функций поле `function.callers` равно 0, хотя вызовы есть (например `CALL 0551` из 0x0124/0x0142, `CALL 16F3` из 0x2D20/0x2D32/0x249E). Поле в текущем прогоне нерабочее, поэтому «что задаёт регистр на входе» проверялось не по нему, а по полному дизассемблированному дампу 0x0100..0x50FE с поиском `CD <lo> <hi>` по каждой функции. Это стоит починить в сканере до Stage 4: без вызовов «input» остаётся недоказуемым.

## Исправления Stage 2, к которым привёл слой параметров

* `func_copy_text_block` (0x017C): длина — **пара BC (16 бит)**, а не «B байт»; утверждение «после RET HL = конец приёмника» неверно: `PUSH H` выполняется **после** `XCHG` @0x017C, поэтому `POP H` @0x01A1 возвращает HL = **базу приёмника**, а конец приёмника уходит только в [0x0840]. Проверены все 10 мест вызова (0x174A, 0x1C93, 0x1FCA, 0x2219, 0x22FC, 0x23D3, 0x23FB, 0x27B9, 0x2B3B, 0x2B47) — выходящие HL/DE не читает ни одно.
* `func_write_plane_run` (0x05B7): режим прогона несёт **не A** (внутри A только пишется), а флаги Z/P на входе — `carrier=flags:Z,P` (`JZ 05CB`, `JPE 05CB`, `JP 05D3`).
* `func_attract_draw_row` (0x2680): DE на входе **не читается** (`MOV E,M` @0x2683, `MOV D,M` @0x269B — DE это выход), признаки сдвига приходят через память [0x7DE5]/[0x7DE6].
* `func_add_score_display` (0x1751): единственный параметр — **A** (BCD-прибавка, первое использование `ADD L` @0x1757); B/D/E/H — сохранённый контекст и внутренние `LXI`.
* `func_split_bcd_pair` (0x17AD): HL — **вход** (адрес приёма двух цифр), а не выход.
* `func_draw_text_record` (0x16F3) и `func_draw_text_records` (0x2D1B): формат текстовой записи **доказан** — `[x, y, текст..00]` (дамп таблицы 0x2B8B: `0A 08 'FROM DUNGEONS' 00 | 05 0B 'HIT BUTTON OR SPACE KEY' 00 | 09 0E …`). Заголовок снимает 0x2D1B двумя `INX H` **до** вызова, поэтому в 0x16F3 HL всегда приходит на первом символе; `INX H` перед первым `MOV A,M` в цикле длины — не «пропуск заголовка», а сдвиг счёта, из-за которого B равно точному числу значащих байт (трассировка на «ABC»: B=3, копия пишется от сохранённого HL без терминатора). Строка `SCORE:` @0x24B2 и `PLAYER` @0x2C9D — примеры вызовов 0x16F3/0x2D2F **без** заголовка, то есть с чистым текстом.
* `func_draw_text_record_safe` (0x2D2F): вопреки комментарию Stage 2, это **не** вывод таблицы: вызывающий цикл @0x2C3C держит HL неизменным (`LXI H,2C9D` один раз) и шагает только по строкам (`INR D` дважды за итерацию, @0x2CB7 — `DCR D`), то есть одна и та же строка перерисовывается на нескольких рядах.
* Неформальные строки `params` вида `-> A=…` у `func_dec_effect_steps`, `func_attract_frame_step`, `func_attract_timer_tick`, `func_attract_timer_read`, `func_rng_lcg_step` описывали результат: перенесены в `returns`, в `params` записано `(нет)`.

## Что осталось недоказанным

1. **`RET`-слоты 0x0121, 0x01A4, 0x01A5, 0x01A6, 0x01E5.** `params=(нет)` верно для их теперешнего содержимого (один `RET`). Если подтвердится, что в них патчится JMP-хук (по образцу самопатча 0x04EE), ABI придёт от обработчика, и свойство нужно переписывать.
2. **`func_find_free_record_slot` (0x1E75).** Назначение не установлено (open question Stage 2), в кандидатах сканера функции нет — носители вручную не утверждались, чтобы не выдумывать ABI.
3. **Размеры функций остались `-1`.** «Читается до первой записи» считалось по границам известной части тела; ни один **отвергнутый** кандидат при этом не опирался на байты вне тела — все отказы закрыты инструкциями внутри тела (`PUSH`/`POP`/`LXI`/`MVI`/`RET`), так что пересмотра вердиктов смена границ не вызовет, но может добавить параметры.
4. **Оси у признаков сдвига** (0x265B → [0x7DE5]/[0x7DE6], 0x2680): доказаны факт чтения и ветвление `JZ`/`INR`; какая ось соответствует байту в пользовательском смысле — вывод из формул `0x34 + 2v` и `0x10 + 2h`, проверки по изображению экрана не было.
5. **Отсутствие стековых параметров** — вывод статический, но покрывающий весь достижимый из 0x0100 код (`debug_coverage_report`: 4663 инструкции, 45,2% образа, все вхождения `SP` перечислены в Method). Динамической проверки трассировкой с контролем `SP` не было; области вне достижимого кода (таблицы 0x0217..0x03D1, 0x04D6..0x0550, графика 0x3000+) разбирались только линейно, и найденные там `INX SP`/`DCX SP`/`SPHL` — раскодирование данных, а не команды.
6. **Порядок полей в заголовке записи** `[x][y]` (младший байт слова позиции = первый байт заголовка) следует из `MOV E,M; INX H; MOV D,M` в 0x2D1B и из использования E как столбца (маска `ANI 1Fh`), но визуально на кадре не подтверждён — это уровень Stage 6.

## Передача дальше (не Stage 3, но из него следует)

1. **Round-trip нужно пересобрать**: по контракту ТЗ после ручной пачки правок RDB экспорт пересобирается `utils/analyze/run_pipeline.sh riseout --from export_asm`. Stage 3 менял только `comment`/`properties` (имена, типы, размеры, связи и порядок объектов не тронуты: 360 объектов, 95 функций, 164 связи — как после Stage 2), поэтому бинарный результат сборки измениться не должен; пересборку выполняет тот, кто следующим пишет в RDB.
2. **Два дефекта сканера**, мешающие Stage 4+: `function.callers` всегда 0 (см. выше) и отсутствие ролей «пара регистров» — из-за этого 44 `input`-кандидата дали только 21 параметр, остальное срослось по `H`+`L` и `D`+`E` вручную.
3. **Заготовки для Stage 5/6**: у 5 функций параметр помечен как «вход-выход» (HL движется по таблице или буферу и на выходе указывает на следующий элемент: 0x03D2, 0x16F3, 0x1E5D, 0x2680, 0x2D1B) — это итераторы, их удобно проверять прогоном с трассировкой памяти; формат записей `[x, y, текст..00]` и адрес следующего элемента в [0x07DEB] — готовый критерий для рендер-проверки.

## Примечание: однострочные комментарии

Комментарии и `properties` объектов RDB обязаны быть **однострочными**: `v06c-asm-export` печатает их в `layout.asm` как `; …` без экранирования многострочности, поэтому обрыв строки превращает остаток комментария в код — `z80asm` отвечает `error: invalid character` (в riseout таких было 34, round-trip = `blocked`).
Инцидент и починка: Stage 3 записал `\n` в 34 комментариях; тексты зафиксированы дословно, но в одну строку через `debug_set_rdb_comment` + `debug_save_rdb` (360 объектов, `dirty=false`), экспорт пересобран `run_pipeline.sh riseout --from export_asm` — `syntax_check: clean`, `roundtrip_verify: OK, byte-for-byte identical` (0 расхождений из 20480).
Побочный эффект: те же вылезшие в листинг слова комментариев давали и 147 находок `symbolic_operand_lint` (`undefined_symbol` вида «layout.asm:8 — операнд abi_scan»); после починки — **0**.
