# Stage 9. Поиск и исследование карт уровней

## Goal

Найти и исследовать карты уровней игры PUTUP: определить точку входа в код
загрузки уровня после нажатия пробела, функцию очистки экрана, функцию рисования
уровня по карте, вычисление адреса карты, формат записи уровня и механизм выхода.
Создать в RDB объект `data_level_maps` (таблица карт) и отдельные объекты
`data_level_01 .. data_level_15`.

## ROM

- Файл: `putup.rom`
- Размер: 17664 байт
- SHA256: `8486442efc390b15860ec7f69c32db93b0884908565fa11fec57d5c551b4e9a6`
- RDB: `./src/putup.rdb` (platform `vector06c`, version 1)
- Объектов в RDB: **167** (было 153 → добавлено 14 объектов `data_level_02..15`)

## Profile / Tasks

- Profile: `reverse_engineering`
- Метод: MCP-first. Все факты получены через `vector-debugger`
  (`debug_disassemble_range`, `debug_read_memory_range`, `debug_get_rdb_object`,
  `debug_get_state`). Самостоятельное дизассемблирование не выполнялось.
- ROM загружен, эмуляция на паузе (`running=false`), PC=0x042A.

## Findings

### Finding 1. Путь после нажатия пробела (TZ шаги 1–3)

Location: `func_main_init` (0x0B57) → `lbl_title_key_poll` (0x0C65) →
`func_level_loader` (0x197C)

Observation (MCP-verified, `asm/lbl_title_key_poll.asm`, `asm/func_main_init.asm`):

- `func_main_init` (0x0B57–0x0C64) fall-through в `lbl_title_key_poll` (0x0C65).
- Цикл ожидания пробела `loc_0C68`:
  ```
  0x0C68  XRA A
  0x0C69  PUSH B
  0x0C6A  CALL func_check_start_key
  0x0C6D  POP B
  0x0C6E  ORA A
  0x0C6F  JNZ loc_0C9D        ; пробел/SHIFT нажат -> старт игры
  0x0C72  DCX B / ... / JNZ loc_0C68   ; отсчёт таймаута (BC=0C00h)
  ```
- По таймауту — бегущая строка в буфере 0x5180 и возврат в `lbl_title_key_poll`.
- **При нажатии пробела (`loc_0C9D`):**
  ```
  0x0C9D  CALL func_music_start_track   ; запуск музыки
  0x0CA0  JMP  func_level_loader        ; переход в загрузчик уровня (0x197C)
  ```

Conclusion: точка входа в код загрузки уровня после пробела — `JMP func_level_loader`
(0x0CA0). Confidence: **High**.

### Finding 2. Очистка экрана после старта игры (TZ шаг 2)

Location: `func_level_loader` @ 0x19A0–0x19A3

Observation (MCP-verified, `asm/func_level_loader.asm`):
```
0x19A0  LXI SP, 0100h
0x19A3  CALL func_clear_textbuf   ; очистка текстового/экранного буфера
```

Conclusion: очистка экрана (буфера) выполняется вызовом `func_clear_textbuf`
(0x1BE5) внутри `func_level_loader` непосредственно перед рисованием карты.
Аналога отдельного `func_vram_clear` на этом пути нет — очистка совмещена с
загрузчиком уровня. Confidence: **High**.

### Finding 3. Функция рисования уровня по карте (TZ шаг 3)

Location: `func_level_loader` (0x197C, 523 байта)

Observation: `func_level_loader` сама является функцией рисования уровня. После
очистки буфера она вычисляет адрес карты и рисует все тайлы, HUD, игрока и
сущности, затем `JMP lbl_main_game_loop` (0x0E85). Отдельной функции рисования
карты не существует — отрисовка встроена в загрузчик. Confidence: **High**.

### Finding 4. Вычисление адреса карты текущего уровня (TZ шаг 4)

Location: `func_level_loader` @ 0x19A6–0x19B8

Observation (MCP-verified):
```
0x19A6  LDA var_level        ; A = номер уровня (1..15)
0x19A9  DCR A                ; A = level-1
0x19AA  LXI H, data_level_maps   ; HL = 0x1C8E (база таблицы карт)
0x19AD  JZ  loc_19B8         ; если level==1 -> смещение 0
0x19B0  LXI D, 00B0h         ; D = 176 (0xB0) = размер одной карты
loc_19B3:
0x19B3  DAD D                ; HL += 176
0x19B4  DCR A
0x19B5  JNZ loc_19B3         ; повторить (level-1) раз
loc_19B8:
         ; HL = 0x1C8E + (level-1)*176
```

Conclusion: **адрес карты = 0x1C8E + (level−1)·176**. База таблицы карт
`data_level_maps` = **0x1C8E**, шаг = **176 байт (0xB0)**. Confidence: **High**.

### Finding 5. Координаты выхода — НЕ отдельное поле (TZ шаг 4)

Observation: в `func_level_loader` отсутствует чтение каких-либо байтов координат
выхода из карты. Карта читается ровно 176 байт (см. Finding 6). Точное совпадение
арифметики (15·176 = 2640 = 0x26DE − 0x1C8E, где 0x26DE — следующий объект
`data_tile_table_26DE`) доказывает, что на отдельные координаты выхода места нет.

Выход с уровня **закодирован тайлом** и определяется по коллизии:
- `func_game_update` (0x0CE0): проверка тайла `'t'` (0x74) под игроком @0x0DF0/
  0x0DFE/0x0E0F/0x0E1D; при коллизии `JNZ 13AAh` @0x0E2D (обработчик
  спец-тайла/бонуса).
- Обработчик тайла 0x0F6D инкрементирует 0x08E9; далее
  ```
  0x0FC9  LDA 08EAh
  0x0FCC  CPI 02h
  0x0FCE  JZ  197C        ; -> func_level_loader (var_level++ => следующий уровень)
  ```
  т.е. переход на следующий уровень происходит при `0x08EA == 2` через
  `func_level_loader`.

Conclusion: формат карты — «иной» по терминологии TZ шага 6: **176 байт тайлов,
без отдельных координат выхода**; выход — тайл, распознаваемый по коллизии.
Confidence: **High** (адрес карты/петля) + **Medium** (точная идентификация
тайла-выхода среди спец-тайлов 3..14 — по control-flow, без побайтового
сопоставления каждого тайла).

### Finding 6. Цикл обхода 16×11 = 176 байт карты (TZ шаг 4)

Location: `func_level_loader` @ 0x19B8–0x19E0

Observation (MCP-verified):
```
0x19B8  LXI D, 0000h         ; D=col(0), E=row(0)
0x19BB  LXI B, 00B0h         ; BC = 176 (счётчик байт карты)
loc_19BE:
0x19C0  MOV A, M             ; A = тайл-индекс из карты
0x19C1  ADD A
0x19C2  ADD A                ; A = tile*4
0x19C3  LXI H, data_tile_graphics  ; 0x2706
0x19C6  CALL func_hl_add_a   ; HL = 0x2706 + tile*4 (4 байта графики тайла)
0x19CA  CALL func_draw_tile_to_buf ; рисунок 2x2 тайла в буфер
0x19CE  INR D / INR D        ; col += 2
0x19D0  MOV A,D / CPI 20h / JNZ loc_19DA
0x19D6  MVI D,00h / INR E / INR E   ; при col==32: col=0, row += 2
loc_19DA:
0x19DB  INX H                ; следующий байт карты
0x19DD  DCX B
0x19E0  JNZ loc_19BE         ; 176 итераций
```

Conclusion: карта обходуется побайтово (176 байт), каждый байт — тайл-индекс,
рисуется как 2×2 тайла. Колонки 0,2,…,30 (16 шт.), при col==32 переход на
следующий ряд (row += 2) → **16 колонок × 11 рядов**. Confidence: **High**.

### Finding 7. Базовый адрес и размер таблицы карт (TZ шаг 5)

- База таблицы карт: **0x1C8E** (`data_level_maps`).
- Размер одной карты: **176 байт** (16×11).
- Количество уровней: **15**.
- Итоговый размер таблицы: 15 × 176 = **2640 байт**, диапазон **0x1C8E..0x26DD**.
- Граница подтверждена: 0x1C8E + 2640 = **0x26DE** = начало следующего объекта
  `data_tile_table_26DE`. Таблица карт занимает ровно 2640 байт без остатка.

Confidence: **High**.

### Finding 8. Структура каждой карты (TZ шаг 6)

Проверено побайтовым чтением через `debug_read_memory_range` на репрезентативных
картах: **01** (0x1C8E), **08** (0x215E, середина), **15** (0x262E, последняя).

Наблюдения (единообразны для всех трёх):
- Байт 0..15 (ряд 0) = `2` — верхняя стена.
- Байт 160..175 (ряд 10) = `2` — нижняя стена.
- Первый и последний байт каждого ряда = `2` — боковые стены.
- Внутренние байты — тайл-индексы: `1` = пол/пусто, `2` = стена,
  `3..14` = спец-тайлы (предметы/враги/выход). Наблюдаемые значения:
  карта 01 → 1,2,3,4,5,7,8,10,11; карта 08 → 1,2,3,5,7,8,11,13,14;
  карта 15 → 1,2,3,4,5,6,7,8.
- Отдельных байтов координат выхода нет (см. Finding 5).

Conclusion: **формат карты = 176 байт тайл-индексов, row-major 16×11, граница из
тайла 2**. Структура одинакова для всех 15 карт (точное совпадение арифметики
таблицы + единообразие трёх проверенных карт). Confidence: **High** для формата;
полная побайтовая расшифровка назначения каждого спец-тайла (3..14) — за рамками
Stage 9 (относится к поведению/Stage 10).

## RDB: созданные/обновлённые объекты (TZ шаги 7–8)

### Шаг 7. `data_level_maps` (таблица карт)

- Адрес: 0x1C8E, тип `data`, размер 2640.
- Комментарий обновлён и описывает: базовый адрес (0x1C8E), размер одной карты
  (176 байт), формат (176 тайл-индексов row-major 16×11; 1=пол, 2=стена,
  3..14=спец-тайлы; выход закодирован тайлом, коллизия), количество уровней (15),
  механизм смены уровня (0x0FCE `JZ 197C` при 0x08EA==2), границу таблицы
  (0x26DE = `data_tile_table_26DE`).
- Существующие связи (Stage 6): `func_level_loader → data_level_maps` (0x1C8E),
  `func_level_loader → data_level_params` (0x1C0E) — подтверждены `LXI H` в коде.

**Примечание о `data_level_01` (ограничение RDB).** RDB хранит не более одного
объекта на один адрес (`debug_add_rdb_object` вернул
`"RDB object already exists at this address"` для 0x1C8E). Адрес первой карты
(0x1C8E) совпадает с базой таблицы `data_level_maps`, поэтому отдельный объект
`data_level_01` создать нельзя — первая карта представлена базой таблицы
`data_level_maps` (её первые 176 байт). Объекты `data_level_02..data_level_15`
(14 шт.) созданы и покрывают остальные карты; совместно с `data_level_maps`
(0x1C8E, 2640 байт) они полностью покрывают диапазон таблиц 0x1C8E..0x26DD.
Это единственное отступление от буквальной формулировки шага 8, вызванное
ограничением хранилища RDB, а не ошибкой анализа.

## Verified Facts

1. После пробела: `lbl_title_key_poll` @0x0C9D → `CALL func_music_start_track`,
   `JMP func_level_loader` (0x0CA0). [MCP: disassembly]
2. Очистка экрана: `func_level_loader` @0x19A3 `CALL func_clear_textbuf`. [MCP]
3. Адрес карты = 0x1C8E + (level−1)·176 (петля 0x19B3, шаг 0xB0). [MCP]
4. Петля обхода карты @0x19BE: 176 итераций, 16 колонок × 11 рядов,
   col+=2 wrap@32 → row+=2, тайл = data_tile_graphics(0x2706)+tile*4. [MCP]
5. Таблица карт: база 0x1C8E, 15×176 = 2640 байт, 0x1C8E..0x26DD;
   0x26DE = `data_tile_table_26DE`. [MCP]
6. Структура карты (01/08/15): 176 тайл-индексов, row-major 16×11, граница = тайл 2,
   внутренние тайлы 1..14. [MCP: read_memory_range]
7. Смена уровня: 0x0FC9 `LDA 08EAh`; 0x0FCC `CPI 02h`; 0x0FCE `JZ 197C`
   (`func_level_loader`, var_level++). [MCP]
8. RDB: 167 объектов, dirty=false после `debug_save_rdb`. [MCP: get_rdb_info]

## Inferences

- Выход с уровня закодирован спец-тайлом и распознаётся по коллизии
  (`func_game_update` 't'(0x74) → 0x13AA; счётчик 0x08EA==2 → следующий уровень),
  а не отдельными байтами координат. [Medium]
- Назначение тайл-индексов: 1=пол, 2=стена (высокая уверенность по границам карт);
  3..14 = предметы/враги/выход (требует побайтовой расшифровки в Stage 10). [Medium]

## Hypotheses

- Конкретный тайл-индекс, являющийся «выходом», не сопоставлен побайтово для всех
  15 карт (требуется трассировка коллизий/поведения). [Low]

## Unknowns

- Точное поведение каждого спец-тайла 3..14 (какой именно тайл инициирует выход,
  какие — предметы/враги) в рамках Stage 9 не расшифровывалось.
- Байты параметров уровня `[+0]`@0x0911 и `[+1]`@0x0912 в `data_level_params`
  не читаются ни одной экспортированной функцией (назначение неизвестно).

## Limitations

- Анализ статический (дизассемблирование + чтение памяти); динамическая
  трассировка коллизий выхода не выполнялась.
- Структура проверена побайтово на 3 из 15 карт (01/08/15) + точная арифметика
  таблицы; остальные карты покрыты формулой адреса и размером 176.
