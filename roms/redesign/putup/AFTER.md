# Инвентарь стандартных py-скриптов для анализа Vector-06C ROM

Документ выделяет из методики `TZ.md` и отчётов
`reports/Stage1.md … Stage12.md` (+ `reports/Stage11_music_spec.md`) те шаги,
которые являются детерминированной рутиной
и могут выполняться скриптами без привлечения ИИ-агента.

Объект исследования: `putup.rom` (17664 байт, org `0x0100`,
SHA256 `8486442e…b4e9a6`), RDB `src/putup.rdb` (179 объектов после Stage 12).

Статус документа: **только постановка, без реализации.** Решение о способе
доступа скриптов к отладчику принято и зафиксировано в §7 (R1).

---

## 1. Техническая база: скрипты возможны без нарушения «MCP-first»

| Факт | Следствие |
|---|---|
| `v06c-mcp` — бинарь со **stdio-транспортом** (JSON-RPC, `debugger/mcp/mcp_main.cpp:84`) | Python может быть полноценным MCP-клиентом: spawn + `initialize` + `tools/call`. Своего дизассемблера не требуется |
| RDB на диске — обычный JSON (`{"format":"rdb","objects":[…]}`) | Чтение RDB для линтов/сверки/отчётов тривиально; запись — только через RDB API |
| Есть готовый CLI `v06c-asm-export --rom --rdb --output` | Экспорт asm (Stage 8/10) уже оскриптован; нужен wrapper + валидация результата |
| Эмулятор стейтовый (один процесс держит ROM, память, трейсы, breakpoints) | Нужна одна долгоживущая клиент-сессия на весь прогон, а не «новый запуск на каждый вызов» |

### Конфликт с формулировкой TZ.md (Stage 0)

В TZ.md стоит запрет: *«Никаких дополнительных скриптов не писать для
пост-обработки полученных от MCP-сервера данных»*. Фактически он уже
нарушался и признан нежизнеспособным:

* Stage 10: «Скрипт-сверка (только для контроля полноты, НЕ для обработки
  MCP-данных) подтвердила: все 85 не-кодовых объектов RDB покрыты файлами»;
* Stage 6/7: `debug_compare_memory_snapshots` недоотчитывает плотные диффы,
  поэтому ground truth брали ручным побайтовым сравнением `read_memory_range`;
* `roms/redesign/testay/.rt/` — рабочие `cov2.py` и `exact_build.py`;
* Stage 7/11 — скриптовый поиск байтовых последовательностей портов.

Фактически принятый режим работы (сам `TZ.md` не правится — §7 R3):

> Скрипту разрешено (а) вызывать MCP, (б) кэшировать ответы MCP,
> (в) обрабатывать RDB и asm-артефакты, строить отчёты и проверки.
> Запрещено — декодировать опкоды, строить control flow и интерпретировать
> hex-дамп как программу самостоятельно, подменяя Debugger.

## 2. Принцип разделения «скрипт vs ИИ»

| Уровень | Определение | Примеры из TZ |
|---|---|---|
| **A** | Полностью детерминировано: вход — ROM/RDB/ответы MCP, выход — артефакт; проверка арифметикой или повторным MCP-вызовом. ИИ не нужен | Stage 1 пп. 1–4, Stage 2 пп. 1–4, Stage 4 п. 2, Stage 8 п. 1, Stage 10 пп. 1–7 |
| **B** | Скрипт собирает доказательную базу и кандидатов с оценками; ИИ выбирает, называет, интерпретирует | Stage 3, Stage 7 пп. 2–6, Stage 9 пп. 3–6, Stage 11 пп. 2–4 |
| **C** | Только ИИ: семантика, гипотезы, классификация доказательств | Stage 3 п. 3, Stage 6 пп. 2–4, Stage 11 пп. 3–5 |

По объёму работ над `putup.rom` на уровнях A/B ушло порядка 60–70 % времени
Stage 1, 2, 4, 7, 8, 9, 10 — это перебор, арифметика, диффы и форматирование.

## 3. Каталог скриптов

### G0. Инфраструктура (без неё остальное не пишется)

| Скрипт | Вход | Выход | Что закрывает |
|---|---|---|---|
| `mcp_session.py` | — | долгоживущий клиент `v06c-mcp` | **единственная точка доступа к отладчику для всех G-скриптов** (решение R1, §7): spawn бинаря + `initialize`, JSON-RPC поверх stdio, таймауты, ретраи, одна сессия на весь прогон (иначе каждый скрипт сам себе транспорт). Проверяет состав сервера через `tools/list` и падает с понятной ошибкой, если нужного инструмента в сборке нет (§7 R1.2) |
| `evidence_cache.py` | вызов + параметры | `work/mcp/<hash>.json` | кэш всех ответов MCP; повторные вызовы не идут в эмулятор; отчёт ссылается на реальные артефакты; воспроизводимость прогона |
| `naming.py` | тип, адрес, префикс | `func_* / data_* / str_* / music_* / var_* / *_unknown` | конвенция имён TZ Stage 0 в одном месте |
| `probe.py` (`run_and_freeze`) | ROM, org, секунды | CPU state, screen info, memory map, memory access map, io trace, снапшоты | **весь Stage 1, пп. 1–4** — «запустить, ждать 5 с, не останавливая, собрать карту памяти и порты» |

### G1. First-pass RDB seeding (Stage 2, уровень A)

`seed_rdb.py` — один прогон превращает ROM в готовый скелет RDB, чтобы ИИ не
тратил время на рутину:

1. `debug_analyze_code` от `0x0000`/`0x0100` и дополнительно от всех известных
   entry points (Stage 2: `instruction_count = 3507`, `code_bytes = 6526`).
2. Непрерывные `debug_disassemble_range` по **всему** диапазону образа — для
   правильных границ. Обоснование из Stage 8: «дизассемблирование с произвольного
   адреса может "съезжать" на данных/gap-байтах», поэтому код брали прогонами
   0x0100–0x08C2 / 0x0E85–0x1BF9 / 0x3858–0x3DE7 с разбиением по границам
   RDB-объектов (`var_music_voice2_flag` @0x3BC8).
3. Из операндов: цели `CALL/JMP/RST` → функции (Stage 2: «310 CALL-инструкций →
   53 точки входа» — чистая частота); `LDA/STA/LHLD/SHLD/LXI H,imm` в RAM →
   переменные; `OUT port` → I/O-константы.
4. Классификация по access map: `fetch > 0` → код; `read > 0, write = 0` →
   константные данные (Stage 1: `0x2700–0x3700`, `0x3E00–0x4400`); `write > 0`
   внутри образа → переменные/RAM-буферы в собственном образе.
5. Блоки «только чтение», не покрытые кодом → `data_*_unknown` с оценкой границ
   по смежным объектам.
6. Запись в RDB **через API** батчами (~10 вызовов), затем `debug_save_rdb`.

Экономия: Stage 2 у ИИ — 114 строк отчёта, из которых механическими являются
пп. 2–4 и все таблицы адресов/размеров.

### G2. Coverage / closure fixpoint (уровень A) — слепые зоны анализатора

Найдено ранее на TESTAY: анализатор не ставит в очередь цели условных переходов,
из-за чего области внутри уже зарегистрированных функций остаются непокрытыми
(`0x032E-0x0331`, `0x0437-0x0441`), и закрываются только явными `Label`-затравками.

`coverage_fix.py`:

* множество байт образа − (code ranges из `analyze_code` + extents RDB-объектов)
  = gaps;
* пересечение с `branch_target` из `disassemble_range` → «переход есть, объекта нет»;
* итеративно добавляет `Label`-затравки, перезапускает `analyze_code`, пока
  покрытие не станет 100 % либо множество целей не перестанет расти;
* печатает отчёт: покрытие % и список gap-регионов. Для putup этот список
  собирали руками в Stage 8: `0x0F39–0x1122`, `0x1155–0x1196`, `0x1253–0x1309`,
  `0x13AA–0x1476`, `0x388C–0x3901`, `0x3DC5–0x3DCC`.

### G3. RDB lint (уровень A) — то, на чём Stage 8 спотыкался

`rdb_lint.py` — только чтение RDB (JSON) + образа ROM:

* перекрытия экстентов и «не более одного объекта на адрес» (из-за ограничения
  в Stage 9 нельзя создать `data_level_01`, т.к. 0x1C8E занят `data_level_maps`);
* размеры, наезжающие на соседа → кандидаты на исправление. Stage 8 вручную правил
  три объекта: `func_snd_toggle` 16→18, `func_memcpy` 12→11,
  `func_music_load_voice_params` 75→62 — это арифметика «до следующего объекта /
  до `RET`»;
* висячие связи, отсутствующие `params`/комментарии, счётчик имён `*_unknown`
  (Stage 3 финишный критерий «remaining `_unknown`: 0» = строка из линта);
* **детектор таблиц указателей**: в DEFW-блоке доля значений, попадающих в
  ROM-диапазон и совпадающих с началом RDB-объектов → автоматически находим
  `data_snd_dispatch_table` (0x01CD), `data_snd_toggle_table` (0x0280),
  `data_glyph_ptr_table` (0x0600), `data_vram_col_table` (0x051B) и поднимаем
  флаг «при экспорте подставь символы» (правило Stage 10 п.5, делалось глазами).

### G4. Активные области, самораспаковка, сигнатуры железа (уровень A/B)

`unpack_scan.py` + `io_signature.py` + `memory_diff.py`:

* **Дифф образа vs рантайма.** `read_memory_range` по 0x0000–0x7FFF в двух точках:
  «сразу после load, PC=entry» и «после N секунд». Совпало с образом → статические
  данные; отличается → создан/распакован в рантайме. Для putup: блок глифов
  `0x6000` и спрайты `0x7418` до запуска не существуют.
* **Пары источник → приёмник.** Из операндов `LXI D,src` + `LXI H,dst`
  (+ `CALL func_memcpy` 0x1BC9) строим направленный граф распаковки:
  `0x2F61→0x7418`, `0x3041→0x6000` (упакованный шрифт), `0x2761→0x6000`.
  Это и есть «алгоритм самораспаковки ROM» в машиночитаемом виде.
* **Проверка регенерации.** Обнулить приёмник (`debug_write_memory`), довести до
  точки возврата загрузчика, сравнить с эталоном. В Stage 7 Finding 4 так
  доказывали `func_load_glyph_block` вручную: обнуляли glyph 65 @0x6820, ставили
  PC=0x0401, BP=0x042A — глиф восстановился. Полностью тривиализируется.
* **Детектор runtime-патчей (важно для экспорта).** Адреса, где байты образа ROM
  и рантайм-памяти расходятся, но сами не являются данными: `0x03F8` в образе
  `00 00 00`, а движок самозаписывает туда `CD 58 38` = `CALL func_music_tick`
  (Stage 12, правка `func_vblank_isr.asm` → 3 × NOP). Скрипт обязан выдавать такой
  список отдельно: **экспорт должен брать байты из образа, а из рантайма — только
  патч-условие**, иначе ассемблированный ROM будет несовместим.
* **Карта активности по портам** (Stage 1 сделала это руками): горячий путь
  `IN 01h` (~1 чтение на 25 инструкций, значение 0xE2) + полный список `IN/OUT`
  из образа с адресами инструкций. Скрипт строит таблицу
  «порт → адреса инструкций → направление → частота» и **детекторы железа** по
  сигнатурам:
  * `OUT 00h ← 8Ah/88h` — управляющее слово KR580VV55;
  * `OUT 03h` (маска строки) + `IN 02h` + 8-итерационный цикл → клавиатурная
    матрица 8×8 в буфер;
  * `OUT 0Ch` — палитра (позиционно-зависима от растра);
  * `OUT 08h ← {36h,76h,B6h}` + `OUT 0Bh/0Ah/09h` — KR580VI53, три тон-канала;
  * `0Dh/0Eh` — AY-3-8910 (в putup отсутствует, что и дало ответ Stage 11 п.4).

  Именно сигнатура портов в Stage 3 переквалифицировала `func_set_color` →
  `func_sound_op`; такой переквалификации ИИ не требуется.
* **Стабильный побайтовый дифф снапшотов** как обход дефекта
  `debug_compare_memory_snapshots` (Stage 6, Limitations) с обязательной
  пометкой «ранее reported value — lower bound».

### G5. Параметры функций и вызывные конвенции (Stage 4, уровень A+B)

`abi_scan.py`:

* **Статика:** на входе функции — какие регистры читаются до первой записи;
  на путях к `RET` — какие пишутся; `PUSH/POP`-пары; `SHLD/LHLD` в RAM →
  «аргумент через память». Это покрывает ~90 % таблицы Stage 4 (69 функций,
  100 % coverage по `params`).
* **Динамика:** breakpoint на функцию → `debug_run` → снять `AF/BC/DE/HL/SP` →
  повторить 3–5 срабатываний → кандидат «входной регистр меняется, остальные
  константны». В Stage 4 ровно так подтвердили `A = op_index(0..15)`, `E = value`
  двумя хитами (0x00/0x98 и 0x09/0x0F) — автоматизируется циклом в несколько строк.
* **Бонус, который руками не использовался:** значение `SP` на входе; чистый стек
  (`SP=0x0100`) ⇒ вызов был `JMP`, а не `CALL` (в Stage 6 один такой замер делали
  вручную на 0x0E85).
* Выход: `params`-property в RDB + поле `evidence` + уровень уверенности; ИИ
  дописывает только человекочитаемое описание.

### G6. Строки, глифы, таблицы (Stage 7, уровень A для «где», B для «что»)

* `strings_scan.py` — цепочки печатных символов ASCII **и** KOI8-R
  (`0xC0–0xFF` / `0xE0–0xFF`), терминаторы `0x00`/`0xFF` → `str_*` с комментарием
  из содержимого. В Stage 7 найдены 12 строк, включая требование TZ «в ROM есть
  ещё другие строки. Их тоже надо найти» — это буквально `strings` по диапазону
  (`0x0925`, `0x0A06–0x0B3B`).
* `table_shape.py` — эвристики формата данных: периодичность/автокорреляция блока;
  «все слова монотонно убывают» (таблица периодов `0x421A`, 96 слов LE);
  «все значения < N» (тайлы 1..14 в картах `0x1C8E`); шаг записи по
  автокорреляции (stride 20 у `data_music_vibrato_table`, 8 у `data_level_params`,
  176 у карт уровней); «слово-указатель = base + i×K» (`0x6000 + N·32`, найдено за
  одно чтение в Stage 7 — такие структуры ищутся массово).
* `glyph_scan.py` — для блока с фиксированным шагом и 4×8 байт: рендер PNG-плитки
  на каждый индекс. ИИ/человек смотрит картинку вместо чтения hex-строк вида
  `[0,CC,CC,FC,CC,CC,78,30]`.
* `vram_credits.py` — по адресу строки + таблице колонн (`0x051B`) + screen-base
  (`0x08D0`) просчитать, в какие байты VRAM она ляжет, и сверить с фактическим
  VRAM после кадра. Позволяет **автоматически проверить критерий TZ Stage 7 п.7**
  («все глифы всех строк найдены»), а не сэмплированием A / В / 0x9B, как делали
  в Stage 7 (Limitations).

### G7. Экспорт и проверка сборки (Stage 8/10/12, уровень A)

* `export_asm.py` — обёртка над `v06c-asm-export`, затем обязательная сверка
  1:1 «RDB func/label ↔ файлы» (Stage 8: 82 = 82, «In RDB but NO asm file: нет»,
  «asm file but NOT in RDB: нет»).
* `symbolic_operand_lint.py` — найти в asm-файлах hex-операнды, совпадающие с
  началом RDB-объекта, но не заменённые (пропущенная символизация), и наоборот —
  константы, которые заменять нельзя (`LXI B,0100h`, `LXI D,03F8h`, `LXI E,14h`
  из правил Stage 8).
* `syntax_check.py` — прогнать каждый файл через `z80asm -m=8080_strict -b`
  отдельно; «undefined symbol» классифицировать как ожидаемую внешнюю ссылку.
  Так в Stage 10 и нашли, что в этой сборке тулчейна директива `INCBIN`, а не
  `.incbin` — 20 файлов правились вручную; линт ловит это до.
* `roundtrip_verify.py` — перенос работающего решения из TESTAY
  (`.rt/exact_build.py`) и уже существующего putup (`tools/gen_layout.py`,
  Stage 12): раскладка каждого диапазона по истинному адресу с `defs addr-$`,
  срезка фантомных 256 NOP диапазона `0x0000`, пропуск данных, вложенных в
  уже выданный блок → сборка → `0 различий` с исходным ROM. Это и есть
  объективный критерий приёмки Stage 12 — для putup он уже выполнен:
  `src/PUTUP_NEW.ROM` побайтово равен `putup.rom` (17664 байта, SHA256 совпадает,
  `make verify`). Сюда же контроль того, что `EQU` не переносится между `.o`
  (ограничение Stage 10 → требование общего include `var_ram_symbols.asm`).
* `measure_sizes.py` — **закрытие недостоверных размеров** (Stage 12:
  «замеренные длины `tools/sizes.json` отличаются от заголовочных `; Размер` у
  нескольких файлов; эталон — RDB-адрес + измеренная длина»). Метод уже найден и
  работает: плотная склейка эмитов без `defs` в `asm/measure.asm`, сборка
  `z80asm -s`, истинный размер объекта = дельта соседних меток в `.sym`.
  Это снимает каскад ошибок `defs < 0`; приём полностью детерминирован.
* `toolchain_lint.py` — две конкретные ловушки, найденные в Stage 12 и
  проверяемые статически: (1) `z80asm -b` с ненулевым `org 0100h` **дважды**
  применяет смещение к абсолютным операндам (`JMP func_main_init` → 0x0C57 вместо
  0x0B57) при корректном `.sym` → правило «`org 0h` + обрезка `bin[0x100:…]»;
  (2) hex-литералы на A–F требуют ведущего нуля (`DFh`→`0DFh`, `B6h`→`0B6h`) —
  3 места правились вручную (`ANI 0DFh`, `MVI A,0B6h`).

### G8. Спека-дривен конвертеры (Stage 11, уровень A)

Модель уже доказана на putup: ИИ пишет **спецификацию**
(`Stage11_music_spec.md`), скрипт по ней работает (`tools/putup2midi.py`,
157 строк, сам сверяет прочитанные потоки с дампом §10 и прерывается при
несовпадении).

* `music_spec.json` — машиночитаемый вид той же спеки (адреса дорожек и формула
  `0x3E29 + N*0x100`, `MIDI = code + 30`, `BASE=6`, `DURATION=6`, `LOOP=96`,
  tick ≈ 19.97 мс, маппинг каналов) — **в RDB properties**, а не в двух местах
  (md + хардкод в py), как сейчас.
* `music2midi.py` — generic-конвертер по спеке. `putup2midi.py` и
  `testay2midi.py` (370 строк) сейчас дублируют запись SMF → общий `midifile.py`.
* `period_table_verify.py` — проверка «таблица равнотемперированная»
  (`period[i] ≈ round(3822 / 2^(i/12))`, каждые 12 индексов период делится на 2)
  и «A4 = 440 Гц при f(VI53) = 1.5 МГц». В Stage 11 на это ушла опровергнутая
  гипотеза 6×/+36 → 12×/+24; скрипт опроверг бы версию 6× мгновенно
  (`1500000/(12*284) = 440.1`, при 6× вышло бы 880 Гц = A5).

### G9. Отчётность (уровень A)

`report_gen.py` — `reports/StageN.md` по шаблону скилла
(Goal / ROM / Method / Findings / Verified Facts / Inferences / Hypotheses /
Unknowns / Limitations / Recommended Next Steps):

* шапка ROM (файл, размер, org, диапазон, SHA256, mapping entry `0x0000`,
  program entry `0x0100`) — из кэша;
* блок `Result summary` (Objects / Links / `*_unknown` / путь RDB / save dirty) —
  из `debug_get_rdb_info` + G3. Этот блок набирался руками в **каждом** из
  отчётов Stage 2–11, и в нём же в Stage 7 нашли пересчёт-опечатку
  (размер `str_credits_koi8` 104→100, терминатор 0x098C→0x0988, 43→39 пробела);
* «Evidence» — автоподстановка реальных фрагментов `read_memory_range` /
  `disassemble_range` из кэша с адресами (это и есть требование «Facts,
  а не догадки»);
* журнал действий (какие MCP-вызовы, сколько раз, какие версии) — для
  воспроизводимости и для разбора расхождений с реальным железом.

## 4. Что остаётся исключительно за ИИ (не автоматизируется)

1. **Назначение и имя.** `func_set_color` → `func_sound_op` (Stage 3),
   `data_note_freq_table_ch0` → `data_music_vibrato_table` (Stage 11: таблица
   вообще не про частоты), «`0x08F5` — LEVEL, а не lives» (Stage 6, correction),
   `func_draw_image` → `func_load_glyph_block` (Stage 7). Скрипт даёт кандидатов и
   улики, смысл решает ИИ.
2. **Интерпретация неизвестного кодирования.** Паковка `data_packed_font_3041`
   (Stage 7 так и осталась Unknown: четыре writer'а с масками 0x80/0x40/0x20/0x10
   и правилом `dest = (hi ? dest_old : 0) | (lo ? ~dest_old : 0)`), семантика
   gate/op6…op13 заголовка партитуры (Stage 11 Unknowns).
3. **Классификация Fact / Inference / Hypothesis и Hardware / Emulator** —
   например «50.08 Гц = Emulator Behavior» (Stage 11 F6), «порт 09h подтверждён
   только дизассемблированием, в живой io_trace не попал» (Stage 11 F5).
4. **Выбор направления исследования:** «после пробела → `func_level_loader`»,
   «карта = база + (level−1)·176», «3 голоса, отдельной DEFW-таблицы указателей
   нет» — цепочки рассуждений Stage 6/9/11.
5. **Решение «это данные, а не код»** по правилу скилла «не судить по соседним
   байтам»: скрипт даёт статистическую достижимость, вывод об областях
   `0x2700–0x3700` требует evidence-рассуждения.
6. **Формулировка финальных выводов.** Например «выход с уровня закодирован
   тайлом, отдельного поля координат нет» (Stage 9 Finding 5) — скрипт даёт
   арифметику границ (15·176 = 2640 = 0x26DE − 0x1C8E), вывод делает ИИ.

## 6. Предлагаемый порядок внедрения

1. **G0 + G1 + G2 + G9** — «нулевой» проход без участия ИИ: ROM → засеянная RDB
   (функции, переменные, данные с `*_unknown`) + 100 % покрытие + скелеты отчётов
   Stage 1/2 с готовыми счётчиками. Это и есть постановка задачи: у ИИ сразу
   готовая структура.
2. **G3 + G4** (порт/VI53/unpack-сигнатуры) — снимает Stage 1 целиком и половину
   Stage 3–5: подсистема определяется по набору портов.
3. **G5** — Stage 4 почти без ИИ.
4. **G6 + G7** — Stage 7/8/10 плюс объективная приёмка Stage 12 (round-trip).
   Часть G7 уже существует как рабочий код putup: `tools/gen_layout.py`,
   `tools/sizes.json`, `make full` / `make verify` — их нужно не писать заново,
   а обобщить (убрать привязку к putup/RDB-именам этого ROM).
5. **G8** — спецификация в RDB, generic `music2midi.py`, общий `midifile.py`.
6. **Затем — перенос в `v06c-mcp`** (решение R1.3): когда скрипты обкатаны на
   нескольких ROM, горячие циклы уезжают в C++ как новые MCP-инструменты.

Ожидаемый эффект по `putup.rom`: из ~2500 строк отчётов механическая часть — это
все таблицы адресов/размеров/значений, все блоки `Result summary`, все
перечисления функций/файлов/gap-регионов и все арифметические проверки границ.
Время ИИ смещается к разделу 4 (назначение, имена, семантика форматов).

## 7. Принятые решения

### R1. Доступ скриптов к отладчику — только через MCP-сервер

**Формулировка:** на этапе Python-прототипов единственный канал доступа
G-скриптов к эмулятору/отладчику — `v06c-mcp` (stdio JSON-RPC). Прямое
использование `libdebugger_core` / `libdebugger_adapter` из скриптов запрещено.

**Уточнение границы запрета:** официальный CLI самого отладчика
(`v06c-asm-export --rom … [--rdb …] --output …`, бинарь в `debugger/build/`)
под запрет не подпадает — это не Python, лезущий в ядро, а штатный инструмент,
использующий тот же `debugger_core` и тот же код RDB; G7 вызывает его как внешний
процесс. Тот же путь (прямая линковка с `debugger_core`) уже легитимен для
`test_*`-исполняемых файлов отладчика — но не для наших скриптов.

**Обоснование:** у скрипта и у ИИ-агента должен быть один и тот же источник
истины, иначе расхождение «скрипт сказал одно, Debugger — другое» станет
нормой, а не аномалией. Скорость на прототипе целью не является — она станет
целью на втором этапе (R1.3).

**R1.1. Этап 1 (сейчас).** Обкатать скрипты на нескольких ROM (`putup`,
`testay`, + ещё 1–2), замерив на каждом прогоне число MCP-вызовов и wall time.
Без этих цифр непонятно, что именно переносить в C++.

**R1.2. Ограничение, которое надо знать: в сервере нет пакетных и поисковых
вызовов.** Проверено по
`mcp::tool_builder` в `mcp/mcp_adapter.cpp` — сервер регистрирует **64**
инструмента. Ближайшее к поиску по содержимому — `debug_find_rdb_object`
(поиск по имени объекта) и `debug_get_memory_access_map`; вызовов вида «найти
байтовую последовательность в диапазоне», «найти immediate», «прочитать байты
VRAM», «агрегировать активность порта» — нет, и в `SKILL.md` их тоже нет
(проверено grep'ом по обоим файлам). Найденное при этом расхождение документации
с бинарём (`debug_shutdown`) устранено — §7 R4. Но отсутствие
поисковых вызовов — не блокер: Stage 7/11 читали байты через
`debug_read_memory_range` и выбирали нужное в Python. Держать в уме нужно:

* сигнатурный поиск G4, сверка глифов G6 и дифф G4 работают как «прочитал
  диапазон → обработал сам»: число round-trip линейно растёт с размером образа;
* скрипты не вправе предполагать наличие инструментов, которых нет: G0 обязан
  свериться с `tools/list` на старте и упасть с внятной ошибкой.

**R1.3. Этап 2 (после обкатки).** Горячие циклы переносятся в `v06c-mcp` как
пакетные инструменты — ради скорости и стандартизации. Кандидаты определены
заранее:

| Скрипт | Горячая операция (сотни–тысячи round-trip сейчас) | Будущий инструмент сервера |
|---|---|---|
| G1 | дизассемблирование всего образа прогонами | `debug_disassemble_image`, либо поднять лимит `length` / `max_instructions` |
| G2 | fixpoint «gaps → затравки → analyze_code» | `debug_coverage_report` (gap-регионы + цели переходов без объекта) |
| G4 | постраничное чтение 0x0000–0x7FFF в двух моментах | честный `debug_diff_memory(a, b, range)` взамен дефектного `compare_memory_snapshots` (§5) |
| G4 | поиск сигнатур железа по образу | `debug_find_bytecode_sequence` / `debug_find_immediate_in_range` — их в сервере нет вообще (§7 R1.2) |
| G6 | чтение VRAM под сверку строк | `debug_get_vram_bytes` / `debug_get_screen_pixel` — сейчас доступен только `debug_get_vram_info` |
| G5 | цикл «breakpoint hit → снять регистры» ×3–5 | пакетный hit-профиль функции: N срабатываний одним вызовом |

Правило переноса: в C++ уезжает только то, что уже доказало правильность на
Python-версии и имеет замеренную стоимость; Python-реализация остаётся эталоном
для сверки результата нового инструмента. Самостоятельный поиск по байтам не
нарушает запрет TZ Stage 0: в дампе ищутся паттерны, а не смыслы инструкций —
декодированием опкодов по-прежнему занимается отладчик.

### R2. Размещение скриптов — `utils/analyze/`

Общий пакет анализа живёт в `utils/analyze/` (рядом с существующими
`utils/emulator/`, `utils/*.py` конвертерами), потому что методы не зависят от
конкретного ROM. Продолжают жить в `roms/redesign/<rom>/tools/` только
привязанные к одному ROM артефакты: `gen_layout.py`, `sizes.json`,
`putup2midi.py` — generic-части из них уезжают в `utils/analyze/`, а
ROM-специфичное (адреса дорожек, формулы партитур) остаётся в проекте и
подключается как данные/спека.

### R3. `TZ.md` не правится

Запрет в Stage 0 остаётся в буквальной формулировке, документ методики не
переписывается. Режим работы скриптов определяется здесь (§7 R1): скрипту
разрешено вызывать MCP, кэшировать ответы, обрабатывать RDB и asm-артефакты,
строить отчёты и проверки; запрещено — декодировать опкоды и строить control
flow самостоятельно. Формальные расхождения с уже сделанным (скрипт-сверка
Stage 10, побайтовые диффы Stage 6/7, `testay/.rt/`) считаются принятой
практикой и не требуют легализации через TZ.md.

### R4. Скиллы приведены в соответствие с собранным сервером

`debug_shutdown` удалён из сервера намеренно (инструмента останова нет — сессия
MCP живёт вместе с процессом `v06c-mcp`). Поэтому правится не сервер, а
документация этого проекта: `.qoder/skills/vector06c-debugger/SKILL.md` и
`.qoder/agents/vector06c-analyst.md`. Сделано: ссылка на `debug_shutdown`
заменена на явное «инструмента останова нет», счётчик «61 инструмент» →
«64 инструмента», добавлены отсутствовавшие в описании реальные вызовы
`debug_set_breakpoint_enabled` и группа Keyboard (`debug_press_key`,
`debug_release_key`, `debug_type_key`, `debug_list_keys`). Проверка:
множество имён `debug_*` в доках и множество `mcp::tool_builder` в
`mcp/mcp_adapter.cpp` теперь совпадают — 64 = 64, разностей ни в одну сторону.
