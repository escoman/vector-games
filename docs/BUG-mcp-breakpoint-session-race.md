# Мини-баг-репорт: брейкпоинт «не работает» при замере через MCP-дебаггер

**Где встретилось:** тестовое приложение замера положения луча `.scratch/timer_probe`
(останов на `timer_wait`, чтение `debug_get_beam_state`).
**Компонент:** workflow работы с брейкпоинтами через vector-debugger MCP (`v06c-mcp`).
**Статус:** это НЕ дефект движка — ловушка использования stateful-сессии. Ниже — чтобы
агент/человек не тратил время на ложную «нерабочую точку».

---

## Симптомы
1. `debug_load_rom` → сразу `debug_set_breakpoint(0x0216)` → `debug_run`: CPU уходит в
   свободный бег и **не останавливается** на точке (наблюдалось ~1791 кадр без останова).
2. `debug_set_breakpoint(0x0216)` вернул успех, но `debug_list_breakpoints` тут же показал
   `count: 0`. Ещё один `debug_set_breakpoint(0x0216)` ответил `"breakpoint already exists"`.
   То есть точка реально была в таблице, но `list` прочитал устаревшее состояние.

## Корневая причина
Обе — следствие того, что дебаггер = **одна stateful-сессия**, а вызовы MCP были
распараллелены (sent in one batch), плюс загрузка ROM намеренно чистит точки.

- **`load_rom` сбрасывает все брейкпоинты** — `DebugBackend::loadRom()` вызывает
  `clearBreakpoints()` (`src/backend.cpp:141-147`, Stage 6.20.1: «stale breakpoints must not
  carry over»). Если `set_breakpoint` ушёл параллельно с `load_rom` и обработался раньше
  очистки — точка молча стирается. Отсюда симптом 1.
- **`set_breakpoint`/`list_breakpoints` — разные точки чтения состояния.** Add идёт через
  очередь команд (`requestAddBreakpoint` → `submitAndWait` → `processCommand`:
  `addBreakpoint()` + `syncBreakpointsToTarget()`, `src/backend.cpp:1212-1222`). Если `list`
  вызван параллельно с `set`, он может прочитаться раньше коммита — `count: 0` при том, что
  add уже принят (`getBreakpoints()` читает `breakpoints_`, `src/backend.cpp:728-737`).
  Отсюда симптом 2.

## Что НЕ является багом (проверено эмпирически)
На текущей сборке (`3922c2e`, MCP `buildSeq 11`) **постановка брейкпоинта во время активного
Run работает**: ROM крутился в свободном беге, точка на `0x0216` добавлена без паузы — эмуляция
корректно встала (`cpu_pc=0x0216`, кадр 2771). Очередь команд обслуживается каждый кадр
(`src/backend.cpp:2043`), поэтому новая точка становится активной ≤1 кадра. Рабочий «костыль»
«пауза → точка → Run» не обязателен на этом билде.

## Корректное использование (инварианты для агента)
1. Вызывать инструменты дебаггера **строго последовательно**, не батчить параллельно:
   `load_rom` → дождаться → `set_breakpoint` → дождаться → `run`.
2. Брейкпоинты ставить **только после завершения `load_rom`** (загрузка их сбрасывает).
3. После `set_breakpoint` для подтверждения делать `list_breakpoints` **отдельным, следующим
   вызовом** (не в том же батче, что и `set`), иначе можно прочесть `count: 0` из-за гонки.
4. `debug_set_breakpoint` с ответом `"breakpoint already exists"` = точка уже стоит — это
   успех, а не ошибка.

## Мелкое предложение (по желанию, на стороне сервера)
- Сериализовать/блокировать мутации внутри одной MCP-сессии, чтобы параллельные вызовы не
  перемешивались, либо честно отражать в `list_breakpoints` уже принятые (но ещё не
  обработанные потоком эмуляции) команды.
- Документировать в описании `debug_load_rom`, что он сбрасывает брейкпоинты.

## Утилитарные адреса (для воспроизведения на timer_probe)
ROM: `.scratch/timer_probe/timer_probe.rom`, org `0x0100`.
Точка останова: `0x0216` (первая инструкция сразу после `call _timer_wait`).
Запись: `rec_target=0x0222`, `rec_remain=0x0223`, `rec_timer=0x0225`, `rec_index=0x0227`.
