# ТЗ: подсистема вывода спрайтов с синхронизацией с лучом (`lib/gfx/` — «beam sprites», API-префикс `spr_`)

Документ — задание на проектирование. Цели, правила для игр, контракты и
приемка сформулированы так, чтобы подсистема **прямо сейчас** вобрала весь
наработанный опыт putup-«гонки луча» (BLINK.MD, растер-гарды, Этап 1 огня,
E1-E3 кеши, гейты e2/e3/e4, инструменты beam_*).

---

## 1. Постановка задачи

### 1.1 Цели
1. **Гарантия отсутствия мерцания/tearing**: ни одна запись в видимую область
   VRAM не совершается, пока луч сканирует полосу записываемого ряда.
2. **Упрощение разработки игр**: игра объявляет тайлы/паттерны/спрайты один
   раз (загрузка уровня) и в игровом цикле меняет **только позиции и кадры
   анимации**. Вся растер-магия, erase, бюджеты, атомарность — внутри
   подсистемы. Аналог по интерфейсу — аппаратные спрайты NES (OAM), где игра
   пишет 4-байтные записи, а «железо» рисует.
3. **Детерминированный темп**: длительность кадра = высота кадра (312 строк),
   не зависит от числа обновлений; никаких «плавающих» просадок темпа.

### 1.2 Нецели (осознанно вне области)
- Аппаратный странипереворот VRAM на Vector-06C **отсутствует** — подсистема
  его не эмулирует «целой страницей», только покадровую консистентность.
- Полноэкранная анимация тайлмапа 50 Гц (бюджет растра это не позволяет,
  см. §7); широкие анимируемые ряды — с частотой, которую задаёт игра.
- Звук/музыка: подсистема только **не мешает** вокабулятору (см. НФ-5).

### 1.3 Известные факты платформы (замерено на putup, не принято на веру)
| Факт | Число | Источник |
|---|---|---|
| Тиков ВИ53 на строку растра / строк в кадре | 96 / 312 (=0x7500) | `lib/timer`, модель beam_state |
| Виден. поле: строки растра | 24..280 | BLINK.MD «Калибровка» |
| Полоса ряда `row` (8 глифов) | растр-линии 48+8·row .. +15 | BLINK.MD, проверено диффом VRAM |
| Фаза: `beam_line − elapsed/96` | мед +5,3 строки, константна | BLINK.MD (ISR ack latency) |
| Flat-глиф 8×8 в VRAM (4 плоскости, raw) | ~12 строк (1170T) | func_render_glyph |
| Tile 2×2 erase (`draw_tile_at_ptr`) | 29..40 строк | BLINK.MD «ЗАМЕРЫ» |
| OR-композит 2×2 (`render_tile_vram_or`) | 70,7 строк | BLINK.MD; базовая линия для Э0-перемера с отдельной маской (§2.1.3) |
| OR широкий 3 колонки (`or3`) | 104,5 строк | BLINK.MD |
| Инстанс «герой» целиком (erase+OR) | мед 101,4 / max 137,4 строк | BLINK.MD |
| DI дольше ~500..900T ломает музыку (VBlank-секвенсор) | — | история title-music slowdown (func_render_glyph) |
| Пересборка кешей сдвигов в кадре | 407 строк → пропуск кадра | e3_budget (урок E3-6a) |

## 2. Архитектура

### 2.1 Хранилища (как в NES: pattern table / OAM / фон + маска как отдельная сущность)
1. **Хранилище тайлов 8×8** — существующая конвенция putup/lib:
   plane-major 32 байта (4 плоскости × 8 строк, строки в столбце континуальны),
   индекс = код тайла; допустим compact-тег (бит0 слова указателя = одно-
   плоскостная маска). Для спрайтов **рекомендован raw** (compact измерен
   медленнее из-за table-lookup: 1350T vs 1170T).
2. **Библиотека паттернов спрайтов** (ROM уровня). Паттерн = произвольная
   мозаика из тайлов (putup-классика — 2×2), записи
   `{ s8 dx_cells; s8 dy_cells; u8 code; u8 attr; }` × n.
   `attr`: бит0-3 приоритет/порядок наложения, бит6 флаг «композит по маске».
3. **Хранилище масок** (ROM уровня, опционально). Маска — **отдельная
   сущность дизайна**, не занятая плоскость VRAM: 8 байт на тайл
   (1 бит/пиксель, row-major, бит7 = пиксель 0 строки — та же конвенция,
   что в глифах), индекс = код тайла, таблица `mask_tab` в декларациях
   уровня. Пустая (`00h`) = полнопрозрачный тайл; `FFh`×8 = непрозрачный
   (композиция вырождается в overwrite, подсистема вправе пропустить AND).
   Для flat-only тайлов маска отсутствует — не плодит mask-копий.
   Бинарной маски достаточно: аппаратной полупрозрачности у Vector-06C нет
   (тень героя в putup = AND по маске — ровно бинарная).
4. **Таблица экземпляров** (RAM, аналог OAM, 4 байта на спрайт):
   `{ u8 y; u8 x; u8 pat; u8 flags; }`, `pat=0xFF` — скрыт. Плюс
   **тень последнего commits** `{ y, x, pat }` на экземпляр — по ней
   планировать erase.
5. **Тайлмап фона** (RAM/ROM уровня, 1 байт кода на клетку поля): источник
   erase-до-состояния-фона. Статичен на уровне; правится только через
   `spr_bg_put`.

### 2.2 Конвейер кадра (технология вывода — внутри подсистемы)
```
 VBlank(RST7)  timer_start()                       ── кадр 0
 |             [игра: kbd, логика, анимация — пишет только таблицу экземпляров]
 |  spr_update()   diff(экземпляры vs тень) -> план по рядам:
 |                   на каждый грязный ряд: список erase-записей + draw-записей,
 |                   оценка стоимости в строках растра (см. §4)
 |  spr_render()   ИСПОЛНЕНИЕ ПЛАНА, отсортированное по рядам СВЕРХУ ВНИЗ,
 |                   в такт лучу (см. §3.1): каждый ряд пишется только когда
 |                   луч уже ниже его конца (elapsed >= bot(row)) — «behind-the-beam
 |                   pacing». Возврат к концу кадра; недописанные ряды — в план
 |                   следующего кадра (флаг перерасхода).
 |  ... остаток бланкинга свободен музыке/вводу ...
 VBlank(RST7) ── кадр 1 (тени обновлены -> вид консистентный кадр)
```
Игровой контракт цикла (и есть «конструктор»):
```c
for (;;) {
    v06_wait_frame();
    game_logic();          // ТОЛЬКО spr_move/spr_show/spr_hide/spr_bg_put
    spr_update();
    spr_render();          // блокирует до конца кадра — темп = 50 Гц всегда
}
```

### 2.3 Что замещает в существующих играх
Подсистема инкапсулирует и обобщает: `func_render_glyph`+`data_vram_col_table`
(адресация), `func_raster_guard_hero/_enemy/_row` (+атомарность ряда),
`func_hero_repaint_over`/erase-dispatch (тени), E1/E2/E3 pre-shift кеши,
`data_flip_tab`-анимацию (фазы паттернов), chunked-скан (`spr_update` = diff,
не слепой скан), OR-композит героя с маской П0 (маска становится отдельной
сущностью §2.1.3, плоскость освобождается).

## 3. Технология вывода: правила принятия решений (НФ-1…НФ-5 = §3.1…§3.5)

### 3.1 Базовое правило записи (НФ-1, ядро гарантии)
Для каждого ряда плана запись разрешена **только** при
`elapsed >= bot(row)`, где `bot(row) = TIMER_LINES(48 + 8·row + 8)`, ИЛИ при
условии `top(row) − elapsed − BEAM_LEAD > row_cost + MARGIN_MIN`
(«успеем до луча» с запасом; `BEAM_LEAD = 6 строк` — калибровочные +5,3,
MARGIN_MIN ≥ 8 строк). **Деградация всегда к behind-the-beam**: если
оценка сомнительна — ждём прохода.

Следствия (все — уроки putup, зашитые как инварианты):
- **Ряд-атомарность**: решение (§3.1) принимается ОДИН раз на ряд при
  попадании в него плана и не пересматривается для клеток ряда. Никаких
  per-cell решений — они дают «плывущий» двухфазный шов (Этап 0 огня).
- **Целый ряд за один проход луча**: если ряд не влезает в остаток кадра по
  бюджету — переносится ЦЕЛИКОМ в следующий кадр; частичная запись ряда
  запрещена (консистентность важнее отзывчивости; константа задержки +1 кадр
  предпочтительнее рваных швов).
- **Единственное пересечение**: ряды обрабатываются сверху вниз в такт лучу —
  поток записей догоняет луч ровно сзади и никогда не пересекает его
  повторно; «резонанс» из нескольких пауз на кадр структурно невозможен,
  потому что пауза — не блокировка, а пейсинг (логика уже закончена).
- **Широкие анимируемые ряды** (типа огня в putup: 28×~12 строк ≈ 250 >
  пред-лучевое окно) попадают в behind-the-beam-ветку автоматически и
  пишутся за второй «хвост» того же кадра — с гарантией одной фазы.
- **Стоп-лист**: никакой активной загрузки в бланкинг как основного режима
  (бланкинг мал, ~26+32 строк, и музыкальный секвенсор там же). Бланкинг —
  только для `spr_init`/полных перерисовок уровня.

### 3.2 Erase/draw порядок
В ряду: сначала все erase (по теням: фон из тайлмапа; порядок — чтобы не
трогать клетки, которые в этом ряду же перерисовываются тем же рядом draw),
затем draw по приоритету (младшие — раньше, старшие поверх). Пересечения
спрайтов одного ряда разрешаются:
- непрозрачным overwrite по приоритету (дёшево, flat-путь), либо
- композитом по **отдельной маске тайла** (§2.1.3): content AND маской,
  фон OR маской (оверлей-класс «герой», attr-флаг) — бюджетно дорогой путь,
  **лимит: ≤ 2 OR-инстанса на кадр**; цена пересчитывается на Э0 с учётом
  маски из ROM вместо VRAM (паспорт §4: базовая линия 70,7 строк).
  Putup-приём «П0 тайла = позиция маски» (занятая плоскость) остаётся
  допустимой внутренней оптимизацией, но не API.

### 3.3 Субпиксельные позиции (4 px)
Сдвиги ±4px по X/Y — только **precompute на загрузке уровня** (по модели
`data_hero_shift_cache` putup: композит 3 колонки × 2 строки × 32B),
запрет на побитовую математику/пересборку в кадре (урок E3: 407 строк).
Паттерны, для которых сдвиги запрошены (`flags` паттерна), получают до 4
вариантов; память под кеш объявляется при `spr_init` и лимитируется уровнем.
`spr_move(x, y)` принимает байтовую сетку; суб-шаг выражается выбором
сдвинутого варианта паттерна, план для подсистемы неотличим от обычного.

### 3.4 Анимация
Фаза (кадр анимации) — поле экземпляра или per-pattern счётчик каденции
(`anim_every_n_frames` в дескрипторе уровня). Смена кода паттерна выполняется
как обычный move: через план, рядом-атомарно. Широкие анимируемые поля
(огонь/мерцание) не требуют игровых сканов — они штатные паттерны.

### 3.5 Защита от аномалий
- `timer_wait` уже завершается при переполнении счётчика (кадр упущен) —
  scheduler обязан корректно перенести хвост плана на следующий кадр
  (done-флаг на ряд), без зависаний и без записи ряда «вразноброд».
- Полный стоп-двигатель (загрузка/сбой секундомера, `var_raster_flag`=0 на
  заставке): режим `SPR_OFF` — записи только в бланкинг, с полным
  перерасходом кадра (устаревший титульный путь exolon/putup). Явный флаг
  уровня: `beam_sync = 0/1`.
- Антизацикливатели вроде `var_raster_cap` сохраняются как debug-assert
  сборка (в релизе — assertion-free, пейсинг не может зациклиться, см. §3.1).

## 4. Бюджет растра (паспорт стоимости)

Правило планирования: стоимость ряда = Σ записей × измеренная цена +
накладные плана. Цены **перемеряются на этапе 0** и хранятся таблицей
`spr_cost` (в прошивке — константы). Текущие ориентиры (putup-замеры):

| Операция | Строки | Комментарий |
|---|---|---|
| flat-глиф raw | ~12 | 1170T |
| tile 2×2 flat (4 глифа) | ~48 | erase-класс |
| tile 2×2 erase через буфер | 29..40 | draw_tile_at_ptr |
| OR 2×2 | ~71 | or-композит |
| OR3 широкий | ~105 | 3-колоночный оверлей |
| инстанс героя (erase+OR) | мед 101, max 137 | 1 OR-инстанс = ~45% кадра! |
| guard/план решения на ряд | ≤ 2 | настраиваемый, не >1% бюджета |

Кадровый бюджет: 312 строк; резерв: логика/музыка/опрос клавиатуры ≤ ~90;
=> **потолок спрайт-рендера ≈ 200-220 строк/кадр**. Типовые допущения
конструктора: до ~10 движущихся спрайтов 2×2 в flat-пути ИЛИ до 2 OR-
инстансов «герой-класса» + 4-6 flat. Перерасход -> отброс целых инстансов
по политике приоритета round-robin (мерцание всего спрайта лучше шва на
ряду; как 8-на-строку в NES) + `spr_overbudget() != 0` для диагностики.

## 5. API (декларации в `v06.h`, реализация `lib/gfx/spr.c` + `spr.asm`)

```c
/* --- загрузка уровня ---------------------------------------------------- */
typedef struct { const spr_pat_t *pats; const uint8_t *map;      /* тайлмап */
                 uint8_t rows, cols; uint8_t beam_sync;          /* §3.5 */
                 const uint8_t *mask_tab;       /* 8B×tile, 0 = нет масок */
                 const spr_anim_t *anims; } spr_level_t;
void spr_init(const spr_level_t *lvl);   // пересборка кешей сдвигов; окном
                                         // записи = бланкинг; чистит тени
/* --- игровой цикл: эти мутаторы меняют позицию/вид ---------------------- */
void spr_move  (uint8_t id, uint8_t x, uint8_t y);  // байтовая сетка клеток
void spr_show  (uint8_t id, const spr_pat_t *p);    // новый паттерн/кадр аним.
// spr_pat_t: { s8 dx, s8 dy, u8 code, u8 attr } (записи паттерна)
//   attr: бит0-3 приоритет, бит6 = композит по маске тайла (см. §2.1.3, §3.2)
void spr_hide  (uint8_t id);
void spr_bg_put(uint8_t col, uint8_t row, uint8_t code); // клетка фона
/* --- кадровый контракт --------------------------------------------------- */
void spr_update(void);   // diff -> план по рядам (после game_logic)
void spr_render(void);   // исполнение плана в такт лучу; возврат = конец кадра
uint8_t spr_overbudget(void);           // байт статуса (для отладки/HUD)
/* --- примитивы для игр, сохраняющие гарантию ---------------------------- */
void spr_blank_wait(void);              // spin до бланкинга (palette/HUD-правки)
```
Соглашения: callee-cleanup для asm-функций с ≤2 параметрами (память
z88dk/ABI), регистровая прозрачность — как у putup-гардов (вызывающий не
теряет DE/HL). Прямые записи в VRAM из игры вне подсистемы **запрещены**,
кроме палитры (`gfx_set_palette` — бланкинг-примитив) и `spr_blank_wait`-окна.

## 6. Правила для игр, использующих подсистему (ТФ)

- **ТФ-1 Единственный писатель.** Вся видимая графика уровня — через `spr_*`.
  Свой текст/HUD — либо как тайлмап-клетки, либо в окне `spr_blank_wait`.
- **ТФ-2 Никаких собственных EI;HLT и ожиданий** внутри кадра, кроме
  контрактных `v06_wait_frame` и `spr_render`. Пауза «до конца кадра» —
  свойство подсистемы, не игра её организует.
- **ТФ-3 Никаких длинных DI.** Критические секции ≤ ~200T. Музыкальный
  секвенсор живёт на VBlank; канал 2 VI53 занят таймером — звуковые движки
  ограничивать маской 0x03 (уже правило `lib/timer`).
- **ТФ-4 Изменения — только таблицы.** В игровом цикле игра пишет
  экземпляры/тайлмап; не читает и не пишет VRAM, не знает про луч, пороги и
  фазы. Единственная видимая обратная связь — задержка отображения ровно 1
  кадр (константа контракта, а не артефакт).
- **ТФ-5 Бюджет — обязанность игры.** Суммарная объявленная динамика
  (движущихся спрайтов × тип пути) обязана влезать в паспорт §4; перегруз
  трактуется как баг игры (детектируется `spr_overbudget`).
- **ТФ-6 Анимация — через фазы паттернов**, не через собственные сканы поля.
- **ТФ-7 Переходы уровня** (заставка->игра) — через `spr_init`; режим
  `beam_sync=0` на заставках легитимен (много writes, гарантия не нужна).

## 7. Оптимальные практики реализации (из putup, обязательны к применению)

1. **Precompute вместо runtime-математики**: сдвиги, композиты, фазы —
   кеши на init. Худшая находка putup — пересборка кеша в кадре (407 строк);
   лучшая — E3-6a prebuild с поиском промаха «draw выровненно».
2. **Прозрачность гардов** (PUSH/POP PSW,B,D,H) — hot path игр на 8080 живёт
   регистрами; любой сервисный вызов внутри чужого цикла обязан их беречь
   (XCHG-идиомы, DE.H-базы таблиц).
3. **Пороги — только через `timer_*`** (elapsed = 0x7500−count), модель ряда
   `48+8·row` и калибр. BEAM_LEAD=+6 строк из BLINK.MD, а не из головы.
4. **Стоимость каждой примитивной операции измеряется инструментом, а не
   оценивается** (beam_hero/beam_pickup/pipeline). Перед оптимизацией —
   прогон по real-raster; помнить: BP-потоки морозят луч, одинарные trap-замеры
   валидны, потоковые — нет (память tool_experience).
5. **Единица консистентности — ряд глифов (8 строк)**, никогда не «клетка»
   и не «кадр целиком» (широкие ряды не влезают; см. Этап 1 огня).
6. **Fail-safe лучше зависания**: все ожидания ограничены кадром
   (semantics `timer_wait`), перенос хвоста плана на следующий кадр штатный.
7. **Compact/raw-тег глифа и space-fastpath** остаются (экономия на статичных
   фоновых записях), но спрайтовый путь — raw (замерено быстрее compact).
8. **VRAM-адресация скрыта**: col_table/плоскости/Y-инверсия — внутренние
   детали; для 512-режимов — таблица колонок на режим (`gfx_modes.width_div8`,
   (`plane_mask`), закладываемо на этапе 2. Маска как отдельная сущность (§2.1.3) —
   способ НЕ занимать плоскость в 4-цветных режимах.
9. **Тени и diff вместо слепых сканов**: putup-чанки (128 клеток/кадр,
   var_scan_ptr) — обход вслепую; подсистема знает, что изменилось, и
   платит за фактические грязные ряды.
10. **Инструменты принимаются вместе с кодом** (см. §8): без tearing-детектора
    подсистема не считается готовой.

## 8. Гарантии и критерии приёмки

Гарантии контракта (для игр):
- **Г1 Tearing = 0**: нет ни одной записи в видимую VRAM при луче внутри
  полосы записываемого ряда (±0; «успеем»-ветки с запасом не считаются
  нарушением, но должны быть проверяемы).
- **Г2 Консистентность ряда**: на любом кадре каждый видимый ряд однофазен
  (каждая клетка ряда отражает ровно один плановый кадр).
- **Г3 Темп**: период цикла ровно 1 hw-кадр при любом штатном загруженном
  кадре; музыка (VBlank-секвенсор) не пропускает тиков.
- **Г4 Задержка**: изменение позиции видно через ровно 1 кадр; не более.

Гейты (по аналогии с putup e-серией; инструменты — апгрейд `tools/beam_*.py`
в тестовый ROM подсистемы):
- **A1 tearing-детектор**: BP-инструмент на всех writer'ах (`gfx_put_char*`,
  `gfx_plane_or`, внутренний blit) + сверка полосы ряда vs beam/elapsed на
  момент записи; синтетика: 12 спрайтов в одной строке, широкий анимируемый
  ряд, sprite на границе видимого поля, запись на wrap-рубеже кадра.
- **A2 budget-meter**: распределение строк на кадр на стресс-сцене
  (предел §4), таблица worst-case.
- **A3 consistency-checker**: потактовые снимки VRAM, row-phase униформность
  (обобщение e4 модели «тёмная/светлая фаза == record(кодов)»).
- **A4 byte-exact**: вывод подсистемы побайтово == эталонный ручной render
  того же состояния (compare_color-подход) — «гард не портит картинку».
- **A5 tempo**: 600 кадров стресса, Δframe_count строго 1 на цикл, 0
  пропусков VBlank-тиков музыки.

## 10. Открытые вопросы (решаются на Э0)
1. Максимальное число экземпляров (предложение: 16, OAM-подобно) и размер
   библиотеки паттернов; RAM-бюджет теней/кешей (оценка: 16×4 + тени
   16×3 + кеш-план ~24×8 ≈ 350B + shift-cache по декларации уровня).
2. Портировать ли chunked-скан как fallback для гигантских полей анимации,
   или diff-план обязателен (предложение: обязателен; широкий ряд =
   декорированный «паттерн-лента», план один индекс).
2a. Materialизация маски: streaming AND/OR из ROM (предложение: да, базовый
   путь) vs внутренний VRAM-кеш композитов, резервирующий плоскость при
   `spr_init` (только если Э0-перемер покажет выгоду; для игр — не API).
3. Текст/HUD: единый тайлмап-слой или отдельный blanking-API (предложение:
   HUD = клетки тайлмапа + `spr_blank_wait` для строковых обновлений).
4. Поведение при намеренной перегрузке (демо-сцены): политика flicker
   round-robin или блокировка move до освобождения бюджета.
5. Нужен ли hw-режим «приоритет по pixel-ne-zero» (NES-like) поверх
   mask-as-entity: формально выражается двумя масками/пиксельным сканом,
   но стоимость — пересчёт на каждый пиксель; пред: нет, инстанс-приоритет
   + маска покрывают «герой-класс» semantics.
